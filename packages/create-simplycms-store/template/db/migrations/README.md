# Канон міграцій ядра SimplyCMS

Ця тека — **джерело правди застосовного SQL** ядра. Її везе tarball пакета
`simplycms` (`files: [… "migrations"]`), звідси її читають `simplycms db:diff`
і `simplycms doctor` (перевірка №7) у магазині.

## Склад

| Файл | Що робить | Хто його володіє |
|------|-----------|------------------|
| `0000_prelude.sql` | схема `app`, функція `app.current_user_id()`, ролі `app_runtime`/`app_user`/`app_admin` | рука (drizzle-kit цього класу об'єктів не емітить) |
| `0001_init.sql` | уся схема: доменні таблиці + таблиці Better Auth + `media` + `mail_outbox`, ени, індекси, RLS-політики | `pnpm db:rebaseline` (вивід `drizzle-kit generate` + два `COMMENT ON COLUMN`); руками не правиться, див. `docs/architecture/data-layer.md` § «Міграції» |
| `0002_grants.sql` | явні GRANT-и по таблицях; зняття мовчазних дефолтів PUBLIC | рука |
| `0003_seed.sql` | довідники чистого магазину, ідемпотентні | рука |
| `0004_functions.sql` | функції й тригери над таблицями (`refuse_banned_session` / `sessions_refuse_banned`, `languages_guard` — машина станів мови, `require_source_translation` + процедура підключення `attach_source_translation_triggers` — обовʼязковий рядок основної мови перекладних сутностей), ідемпотентні | рука (drizzle-kit функцій і тригерів не емітить) |

Порядок жорсткий і не випадковий: політики `0001` посилаються на
`app.current_user_id()` і на роль `app_user`, гранти `0002` потребують уже
наявних таблиць, сід `0003` — уже наявних довідникових таблиць, а `0004` — тригери на таблицях
`0001` і ролі з `0000` (тригерна функція читає `users`, `REVOKE` — з PUBLIC).
Ручні функції/тригери живуть лише в ручних файлах: `0001` лишається чистим
генератом drizzle-kit.

🔴 **Контракт id (трек V2-К3, етап Е0) — читати перед регенерацією.**
Таблиці «Категорії A» оголошені як `"id" uuid PRIMARY KEY NOT NULL` —
**без** `DEFAULT gen_random_uuid()`. Це не ручна правка генерату:
джерело — `schema.ts`, де ці колонки не мають `.defaultRandom()`, тож
drizzle-kit відтворює форму сам. Ключ генерує **викликач** (браузер —
`crypto.randomUUID()`, сервер — `randomUUID()`), інакше оптимістичний
рядок клієнтського кеша розійшовся б ключем із серверним.

Скрипт `pnpm db:rebaseline` дописує до виводу drizzle-kit лише два
`COMMENT ON COLUMN` — вони пояснюють контракт тому, хто дивиться на схему в ізоляції. Склад
Категорії B (де `DEFAULT` лишається) стережуть гейти
`id-defaults.test.ts` і `explicit-ids.test.ts`.

## Чому історії міграцій більше немає

До 2026-08-23 канон був байт-дзеркалом `supabase/migrations/` — 33 файли, що
описували еволюцію демо-магазину `alterenergy`: FK на схему GoTrue
`auth.users`, об'єкти Supabase Storage, `DO $$`-фокуси навколо чужих
тригерів. Для стеку v2 вони неробочі за побудовою, а реплеїти їх на чистому
Postgres можна було лише через «вічний шим» — рукотворні заглушки `auth.*` і
`storage.*`.

Рішення **B13** (амендмент 2026-08-23 до
[`backend-contract-v2-design.md`](../../../docs/superpowers/specs/2026-08-19-backend-contract-v2-design.md))
знімає це: клієнтів і живих магазинів на v2 ще немає, `schema.ts` уже був
SSOT — тож історія видаляється повністю, а на її місце стає чистий baseline
із сідом. Стара тека лишається в git-історії (`git log --diff-filter=D --
supabase/migrations`); для перезапуску `alterenergy` вона не потрібна — там
`pg_dump` даних, а не DDL-реплей.

Доказ, що шим більше не потрібен, — сам накат: baseline лягає на порожню БД
без єдиної згадки `auth.` чи `storage.`
(`packages/simplycms/test-harness/pg/__tests__/baseline.test.ts`).

## Привілеї під гейтом

До 2026-08-23 у репо не було **жодного** GRANT-а: привілейна поверхня прода
існувала як неявний дефолт платформи Supabase — поза ревʼю і поза будь-яким
гейтом. `0002_grants.sql` робить її текстом, а
`test-harness/pg/__tests__/grants-parity.test.ts` — вимірюваною: фактичний ACL
чистої БД звіряється з декларацією `__tests__/fixtures/grants.ts`. Нова
таблиця без гранта, зайвий грант, `GRANT … TO PUBLIC` чи будь-яке право в
`app_runtime` червонять `pnpm test:schema`.

## Як змінюється схема ядра

🔴 **До `1.0.0-rc.1` (baseline `0000…0004` не заморожено)** окремих файлів міграцій
не додають — baseline перегенеровують:

```bash
# 1. правка packages/simplycms/src/schema/schema.ts
pnpm db:rebaseline     # 2. drizzle/ (одна міграція 0000_init + знімок + журнал) і 0001_init.sql
#                           3. ручні файли: 0002_grants (гранти нової таблиці), 0003_seed, 0004_functions
pnpm template:sync     # 4. копії в шаблоні скаффолдера й host CLI
pnpm test:schema       # 5. накат усього канону на чисту БД + поведінка RLS
```

Скрипт детермінований (без мережі й БД; `when` журналу й `id` знімка нормалізовано):
два прогони поспіль дають нульовий диф, а знімки `drizzle/**` руками не правляться.

**Після `1.0.0-rc.1`** нова схема йде лише новим файлом:

```bash
pnpm db:diff <name>    # schema.ts → drizzle-staging → NNNN_<name>.sql тут
```

Нумерація послідовна й безперервна: `db:diff` бере наступний вільний
префікс. Файли **immutable** — щойно міграція виїхала в релізі, її вміст не
міняється (це асертить `simplycms db:diff` у магазині: спільне ім'я з іншим
вмістом — помилка без запису).

🔴 **До `1.0.0-rc.1` baseline `0000…0004` ще не заморожено.** Його правлять як виняток
baseline (`docs/architecture/data-layer.md`), і кожна така правка в релізі дає в `CHANGELOG`
попередження «перестворити БД»: магазин, що вже накотив файл, тримає його sha256 у журналі
`public.simplycms_migrations`, тож `MigrationChecksumError` на старті контейнера для файла ядра
називає дію — базу створюють заново (локально — порожня БД і `pnpm simplycms db:apply`, у монорепо платформи `pnpm db:demo`; на
сервері — новий порожній екземпляр БД). Заморожування — крок релізу `1.0.0-rc.1`; далі нова схема йде лише новим файлом, що несе
свої гранти й RLS у собі (окремого «оновлення `0002_grants.sql`» немає).

Накат іде через `simplycms/migrate` (`applyMigrations`): кожен файл — в одній
транзакції разом зі своїм записом у журнал, тож `create index concurrently` і
власні `begin`/`commit` у файлі відкидаються ще до накату. Деталі —
[`docs/architecture/data-layer.md`](../../../docs/architecture/data-layer.md).

## Міграції плагінів

Плагінні `plg_*`-міграції сюди **не потрапляють**. Кожен плагін везе власну
теку `migrations/` у своєму пакеті; `simplycms db:diff` порівнює магазин із
N канонами одразу (ядро + кожен установлений плагін) і докочує їх поверх
baseline, проходячи SQL-лінт межі довіри (плагін сміє чіпати лише
`plg_<name>_*`). Деталі — [`docs/architecture/plugins.md`](../../../docs/architecture/plugins.md).
