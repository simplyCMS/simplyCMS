# Магазин на SimplyCMS

Каркас магазину (вітрина, адмінка, профіль, кошик, чекаут) приходить пакетом
`simplycms` із npm. Цей репозиторій — тонка збірка: конфіг, тема, плагіни й
власні роути в `src/routes/my/`.

## Вимоги

**pnpm 11+** (версія прибита в `packageManager`, тож corepack підтягне її сам)
і **Node 24+** (`process.execve` прод-старту). npm і yarn не підтримуються: магазин налаштований через
`pnpm-workspace.yaml` (`allowBuilds`), а інші менеджери це поле ігнорують і
зберуть проєкт у неперевіреній конфігурації.

> 🔴 **Якщо `pnpm install` скаржиться на `minimumReleaseAge`** — це не помилка
> магазину. pnpm 11 за замовчуванням не ставить пакети, опубліковані менш ніж
> добу тому (захист від supply-chain-атак). Найпростіше — зачекати добу після
> виходу нової версії `simplycms`.
>
> Якщо чекати не можна, тимчасово додай у `pnpm-workspace.yaml`:
> `minimumReleaseAge: 0`, і прибери після установки. Разового прапорця
> `--config.minimumReleaseAge=0` на `pnpm install` **не досить**: `pnpm build`
> сам перезапускає install (`runDepsStatusCheck`) уже без нього і впреться
> знову.

## Агент і деплой

Магазин створено для роботи з агентом (Claude Code чи Codex). Відкрийте його в
корені цієї теки й скажіть: «розгорни магазин». Хук старту сесії покаже агенту
стан магазину, а `AGENTS.md` поведе на скіл `simplycms-onboarding`: власна БД,
сховище S3, пошта SMTP, міграції на старті й перевірка готового магазину.
Кожну зміну агент показує наперед і виконує лише за вашою згодою. Далі ті самі
скіли ведуть оновлення (`simplycms-update`), діагностику (`simplycms-diagnose`)
і редизайн (`simplycms-redesign`) — деталі в розділі «Агентні скіли» нижче.

Без агента те саме робиться вручну — «Наступні кроки» нижче.

## Наступні кроки

### 1. Заповнити `.env.local`

```bash
cp .env.example .env.local
```

Обов'язкових ключів рівно три: `DATABASE_URL` (підключення роллю
`app_runtime`), `BETTER_AUTH_SECRET` (`openssl rand -base64 32`) і
`VITE_SITE_URL`. Перші два серверні: читаються з `process.env` у рантаймі, тож
їхня зміна потребує перезапуску процесу, а не перезбірки. Сховище S3 і пошта SMTP —
опційні групи драйверів «все або нічого», вони закоментовані в `.env.example`.

### 2. Накотити схему БД

Потрібне підключення **суперкористувача** кластера Postgres (у Dokploy і в образі `postgres` —
користувач `postgres`): додай його в `.env.local` (або в env процесу) як `MIGRATION_DATABASE_URL`.
Це не `DATABASE_URL`: роль `app_runtime` не має прав створювати схему, ролі й таблиці, тож команда
ніколи не падає назад на неї. Суперкористувач потрібен, бо перший файл схеми створює ролі `app_*` і
задає їм атрибути (`nosuperuser`, `nobypassrls` …), а ці атрибути Postgres дозволяє міняти лише
суперкористувачу. Керовані Postgres, де роль має лише CREATEROLE (Supabase, RDS тощо), не
підтримуються.

`db/migrations/` — схема ядра SimplyCMS: baseline (`0001_init.sql`) плюс
передумови, гранти й сід довідників. Накат — одна команда; файли накочуються
**в порядку імен**, а журнал `public.simplycms_migrations` (з контрольними сумами)
запам'ятовує накочене, тож повторний запуск накочує лише нові файли:

```bash
pnpm simplycms db:apply            # --dry-run: показати, що накотиться; --check: код 3, якщо є що
```

Окремий клієнт Postgres не потрібен. Пароль `app_runtime` із `DATABASE_URL` команда синхронізує сама
(він має складатися лише з друкованих ASCII-символів).

🔴 Нумерація послідовна, а не за часом: порядок накату мусить бути
детермінованим і не залежати від годинника машини, що згенерувала файл.

### 3. Призначити власника

Магазин навмисно не робить адміном «того, хто перший зареєструвався»: роль
`admin` дає ЛИШЕ запрошення (або наявний адмін). Випускає його власник проєкту
з консолі:

```bash
OWNER_EMAIL=you@example.com pnpm owner:invite
```

Команді потрібен рівно `DATABASE_URL` із `.env.local` — `service_role`-ключа
Запрошення пишеться прямо в Postgres, тим самим кодом
ядра, що обслуговує сторінку прийняття.

🔴 **Лист іде через порт пошти**, а що саме побачите в консолі, залежить від налаштувань:

- налаштовано `SMTP_URL` і `MAIL_FROM` — лист піде на `OWNER_EMAIL`, у консолі лише
  «Лист надіслано на …», посилання **не** друкується;
- пошти немає, локальна розробка (`NODE_ENV` не `production`) — драйвер `log`, посилання
  друкується в консоль: скопіюйте його й відкрийте самі;
- пошти немає, прод (`NODE_ENV=production`) — команда завершується з кодом 1 і нічого не
  випускає: налаштуйте `SMTP_URL`/`MAIL_FROM` або свідомо додайте `--print-link`
  (`pnpm owner:invite --print-link`) — тоді посилання з’явиться в консолі.

Посилання веде на `/auth/invite?email=…&token=…`, де запрошений задає пароль і одразу
потрапляє в адмінку. Його база береться лише з `VITE_SITE_URL` (без нього команда
відмовляє — фолбеку на localhost немає).

Роль `admin` видається лише ПІСЛЯ прийняття запрошення, а прийняття гасить усі
наявні сесії цього акаунта: якщо хтось уже зареєструвався на пошту власника,
команда про це попередить, але адміном він не стане.

Команда ідемпотентна: повторний прогін не створює другого користувача — він
перевипускає токен, гасячи попереднє посилання. Токен живе
24 години; у БД лежить лише його SHA-256, тож дамп таблиці `verifications`
дійсного посилання не дає.

### 4. Запустити

```bash
pnpm dev      # розробка, http://localhost:3000
```

Порт dev-сервера прибитий у `vite.config.ts` до `3000` — щоб збігався з
`pnpm start` і з дефолтом `VITE_SITE_URL`, з якого `owner:invite` будує
посилання запрошення: інакше воно вело б на порожній порт.

Прод:

```bash
pnpm build                  # dist/client + dist/server
node scripts/start.mjs      # накат міграцій під MIGRATION_DATABASE_URL, далі execve на server.mjs
```

`node scripts/start.mjs` — єдина стартова команда платформи (Dokploy тощо); порт — `PORT`,
за замовчуванням 3000. `pnpm start` (`node server.mjs`) лишається локальним запуском
зібраного бандла **не для проду**: він не накочує міграції.

🔴 Кожному магазину — власний екземпляр Postgres (не лише база в спільному кластері): ролі
`app_runtime`/`app_admin` кластерні, спільний кластер ділить їх між магазинами.
`pnpm simplycms doctor --online` попередить, якщо це не так.

### 5. Перевірити себе

```bash
pnpm simplycms doctor
```

Read-only діагностика магазину: версії ядра, env, host-файли, міграції, конфіг.
Той самий CLI (`@simplycms/cli`, уже в `devDependencies`) далі обслуговує
магазин: `simplycms add` — встановлення плагінів/тем, `simplycms update` —
оновлення ядра з доганянням host-файлів, `simplycms db:diff` — донесення нових
core-міграцій. Повна інструкція —
[docs/architecture/cli.md](https://github.com/simplyCMS/simplyCMS/blob/main/docs/architecture/cli.md).

## Агентні скіли

Разом із ядром приїжджають скіли для агентів (Claude Code та інші агенти, що читають `.agents/skills/`) — покрокові
інструкції під типові задачі магазину, напр. редизайн за референс-сайтом. Їхні
файли лежать у пакеті (`node_modules/simplycms/skills/`), а `.agents/skills/` і
`.claude/skills/` — це **симлінки** на них, які створює скаффолдер.

🔴 Копії немає навмисно: скіл оновлюється разом із ядром (`pnpm install`), а
форк у репозиторії магазину старів би мовчки. Якщо лінк зник чи зламався
(наприклад, після ручного чищення `node_modules`), полагодь:

```bash
pnpm simplycms update   # доробить відсутні лінки, прибере осиротілі
```

Перевірити, що агент бачить скіл:

```bash
head -3 .claude/skills/simplycms-redesign/SKILL.md
```

### Хук старту сесії Claude Code

`.claude/settings.json` запускає `.claude/hooks/session-start.mjs` на старті сесії
(`startup|clear|compact`) і віддає агенту стан магазину (`simplycms status --hook`).
Запис — exec-форма (`command: node`, `args` зі шляхом через `${CLAUDE_PROJECT_DIR}`),
тож шлях шима не залежить від cwd: за документацією Claude Code cwd хука слідує за cwd
агента, і після `cd` відносний шлях на `clear|compact` пішов би не з кореня. Claude Code
читає `.claude/settings.json` лише з теки старту сесії (з підтеки він не читається
взагалі) — запускай агента з кореня магазину.

Потрібен Claude Code ≥ 2.1.139 (поле `args` у хуках); перевірено на 2.1.296. `pnpm
simplycms doctor` (№18) попередить, якщо встановлено старішу версію.

## Драйвер БД (`pg`)

`pg` — пряма залежність цього магазину (`package.json`), а не лише транзитивна ядра. Версія мусить
збігатися з peer-діапазоном `simplycms` (`simplycms doctor`, №13, перевіряє): без прямої залежності
збірка вклеює `pg` у серверний бандл, і магазин не стартує. `simplycms update` версію `pg` не
змінює — лише підказує, що оновити.

## Що де лежить

| Шлях                  | Призначення                                        |
| --------------------- | -------------------------------------------------- |
| `simplycms.config.ts` | Конфіг магазину: SEO, локаль, валюта, теми, плагіни |
| `routes.ts`           | Монтування роутів ядра + власних (`src/routes/my/`) |
| `src/routes/my/`      | Кастомні сторінки цього магазину                    |
| `themes/default/`     | Активна тема: manifest + tokens + components        |
| `plugins/`            | Встановлені плагіни                                 |
| `db/migrations/`      | Схема БД (ядро SimplyCMS)                           |
| `scripts/`            | Обслуговуючі команди магазину (`owner:invite`)      |
| `.agents/skills/`     | Симлінки на скіли пакета `simplycms` (агенти)       |
| `.claude/skills/`     | Ті самі скіли для Claude Code                       |
