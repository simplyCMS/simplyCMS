# CHANGELOG і BREAKING

Журнал змін ядра їде в tarball пакета: `node_modules/simplycms/CHANGELOG.md`. Там — журнал
ВСТАНОВЛЕНОЇ версії; про нову версію він ще не знає. Тож цільовий журнал читай із tarball
цільової версії, не встановлюючи її (мережа, лише читання):

```bash
T=$(mktemp -d)
npm pack simplycms@<цільова> --pack-destination "$T" --silent
tar -xzOf "$T"/simplycms-<цільова>.tgz package/CHANGELOG.md > "$T/CHANGELOG.md"
```

Цільову версію бери з `npm view simplycms dist-tags` (`latest` або `next` для пререлізу) або
від власника. Тека з tarball — тимчасова: після читання прибери її за іменем (rm -r на цей шлях).

## Що читати

1. Поточна версія — `node_modules/simplycms/package.json`, поле `version`.
2. У журналі кожна версія має заголовок `## [X.Y.Z]`. Прочитай ВСІ версії між поточною і
   цільовою; розділ `### 🔴 BREAKING для магазинів` — те, що вимагає дій у магазині.
3. Підсумок власнику коротким списком: що зламається, що робити (команда чи правка), чи є
   міграція і чи вона ризикова (`references/migrations.md`).

Дії з BREAKING, що вже траплялись: додати залежність (`pnpm add pg@…`), перенести теку
(`git mv supabase/migrations db/migrations`), перестворити локальну БД. Кожна з них — мутація:
прев'ю → згода → застосувати.

BREAKING 0.15.0 «базу перестворити» (baseline міграцій змінено): локально — порожня БД і
`pnpm simplycms db:apply` (у магазині немає `db:demo`); на сервері — новий порожній екземпляр
Postgres, далі старт контейнера накочує міграції. Дані 0.14 не переносяться автоматично. Для 0.x
`simplycms update` перетинає мінорну межу лише з явним `--to`.
