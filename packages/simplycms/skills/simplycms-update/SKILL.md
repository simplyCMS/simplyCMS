# Оновлення платформи — безпечно й з даними на місці

Запускай агента з **кореня магазину** і не роби `cd` у підтеки перед CLI. Дані магазину
недоторкані: схема змінюється лише НОВИМИ міграціями, накочену міграцію не правлять.

## Старт: стан, а не здогадка

```bash
pnpm simplycms status --json
pnpm simplycms update --check
```

`update --check` не ходить у мережу й нічого не пише: код `0` — магазин збігається з каноном
своєї версії, `3` — є розбіжність, `1` — помилка. Магазин без чистого `git status` спершу
доведи до чистого стану (коміт власника), інакше `git diff` після оновлення не відрізнити від його правок.

## Ланцюжок етапів

1. **Що змінилось** — `references/changelog.md`: розділ BREAKING між поточною і цільовою версією.
   Журнал цільової версії береться з її tarball (`node_modules/simplycms/CHANGELOG.md` — лише
   журнал ВСТАНОВЛЕНОЇ версії); підсумок власнику списком, що вимагає дій магазину.
2. **Оновлення пакетів і файлів** — `pnpm simplycms update`: ставить ядро і сателіти на цільову
   версію, далі звіряє host-файли, лінки скілів і файли агента. Мажорну межу сама не перетинає
   (див. нижче). Якщо звіт показав дрейф host-файлів, перепиши їх `update --write` лише після
   прев'ю (`update --check`) і згоди власника; далі — `git diff` і ревʼю. Шими `scripts/start.mjs`
   і `scripts/owner-invite.mjs` — теж host-файли (логіка в ядрі), їх не правлять руками. `update`
   файлів, яких у каноні вже немає, не видаляє: осиротілі файли, названі в BREAKING (напр.
   `owner-invite-core.mjs` у теці `scripts` при переході на 0.15), видали за згодою власника.
3. **Міграції** — `pnpm simplycms db:diff`, потім `db:diff --write` лише після ревʼю SQL
   (`references/migrations.md`).
4. **Локальна перевірка** — `pnpm simplycms db:apply` на локальній БД, `pnpm build`,
   `pnpm simplycms doctor --online`.
5. **Бекап перед ризиковою міграцією** — ручний, до деплою (`references/migrations.md`).
6. **Коміт і деплой** — коміт у `main`; autoDeploy збирає і накочує міграції на старті.
7. **Перевірка живого** — `pnpm simplycms smoke https://<домен>`, `pnpm simplycms status`.
   Не зелено — передай керування `simplycms-diagnose`.

## Межа сумісності — лише свідомо

Межа сумісності — мажорна версія з 1.0 і мінорна для 0.x (`0.14 → 0.15` її перетинає).
`pnpm simplycms update` без `--to` зупиняється з кодом `3`, коли ціль перетинає межу
(або поточна версія невідома). Це не помилка, а запитання до власника: прочитай BREAKING між
версіями, перекажи власнику, що зламається саме в цьому магазині, і лише з його згоди —
`pnpm simplycms update --to <версія>`. З 0.14.x на 0.15.0+ база без журналу міграцій не
підніметься (`UnjournaledDatabaseError`): створи базу заново — локально порожня БД і
`pnpm simplycms db:apply`, на сервері новий порожній екземпляр БД; скажи про це власнику ДО `--to`. Пререліз `X.Y.Z-rc.N` живе під тегом `next`; точну
версію задавай явно.

## Правило кожної мутації: прев'ю → згода → застосувати

Правило діє на БУДЬ-ЯКУ мутацію, чим би вона не робилась: командою CLI, MCP Dokploy, UI
панелі чи командою на сервері. Для `update` прев'ю — `update --check` і список BREAKING;
для міграцій — текст SQL; для деплою — перелік змін у `git diff` і ризик. Покажи власнику,
дочекайся явного «так» і лише тоді застосовуй. Згода на один крок не діє на наступний.

## Секрети

Значення секретів не друкуй, не проси в чаті, не клади аргументом команди. Змінні Dokploy —
лише скриптами `simplycms-onboarding` (`dokploy-env set KEY --from-secrets <файл>`).

## Межі — чого скіл НЕ робить

- Не перетинає межу сумісності (мажорну з 1.0, мінорну для 0.x) без явної згоди власника й `--to`.
- Не правит і не видаляє накочені міграції: зміна схеми — нова міграція.
- Не накочує міграції на прод-БД вручну: їх накочує старт застосунку; ризикову — після бекапу.
- Не деплоїть і не пушить без слова власника.
- Не лагодить поламане — це `simplycms-diagnose`; не розгортає нову інфраструктуру — `simplycms-onboarding`.
