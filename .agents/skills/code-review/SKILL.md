# Code Review — simplyCMS

Мета рев'ю — **не знайти якнайбільше**, а не пропустити те, що коштуватиме окремого
fix-етапу, і не завалити замовника шумом.

Цифра, з якої усе випливає:

> **~40%** знахідок не переживають адверсаріальної перевірки.
> Це **емпірика архіву спорідненого репо metahub** (звідки прийшов цей скіл);
> власної статистики в simplyCMS ще немає — накопичуємо. Порядок величини
> приймаємо як робочу гіпотезу: якщо частка хибних спрацювань перевищує 20%,
> звіт перестають читати, і рев'ю стає дорогою імітацією.

Тому обов'язкові рівно дві речі: **фільтр за впевненістю** і **спроба спростувати
кожну знахідку**. Усе інше — налаштування.

---

## 0. Гейт доцільності

Не рев'юй те, що не варте рев'ю. Пропусти (і скажи про це одним рядком), якщо диф —
це лише: перейменування без зміни семантики з зеленими гейтами, оновлення лок-файлу,
форматування, регенерований `src/routeTree.gen.ts` чи `supabase/types.ts`, або зміна
доків без коду. Рев'ю таких дифів дає нітпіки, а не сигнал.

Перед стартом визнач **межу**: `git diff <base>...HEAD` або конкретний діапазон
комітів. Рев'ю без явної межі перетворюється на аудит усього репо.

---

## 1. Шкала — фіксована, без варіацій

Severity — рівно три значення (довільні написання агрегувати неможливо):

| Severity | Критерій |
| -------- | -------- |
| `blocker` | зламана поведінка, втрата даних, дірка в доступі (RLS/guard), або задача не виконана по суті |
| `major`   | дефект, який вилізе в проді або на наступному етапі; борг, що множиться |
| `minor`   | локальна неохайність; виправити дешево, не блокує |

Кожна знахідка отримує **confidence 0-100** за цією рубрикою (давати виконавцю
дослівно):

- **0** — не витримує легкої перевірки, або це пре-існуючий дефект поза дифом;
- **25** — можливо реальне, але підтвердити не вдалося; стилістика, не названа в каноні;
- **50** — реальне, але рідкісне або дрібне на тлі решти дифу;
- **75** — перевірено, дуже ймовірно вистрелить на практиці; або прямо суперечить
  `AGENTS.md` / `.github/instructions/*`;
- **100** — доведено кодом: є конкретний вхід чи стан, за якого воно зламається.

**Поріг: знахідки з confidence < 80 у звіт не потрапляють.** Вони йдуть в окремий
короткий список «відкинуто на порозі» — без деталей, одним рядком кожна.

---

## 2. Лінзи — обирай за тим, що зачепив диф

Не «виміри якості», а **різні джерела сигналу**. Одна лінза = один незалежний прохід
(окремий агент, якщо є така можливість). Типово спрацьовує 3-4 з шести.

| Лінза | Коли обов'язкова | Що шукає |
| ----- | ---------------- | -------- |
| **correctness** | завжди | баги в самих змінах: edge cases, `null`/`undefined`, межі, помилкові умови. Читає **лише диф** плюс мінімум контексту — глибоке занурення тут дає нітпіки |
| **test-honesty** | диф торкнувся тестів | чи тест справді впаде, якщо зламати код (мутаційна перевірка); чи фікстури й моки відповідають **реальним** типам БД і формам виклику |
| **drift** | є план/спека/доки | розходження написаного з кодом: невиконані пункти, відмічені `[x]` без коду, застарілі твердження в `docs/superpowers/{plans,specs}`, `docs/tasks`, `AGENTS.md`, `CLAUDE.md`, `.github/instructions/*` |
| **architecture** | зачеплено >2 пакети `packages/simplycms/*` або межа src↔пакети | легасі й подвійні кодошляхи «старий+новий», dead code, порушення конвенцій репо й напрямку залежностей |
| **data-layer** | зачеплено БД, міграції, кеш TanStack Query, RLS, Storage | схема, типи, інвалідація, доступ (деталі нижче) |
| **history** | змінено давній або гарячий код | `git log -p`/`git blame` по змінених місцях: що вже фіксили тут раніше і чи не відкочується той фікс |

Пропорції випливають зі структури simplyCMS: код розтягнутий між SSR-вітриною і
client-only адмінкою, між тонкою збіркою `src/` і шаруватими пакетами ядра, а схема
БД живе в міграціях із **генерованими** типами — тому drift, межі пакетів і шар
даних дають найбільше сигналу. (Класи дефектів, успадковані з metahub як орієнтир:
drift, типи, кеш/інвалідація, edge cases, легасі, RLS, моки. Це орієнтир, не
статистика цього репо.)

**Доменні критерії simplyCMS** (конкретика для двох лінз — решта в
`.github/instructions/*` за темою: `architecture-core`, `data-access`,
`ui-architecture`, `coding-style`, `optimization`, `storage`, `editor`, `tooling`):

- `architecture` — напрямок залежностей **за тірами з
  `packages/simplycms/README.md`** (це джерело, не переказуй по пам'яті):
  T0 `objects` → T1 `domain` → T2 `data-supabase`/`react-query`/`storefront` →
  T3 `ui` → T4 `plugins`/`themes` → T5 `admin`. 🔴 Два факти, без яких лінза дає
  хибні спрацювання: пакети одного тіру — **сиблінги**, а не ланка ланцюга
  (`data-supabase` і `react-query` обидва залежать лише від `objects`, один від
  одного — ні); `core` — **legacy-фасад поза тірами**, що декомпозується, і його
  наявні ребра (`core → plugins`, `core → *-ui`, `theme-system → core`) — відомий
  борг, а не свіже порушення: позначай їх, лише якщо диф їх **додає** або
  поглиблює. Далі — server/client розділення (`createServerFn` у `src/server`, route
  loaders, middleware у `src/start.ts`) проти client-only адмінки (`ssr: false`
  **завжди** з `pendingComponent`); теми — презентація, логіки не містять; імпорти
  пакетів через аліаси, не відносними шляхами; барелі не змішують server-only й
  client-safe експорти; `src/routeTree.gen.ts` руками не редагується.
- `data-layer` — зміни схеми йдуть **локальними міграціями** в
  `supabase/migrations/` + `pnpm db:migrate` (Supabase MCP — лише інспекція:
  `list_tables`, read-only `execute_sql`, `get_advisors`).
  🔴 **Не став `major` за «суперечить канону»**, якщо диф робить локальну
  міграцію: `data-access.instructions.md` тут суперечить сам собі (рядок 51 —
  «міграції живуть у `supabase/migrations/`»; рядки 15/55/103 — ще MCP-only) і
  виправляється Task 12.5 Step 4 плану Фази 0. Діє правило локальних міграцій.
  Далі: типи регенеровані
  (`pnpm db:generate-types`, `supabase/types.ts` руками не правиться);
  RLS-політики на кожній зачепленій таблиці; **жодного глобального
  supabase-singleton** — DI через `SupabaseProvider`/`useSupabaseClient` або
  порти-репозиторії з `objects`; Zod-валідація входу на сервері; інвалідація
  TanStack Query (стабільні `queryKey`, адекватний `staleTime`,
  `router.invalidate()`) відповідає тому, що змінили; типи БД проти реальних
  PostgREST-відповідей; N+1.

**Стек залежить від того, що саме зачепив диф** — не змішуй правила різних зон:

| Зона | За чим перевіряти |
| ---- | ----------------- |
| `storefront-routes/routes/_storefront*` | SSR: route loaders, дані з `storefront-routes/src/server`, каркас `StorefrontShell`, SEO (`storefront-routes/src/seo`) |
| `admin-routes/routes/*` | client-only: `ssr: false` **лише** на `admin.tsx` + `pendingComponent`, guard у `src/start.ts`, TanStack Query замість loader-даних |
| `storefront-routes/routes/{_protected*,auth,api}` | auth-гейти, cookie-сесії `@supabase/ssr`, серверні роути |
| `*/src/server` | `createServerFn`: Zod-валідація входу, перевірка сесії/ролі, жодних client-only імпортів |
| `routes.ts`, `src/routes/` | дерево збирає `virtualRouteConfig`; host тримає лише `__root.tsx` + `my/` (гард — `tests/virtual-routes-escape.test.ts`) |
| `packages/simplycms/*` | межі пакетів і напрям залежностей, публічні барелі, ліміт 150 рядків, відсутність прив'язки до `src/` |
| `themes/*`, `plugins/*` | контракт теми v2 (`manifest+tokens+components`, без сторінок/лейаутів), реєстрація з `config.themes`, нуль бізнес-логіки й прямих запитів до БД |

**Два правила для формулювання «як лагодити»:**

- **єдиний патерн для домену** — пропонуй те, що зводить усі компоненти домену до
  одного механізму, а не ще один окремий випадок;
- **без обгорток поверх обгорток** — рішення має працювати через наявні механізми;
  якщо наявна абстракція застаріла, скажи це прямо й запропонуй міграцію, а не
  нашарування.

**Лінза `history` — найнедооціненіша.** Саме в git-історії змінених місць лежить
контекст «це вже ламали, ось так фіксили».

Пошук по репо — **`git grep`**, не `grep -r`: інакше провалишся в `node_modules`,
`.output` і генерат.

## 3. Adversarial-крок — обов'язковий, не опційний

Кожна знахідка з попереднього кроку йде на **спробу спростування** — окремим проходом
(бажано окремим агентом, який не бачив, як знахідку формулювали):

- завдання формулюється як «**спростуй це**», а не «перевір»;
- **дефолт — спростовано**: якщо доказу немає, знахідка не проходить;
- доказ = конкретний фрагмент коду, конкретний вхід, або відтворений запуск
  (гейти в канонічному порядку: `pnpm format:check` → `pnpm lint` → `pnpm build`
  → `pnpm typecheck` → `pnpm test`; **build перед typecheck**, бо build генерує
  `src/routeTree.gen.ts`; гейт саме `format:check` — `pnpm format` це
  `prettier --write`, він не червоніє. 🔴 `prettier` наразі не встановлений
  (`devDependencies` його не містить, CI format не запускає) — тож де-факто
  гейти починаються з `lint`; це борг, а не привід писати «format зелений»);
- вердикт: `CONFIRMED` (з confidence) / `REFUTED` (з причиною) / `PARTIAL`
  (реальне, але не так і не там, де описано) — з переформулюванням.

Окремо перевіряй **власні знахідки синтезатора**: те, що зведення додало «від себе»
під час агрегації, ніхто не перевіряв — це класичне джерело галюцинацій.

Одностайність рев'юверів — не доказ. Усі проходи робить та сама модель, тож збіг може
бути спільним байасом, а не істиною.

## 4. Формат звіту

```
## Вердикт
ПРИЙНЯТИ / ПРИЙНЯТИ З ЗАУВАЖЕННЯМИ / ПОВЕРНУТИ — одне речення чому.

## Знахідки (confidence ≥ 80)
### [blocker|major|minor] коротка назва — confidence NN
**Де:** файл:рядок
**Що:** одне-два речення
**Доказ:** фрагмент коду / вхід, за якого ламається / вивід запуску
**Як лагодити:** конкретна дія, не «варто розглянути»

## Відкинуто на порозі
- назва — причина в піврядка (по одному рядку, без деталей)

## Не перевірено
- що лишилось поза межею рев'ю і чому (живий смок, SSR-рендер у браузері,
  міграція на реальній БД, продуктивність під навантаженням…)
```

Порожні секції не вигадуй. Секцію «Не перевірено» **не пропускай**: рев'ю, яке не
називає своїх меж, читається як гарантія, якої воно не давало.

## 5. Анти-патерни

- **Рев'ю за звітами виконавців.** Агенту дали «підсумки виконавців» і він переказав
  їх як перевірку. Читай **диф і код**, звіт — лише навігація по ньому.
- **Довіра зеленим тестам.** Тест, який лишається зеленим після зламу коду, — не тест.
  Якщо диф додав тести, а мутаційної перевірки не було, це `major`, а не «ок».
- **Довіра зеленому `pnpm typecheck` без build.** Якщо роути змінились, а
  `src/routeTree.gen.ts` не перегенерований, typecheck перевіряв застарілий граф.
- **Одноагентне рев'ю великого етапу.** Великий етап, прийнятий одним агентом,
  типово віддає 3-5 дефектів наступному незалежному аудиту, і fix-етап коштує на
  порядок дорожче за саме рев'ю.
- **Нітпіки замість дефектів.** Стиль, назви й форматування — лише якщо прямо названі
  в `AGENTS.md` або `.github/instructions/*`. Інакше це шум, що з'їдає довіру до
  решти звіту.
- **«Варто було б розглянути…».** Знахідка без конкретної дії не є знахідкою.
- **Рев'ю без межі** (`git diff` невідомо від чого) перетворюється на аудит репо і
  тоне в пре-існуючих проблемах, до яких диф не має стосунку.

## 6. Оркестрація

Розмір рев'ю має відповідати ціні помилки, а не звичці. Орієнтир:

| Що рев'юємо | Лінз | Adversarial |
| ----------- | ---- | ----------- |
| дрібний фікс, 1-2 файли | 1 (`correctness`) | по знахідках `blocker`/`major` |
| етап плану | 3-4 за таблицею §2 | усі знахідки |
| робота перед мержем гілки, чутливий код (оплата, замовлення, доступи, міграції) | усі релевантні + `history` | усі знахідки, для `blocker` — два незалежні скептики |

Лінзи виконуються **паралельно й незалежно** (вони не мають бачити висновків одна
одної — інакше отримаєш узгоджений байас замість незалежних думок). Adversarial-крок
іде після. Зведення робить оркестратор: дедуплікує, сортує за severity, і **сам
перевіряє все, що додав від себе**.

У Claude Code для цього є субагенти `code-review` (одна лінза за виклик) і
`code-review-verifier` (адверсаріальний скептик) — обидва працюють за цим скілом.
Для рев'ю чужого GitHub PR лишається вбудований `/review`; цей скіл — про локальну
гілку перед мержем.
