# Додаткове дослідження та комплексне рішення

Контекстом для цього промту є **усі попередні повідомлення чату, що стосуються проблемного
питання** — code review, аналіз clarify-питань, або поточне обговорення. Нерелевантні
повідомлення про інші теми — ігноруй. Жодних прикріплених файлів не потрібно. Якщо контекст
неповний або проблемні питання не ідентифіковані — запитай уточнення у користувача.

## Завдання

Проведи **глибоке дослідження** по кожному проблемному питанню, визначеному в попередній
частині розмови, і запропонуй **комплексне рішення** для кожного з них.

## Джерела для дослідження

> **Пріоритет інструментів:** 1) кодова база → 2) БД → 3) документація бібліотек →
> 4) архітектурна документація SimplyCMS. Використовуй тільки ті інструменти, які релевантні
> для поточного питання.

### Кодова база

- **Orientation-first:** спершу скіл `codebase-research` — його
  `.agents/skills/codebase-research/scripts/orient <Символ1> <Символ2> …` покаже, де лежить
  і хто споживає (з транзитивними через барелі); граф або `rg`-fallback обирає сам.
  Для широкої карти незнайомої області — `graphify query "Symbol1 Symbol2" --budget 1500`
  (🔴 токени-імена символів, НЕ речення: матчер без стемінгу й синонімів дає шум).
  Це дешевше і ширше за сліпе читання файлів.
- Якщо питання торкається незнайомого домену або потрібна cross-package інвентаризація —
  делегуй `Agent(subagent_type: "codebase-research")`: він працює за тим самим скілом,
  повертає дельту й якорі, і не роздуває головний контекст.
  Для декількох незалежних питань — fan-out кількома паралельними Agent-викликами в
  одному повідомленні, кожен на своє питання.

### База даних

- **Supabase MCP** (`list_tables`, `execute_sql`, `get_advisors`, `list_migrations` тощо) —
  **завжди** для питань, пов'язаних із БД: схема таблиць, RLS-політики, FK-зв'язки,
  SQL-запити та їх результати. Використовуй лише в інспекційному режимі (read-only) —
  MCP тут **не** застосовує міграції.
- Джерело правди про схему в самому репо — локальні `supabase/migrations/` і
  згенерований `supabase/types.ts` (`pnpm db:generate-types`). Ніколи не припускай стан
  БД — перевіряй через MCP і звіряй із файлами в репо.

### Документація бібліотек і зовнішніх рішень

- **Context7 MCP** — **завжди** для документації будь-якої бібліотеки або зовнішнього сервісу
  (TanStack Start/Router/Query, React 19, Zod 4, Supabase JS SDK, Tiptap 3, Tailwind v4 тощо).
  Ніколи не покладайся на навчальні дані — API могли змінитися.

### SSR / рендеринг / теми

- Досліджуй через **кодову базу + Context7 MCP**: route loaders та `createServerFn` у
  `packages/simplycms/src/storefront-routes/server/` (`themes.ts`, `products.ts`, `auth.ts` тощо), різницю рендер-стратегій між
  `_storefront` (SSR) і `admin` (`ssr: false` + client-side guard), ізоморфну реєстрацію тем
  у `src/theme-registry.ts`, резолюцію активної теми з БД через `getActiveTheme`, request
  middleware в `src/start.ts` (admin guard) та SEO-роути в `packages/simplycms/src/storefront-routes/seo/` (sitemap, robots).
  Ніколи не припускай поведінку рендерингу чи резолюції теми — перевіряй реальні реалізації.

### Клієнтський стан / TanStack Query

- Аналізуй TanStack Query 5: query keys, `staleTime`, інвалідацію, а також межу — що робить
  route loader (SSR-first fetch), а що клієнтський хук на Query. Для кращого розуміння API —
  Context7 MCP.

### UI

- Для питань про UI-компоненти — глобальний скіл `shadcn` і
  `.github/instructions/ui-architecture.instructions.md` (структура тем, shadcn/ui патерни).

### Архітектурна документація SimplyCMS

- `.github/instructions/*`, `AGENTS.md`, `CLAUDE.md`, `docs/architecture/*` — перевіряй
  відповідність запропонованих рішень архітектурним правилам проєкту. Для питань, дотичних
  до платформного пивоту — `docs/superpowers/specs/2026-07-30-platform-architecture-design.md`
  і трекінг `docs/tasks/platform-roadmap.md`.

## Модельний тіринг при fan-out

Якщо питань декілька і вони незалежні — розвідку по кожному делегуй окремим агентам на
`model: "sonnet"` паралельно (одне повідомлення, кілька Agent tool calls). Синтез,
порівняння альтернатив і фінальне рішення роби сам або через `Agent(model: "opus")`, якщо
питання архітектурно неоднозначне і варте другої думки. Claude Code тут — оркестратор і
валідатор: не ретранслюй висновки субагента як факт без власної перевірки ключових тверджень.

## Принципи формування рішень

> Ці принципи є обов'язковими при формуванні кожного рішення.

- **Повне рішення за один прохід.** Не пропонуй напіврішень або "виправимо пізніше". Мета —
  вирівняти всі різночитання, виключення та уточнення повністю зараз, за цей прохід.
- **Відхилення від норми — повідомляй, не вирішуй автоматично.** Якщо в кодовій базі є
  нестандартна поведінка або виключення з паттерну, які потребують рішення про стандартизацію
  — повідом про це явно та дай рекомендацію. Не приймай рішення замість користувача і не
  намагайся охопити **абсолютно** всі відхилення — важливіше виокремити ті, що реально
  впливають на підтримуваність.
- **Максимальна стандартизація.** Завжди обирай рішення, яке забезпечує **єдиний спільний
  патерн** для всіх компонентів домену. Це дозволяє легко підтримувати, розширювати та
  вдосконалювати код в одному місці, коли це реально буде потрібно.
- **Без нових абстракцій поверх абстракцій.** Категорично проти розробки нових обгорток
  (wrappers) поверх існуючих для тимчасової вигоди. Кожне рішення має працювати нативно через
  існуючі механізми — особливо якщо поточні абстракції вже застарілі.

## Формат відповіді

Для **кожного** виявленого проблемного питання:

### [Назва проблеми]

**Поточний стан** (що саме є проблемою, підтверджено дослідженням)
**Першопричина** (чому це виникає)
**Запропоноване рішення** (конкретні кроки, приклади коду якщо потрібно)
**Ризики та альтернативи** (якщо рішень кілька — порівняй їх)
**Посилання** (які інструменти/джерела підтвердили висновок)

---

**Важливо:** Не припускай — досліджуй. Якщо питання стосується БД чи документації
бібліотеки — виклич відповідний інструмент/скіл перед тим, як робити висновки.
