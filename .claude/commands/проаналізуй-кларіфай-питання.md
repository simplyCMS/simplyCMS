# Context Processing

> **Порядок виконання:** 1) критична оцінка постановки → 2) архітектурна відповідність → 3) clarify-питання → 4) суперечності → 5) структура фаз. Виконуй послідовно, не пропускай кроків.

Файл задачі/спека (або документ з clarify-питаннями) передається через `$ARGUMENTS` — або через `@`-mention (вже в контексті), або як plain path (тоді прочитай його через Read). Використовуй його як **baseline**. Якщо документ неповний, відсутній або пошкоджений — надай звіт про відсутні розділи і короткий опис впливу цього на виконання задачі (1-2 речення на розділ), замість того щоб зупинятись або запитувати уточнень.

**Clarify-питання — включай у звіт, не в чат.** Аналіз виконуй самостійно і включи clarify-питання у звіт як розділ 3 нижче. Це питання до документа для його автора, а не запит до користувача в чаті. Звіт — письмовий документ.

1. Прочитай документ і зроби **критичну оцінку якості постановки**:
	- що вже враховано добре (сильні сторони)
	- чого бракує (прогалини)
	- що містить багатозначні терміни, суперечливі твердження або неповну інформацію
	- де документ суперечить сам собі (терміни, scope, вимоги, дедлайни, DoD)
	- що є помилкою або технічно ризиковим припущенням
	- перевір, чи не розробляється це нове рішення там, де вже є готове (DRY)

2. Перевір **архітектурну відповідність** канону (`.github/instructions/*`, `AGENTS.md`) і спеці платформи (`docs/superpowers/specs/2026-07-30-platform-architecture-design.md`) відносно реальних патернів у `src/`, `packages/`, `themes/`.
у звіті явно позначай порушення. Основні моменти, на які звертай увагу:
	- використання пакетів `@simplycms/*` замість локальних копій UI/core/admin
	- SSR для storefront-сторінок (`_storefront/`), client-only (`ssr: false` + обов'язковий `pendingComponent`) для адмінки
	- cookie-based auth через `@supabase/ssr` (не localStorage JWT). Guard-ів три рівні, і всі легітимні: request middleware `src/start.ts` (серверний, для `/admin`), `beforeLoad` у `storefront-routes/routes/_protected.tsx` (перевірка сесії) і `beforeLoad` у `admin-routes/routes/admin.tsx` (роль, після гідрації)
	- система тем (контракт v2): `ThemeRegistry.load(themeName)` повертає `{manifest, tokens, components, settings?}` — без `pages`; канонічні сторінки живуть у `@simplycms/storefront-routes/src/pages/` (тема — лише презентація, без бізнес-логіки)
	- система плагінів: розширення через `HookRegistry`, не форк core-коду
	- кеш-інвалідація через `staleTime`/router invalidate + TTL-кеші серверних функцій — тут немає ISR/`revalidatePath`
	- зміни схеми БД без локальної міграції в `supabase/migrations/` + подальшого `pnpm db:generate-types`

3. Витягни всі clarify-питання (якщо в документі їх немає — сформуй 5–12 найімовірніших clarify-питань для такого типу задачі):
	- для кожного питання дай 2–3 варіанти відповіді:
		- що змінюється в scope/поведінці
		- плюси/мінуси та ризики
		- рекомендований дефолт і чому
	- при формуванні рекомендованого дефолту дотримуйся принципів:
		- **Максимальна стандартизація** — перевага рішенням, що забезпечують єдиний патерн для всіх компонентів домену
		- **Без нових абстракцій поверх абстракцій** — рішення має працювати нативно через існуючі механізми; якщо поточна абстракція застаріла — зазнач це явно замість нашаровування
		- **Повне рішення** — не рекомендуй напіврішень із розрахунком "доробимо пізніше"; якщо є відхилення від норми, що потребують стандартизації — виокрем їх окремо для рішення замовника

4. Перевір суперечності та неоднозначності у документі:
	- Витягни всі суперечності (якщо в документі їх немає — знайди потенційні суперечності для такого типу задачі)

5. Перевір структуру задачі на предмет розділення по фазам виконання та наявністю чеклистів для поетапного виконання через coding agent. Кожна фаза має містити: мету, scope, ризики, checklist, визначення готовності (DoD для фази).
