# Перевірка реалізації

$ARGUMENTS

**Два режими — визначаються наявністю аргументу:**

- **З файлом задачі** (`docs/tasks/`, `docs/superpowers/plans/`, `docs/superpowers/specs/` —
  через `@`-mention або plain path; опційно фаза: "Phase 2" чи діапазон "Phase 1-3") →
  перевіряєш і **відповідність чеклісту**, і код.
- **Без аргументу** → чисте рев'ю поточної гілки: межа =
  `git diff main...HEAD` (або `git merge-base` з базовою гілкою `main`). Кроки про
  фази пропускаєш, решта флоу — та сама. Не питай файл задачі, якщо його не дали.

Claude Code тут виступає **orchestrator + фінальний валідатор**: сам ставить діагноз, не
просто ретранслює вивід субагентів — "trust but verify" щодо будь-якого делегованого
фрагмента.

## Крок 1 — Розбір задачі та scope

**Режим із задачею:**

1. Прочитай файл задачі повністю.
2. Визнач фази за мітками "Phase N" / "Фаза N". Якщо не позначено — вважай задачу однофазною.
3. Визнач scope review: конкретна фаза → тільки вона; діапазон → послідовно; не вказано →
   **всі фази** послідовно.

**Режим без задачі:** scope = весь диф гілки; замість «фаз» працюй логічними групами
змін (за комітами або за доменами: `src/routes`, `packages/*`, `themes/*`,
`supabase/*`), щоб звіт лишався читабельним.

## Крок 2 — Орієнтація

- `git log`/`git diff main...HEAD` (або відповідний діапазон комітів) — щоб побачити реально
  змінені файли, а не покладатись лише на опис у task-документі.
- `.agents/skills/codebase-research/scripts/orient <змінений символ> …` покаже ripple
  (кого ще зачіпає зміна) — саме для перевірки **повноти охоплення**: чи не забули споживача,
  якого видно лише через барель (`@simplycms/*`, `@themes/*`, `@plugins/*`).
  Якщо етап робив rename/видалення — спершу `graphify update . --force`, інакше граф
  віддасть привидів (orient це позначить як `ФАЙЛУ НЕМАЄ`).
- Якщо контексту недостатньо (незнайомий домен, cross-package scope) — делегуй
  `Agent(subagent_type: "codebase-research")`. Пропускай цей крок, якщо scope і так чіткий.

## Крок 3 — Рев'ю (цикл по фазах / групах змін)

Для **кожної фази** у scope, послідовно (без файлу задачі — по одній логічній групі
змін, а пункт 1 пропускаєш):

1. **Conformance — унікальна частина цієї команди.** Зістав чекліст фази з `git diff`:
   пункти позначені `[X]`, але коду немає або він неповний; пункти без позначки, що
   фактично зроблені; невідповідність між сусідніми фазами. Для великих фаз делегуй
   `Agent(subagent_type: "code-review")` з лінзою **`drift`**, передавши пункти
   чекліста й межу дифу.
2. **Рев'ю коду — за скілом `code-review`** (він задає вибір лінз, шкалу
   `blocker/major/minor` × confidence з порогом 80, формат звіту й анти-патерни):
   `Agent(subagent_type: "code-review")` по одній лінзі на виклик, паралельно →
   далі `Agent(subagent_type: "code-review-verifier")` на **кожну** знахідку.
   Для чутливого коду в simplyCMS — auth і admin-guard у `src/start.ts`, checkout
   і замовлення, ціни й знижки в `packages/domain`, RLS-політики в
   `supabase/migrations` — додай лінзи `data-layer` і `history` та по два скептики
   на кожен `blocker`.
3. Зафіксуй findings фази перед переходом до наступної.

## Крок 4 — Консолідований звіт

Один звіт прямо в чаті (окремий файл не створюй), **формат — §4 скіла `code-review`**.
Дві відмінності від дефолтного формату:

- у «Підсумок» додай рядок **Відповідність задачі** — що відмічено `[X]` без коду,
  що зроблено понад чекліст;
- знахідки групуй за фазами, якщо фаз більше однієї, і додай короткий блок
  **Наскрізне** — суперечності між фазами й дубльовані патерни.

Якщо після звіту тобі доручають виправити знайдене — після фіксів **перевір лише те,
що змінили фікси** (`git diff <sha-до-фіксів>...HEAD`), ліміт 2 кола; далі `blocker`
виноситься власнику як рішення, а не як доробка.
