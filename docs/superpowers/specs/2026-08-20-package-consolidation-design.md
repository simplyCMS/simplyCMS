## 1. Мотивація — виміряно кодом, не припущено

1. **«Модульність» установки не використовується.** Шаблон магазину
   (`package.json.tpl`) ставить **23 з 26 пакетів завжди і разом**, однією
   синхронною версією. Поза установкою лише `schema` (внутрішній тулінг),
   опційна тема-референс і сам скаффолдер.
2. **Гранулярність місцями церемоніальна**: `runtime` — 3 файли / 144 LOC,
   `cart-ui` — 294 LOC, `admin-routes` — 43 файли / 308 LOC тонких
   обгорток; кожен — із повним manifest/exports/tsup/publish-циклом.
3. **Граф — не дерево**: `core` (legacy-фасад) залежить від 13 пакетів,
   `storefront-routes` — від 11; це один застосунок у 26 коробках.
4. **Вартість задокументована самим репо**: «Чеклист нового пакета»
   (`packages/README.md`) — 10 пунктів із мінами (буквальне
   `"private": false`, інакше пакет мовчки випадає з packaging-гейта;
   мовчазна незворотна публікація при мержі); ціла інфраструктура
   (`pilot-pack`, tarball-parity, `audit-deps`/`audit-exports`,
   `pack-inspect`, синхронний бамп) існує, щоб обслуговувати розрізаність.
5. **Класичні аргументи «за багато пакетів» тут не працюють**: незалежного
   версіонування немає (свідомо вимкнене синхронною версією), вибіркової
   установки немає (п. 1), tree-shaking від меж пакетів не залежить
   (Vite шейкає по модулях), клієнт/сервер-розділення й сьогодні тримається
   на **субшляхах**, а не на пакетах (прецедент
   `@simplycms/themes/safeFontStylesheets`).
6. **Прецеденти індустрії**: OpenCart/WooCommerce (модель-натхненник) —
   ядро-моноліт + розширення; Payload 3 — один пакет `payload` + адаптери
   провайдерів (пряма карта B2/B4 спеки V2); Hydrogen — 2 пакети + CLI.
   Medusa v2 — застереження: десятки пакетів із примусово синхронними
   версіями = вся вартість без вигод. Правило: **окремий пакет заслужений
   лише незалежним споживачем або незалежним ритмом версій.**
7. **Момент — зараз**: V2 і так переписує ~80 % коду пакетів
   (supabase/data-supabase/react-query/лоадери/адмінка/типи) і сам
   відкриває питання розкладки (К1). Консолідація після V2 = подвійний
   churn тих самих файлів; за інерцією V2 без К0 навіть ЗБІЛЬШИВ би
   кількість пакетів (db, auth, data-pg).

## 3. Цільова структура

```
simplycms                          ← фреймворк, unscoped
├── src/
│   ├── contracts/                 ← T0 (нинішній objects; + /views, /views/fixtures)
│   ├── domain/                    ← T1 (pricing/discounts/inventory/shipping)
│   ├── schema/                    ← T1 (Drizzle; V2-B12 зробить єдиним джерелом типів)
│   ├── supabase/ data-supabase/   ← T2 (переїзд як є; зносить V2 уже як субшляхи)
│   ├── react-query/ runtime/ i18n/ storefront/            ← T2
│   ├── ui/                        ← T3
│   ├── themes/ plugins/ plugin-sdk/                       ← T4
│   ├── admin/ routes/{storefront,admin}/ + feature-UI     ← T5 (5×*-ui розчиняються
│   │                                                        у storefront/admin-шарах)
│   └── theme-sdk/                 ← створює V2-К5 (ПК5)
├── skills/
│   └── redesign-from-reference/   ← SKILL.md + scripts/ (ПК8)
└── package.json                   ← exports: субшляхова мапа (стереже audit-exports)

@simplycms/cli · create-simplycms-store · @simplycms/theme-solarstore · @simplycms/plugin-faq
```

Фінальний розклад тек/субшляхів — імплементаційний план; інваріанти спеки:
субшлях на кожен нинішній публічний вхід (парність споживаних субшляхів
стереже `audit-exports`), server-only входи не течуть у клієнтські барелі,
`skills/**` їде в tarball (`files`).

## Додаток A. Довідка: жива проба skills.sh (2026-08-19)

Збережено з видаленого плану доставки — знання про стандарт стане в пригоді
(розкладку `.agents/skills/` + `.claude/skills/` ми переуживаємо, канал —
ні). Джерела: README `vercel-labs/skills`, специфікація agentskills.io,
дерево `supabase/agent-skills`, дві живі проби `npx skills add` у чистих
теках.

- **Одиниця установки — тека скіла цілком**: специфікація штатно називає
  `scripts/`, `references/`, `assets/`; проба довезла
  `supabase-postgres-best-practices/references/**` (36 файлів) без втрат.
- **Структура репо-джерела** — `skills/<name>/SKILL.md`, без маніфеста; CLI
  обходить теки-контейнери (`skills/`, `.agents/skills/`, `.claude/skills/`,
  корінь) на глибину 3. Інваріант: `name` у фронтматері = ім'я теки.
- **Матеріалізація у споживача**: реальні файли в `.agents/skills/<name>/`
  (канонічна копія, спільна для ~17 агентів) + симлінк
  `.claude/skills/<name>` → `../../.agents/skills/<name>` + `skills-lock.json`
  у корені (`source`, `sourceType`, `skillPath`, `computedHash`).
- **Оновлення**: `npx skills update` (ручний; завжди latest з git,
  семвер-піну немає — свідома межа каналу). `--copy` кладе реальні файли
  просто в `.claude/skills/`.
- **Чому канал відхилено** (рішення 2026-08-20): джерело правди скілів
  переїхало в npm-пакет `simplycms` (ПК8) — окремий git-репо створив би
  друге джерело правди, розсинхрон версії скіла з версією ядра (латка —
  верифікація сумісності, яку npm дає безкоштовно через lockfile) і третій
  канал доставки поза моделлю П1–П5 маркетплейсу.
