## Тема 2 · Renovate + аудит у CI ✅

- **Renovate, не Dependabot:** версії шаблону живуть у `package.json.tpl`, і тест
  `tests/template-version-parity.test.ts` вимагає їх рівності з коренем; Dependabot `.tpl`

  оверлею: корінь/шаблон/оверлей одним PR.
- Групи: TanStack Start/Router; TanStack DB (3 пакети — точні звʼязки версій); tiptap; React;
  eslint + typescript-eslint; drizzle.
- Точні піни лишаються точними; `minimumReleaseAge` ≥ порогу pnpm; розклад щотижня;
  безпекові — одразу; мажорні — окремими PR; **автомержу немає** (реліз — рішення людини).
- Пакети із записами в `docs/architecture/upstream-workarounds.md` (TanStack, drizzle,
  better-auth, typescript-eslint, tsdown) — мітка + нотатка «перевір записи реєстру».

## Тема 4 · Заголовки безпеки ✅ (хвиля 1) · CSP → беклог

**Факти:** захисні заголовки є лише на роздачі медіа (`storage/serve.ts`); SSR-сторінки — без
жодного. Router вміє nonce на свої скрипти (`router-core` `ssr: { nonce }`,
`router.ts:544`; проставляється в `Scripts.tsx`, `hydrationScripts.ts`,
`renderRouterToStream.tsx`), але звʼязку «nonce з middleware → `getRouter()`» Start готовою
не дає. Статика `/assets` віддається sirv у `server.mjs` ПОВЗ Start.

**Хвиля 1 (зараз):**
- Функція ядра `buildSecurityHeaders(config, { isHttps, pathname })` у `simplycms/runtime` —
  ЄДИНЕ джерело; викликають request middleware (третій елемент `requestMiddleware` у трьох
  `start.ts`) і `setHeaders` sirv (`server.mjs` / `server-runtime.mjs`).
- Дефолти: `X-Content-Type-Options: nosniff`; `Referrer-Policy:
  strict-origin-when-cross-origin`; `Permissions-Policy: camera=(), microphone=(),
  geolocation=(), usb=(), serial=(), bluetooth=()` (`payment` не чіпати — Google Pay);
  `X-Frame-Options: DENY` для `/admin*` і `/auth*`, `SAMEORIGIN` для вітрини;
  `Cross-Origin-Opener-Policy: same-origin-allow-popups` (popup-и OAuth/3-D Secure);
  HSTS лише при довіреному `x-forwarded-proto=https`, `max-age=15552000`, без
  `includeSubDomains`/`preload` (HSTS незворотний на строк дії).
- Конфіг магазину: `simplycms.config.ts` → `security: { frameAncestors?, hsts?: false |
  { maxAge, includeSubDomains }, permissionsPolicy?, coop?, referrerPolicy? }`.
- Тести: юніти `buildSecurityHeaders` (HTTP/HTTPS, `/admin` vs вітрина, конфіг);
  інтеграційні — заголовки на SSR, редіректах, 404, server functions; sirv-статика має
  `nosniff`; `live:smoke` — заголовки на живій сторінці.

**CSP — беклог, окремий трек разом із механізмом інтеграції типових пікселів і аналітики
(рішення власника).** Передумови: санітизація HTML (попередній трек, тема 9); прибрати
інлайн-скрипт `src/routes/__root.tsx:97` (у data-атрибут/meta); канал для сторонніх скриптів
(продуктове рішення — зараз механізму немає взагалі). Нотатки з дослідження: nonce через
`ssr.nonce` + спайк звʼязки middleware → `getRouter()`; спершу Report-Only + ендпоінт
`/api/csp-report` (свідомий виняток у CSRF); декларації origin-ів у маніфестах тем/плагінів;
суворий режим — за вибором магазину; у dev CSP вимкнено (HMR); кеш HTML на CDN знецінює nonce.
Також памʼятати: вебхуки платіжних систем — свідомі винятки CSRF.

### Тема 6 · TanStack Query + SSR-інтеграція Router ✅ (окремий план)

**Спайк (2026-10-05, prod-збірка + Playwright + `db:demo`, `log_statement=all`):**
- **Дефект підтверджено, гірший за гіпотезу.** Зміна назви товару в БД → повернення на
  головну через 65 с і через 310 с — обидва рази показано СТАРУ назву. На 310 с лоадер сходив
  у БД (1 HTTP + 1 транзакція), а UI результат викинув: SWR-`loaderData` засіває запис Query,
  свіжий `initialData` на наявний запис не діє. Два власники свіжості (route `staleTime` і
  Query `staleTime`) не узгоджені.
- Пілот на головній (`@tanstack/react-router-ssr-query@1.167.3`,
  `setupRouterSsrQueryIntegration({ router, queryClient, wrapQueryClient: false })` —
  `QueryClientProvider` уже монтує `CMSProvider`; `ensureQueryData` у лоадері,
  `useSuspenseQuery` у контейнері; view і vm без змін): SSR-HTML з даними — так; зайвих
  клієнтських запитів після гідрації — 0 (до і після; 3 клієнтські serverFn — bootstrap
  тем/плагінів); повернення через 310 с — **свіжі дані**; hover-preload наповнює той самий
  кеш (клік — 0 запитів); попереджень гідрації немає. Ціна пілоту — 6 транзакцій на SSR
  замість 1 (кожен запит — своя `withStorefrontDb`).

**Рішення (власник, 2026-10-05):**
1. **Запит рівня сторінки за замовчуванням:** одна server function і ОДНА транзакція на дані
   сторінки (як `getHomePageData`); лоадер розкладає частини в дрібні ключі через
   `setQueryData`. Дрібні самостійні ключі — лише для частин, що оновлюються незалежно
   (каруселі з власним циклом). Причина: 6 паралельних транзакцій = 6 зʼєднань пулу на один
   перегляд — ризик вичерпання пулу під навантаженням.
2. **Одна політика свіжості — у фабриках `queryOptions` на рівні сутності** (банери, розділи
   — 5 хв; товари каруселей і каталогу — 60 с); `staleTime` маршрутів прибрати;
   `defaultPreloadStaleTime: 0`.
3. **Модель помилок:** `useSuspenseQuery` кидає → `errorComponent` на каркасі вітрини
   (`_storefront`/shells), щоб помилка блоку не валила сторінку; `defaultPendingComponent` —
   запасний для Suspense; основний індикатор — смуга `RouterProgress` (тема 3).
4. **Розгортання по сторінках окремим планом** разом із темою 3: головна (зразок) → каталог,
   розділ (`loaderDeps` для search-параметрів у ключі), товар, властивості; ~7 тестів старої
   поведінки переписати (`home-n-plus-one`, `home-queries-errors` — помилка тепер кидається,
   `page-views-resolve`); `HomePageProps` прибрати з публічного API (без сумісності).
5. **Магазин:** нова залежність `@tanstack/react-router-ssr-query` точним піном
   (`package.json.tpl`, пілотний оверлей), змінений `src/router.tsx` (канон host-файлів,
   `template:sync`, доставка `simplycms update`, перевірка `doctor`); новий субшлях exports
   `./storefront-routes/queries/*` (обидві мапи — інакше Gate пілота падає).
6. Перевірити окремо: інтеграція дегідрує ВЕСЬ кеш Query — переконатися, що колекції адмінки
   (client-only) не потрапляють у SSR-payload.

### Тема 7 · React Compiler ❌ не беремо (замір, 2026-10-05)

- **Замір в адмінці** (prod-збірка Vite 8 з/без компілятора, `react-dom/profiling` +
  `React.Profiler`, Playwright, 4× CPU throttle, медіана 3 прогонів по 7–9 повторів, сід
  200 товарів / 150 замовлень): кількість комітів **не змінилась у жодному сценарії**; час
  рендеру: ціни −3 % (шум), замовлення «Показати ще» −18 %, кількість позиції −14 %,
  фільтр списку на 208 рядків −18 %, пошук у діалозі — у межах шуму; INP-подібні таймінги —
  у межах шуму. Поріг рішення, заданий наперед (≥30 % у двох сценаріях без регресії), — не
  досягнуто.
- Ціна: клієнтський JS +8,9 % raw / **+13,3 % gzip** (мемо-код стискається гірше); чанк
  редагування товару gzip 13,2 → 25,4 КБ.
- Гарячі форми адмінки не компілюються (тихі пропуски): `try/finally` у `PricesEditor`,
  `StockEditor`, діалогах позицій замовлення; 20 пропусків на деструктуризації з дефолтами
  (можливо, звʼязка Babel 8 + компілятор 1.0.0).
- Причина: коміти породжують зміни стану, а не відсутність мемоізації; адмінка й так дешева
  (0–45 мс на типову дію при 4× throttle).
- **Умова перегляду:** лише для довгих списків (200+ рядків) — і спершу віртуалізація
  (TanStack Virtual), а компілятор — у режимі `annotation` на таблицях, якщо віртуалізація
  не допоможе.
- Рамку «React 19» (peer `^19`) це не скасовує — вона лишається рішенням власника.

- `validateSearch` руками в 4 роутах → zod (Router приймає Standard Schema напряму; потрібен
  `.catch` для мовчазного відкидання некоректних значень).
- Захардкоджена `uk`-локаль дат в адмінці (`date-fns` з `uk`, `toLocaleDateString('uk-UA')`)
  → локаль з i18n.

### Тема 11 · Кешування й зображення ⏳
- `Cache-Control` лише на `/media` і SEO; для анонімних SSR-сторінок без `Set-Cookie` —
  кандидат (ризик віддати чужий кошик — лише анонімні).
- Зображення без `srcSet`/`sizes` (8 місць) — потребує серверного ресайзу.

## Свідомо НЕ беремо (з обґрунтуванням)

changesets (наш `pnpm release` з гейтами й синхронною версією 5 пакетів кращий); syncpack
(не читає `.tpl` — наш тест паритету потрібен); `nuqs` (є search params Router); `dinero.js`
(цілі центи вже є); `@total-typescript/ts-reset` (глобально змінює типи — ризик для
опублікованого фреймворку); `vitest-axe` (мертвий); окреме стиснення (sirv уже віддає
gzip+brotli); Storybook (без окремого рішення про каталог компонентів); Rust-порт React
Compiler (`compiler: true` — експериментальний); `t3-env` (контракт env уже стережеться).

## Лишаємо своє (обґрунтовано)

`server.mjs` + `server-runtime.mjs` (пріоритет env, `immutable` для `/assets`, `signal` для
скасування SSR); читання `.env` через `node:util.parseEnv`; `formatPrice` (символ валюти
різний у Node і браузері → гідраційний мисматч); i18n (`translator.ts`, три рівні
каталогів; вада — немає форм множини); реєстри тем/плагінів (контракти платформи); TTL-кеш
теми (серверний кеш між запитами зі скиданням з адмінки); PG-харнес (поведінкова матриця
RLS); реліз-скрипти; тест паритету версій; debounce у двох місцях.

### Тема 14 · Реалтайм ⏳ (дослідження)
- Вибір власника — **Centrifugo** (вже працює в іншому проєкті власника, легкий у розгортанні),
  не ElectricSQL.
- Реалтайм НЕ замінює тему 6 (дефект — неузгодженість двох кешів усередині клієнта; перший
  рендер і гідрація від реалтайму не залежать), але може лягти поверх неї: подія → інвалідація
  ключа Query / колекції TanStack DB.
- Потенційна цінність: адмінка з кількома користувачами (нові замовлення без оновлення,
  одночасне редагування), живі статуси/залишки для покупця.
- Питання дослідження: модель безпеки (канали й авторизація підписок проти нашої RLS-моделі
  через `withActor`), звідки публікувати події (серверний шар після коміту транзакції),
  ціна для self-hosted магазину (ще один сервіс), інтеграція з TanStack DB.

### D1 · 🔴 Можливе падіння Node-процесу при закритті сторінки посеред запиту ⏳
- Побіжна знахідка спайку теми 7: закриття сторінки посеред запиту → `AbortController.abort`
  на `ServerResponse close` → «unhandled» → процес помирає (за звітом агента; власний
  перегляд `server.mjs`/`server-runtime.mjs` показує обробку розриву, тож причину треба
  ВІДТВОРИТИ, а не вгадувати). Якщо підтвердиться — будь-хто кладе магазин, закриваючи
  вкладки. Найвищий пріоритет.
