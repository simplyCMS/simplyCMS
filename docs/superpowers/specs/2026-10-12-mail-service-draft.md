# Власний поштовий сервіс для магазинів — ДРАФТ (наступний етап)

> **Статус: драфт, рішення НЕ ухвалено.** Фіксує дослідження 2026-10-12 і відкриті питання, щоб
> опрацювати окремим етапом після запуску пілоту. Для пілоту діє рішення власника 2026-10-12:
> платформа має лише **порт пошти з SMTP-драйвером** (спека
> [`2026-10-12-pilot-readiness-design.md`](2026-10-12-pilot-readiness-design.md), §3), а пілот шле
> через Resend по SMTP як тимчасовий канал. Resend у код платформи не потрапляє — заміна
> провайдера = зміна `SMTP_URL`.

## Навіщо

Власник не хоче закритий SaaS як довгострокове рішення. Потрібен open-source поштовий сервіс для
транзакційних листів (скидання пароля, запрошення, замовлення) — за аналогією з уже розгорнутою
інфраструктурою: спільне сховище Garage (один сервіс, бакет+ключ на застосунок) або realtime
Centrifugo (сервіс біля кожного застосунку).

## Обмеження, що визначають топологію (факти дослідження)

- **Hetzner Cloud блокує вихідні 25/465** за замовчуванням; розблокування — limit request у консолі
  для акаунта старшого за місяць зі сплаченим рахунком, рішення індивідуальне. 587 не блокується
  ([Hetzner Cloud FAQ](https://docs.hetzner.com/cloud/servers/faq/)).
- **Репутація.** Microsoft періодично блокує цілі діапазони Hetzner (S3150/S3140/5.7.606/5.7.511,
  [Hetzner doc](https://docs.hetzner.com/robot/dedicated-server/troubleshooting/microsoft-blacklist/));
  Gmail вимагає SPF/DKIM, валідні forward+reverse DNS, TLS
  ([Google](https://support.google.com/a/answer/81126)); нова IP з десятками листів на день
  репутації не набирає. Репутація домену (DKIM `d=`) важить більше за IP.
- **Наслідок:** сервіс на кожен магазин = окремий запит на порт 25, окремий PTR і «холодна» IP —
  найгірша доставлюваність і найбільша операційна ціна. Реалістичні варіанти — спільний сервіс
  або зовнішній relay.

## Кандидати (стан на 2026-10-12)

| | Postal | Stalwart |
|---|---|---|
| Ліцензія | MIT | AGPL-3.0 (+ Enterprise) |
| Модель | «self-hosted Mailgun»: організація → поштовий сервер на магазин → домени з DKIM, credentials, ліміти, suppression, webhooks, HTTP API + SMTP | повний поштовий сервер (SMTP/IMAP/JMAP), DKIM-автоматика, черги, webhooks |
| Ресурси | окремий сервер ≥4 ГБ, MariaDB ≥10.6 | ~100 МБ idle, 1 ГБ достатньо |
| Вхідна пошта | ні (лише bounce) | так (скриньки `support@`) |
| Ізоляція магазинів | так (server+credentials на магазин) | multi-tenancy — лише Enterprise |
| Зрілість | v3.3.7, стабільний | v0.16.x, 1.0 очікується; міграції між мінорами з простоєм |
| Dokploy | шаблону немає (власний compose) | шаблон є, порти треба переробити |

Відкинуто: useSend і Plunk (обидва вимагають AWS SES — це знову закритий сервіс), Notifuse (BSL),
Listmonk/Keila/BillionMail (розсилки, не транзакційні), Mox (0.0.x, один мейнтейнер), Haraka/Postfix
(конструктор без suppression/webhooks), Cuttlefish (покинутий). Dev — Mailpit (уже береться в
пілотний етап).

## Попередня рекомендація архітектора

Контракт платформи лишається SMTP (магазин стороннього власника приносить будь-який провайдер).
Для наших магазинів — **спільний Postal** на окремому малому сервері в приватній мережі Hetzner,
поштовий сервер і домен на магазин (модель Garage). Старт — через relay на 587, поки IP набирає
історію; доставку перевіряти на реальних Gmail/Outlook/ukr.net до відкриття магазину.

## Відкриті питання (власник)

1. Чи потрібна вхідна пошта (`support@магазину`, відповіді покупців)? «Так» зсуває вибір до Stalwart
   або окремого вхідного рішення; «ні» — Postal + `Reply-To` на звичайну скриньку власника.
2. Чи будуть магазини сторонніх власників на нашому спільному сервісі (спільна репутація IP), чи
   кожен приносить свій SMTP?
3. Чи потрібні в адмінці статуси доставки й bounce (тоді — HTTP-драйвер Postal з webhooks поверх
   SMTP-порту), чи досить «відправлено»?
4. Який сервер і чи той самий акаунт Hetzner, що й Garage (порт 25 розблоковується на акаунт)?
5. Чи лишається зовнішній relay постійним резервом для Outlook, чи лише на період прогріву?
