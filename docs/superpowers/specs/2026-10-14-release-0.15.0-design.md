## 4. Частина Д — доставка: мінімальний коректний стан

**Принцип (вимога власника).** Зіставлення за назвою або вільним текстом — помилка рішення: лише довідники й
однозначний вибір. Тому механізм «зона за текстом міста чи області» **зноситься**, а не латається. До довідника
населених пунктів (після релізу) зона визначається лише однозначними даними.

Підтверджені дефекти, які закриває ця частина. Відтворення — `~/simplycms-research-ml/verify/{zones,pickup}.mts`,
звіт верифікації — `~/simplycms-research-ml/11-name-matching-verified.md`:

- самовивіз бере зону з прихованого поля міста, а не з точки → `shipping_unavailable`;
- без основної зони тариф береться з довільної зони (`domain/shipping.ts`, `.filter((r) => !zone || …)`);
- зона за вільним текстом міста («Kyiv», «м. Київ» → основна зона);
- `regions` порівнюється з містом;
- `orders.shipping_zone_id` / `shipping_rate_id` ніхто не пише.

**Д1. Зносимо `shipping_zones.cities` і `shipping_zones.regions`** зі схеми (М4), контракту
(`contracts/objects/shipping.ts`), серверу адмінки (`admin-server/impl/shipping-zones`, `columns-to-zod`),
`commerce/shipping-directory.ts`, `domain/shipping.ts`, форми, рядка й картки зони в адмінці, i18n-каталогів
(uk + en, тести парності) і сідів (`db:demo`, `db:showcase`). Місто з адреси покупця більше ніде не впливає на
вибір зони.

**Д2. Рівно одна основна зона — інваріант даних.**

- Не більше однієї: наявний частковий унікальний індекс `idx_shipping_zones_single_default`.
- Не менше однієї: baseline-сід (`0003_seed.sql`) створює основну зону з фіксованим id. Обмеження на рівні БД
  (відкладений constraint-тригер, перевірка на коміті) забороняє стан без основної зони.
- Основна зона завжди активна: `CHECK (NOT is_default OR is_active)`.
- Адмінка:
  - основну зону видалити не можна (зрозуміла відмова через i18n, а не помилка БД);
  - дію «зробити основною» на іншій зоні виконують атомарно, однією транзакцією.
- Назва зони в сіді — так само, як інші системні довідники сіду. Мову сідів системних довідників розв'язує
  хвиля мультимовності, не ця.
- `test:schema` перевіряє інваріант на ВСІХ шляхах запису: створення, оновлення, видалення, зміна основної.
  Негативний контроль — прибрати тригер → тест червоний.

**Д3. Визначення зони — одна функція ядра**, яку використовують котирування чекауту, `placeOrder` і перерахунок
доставки в адмінці (рішення Е5б-2):

- спосіб із доставкою за адресою (кур'єр) → основна зона;
- самовивіз → `pickup_points.zone_id` обраної точки, а якщо там `NULL` → основна зона.

Поле міста у вхідних даних котирування на зону не впливає (`build-quote-input.ts`, `shipping-choice.ts`,
`shipping-providers.ts`).

**Д4. Fail-closed лише для тарифів по зонах.**

- Для способу, ціна якого — тарифи `shipping_rates` по зоні: якщо для визначеної зони немає активного тарифу,
  відповідь `shipping_unavailable` з причиною, видимою покупцю (i18n). Тариф іншої зони — ніколи.
- Fail-open `!zone ||` зноситься.
- Способи з іншим режимом ціни (провайдер-перевізник, майбутній плагін НП) не зачіпаються. Режими — за моделлю
  «спосіб = провайдер + режим ціни» (Е6а).

**Д5. Замовлення пам'ятає зону й тариф.**

- `placeOrder` записує `orders.shipping_zone_id` і `orders.shipping_rate_id` — ті, за якими порахована доставка.
- Перерахунок в адмінці (Е5б-2: за поточними правилами) бере записану зону й поточний тариф цього способу в цій
  зоні та оновлює `shipping_rate_id`.
- Якщо записану зону видалено (`SET NULL`) — зона визначається заново за Д3.

**Д6. Адмінка зон.**

- Форма без міст і областей; основна зона позначена.
- Коротка підказка: «основна зона — для доставки за адресою; інші зони — для точок самовивозу; прив'язка до
  населених пунктів з'явиться з довідником».
- i18n uk + en, парність.

**Д7. Тести — справжнім шляхом.**

- Сценарії з `verify/zones.mts` і `verify/pickup.mts` стають регресійними тестами, які червоніють на поточному
  коді (доказ — прогін до виправлення).
- Ланцюг для самовивозу: вибір точки → котирування → `placeOrder` → рядок `orders` із записаними зоною й
  тарифом.

**Д8. Канон і стан.**

- Описати поточну модель доставки в каноні: `data-layer.md` або чинний документ про доставку — план визначить
  місце за `orient --map "доставка зони тарифи"`.
- У roadmap — рішення власника 2026-10-14: довідник населених пунктів і плагін НП з API ідуть після релізу.
  Це рішення, а не беклог «на колись».

## 5. Частина Ф — boolean-фільтр вітрини

Дефект підтверджено: `FilterSidebar.tsx` ставить `filters[slug] = true`, а `filter-predicates.ts` для не-масиву
повертає `false`. Крім того, `FilterableProduct` не несе значення boolean-властивості. Наслідок — порожній каталог.
Відтворення — `~/simplycms-research-ml/verify/boolfilter.mts`.

**Ф1.** Семантика:

- позначений boolean-фільтр → товари, у яких значення властивості `true`;
- не позначений → без обмеження.

Подання в URL і в серверному лоадері — у тій самій схемі, що й інші фільтри (фасети за id, не за підписом).

**Ф2.** Тест, що проходить реальний ланцюг «стан фільтра → предикат / лоадер → непорожній результат» і червоніє
на поточному коді.
