## 1. Мотивація: чому міняємо, і чому саме зараз

### 1.1. Що показало дослідження (5 висновків)

1. **«Повільність серверного читання» — міф за умови колокованої БД.**
   Next.js-травма власника (браузер→сервер→БД→сервер→браузер) походила з
   serverless cold start (+100–400 мс TLS до БД), **бази в іншому регіоні**
   (+50–150 мс/запит; усунення давало −80 % латентності у виміряних
   кейсах) і водоспадів фетчів. У SimplyCMS жодної з цих умов немає:
   `server.mjs` — довгоживучий процес із пулом зʼєднань, БД колокована в
   обох цільових сценаріях (VPS клієнта / Dokploy-проєкт хмари) — хоп
   сервер→БД <1 мс. Прямий SQL із сервера навіть швидший за
   браузер→PostgREST (~2–3 мс проти ~10 мс на запит: зникає
   HTTP-трансляція + оцінка RLS).
2. **Головний важіль швидкості вітрини — спільний кеш анонімного трафіку**
   (CDN + `Cache-Control` + stale-while-revalidate + інвалідація по події —
   так побудовані Shopify Hydrogen/Oxygen і Vercel Commerce). Пряме
   браузерне читання БД **структурно виключає** спільний кеш: кожен
   відвідувач обходить застосунок. Аудит коду: на SSR-відповідях зараз
   нуль кеш-заголовків, кожен рендер бʼє в БД, на сторінці секції —
   водоспад, на Home — N+1.
3. **TanStack DB знімає суперечку «пряме vs серверне» повністю:** колекція
   з live-запитами (~1 мс, диференціальний dataflow) — це локальні дані в
   браузері незалежно від транспорту; `queryCollection` обгортає довільний
   `queryFn` (serverFn, PostgREST, sync) — джерело взаємозамінне за
   інтерфейсом. Швидкість «браузерного читання» досяжна без виставляння
   БД в інтернет.
4. **AI-краулери не виконують JavaScript** (перевірено на 500 млн запитів
   GPTBot — нуль виконання; ClaudeBot/PerplexityBot так само; виняток —
   лише Gemini). Усе критичне про товар мусить бути в серверному HTML.
   Агентна комерція вже реальна (OpenAI ACP + Stripe: checkout у ChatGPT;
   Google AP2; Shopify вбудовує MCP-ендпоінт у кожен магазин).
5. **Звʼязаність ядра з Supabase — глибока, і зараз останній момент її
   зняти дешево.** Браузер — прямий клієнт БД (каталог, чекаут, профіль,
   вся адмінка), безпека — RLS на `auth.uid()`, auth-флоу — GoTrue
   (verifyOtp/token_hash/inviteUserByEmail/тригер на `auth.users`),
   storage-виклики у 6+ місцях поза портом, SSR-лоадери повз порти, теми
   легально імпортують `@simplycms/supabase` (Р10), контракт
   `usePluginTable` — PostgREST-форма. **З першим стороннім плагіном/темою
   контракт портів заморожується назавжди** (політика маркетплейсу) —
   тому v2 має пройти ДО відкриття подач.

### 1.2. Чому не «мінімальний Supabase-стек»

Розглянуто і відхилено три альтернативи:

- **Повний self-hosted Supabase per tenant**: 1.5–4 GB idle на стек (Kong
  ~2.5 GB із задокументованим витоком памʼяті), 1 стек = 1 проєкт
  (спільний — офіційно нештатно, GoTrue не мультитенантний), Management
  API для self-hosted не існує, три ламкі міграції лише за 2026 рік.
- **Мінімальний Supabase-сумісний стек** (PG+GoTrue+PostgREST+storage-api
  за Traefik, ~250–650 MB): технічно робочий компроміс, але за критерієм
  «подальша експлуатація» програє v2 — платформа назавжди супроводжує
  три чужі лінії версій на кожному тенанті, безпека лишається RLS-only
  (тестується тільки проти живої БД), контракт плагінів лишається
  PostgREST-формою, дуальні типи лишаються.
- **Заміна лише auth (Better Auth) при збереженні PostgREST**: міст
  «Better Auth JWT → PostgREST → auth.uid()» — недокументована пара з
  двома паралельними токен-механізмами; виграш мізерний (GoTrue — один із
  найлегших контейнерів, ~10–50 MB).

**Пункт призначення v2 кращий за всі три**: 2 stateful-компоненти на
тенанта замість 4–5, авторизація тестується vitest-ом без Docker,
одне джерело типів, бекенд-нейтральні порти екосистеми, незалежність від
churn self-hosted Supabase.

## 2. Зафіксовані рішення (B1–B12)

| # | Рішення |
|---|---------|
| B1 | **Сервер-first дані.** Браузер НЕ звертається до БД ні напряму, ні через PostgREST. Канонічні сторінки — SSR через route loaders → `createServerFn` → Drizzle → Postgres. Клієнтський рантайм (навігація, інтерактивність, адмінка) — TanStack Query/DB-колекції поверх тих самих serverFn. PostgREST зникає зі стека |
| B2 | **Контракт бекенда — чистий Postgres + будь-який S3-сумісний storage.** Supabase перестає бути обовʼязковим фундаментом і стає **одним із підтримуваних провайдерів** (його Postgres + S3-сумісний Storage-ендпоінт відповідають контракту). Позиціонування продукту: «TanStack Start + Postgres», ширше, не вужче |
| B3 | **Auth — Better Auth** (MIT, під Vercel з 07.2026): бібліотека всередині Node-процесу, таблиці в тій самій БД через Drizzle-адаптер, cookie-сесії (stateful, revoke миттєвий). Флоу v2: email/password, invite власника, reset, Google OAuth (callback на домені магазину; у хмарі — спільний auth-домен платформи, див. cloud-спеку C9). Плагіни Better Auth підключаються мінімально необхідні (менша CVE-поверхня); версія піниться, security advisories відстежуються. 🔴 **B3′ (амендмент 2026-08-23):** таблиці Better Auth (`users`/`sessions`/`accounts`/`verifications`) — **канонічні в схемі `public`**, описані Drizzle-ом, **PK — uuid** (через власний генератор id BA або DB-default, інакше зміна типу PK розповзеться по FK-колонках). Схема GoTrue `auth.users` **зникає як клас** (не шим, не view): FK 6 таблиць (`orders`, `profiles`, `user_roles`, `wishlists`, `comparisons`, `service_requests`) перепиняються на нову таблицю. `handle_new_user` (створення `profiles`+`user_roles`) і інваріант `first_user_no_auto_admin` (перший signup НЕ адмін) переїжджають із SQL-тригера `on_auth_user_created` у `databaseHooks.user.create.after` — стають TS-кодом і юніт-тестовними. `profiles` лишається окремою 1:1-таблицею (у BA-таблиці — лише auth-мінімум; усе доменне — у `profiles`; менше зчеплення зі сторонньою схемою). Ролі персоналу — таблиця `user_roles` + TS-перевірки (не admin-плагін BA) |
| B4 | **Storage — порт як єдиний канал.** `MediaProvider` (upload/url/delete/transform) — єдина точка роботи з файлами; прямі виклики storage-API поза портом заборонені лінтом. Драйвери v2: `local-fs` (дефолт self-host: файли на диску, роздача через власний static-роут) і `s3` (будь-який S3-сумісний: Hetzner/R2/B2/Garage/Supabase Storage S3-ендпоінт). MinIO як рекомендація — виключений (upstream заархівовано 02.2026) |
| B5 | **Модель безпеки — два рубежі: серверний authz у TypeScript + чинні RLS.** Перший і основний рубіж — типізовані перевірки прав у serverFn-шарі (ролі/власність ресурсів), покриті звичайним vitest без Docker. 🔴 **Уточнено 2026-08-20: RLS НЕ скорочуються і не переписуються — вони продовжують діяти під серверними запитами.** `auth.uid()` — звичайна SQL-функція-читач GUC `request.jwt.claims`; будь-який pg-клієнт відтворює поведінку PostgREST транзакцією `BEGIN; SELECT set_config('request.jwt.claims', <claims>, true); SET LOCAL ROLE <роль>; …; COMMIT` (механізм — [MetaHub §5.4](#8-запозичений-досвід-metahub-2026-08-20), §8). Отже другий рубіж дістається шимом: схема `auth` з функцією `uid()` + непривілейована роль застосунку — 🔴 **без BYPASSRLS і не власник таблиць**, інакше політики мовчки не застосовуються. Наш профіль політик робить шим ще дешевшим: переважна більшість спирається на власну `is_admin()` (SECURITY DEFINER, `SET search_path = public`), яка всередині кличе `auth.uid()`, решта — прямо на `auth.uid()`; тобто в чистому Postgres змінюється рівно **одна** функція, а самі політики їдуть із Drizzle-схеми як є. Наслідок для плану: між зносом Supabase і добудовою TS-матриці **не виникає вікна з одним рубежем**, а «скорочення політик» перетворюється з передумови на опційну пізнішу прибирку. Передумова приземлення — спайк К1 (поведінка SECDEF-хелперів під явною роллю, сумісність із pooler у transaction-mode, гранти ролі) |
| B5″ | 🔴 **ПЕРЕОЗНАЧУЄ B5 (амендмент 2026-08-23), після живого аудиту.** «RLS лишаються як є» відкинуто: спайк довів, що дешевий шлях **існує**, але не довів, що він **правильний**, а аудит показав, що політики ніколи не ревʼюились. Три класи проблем на живій БД (потрійно звірено з міграціями й фікстурою): **шкідливе** — 3 `SECURITY DEFINER`-функції без внутрішнього гарда, викликні `anon` через `/rest/v1/rpc/` (`check_all_users_category_rules()` без аргументів у циклі `UPDATE profiles`; `check_category_rules(uuid)`; `get_user_stats(uuid)` — витік персональних даних в обхід RLS), плюс **нуль GRANT-ів** у репо (280×2 table-grants + 13 EXECUTE — неявний дефолт платформи, який ніхто не обирав; роль без BYPASSRLS падає з `permission denied` ще до RLS); **неоптимальне** — 234 `multiple_permissive_policies`, 21/21 політик на `auth.uid()` у голій формі (`auth_rls_initplan`: предикат щорядка), 32 незаіндексовані FK, 14 мертвих індексів; **зайве** — ~16 «публічне читання»-політик існували лише тому, що браузер робив прямий SELECT. У сервер-first (B1) браузер у БД не ходить → RLS перестає бути єдиним рубежем і стає **страхувальною сіткою проти забутого `WHERE` у репозиторії** (спайк виміряв: застосунок сам виставляє собі claims через `set_config`, тож проти скомпрометованого процесу RLS не захищає — це не межа). Отже **нова модель безпеки**: (1) **перший рубіж** — типізований authz у serverFn (як у B5); (2) **ролі БД як код** — 2–3 ролі (`app_user`: читання каталогу + user-scoped CRUD; `app_admin`: адмінські мутації, вмикається `SET LOCAL ROLE` лише після TS-перевірки; опційно read-only для SEO/фідів), жодна не власник таблиць, жодна без BYPASSRLS; `service_role`-патерн (edge-функція guest-order на service-ключі) помирає як клас; (3) **гранти — явний файл у репо** під гейтом парності привілеїв (закриває дірку структурно); (4) **RLS лише на ~10–12 user-scoped таблицях** (`orders`, `order_items`, `profiles`, `wishlists`, `comparisons`, `user_addresses`, `user_recipients`, `product_reviews`, `service_requests`, `user_category_history`, `user_roles`) — ~20–25 політик замість 93, у `(select auth.uid())`-формі (initplan), з WITH CHECK, з індексами під предикати; на гарячій траєкторії каталогу — **нуль оцінок політик** (прямий внесок у стек швидкості B6). Наслідок: `is_admin()`/`has_role()` зникають із БД → зникають 56 SECDEF-залежних політик, RPC-поверхня цих функцій і сам клас «SECDEF без гарда». Читач GUC при чистому baseline (B13) зветься `app.current_user_id()` — «fake»-схема `auth` більше не потрібна. Розвилка «RLS як є vs TS-only» з B5 **знята**: обрано третій варіант — «RLS-ядро + ролі + гранти». Механізм і харнес спайку (GUC + транзакційна обгортка `withActor` + pooler) лишаються потрібними за будь-якого рішення |
| B13 | 🔴 **Чистий baseline замість історії міграцій (нове рішення, амендмент 2026-08-23).** 33 файли `supabase/migrations/` — історія еволюції демо-магазину `alterenergy`, неробоча для нового стеку (FK на `auth.users`, Supabase-storage-об'єкти, `DO $$`-фокуси). Вони **видаляються повністю**. `schema.ts` уже SSOT (доведено `rls-parity.test.ts`), тож правильний хід без клієнтів — згенерувати з Drizzle-схеми нової моделі (B3′+B5″+бандли §4) **одну baseline-міграцію** `0001_init` + **сід чистого магазину** (owner-порожня БД, готова прийняти першого власника через invite). Стара тека лишається в git-історії; для перезапуску `alterenergy` вона не потрібна (там `pg_dump` даних, не DDL-реплей). Наслідки: зникає «вічний шим» реплею старих міграцій (8 посилань на `auth.users`); `db:diff` працює проти нової baseline; тека `supabase/` перестає бути Supabase-специфічною (config.toml/edge-functions — геть). Це також дає точку для майбутніх схемних бандлів (плагіни `plg_*` докочуються поверх baseline) |
| B6 | **«Стек швидкості» — частина v2, не окремий трек:** (а) full-page кеш SSR для анонімів + CDN перед `server.mjs` (`Cache-Control: public, max-age + stale-while-revalidate`; кошик/чекаут/акаунт — `no-store`), інвалідація по події зміни товару (без глобального purge); (б) in-process LRU-кеш гарячих даних (дерево секцій, тема — патерн `themes.ts` уже є); (в) виправлення знайдених аудитом вузьких місць: waterfall `catalog/$sectionSlug`, N+1 Home, `srcset`/розміри зображень, Suspense-межі для повільних секцій; (г) спека фасетної навігації ([`seo-ssr-faceted-navigation.md`](../../tasks/seo-ssr-faceted-navigation.md)) виконується в контурі вітрини v2 (серверні фільтри в URL — природна частина сервер-first моделі) |
| B7 | **Agent-readiness, дешева частина — в v2:** JSON-LD на ВСІХ канонічних сторінках (зараз лише товар): `Product`/`ProductGroup` (не `AggregateOffer` — Google депрекейтить), `Offer`, `AggregateRating`, `BreadcrumbList`, `CollectionPage`, `Organization` + **обовʼязкові тепер** `MerchantReturnPolicy` і `shippingDetails` — відповідні поля додаються в **Drizzle-схему зараз**, поки вона молода; robots.txt з явними правилами для AI-ботів (GPTBot/ClaudeBot/PerplexityBot/OAI-SearchBot/Google-Extended — allow на товарні сторінки); `llms.txt` — автогенерація за копійки, позиціонується як best-effort (конвенцію великі провайдери не читають); стабільні канонічні URL — інваріант. Product-feed (OpenAI/Google), MCP-сервер магазину, ACP/AP2-checkout — **окремі треки** роадмапу після v2 (консолідації протоколів на ринку ще немає) |
| B8 | **TanStack DB — штатний кеш-шар фронта.** Адмінка переходить першою (CRUD-колекції з optimistic mutations поверх serverFn); вітрина — за нею (кошик, клієнтські довантаження). Electric (read-sync з Postgres, `wal_level=logical`) — опційний модуль для каталогу пізніше, НЕ для чекауту. Redis/Valkey — НЕ в базовому стеку тенанта; додається лише з появою персистентних черг (листи/вебхуки/платіжні ретраї, BullMQ) — і тоді Valkey (ліцензія Redis 8 — BSL). 🔴 **Три умови приземлення (уроки MetaHub, §8), обовʼязкові з першого дня К3, а не після першого бага:** (а) **колекція НЕ рефетчиться від інвалідації React Query** — кожна клієнтська мутація мусить або оптимістично змінити колекцію, або явно викликати її refetch; enforcement — кастомне ESLint-правило (свідомий виняток лише коментарем-причиною), у нашій філософії «контракт стережеться машинно»; (б) **єдина карта інвалідації** «мутація → що протухло» замість ad-hoc-викликів по хуках: у v2 шарів кешу **три** (CDN-сторінки B6, in-process LRU B6, клієнтські колекції), і одна подія «товар змінився» мусить розгортатись у purge тегу + скидання LRU + синк колекції з одного модуля, інакше шари розповзаються; (в) **tiered `staleTime`** одним модулем (шкала «довідники → динамічні дані» + хелпер per-домен) замість magic numbers — сьогодні по коду розкидані `30s/60s/2m/5m/10m` без спільної шкали |
| B9 | **Порти екосистеми v2 — бекенд-нейтральні.** `usePluginTable` перестає бути PostgREST-формою — новий контракт портів плагіна проєктується під serverFn/колекції; теми отримують порти замість легального імпорту `@simplycms/supabase` (знімає Р10-дисклеймер: чесність маркетплейсу щодо тем покращується структурно). Це остання можливість змінити контракти дешево — до першого стороннього пакета (Амендмент 2026-08-20: порти для тем приземлюються як фасад-субшлях simplycms/theme-sdk — спека К0, ПК5.) |
| B10 | **Порядок виконання:** v2 іде **перед** відкриттям подач у маркетплейс (заморозка контрактів портів). (Уточнення за фактом: трек A «theme views» завершився 2026-08-18/19 ДО старту v2 — конфлікту немає: v2 переписує контейнери/лоадери (шар даних), view-model-и і view-и контракту v3 лишаються незмінними; conformance-гейт v3 входить у гейти контурів К2/К5) |
| B11 | **Без зворотної сумісності.** Жодних шимів, дуальних шляхів, feature-прапорців співіснування. Старий Supabase-шар зноситься в тому ж контурі, де приземлюється заміна |
| B12 | **Типи БД — з Drizzle-схеми.** Дуальна система (`supabase/types.ts` генерат магазину + `packages/supabase/src/database.ts` baseline + `types:baseline`-танець) зникає: єдине джерело — `packages/schema` (вже є), типи виводяться Drizzle-ом. Генератор типів Supabase CLI виходить з тулчейна |

## 3. Цільова архітектура

```
БРАУЗЕР
  │  HTML (SSR, повний контент товару — AI-краулери не виконують JS)
  │  TanStack Query/DB колекції ──► serverFn (той самий origin)
  ▼
CDN (аноніми: full-page кеш, SWR; персональне: no-store)
  ▼
Node-процес магазину (server.mjs, довгоживучий)
  ├─ TanStack Start SSR + route loaders (+ Suspense-стрімінг)
  ├─ serverFn-шар: authz (TS, тестовний) → репозиторії (Drizzle)
  │    транзакція запиту несе claims актора → RLS діють як другий рубіж
  ├─ Better Auth (бібліотека: сесії, invite, OAuth)
  ├─ in-process LRU (тема, секції, гарячі дані) + інвалідація по події
  ├─ MediaProvider ──► драйвер local-fs │ s3
  └─ SEO/agent-шар: sitemap, robots(+AI), JSON-LD, llms.txt
  ▼
Postgres (колокований; схема + чинні RLS як другий рубіж — Drizzle,
          міграції db:diff, шим auth.uid() поверх GUC — B5)
S3-сумісний storage (опційно; у хмарі — спільний керований + CDN)
```

**Що зникає зі стека:** PostgREST, GoTrue, storage-api-контейнер,
`supabase-js`/`@supabase/ssr`, anon/publishable-ключі, edge-функція
`get-guest-order` (переноситься в serverFn), генератор типів Supabase CLI,
дуальні типи, `VITE_SUPABASE_*`-контракт клієнта (клієнтові більше не
потрібні креденшели БД взагалі — спрощується і env-контракт CLI-спеки §7:
серверні секрети лишаються `process.env`-only, клієнтських секретів БД
немає як класу).

**Що НЕ змінюється:** TanStack Start/Router/Vite і вся роут-топологія
(`physical()`, storefront-routes/admin-routes), реліз-потяг і пакування,
контракт теми v2.2 (manifest/tokens/components/messages/fonts), i18n-шари,
Drizzle як джерело правди схеми, `db:diff`-конвеєр міграцій (тепер проти
будь-якого Postgres), модель поставки маркетплейсу П1–П5.

## 4. Обсяг по контурах (для імплементаційного плану)

Порядок — від фундаменту до листя; кожен контур завершується зеленими
гейтами і зносом відповідної частини старого шару (B11). Оцінка сумарно —
4–8 тижнів сфокусованої роботи.

1. **К1 Фундамент:** db-шар (Drizzle-клієнт, пул, транзакції; фабрики
   server-only), Better Auth (схема-таблиці, сесії, email/password, invite
   власника — заміна `owner:invite`/`verifyOtp`-флоу, admin-guard у
   `start.ts`), authz-хелпери. Точна пакетна розкладка (доля
   `@simplycms/supabase` → напр. `@simplycms/db` + `@simplycms/auth`;
   `data-supabase` → `data-pg`) — рішення плану, спека фіксує контракти.
   (Амендмент 2026-08-20: розкладку зафіксовано спекою
   [2026-08-20-package-consolidation-design.md](2026-08-20-package-consolidation-design.md),
   ПК4: після треку К0 це СУБШЛЯХИ пакета simplycms — simplycms/db,
   simplycms/auth, simplycms/data-pg; нові пакети не створюються.)
   **Додано 2026-08-20 (§8):** (а) 🔴 **спайк RLS-шима — перший крок
   контуру, до масової переробки лоадерів**: `auth.uid()` поверх GUC,
   роль застосунку без BYPASSRLS, транзакційна обгортка запиту,
   перевірка SECDEF-хелпера `is_admin()` під явною роллю і сумісності з
   pooler у transaction-mode; результат спайку — розвилка «RLS як є» vs
   «TS-only» (B5); (б) **e2e на оновлення сесійної cookie** після
   refresh — окремим пунктом DoD: у MetaHub `Set-Cookie` губився через
   флаш відповіді до завершення middleware-ланцюга, і саме цей клас бага
   тестом «логін працює» не ловиться; (в) борг №1 роадмапу (лист
   запрошення через Mailpit) закривається тут як DoD.

   🔴 **К1 → К1′ (амендмент 2026-08-23) — розширений склад «Фундамент:
   модель даних і безпеки v2».** Розвилка B5 знята (обрано B5″), тож замість
   «спайк → рішення» контур одразу будує цільову модель. Спайк лишається
   першим кроком, але тепер він **доводить харнес**, а не обирає шлях
   (потрійний збіг MD5 уже є). Повний склад — сім блоків, і 🔴 **блоки 0–5
   адитивні** (нові файли/тести поруч із чинним Supabase-шаром, репо зелене
   на кожному PR), а **блок 6 — точка неповернення** (знос GoTrue при живому
   PostgREST деградує майже сотню файлів клієнтського шару з
   `useSupabaseClient` — адмінка, воронка, хуки core; з нього починається
   довга гілка, що тягнеться до працюючої вітрини К2). Звідси стратегія:
   **максимально навантажити 0–5 одним проходом**:
   - **[0] Ревізія-документ + рішення:** цей амендмент (B3′/B5″/B13) — SSOT.
   - **[1] Нова baseline-схема з Drizzle (B13):** auth-таблиці BA
     (uuid-PK, канон у `public`), FK-retarget з `auth.users` (6 таблиць),
     видалення 33 старих міграцій → `0001_init` + сід чистого магазину.
     🔴 **Бандли, що народжуються тут, поки схема відкрита** (щоб не
     відкривати двічі): **B7-поля комерції** (`MerchantReturnPolicy`/
     `shippingDetails`-колонки — JSON-LD-рендер у К2, але колонки зараз);
     **таблиця медіа-метаданих К4** (`entity_type`/`entity_id`/`storage_key`/
     розмір/immutable-власність — інваріанти К4 народжуються зі схемою, не
     доліплюються); **індекси під предикати політик** + чистка 14 мертвих +
     32 FK-індекси (це і є «аудит доцільності»).
   - **[2] Ролі + гранти як код (B5″):** 2–3 ролі, явний grants-файл, гейт
     парності привілеїв (новий, поруч із `rls-parity`).
   - **[3] RLS-ядро ~20–25 політик (B5″):** лише user-scoped таблиці, у
     initplan-формі, + поведінкова матриця «актор × таблиця × операція» з
     🔴 **трьома негативними контролями** (без `SET LOCAL ROLE`; роль із
     BYPASSRLS; `set_config(…, false)`) — без них тест зелений і брехливий
     (виміряно спайком). Гейт `test:schema` — окремий CI-job без Docker
     (за прецедентом job `packaging`), пін на `postgres:17`.
   - **[4] db-шар:** Drizzle-клієнт, пул, обгортка `withActor` (GUC +
     `SET LOCAL ROLE`) — 🔴 **єдиний спосіб дістати з'єднання, машинно**
     (лінт-заборона голого клієнта), інакше два тихі режими відмови
     (виміряні: забутий `SET LOCAL ROLE` мовчки обходить RLS;
     `set_config(…, false)` протікає між клієнтами пулу).
   - **[5] Better Auth (B3′):** email/password, сесії, invite власника
     (заміна `owner:invite`/`verifyOtp`), `databaseHooks` (`handle_new_user`
     + first-user-інваріант у TS), authz-хелпери. Тестується без Docker
     через `better-auth/adapters/memory`; повний контур — над локальним PG.
     **Виведення бізнес-логіки з plpgsql у TS-домен (T1):** category-rules-
     двигун (`check_category_rules` та ін.) — заодно вмирає найнебезпечніша
     з трьох дірявих функцій.
   - **[6] Точка неповернення:** admin-guard у `start.ts` на сесіях BA;
     перемикання auth-роутів клієнта; знос `simplycms/supabase`-фабрик у
     міру переходу. Браузерний доказ (e2e refresh-cookie) і доставка
     invite-листа (SMTP) — недосяжні в CI-оточенні, лишаються боргом (DoD
     переноситься, але доводиться на оточенні власника).
   Пакетна розкладка (доля `simplycms/supabase` → `simplycms/db` +
   `simplycms/auth`; `data-supabase` → `data-pg`) — субшляхи, ПК4 спеки К0.
2. **К2 Вітрина:** SSR-лоадери через репозиторії (злиття двох паралельних
   шляхів «порти vs прямі лоадери» в один), full-page кеш + CDN-заголовки
   + інвалідація, in-process кеш, waterfall/N+1-фікси, JSON-LD скрізь +
   схема-поля повернень/доставки, AI-robots + llms.txt, зображення
   (розміри/srcset через MediaProvider.transform), фасетна навігація за
   її спекою.
   **Форма злиття (додано 2026-08-20, §8):** шов — **дескриптор домену як
   SSOT**: один декларативний обʼєкт на домен (склад полів + мапер рядка
   БД у доменний обʼєкт), з якого породжуються і серверне читання
   (repository/serverFn), і клієнтська колекція К3. Сенс саме в цьому:
   у MetaHub наявність такого дескриптора зробила зміну транспорту
   заміною `queryFn` в **одній фабриці** замість переписування доменів
   поштучно — тобто наступна зміна шару даних коштуватиме дешево.
   Дисципліну стереже drift-guard-тест «кожен домен має дескриптор»
   (жанр у нас уже є — `tests/i18n-coverage`).
3. **К3 Адмінка:** всі прямі `useSupabaseClient()`-виклики → serverFn +
   TanStack DB-колекції; guard-и; сторінки без зміни UX.
   **DoD-додатки 2026-08-20 (B8):** ESLint-правило «мутація парує
   кеш-синхронізацію»; модуль карти інвалідації, спільний для трьох
   шарів кешу (CDN-тег / LRU / колекція); модуль tiered `staleTime` +
   зведення наявних magic numbers до шкали (зачіпає і К2 — хуки вітрини).
4. **К4 Storage:** MediaProvider-порт як єдиний канал (6+ прямих викликів
   зводяться), драйвери local-fs/s3, лінт-заборона прямих викликів.
   **Додано 2026-08-20 (§8) — три інваріанти, що народжуються разом із
   портом, а не доліплюються потім:**
   - 🔴 **облік обсягу**: запис метаданих файлу (тенант/сутність/ключ/
     **розмір**) — у тій самій транзакції, що й видача presigned-upload;
     без власного обліку хмарні тарифи з лімітами сховища нема чим
     рахувати (у S3-порту тригера на `storage.objects` немає — див.
     cloud-спеку C11);
   - 🔴 **незмінність колонок власності** (`entity_type`/`entity_id`/
     `storage_key`/`uploaded_by`) після створення; перепривʼязка — лише
     авторизованою серверною операцією. У MetaHub аудит знайшов рівно цей
     вектор: тримач права «update» перепривʼязує чужий файл до доступної
     сутності й дістає його через проксі;
   - **порядок і чесність видалення**: спершу обʼєкт у сховищі, потім
     рядок метаданих (щоб облік звільняв байти, а невдале прибирання
     можна було повторити); 🔴 fail-open (рядок видалено, обʼєкт лишився)
     створює вічні орфани в бакеті — потрібен явний облік невдач,
     інакше «квота, яку неможливо звільнити» (задокументована граблина
     MetaHub).
5. **К5 Екосистема:** порти плагінів v2, порти для тем (Header/кошик-лічильники
   тощо), оновлення `plugin-faq`/`hello-world`/тем-референсів,
   conformance/dependency-lint під нові межі.
6. **К6 Тулчейн:** типи з Drizzle (B12), пілотні гейти/e2e/сід під новий
   стек (Gate B без Supabase-стека — проти Postgres у Docker), CLI

| Ризик | Мітигація |
|---|---|

| Обсяг: 6 контурів через увесь код | контурні гейти (кожен контур — зелений повний прогін + пілот); без клієнтів немає дедлайн-тиску; план розбиває на фази з DoD |
| Регресія безпеки при переході з RLS-only | authz-шар покривається тест-матрицею «роль × операція» у vitest; **RLS лишаються чинними під серверними запитами через шим B5** (вікна з одним рубежем немає); поведінковий тест політик у К6; `security-review` перед мержем контурів К1–К3 |
| Шим RLS не злітає на спайку (SECDEF/`search_path`, pooler у transaction-mode, гранти ролі) | 🔴 **ЗНЯТО 2026-08-23: спайк виконано.** 33/33 core-міграції лягли на чистий PostgreSQL 16 із шимом ~25 рядків; дамп `pg_policies` байт-ідентичний фікстурі й живій БД (потрійний збіг MD5); SECDEF-ланцюг `is_admin→has_role→auth.uid` працює під явною не-власницькою роллю; pgbouncer у `pool_mode=transaction` ізоляцію тримає, обгортка `BEGIN; set_config(…); SET LOCAL ROLE …; COMMIT` скидається на COMMIT. Бонус спайку — **два відтворені тихі режими відмови** (`set_config(…, false)` протікає на наступного клієнта пулу; забутий `SET LOCAL ROLE` мовчки обходить RLS) — вони стають обовʼязковими негативними контролями гейта `test:schema`, а дизайн ролей B5″ робить другий режим fail-closed (рантайм-роль без прямих грантів) |
| Медіа-облік доліплюється після хмари | інваріанти К4 (розмір у транзакції запису, immutable-колонки, облік невдалих видалень) — частина порту з першого дня; C11 хмарної спеки на них спирається |
| Втрата Supabase-DX для self-host користувачів | контракт «будь-який Postgres + будь-який S3» включає Supabase (його PG + S3-ендпоінт Storage) як провайдера; гайд «старт на Supabase free tier» лишається в доках |
| AI/SEO-регресія під час перебудови вітрини | гард «критичний контент у першому HTML» — асерт у e2e/пілоті (перевірка SSR-відповіді без JS) |

## 8. Запозичений досвід MetaHub (2026-08-20)

Джерело — споріднений проєкт власника `metahub` (той самий стек:
TanStack Start + Supabase; старший, з живими користувачами, уже пройшов
власну оцінку виходу з Supabase). Читалося як **чужий бойовий досвід**,
не як план дій: переносяться механізми й граблі, не архітектура.

**Що взято** (де приземлено):

| Знахідка MetaHub | Куди лягло тут |
|---|---|
| `auth.uid()` — читач GUC; серверне читання **не** вимагає відмови від RLS (`set_config('request.jwt.claims', …, true)` + `SET LOCAL ROLE` у транзакції). Механізм у них позначений як перевірений на рівні визначень функцій, впровадження — через спайк | **B5** + спайк у К1 |
| TanStack DB-колекція не рефетчиться від інвалідації React Query; enforcement кеш-дисципліни кастомним ESLint-правилом | **B8(а)**, DoD К3 |
| Карта інвалідації «мутація → домени» замість ad-hoc-викликів | **B8(б)**, DoD К3 |
| Tiered `staleTime` одним модулем замість per-hook magic numbers | **B8(в)**, DoD К2/К3 |
| Дескриптор домену як SSOT складу полів + мапера → з нього і серверне читання, і колекція; саме він зробив зміну транспорту заміною однієї фабрики | форма злиття шляхів у **К2** |
| Storage: облік байтів на тенанта, immutable-колонки власності (вектор перепривʼязки чужого файлу), порядок видалення й ціна fail-open | інваріанти **К4**, звʼязок із C11 хмари |
| Порядок cutover-ів: спершу деплой сумісного застосунку, ТОДІ обмежувальна зміна БД із готовим rollback-SQL — ніколи standalone-міграцією | **C8** хмарної спеки |
| Втрачені refresh-cookie через ранній флаш відповіді | DoD **К1** (e2e на оновлення cookie) |
| Поведінкова регресія політик замість текстової парності | **К6** |
| «Дисципліна цифр»: у живих контрактах — структурні твердження й іменовані обʼєкти, лічильники застарівають за один PR | стиль правок цієї ревізії (числа політик прибрані з B5) |

**Що свідомо НЕ переносимо:**

- **Realtime/broadcast-контур** (тригери БД → push у колекції) — серце
  їхнього воркспейса; магазину не потрібен. Якщо колись схочемо живу
  адмінку — це готовий референс, але не скоуп v2.
- **Redis-шар кешу і CASL-доставка ability** — у нас один процес на
  магазин, in-process LRU (B6) достатньо; CASL не потрібен.
- **Повний компілятор прав (Authz 2.0)**: права як код → генерована
  проєкція в БД → checksum drift-guard. Для двох ролей магазину це
  оверкіл. 🔴 **Але дизайн-насіння фіксуємо зараз**, бо ролі персоналу
  (менеджер / контент-редактор) рано чи пізно зʼявляться: вимір `scope`
  (`own` / `any`) замість умов-jsonb, requirement-граф дій
  (`delete ⇒ read`), і **escalation-guard** — той, хто роздає права, не
  може видати більше, ніж має сам (порівняння наборів прав `⊆`, а не
  рангів ролей). Наш authz-шар К1 має лишити для цього місце.
- **Їхній розворот у бік серверного читання як прецедент** — у них
  протилежна вихідна: realtime-авторизація і дешевизна org-міграції
  тримаються на DB-resident enforcement. Збіг напряму не означає, що
  наші рішення валідуються їхніми, і навпаки.
