## 1. Мотивація: чому міняємо, і чому саме зараз

### 1.1. Що показало дослідження (5 висновків)

1. **«Повільність серверного читання» — міф за умови колокованої БД.**
   Next.js-травма власника (браузер→сервер→БД→сервер→браузер) походила з
   serverless cold start (+100–400 мс TLS до БД), **бази в іншому регіоні**
   (+50–150 мс/запит; усунення давало −80 % латентності у виміряних
   кейсах) і водоспадів фетчів. У SimplyCMS жодної з цих умов немає:
   `server.mjs` — довгоживучий процес із пулом зʼєднань, БД колокована в
   обох цільових сценаріях (VPS клієнта / Dokploy-проєкт хмари) — хоп
   сервер→БД <1 мс. Прямий SQL із сервера навіть швидший за
   браузер→PostgREST (~2–3 мс проти ~10 мс на запит: зникає
   HTTP-трансляція + оцінка RLS).
2. **Головний важіль швидкості вітрини — спільний кеш анонімного трафіку**
   (CDN + `Cache-Control` + stale-while-revalidate + інвалідація по події —
   так побудовані Shopify Hydrogen/Oxygen і Vercel Commerce). Пряме
   браузерне читання БД **структурно виключає** спільний кеш: кожен
   відвідувач обходить застосунок. Аудит коду: на SSR-відповідях зараз
   нуль кеш-заголовків, кожен рендер бʼє в БД, на сторінці секції —
   водоспад, на Home — N+1.
3. **TanStack DB знімає суперечку «пряме vs серверне» повністю:** колекція
   з live-запитами (~1 мс, диференціальний dataflow) — це локальні дані в
   браузері незалежно від транспорту; `queryCollection` обгортає довільний
   `queryFn` (serverFn, PostgREST, sync) — джерело взаємозамінне за
   інтерфейсом. Швидкість «браузерного читання» досяжна без виставляння
   БД в інтернет.
4. **AI-краулери не виконують JavaScript** (перевірено на 500 млн запитів
   GPTBot — нуль виконання; ClaudeBot/PerplexityBot так само; виняток —
   лише Gemini). Усе критичне про товар мусить бути в серверному HTML.
   Агентна комерція вже реальна (OpenAI ACP + Stripe: checkout у ChatGPT;
   Google AP2; Shopify вбудовує MCP-ендпоінт у кожен магазин).
5. **Звʼязаність ядра з Supabase — глибока, і зараз останній момент її
   зняти дешево.** Браузер — прямий клієнт БД (каталог, чекаут, профіль,
   вся адмінка), безпека — RLS на `auth.uid()`, auth-флоу — GoTrue
   (verifyOtp/token_hash/inviteUserByEmail/тригер на `auth.users`),
   storage-виклики у 6+ місцях поза портом, SSR-лоадери повз порти, теми
   легально імпортують `@simplycms/supabase` (Р10), контракт
   `usePluginTable` — PostgREST-форма. **З першим стороннім плагіном/темою
   контракт портів заморожується назавжди** (політика маркетплейсу) —
   тому v2 має пройти ДО відкриття подач.

### 1.2. Чому не «мінімальний Supabase-стек»

Розглянуто і відхилено три альтернативи:

- **Повний self-hosted Supabase per tenant**: 1.5–4 GB idle на стек (Kong
  ~2.5 GB із задокументованим витоком памʼяті), 1 стек = 1 проєкт
  (спільний — офіційно нештатно, GoTrue не мультитенантний), Management
  API для self-hosted не існує, три ламкі міграції лише за 2026 рік.
- **Мінімальний Supabase-сумісний стек** (PG+GoTrue+PostgREST+storage-api
  за Traefik, ~250–650 MB): технічно робочий компроміс, але за критерієм
  «подальша експлуатація» програє v2 — платформа назавжди супроводжує
  три чужі лінії версій на кожному тенанті, безпека лишається RLS-only
  (тестується тільки проти живої БД), контракт плагінів лишається
  PostgREST-формою, дуальні типи лишаються.
- **Заміна лише auth (Better Auth) при збереженні PostgREST**: міст
  «Better Auth JWT → PostgREST → auth.uid()» — недокументована пара з
  двома паралельними токен-механізмами; виграш мізерний (GoTrue — один із
  найлегших контейнерів, ~10–50 MB).

**Пункт призначення v2 кращий за всі три**: 2 stateful-компоненти на
тенанта замість 4–5, авторизація тестується vitest-ом без Docker,
одне джерело типів, бекенд-нейтральні порти екосистеми, незалежність від
churn self-hosted Supabase.

## 2. Зафіксовані рішення (B1–B12)

| # | Рішення |
|---|---------|
| B1 | **Сервер-first дані.** Браузер НЕ звертається до БД ні напряму, ні через PostgREST. Канонічні сторінки — SSR через route loaders → `createServerFn` → Drizzle → Postgres. Клієнтський рантайм (навігація, інтерактивність, адмінка) — TanStack Query/DB-колекції поверх тих самих serverFn. PostgREST зникає зі стека |
| B2 | **Контракт бекенда — чистий Postgres + будь-який S3-сумісний storage.** Supabase перестає бути обовʼязковим фундаментом і стає **одним із підтримуваних провайдерів** (його Postgres + S3-сумісний Storage-ендпоінт відповідають контракту). Позиціонування продукту: «TanStack Start + Postgres», ширше, не вужче |
| B3 | **Auth — Better Auth** (MIT, під Vercel з 07.2026): бібліотека всередині Node-процесу, таблиці в тій самій БД через Drizzle-адаптер, cookie-сесії (stateful, revoke миттєвий). Флоу v2: email/password, invite власника, reset, Google OAuth (callback на домені магазину; у хмарі — спільний auth-домен платформи, див. cloud-спеку C9). Плагіни Better Auth підключаються мінімально необхідні (менша CVE-поверхня); версія піниться, security advisories відстежуються |
| B4 | **Storage — порт як єдиний канал.** `MediaProvider` (upload/url/delete/transform) — єдина точка роботи з файлами; прямі виклики storage-API поза портом заборонені лінтом. Драйвери v2: `local-fs` (дефолт self-host: файли на диску, роздача через власний static-роут) і `s3` (будь-який S3-сумісний: Hetzner/R2/B2/Garage/Supabase Storage S3-ендпоінт). MinIO як рекомендація — виключений (upstream заархівовано 02.2026) |
| B5 | **Модель безпеки — серверний authz-шар у TypeScript.** Перший і основний рубіж — типізовані перевірки прав у serverFn-шарі (ролі/власність ресурсів), покриті звичайним vitest без Docker. RLS-політики (вже написані в Drizzle) **зберігаються у скороченій формі як другий рубіж** (розділення admin/service-ролей БД, захист від помилки серверного коду); повна матриця політик перестає бути єдиною моделлю безпеки. Деталізація скорочення — імплементаційний план |
| B6 | **«Стек швидкості» — частина v2, не окремий трек:** (а) full-page кеш SSR для анонімів + CDN перед `server.mjs` (`Cache-Control: public, max-age + stale-while-revalidate`; кошик/чекаут/акаунт — `no-store`), інвалідація по події зміни товару (без глобального purge); (б) in-process LRU-кеш гарячих даних (дерево секцій, тема — патерн `themes.ts` уже є); (в) виправлення знайдених аудитом вузьких місць: waterfall `catalog/$sectionSlug`, N+1 Home, `srcset`/розміри зображень, Suspense-межі для повільних секцій; (г) спека фасетної навігації ([`seo-ssr-faceted-navigation.md`](../../tasks/seo-ssr-faceted-navigation.md)) виконується в контурі вітрини v2 (серверні фільтри в URL — природна частина сервер-first моделі) |
| B7 | **Agent-readiness, дешева частина — в v2:** JSON-LD на ВСІХ канонічних сторінках (зараз лише товар): `Product`/`ProductGroup` (не `AggregateOffer` — Google депрекейтить), `Offer`, `AggregateRating`, `BreadcrumbList`, `CollectionPage`, `Organization` + **обовʼязкові тепер** `MerchantReturnPolicy` і `shippingDetails` — відповідні поля додаються в **Drizzle-схему зараз**, поки вона молода; robots.txt з явними правилами для AI-ботів (GPTBot/ClaudeBot/PerplexityBot/OAI-SearchBot/Google-Extended — allow на товарні сторінки); `llms.txt` — автогенерація за копійки, позиціонується як best-effort (конвенцію великі провайдери не читають); стабільні канонічні URL — інваріант. Product-feed (OpenAI/Google), MCP-сервер магазину, ACP/AP2-checkout — **окремі треки** роадмапу після v2 (консолідації протоколів на ринку ще немає) |
| B8 | **TanStack DB — штатний кеш-шар фронта.** Адмінка переходить першою (CRUD-колекції з optimistic mutations поверх serverFn); вітрина — за нею (кошик, клієнтські довантаження). Electric (read-sync з Postgres, `wal_level=logical`) — опційний модуль для каталогу пізніше, НЕ для чекауту. Redis/Valkey — НЕ в базовому стеку тенанта; додається лише з появою персистентних черг (листи/вебхуки/платіжні ретраї, BullMQ) — і тоді Valkey (ліцензія Redis 8 — BSL) |
| B9 | **Порти екосистеми v2 — бекенд-нейтральні.** `usePluginTable` перестає бути PostgREST-формою — новий контракт портів плагіна проєктується під serverFn/колекції; теми отримують порти замість легального імпорту `@simplycms/supabase` (знімає Р10-дисклеймер: чесність маркетплейсу щодо тем покращується структурно). Це остання можливість змінити контракти дешево — до першого стороннього пакета |
| B10 | **Порядок виконання:** v2 іде **перед** відкриттям подач у маркетплейс (заморозка контрактів портів). (Уточнення за фактом: трек A «theme views» завершився 2026-08-18/19 ДО старту v2 — конфлікту немає: v2 переписує контейнери/лоадери (шар даних), view-model-и і view-и контракту v3 лишаються незмінними; conformance-гейт v3 входить у гейти контурів К2/К5) |
| B11 | **Без зворотної сумісності.** Жодних шимів, дуальних шляхів, feature-прапорців співіснування. Старий Supabase-шар зноситься в тому ж контурі, де приземлюється заміна |
| B12 | **Типи БД — з Drizzle-схеми.** Дуальна система (`supabase/types.ts` генерат магазину + `packages/supabase/src/database.ts` baseline + `types:baseline`-танець) зникає: єдине джерело — `packages/schema` (вже є), типи виводяться Drizzle-ом. Генератор типів Supabase CLI виходить з тулчейна |

## 3. Цільова архітектура

```
БРАУЗЕР
  │  HTML (SSR, повний контент товару — AI-краулери не виконують JS)
  │  TanStack Query/DB колекції ──► serverFn (той самий origin)
  ▼
CDN (аноніми: full-page кеш, SWR;购 персональне: no-store)
  ▼
Node-процес магазину (server.mjs, довгоживучий)
  ├─ TanStack Start SSR + route loaders (+ Suspense-стрімінг)
  ├─ serverFn-шар: authz (TS, тестовний) → репозиторії (Drizzle)
  ├─ Better Auth (бібліотека: сесії, invite, OAuth)
  ├─ in-process LRU (тема, секції, гарячі дані) + інвалідація по події
  ├─ MediaProvider ──► драйвер local-fs │ s3
  └─ SEO/agent-шар: sitemap, robots(+AI), JSON-LD, llms.txt
  ▼
Postgres (колокований; схема+RLS-другий-рубіж — Drizzle, міграції db:diff)
S3-сумісний storage (опційно; у хмарі — спільний керований + CDN)
```

**Що зникає зі стека:** PostgREST, GoTrue, storage-api-контейнер,
`supabase-js`/`@supabase/ssr`, anon/publishable-ключі, edge-функція
`get-guest-order` (переноситься в serverFn), генератор типів Supabase CLI,
дуальні типи, `VITE_SUPABASE_*`-контракт клієнта (клієнтові більше не
потрібні креденшели БД взагалі — спрощується і env-контракт CLI-спеки §7:
серверні секрети лишаються `process.env`-only, клієнтських секретів БД
немає як класу).

**Що НЕ змінюється:** TanStack Start/Router/Vite і вся роут-топологія
(`physical()`, storefront-routes/admin-routes), реліз-потяг і пакування,
контракт теми v2.2 (manifest/tokens/components/messages/fonts), i18n-шари,
Drizzle як джерело правди схеми, `db:diff`-конвеєр міграцій (тепер проти
будь-якого Postgres), модель поставки маркетплейсу П1–П5.

## 4. Обсяг по контурах (для імплементаційного плану)

Порядок — від фундаменту до листя; кожен контур завершується зеленими
гейтами і зносом відповідної частини старого шару (B11). Оцінка сумарно —
4–8 тижнів сфокусованої роботи.

1. **К1 Фундамент:** db-шар (Drizzle-клієнт, пул, транзакції; фабрики
   server-only), Better Auth (схема-таблиці, сесії, email/password, invite
   власника — заміна `owner:invite`/`verifyOtp`-флоу, admin-guard у
   `start.ts`), authz-хелпери. Точна пакетна розкладка (доля
   `@simplycms/supabase` → напр. `@simplycms/db` + `@simplycms/auth`;
   `data-supabase` → `data-pg`) — рішення плану, спека фіксує контракти.
2. **К2 Вітрина:** SSR-лоадери через репозиторії (злиття двох паралельних
   шляхів «порти vs прямі лоадери» в один), full-page кеш + CDN-заголовки
   + інвалідація, in-process кеш, waterfall/N+1-фікси, JSON-LD скрізь +
   схема-поля повернень/доставки, AI-robots + llms.txt, зображення
   (розміри/srcset через MediaProvider.transform), фасетна навігація за
   її спекою.
3. **К3 Адмінка:** всі прямі `useSupabaseClient()`-виклики → serverFn +
   TanStack DB-колекції; guard-и; сторінки без зміни UX.
4. **К4 Storage:** MediaProvider-порт як єдиний канал (6+ прямих викликів
   зводяться), драйвери local-fs/s3, лінт-заборона прямих викликів.
5. **К5 Екосистема:** порти плагінів v2, порти для тем (Header/кошик-лічильники
   тощо), оновлення `plugin-faq`/`hello-world`/тем-референсів,
   conformance/dependency-lint під нові межі.
6. **К6 Тулчейн:** типи з Drizzle (B12), пілотні гейти/e2e/сід під новий
   стек (Gate B без Supabase-стека — проти Postgres у Docker), CLI
   (doctor-перевірки env/конфігів під новий контракт), шаблон
   `create-simplycms-store` (env: `DATABASE_URL` + auth-секрети + smtp;
   `pnpm template:sync`), документація (`data-access`, `storage`,
   architecture-доки, README-и пакетів).

## 6. Ризики та мітигації

| Ризик | Мітигація |
|---|---|
| Better Auth: breaking changes у мінорах + CVE-потік у плагінах (задокументовано спільнотою) | пін точної версії; мінімальний набір плагінів; підписка на advisories; оновлення — свідомим PR з прогоном гейтів |
| Обсяг: 6 контурів через увесь код | контурні гейти (кожен контур — зелений повний прогін + пілот); без клієнтів немає дедлайн-тиску; план розбиває на фази з DoD |
| Регресія безпеки при переході з RLS-only | authz-шар покривається тест-матрицею «роль × операція» у vitest; RLS-другий-рубіж лишається на чутливих таблицях; `security-review` перед мержем контурів К1–К3 |
