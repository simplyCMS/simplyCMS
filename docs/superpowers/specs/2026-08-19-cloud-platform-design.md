## 1. Продуктова рамка

Модель Supabase дослівно: **повністю опенсорсний продукт + хмара, що
монетизує лише інфраструктуру** (створення магазину в кілька кліків,
керований деплой, домени, бекапи) — жодної фічі CMS за платним муром.
Обіцянка клієнту: «повний код і дані — у будь-який момент одним кліком»
(механіка — §6). Цільова аудиторія MVP — нетехнічний власник магазину;
розробники обслуговуються опенсорсним шляхом (CLI + self-host).

## 2. Зафіксовані рішення (C1–C13)

| # | Рішення |
|---|---------|
| C1 | **Окремий проєкт в окремому приватному репозиторії `simplycms/platform`.** Кабінет (контрол-плейн) — самостійний застосунок на нашому ж стеку (TanStack Start + Postgres — догфудинг), НЕ частина монорепо і НЕ в реліз-потязі. Прецедент одностайний: n8n (Admin Panel ≠ Workspace), WordPress.com (Hosting Dashboard ≠ wp-admin), Vercel, Medusa Cloud. Адмінка магазину (`@simplycms/admin`) лишається адмінкою ОДНОГО магазину всередині його контейнера — кабінет керує N магазинами через API оркестратора. Відкритість коду кабінету: **закритий на старті** (відкрити можна завжди, закрити назад — ні); якщо колись відкривати — кандидат на Sustainable-Use-подібну ліцензію (n8n-модель), ядра це не стосується |
| C2 | **Сутності кабінету:** `Account` → `Organization` (тут білінг, учасники, ролі) → `Store` → `Domain / Backups / Logs / EnvVars / Deploy actions`. Білінг — на організації, ніколи на магазині («N магазинів під однією підпискою» — безкоштовно з першого дня). Ролі на двох рівнях (org: Owner/Admin/Member; store: Manager/Viewer) — структурно за матрицею Supabase, звужено; MVP може стартувати лише з Owner, але схема даних закладає обидва рівні. `Environment`/preview/staging — свідомо ПІСЛЯ MVP |
| C3 | **MVP-скоуп сторінок кабінету** (чекліст Elestio, буквально): список магазинів організації → створити магазин → сторінка магазину: статус/логи білда й рантайму, redeploy/pause/delete, кастомний домен з авто-TLS, бекапи (розклад + ручний + restore), env-змінні (секрети інтеграцій магазину), версія ядра. Плюс білінг організації (тариф, метод оплати) |
| C4 | **Технологія розгортання — Dokploy self-hosted на власних VPS.** 1 магазин = **1 Dokploy-проєкт: контейнер застосунку + контейнер Postgres** (бекенд-контракт v2; ~400–600 MB на тенанта разом). tRPC API Dokploy — програмне створення/ребілд/видалення; push-to-deploy webhook — канал оновлень. **План Б — Coolify** (зріліший, REST API, важчий): стан тенанта (конфіг у БД платформи + Postgres-дані + медіа в object storage) живе ПОЗА оркестратором, тож міграція оркестратора = передеплой, не втрата даних. Провіжинінг — за внутрішнім інтерфейсом драйвера (create/rebuild/destroy/backup) — оркестратор взаємозамінний |
| C5 | **БД тенанта — звичайний Postgres у тому ж Dokploy-проєкті** (модель власника, тепер без Supabase-обвʼязки завдяки v2). 🔴 **Бекап-контур — передумова першого клієнта, не «потім»**: автоматичний щоденний дамп + WAL-архів (pgBackRest/WAL-G) у object storage, моніторинг успішності (тихі падіння бекап-кронів — задокументована галузева граблина), періодичний тестований restore. Для e-commerce БД = замовлення клієнтів — головний актив. Supabase Cloud як драйвер БД — більше НЕ базова траєкторія; лишається опцією для self-host користувачів продукту |
| C6 | **Storage тенантів — спільний керований S3 + CDN**, bucket/префікс на тенанта: Hetzner Object Storage (якщо VPS-парк на Hetzner; €5/TB, копійчаний egress) або Cloudflare R2 (нульовий egress) + Bunny/Cloudflare pull-zone перед публічними URL медіа. Жодного storage-процесу на VPS тенантів. Драйвер `s3` з контракту v2 |
| C7 | **Володіння кодом — гібрид «без git за замовчуванням + Підключити GitHub»** (Shopify-патерн + планка Lovable): (а) дефолт — магазин створюється БЕЗ git-репо: тенантський стан (тема/плагіни/версії ядра/налаштування) — записи в БД платформи; збірка **матеріалізується** з шаблону `create-simplycms-store` + конфігу при кожному деплої; редагування теми/своїх сторінок — вбудований редактор (C10); (б) кнопка **«Підключити GitHub»** переводить магазин у git-режим: платформа генерує повний репозиторій в **акаунт клієнта** (Lovable-модель), далі push-to-deploy; це ж і є eject — репо вже в клієнта. Свій git-сервер (Gitea/Forgejo) — відхилено: прецедентів на споживчому масштабі немає, +1 stateful-сервіс на нашій шиї |
| C8 | **Оновлення ядра флоту:** для no-git магазинів — **централізовано, хвилями з канаркою** (Ghost(Pro)/Magic Pages-модель: staging-прогін релізу → канарні тенанти → хвилі; відкат = передеплой попередньої версії); для git-магазинів — PR від бота платформи (Renovate-стиль), деплой після мержу клієнтом. 🔴 Для плагінів з міграціями пайплайн деплою ОБОВʼЯЗКОВО виконує ланцюжок `simplycms db:diff --write` → накат міграцій на Postgres тенанта → регенерація типів — `simplycms add` сам міграції не застосовує (знахідка критики: без цього кроку плагін з таблицями падає на першому запиті). 🔴 **Дисципліна порядку (амендмент 2026-08-20, досвід MetaHub): спершу деплой застосунку, СУМІСНОГО з обома станами схеми, і лише потім — обмежувальна зміна БД (drop/rename/NOT NULL/звуження RLS), з готовим rollback-SQL у тому ж кроці.** Обмежувальна зміна, накачена standalone-міграцією поперед коду, — це гарантований outage; у флоті вона множиться на N тенантів і кладе всю хвилю. Розширювальні зміни (нова колонка/таблиця) цього обмеження не мають. Пайплайн деплою робить порядок структурним, а не питанням дисципліни виконавця: крок «міграції» завжди ПІСЛЯ успішного старту нового контейнера на канарці |
| C9 | **Auth:** кабінет і магазини — Better Auth (v2). Google OAuth магазинів — через **спільний auth-домен платформи** (`auth.simplycms.app`, state-параметр несе тенанта, внутрішній редирект на домен магазину): ліміт Google — 100 redirect URI на OAuth-клієнт — робить «свій домен на consent-екрані кожного магазину» немасштабованим незалежно від бібліотеки (WorkOS-патерн). Магазин зі своїм платним планом може отримати власний OAuth-клієнт як преміум-опцію пізніше |
| C10 | **Редагування коду:** вбудований Monaco-редактор у кабінеті — лише для файлів теми (copy-in) і власних сторінок `src/routes/my/` (Shopify Edit code-модель; нуль інфраструктури, збереження → коміт стану в БД платформи → ребілд) + «Відкрити у своєму VS Code» через Remote Tunnels у контейнер тенанта (безкоштовно) або клон GitHub-репо в git-режимі. Повний cloud-IDE (code-server/Coder per tenant) — НЕ в MVP: реальна recurring-вартість і поверхня атаки; можлива платна преміум-фіча значно пізніше |
| C11 | **Білінг:** фіксовані тіри через Stripe (тут платить **покупець магазину** — обмеження Stripe щодо України стосується отримувачів виплат, не платників), підписка на рівні Organization. Орієнтир: собівартість інфраструктури ~$3–6/міс на магазин (частка VPS + частка object storage + бекапи) → тарифи від ~$29/міс; юніт-економіка ЧЕСНО включає support-load (10 нетехнічних тенантів ≈ 3–5 год/тиждень — головна стаття; мітигації: self-service доки, статусна сторінка, межі підтримки в тарифах, invite-only перші клієнти). Usage-based — пізніше (Stripe Billing Meters). 🔴 **Передумова тарифів із лімітами (амендмент 2026-08-20): облік обсягу сховища веде сам магазин** — метадані файлу з розміром пишуться в його БД у транзакції запису (інваріант К4 бекенд-контракту v2). Спільний S3 (C6) тригерів на обʼєкти не має, тож без цього обліку ліміт «X ГБ медіа» не є ані вимірним, ані примусовим; кабінет читає значення з тенанта. Урок MetaHub іде в комплекті: облік, який не вміє **звільняти** байти (орфани після невдалого видалення, вічно утримувані версії), за рік перетворює квоту на фікцію — метрика «облікові байти vs фактичні в бакеті» має бути звірювана. Єдина точка резолву прав тарифу (`cloud` = підписка організації; майбутній self-host = ліцензійний файл) — один гейтинг-код, два джерела: закладається структурно зараз, щоб не переписувати гейти при появі платного self-host |
| C12 | **Стик із маркетплейсом:** транзакційні дії («Створити магазин», «Install to my store», пізніше «Buy») живуть на `cloud.simplycms.dev` — вітрина simplycms.dev лишається статичною назавжди, передає контекст редиректом (`?package=<slug>`). One-click install = зміна конфігу тенанта (еквівалент `simplycms add`) → ребілд через C8-пайплайн; встановлюються лише записи tier official/verified (n8n Cloud-прецедент) |
| C13 | **Порядок: хмара ПЕРЕД платним маркетплейсом.** Хмара монетизує доведену потребу (хостинг) і створює аудиторію покупців тем; безкоштовний one-click install не потребує ні приватного реєстру, ні entitlements. Платний тір маркетплейсу — за demand-гейтом після хмари |

## 3. Ключові флоу

**Створення магазину** («кілька кліків»): форма (назва, піддомен) →
платформа: (1) записи Store в БД кабінету; (2) Dokploy-проєкт: Postgres-
контейнер (+ бекап-крон) і контейнер застосунку; (3) матеріалізація збірки
з шаблону + накат core-міграцій + сід + створення власника (invite-флоу
v2); (4) піддомен `<slug>.simplycms.app` + TLS; (5) готово — лінк на
магазин і його адмінку. Кастомний домен — CNAME + авто-TLS через Traefik
Dokploy.

**Встановлення теми/плагіна з вітрини:** клік на вітрині → редирект у
кабінет → вибір магазину → конфіг тенанта оновлюється (пакет@verifiedVersion)
→ пайплайн: матеріалізація → build (validate*Module — штатний гейт) → для
плагінів: міграції+типи (C8) → рестарт контейнера. Відкат = попередній
конфіг + передеплой.

**Оновлення ядра:** новий реліз `@simplycms/*` → staging-тенант платформи
→ канарні магазини (згода в налаштуваннях) → хвилі по флоту; git-магазини
отримують PR.

**Eject («забрати все»):** один клік → (1) git-репо з повним кодом
магазину (як «Підключити GitHub», або архів); (2) дамп Postgres + архів
медіа з S3; (3) self-host runbook (уже існує: «Production Run» у CLAUDE.md
+ доки). Зворотний шлях (onboard існуючого self-host магазину в хмару) —
поза MVP.

## 4. Економіка і масштаб (орієнтири)

- Сервер 64 GB (dedicated-клас): ~80–120 магазинів (застосунок ~250–300 MB
  + Postgres ~150–350 MB tuned на тенанта) — собівартість інфраструктури
  ~$1–3/міс на магазин + storage/бекапи.
- MVP-фіксовані витрати: 1 VPS/dedicated + object storage + домени ≈
  $60–120/міс; беззбитковість — перший десяток платних магазинів **по
  інфраструктурі**; по часу власника — див. C11 (support-load —
  визначальна стаття, тому invite-only старт).
- Масштабування: другий сервер через multi-server Dokploy (SSH) без зміни
  архітектури; далі — окремі сервери під «важкі» тарифи.

## 5. Межі MVP (свідомо поза скоупом)

- Environments/preview/staging для тенантів (Medusa/Vercel-рівень зрілості).
- Демо-стори тем (Shopify Theme Store-патерн, головний конвертер продажу)
  — природно зʼявляються на цій інфраструктурі, окремий пункт після MVP.
- BYO-інфраструктура (свій Supabase/Postgres/S3 клієнта в хмарі) — сегмент
  розробників, який обслуговує self-host; не MVP кабінету.
- Повний cloud-IDE; білінг usage-based; автоматичні виплати вендорам
  (платний тір маркетплейсу — окремий трек після хмари).
- Мультирегіон, k8s.

## 6. Ризики та мітигації

| Ризик | Мітигація |
|---|---|
| Втрата БД тенанта (замовлення!) | бекап-контур як передумова першого клієнта (C5): WAL-архів + моніторинг + тестований restore; сторінка Backups у кабінеті з першого дня |
| Dokploy pre-1.0 / маленька команда | драйвер-інтерфейс провіжинінгу (C4), Coolify план Б, стан тенанта поза оркестратором |
| Support-load зʼїдає час власника | invite-only старт, self-service доки, статусна сторінка, межі підтримки в тарифах; юніт-економіка рахує години, не лише залізо |
| Дрейф матеріалізованих збірок vs шаблон | збірка завжди генерується з канонічного шаблону версії X + конфігу (ніяких ручних правок у контейнері); кастомний код — лише через C7/C10-канали, що зберігаються в БД/git |
| «Хвиля» оновлення ламає флот | канарки + хвилі + автоматичний відкат на червоному health-check; версія ядра пінится per tenant — хвиля рухає пін, а не latest |
| Обіцянка «без lock-in» проти no-git дефолту | формулювання чесне: «повний код — у будь-який момент одним кліком» (eject §3); git-режим — один клік у будь-який момент |

## 7. Синхронізація з іншими документами

- Замінює §9.3 маркетплейс-спеки (там лишено вказівник сюди).
- Залежить від бекенд-контракту v2 (тенант без Supabase-стека) — хмарний
  трек у роадмапі стоїть після v2. 🔴 Точковий стик: **облік обсягу
  сховища** (C11) — це інваріант контуру К4 v2, він мусить приземлитись
  ТАМ; хмара його лише читає. Якщо К4 приземлиться без обліку, тариф із
  лімітом медіа доведеться або відкладати, або добудовувати міграцією по
  всьому флоту.
- Запозичений досвід MetaHub (порядок cutover-ів C8, облік/квоти C11) —
  джерела й межі: §8 бекенд-контракту v2.
- Модель поставки пакетів П1–П5 і tier-гейт хмари (official/verified) —
  без змін, споживаються як є.
- Юрисдикційні перевірки платіжного контуру ВЕНДОРІВ (MoR, Україна) — не
  блокують хмару (тут інший платіжний контур: Stripe, платить покупець).
