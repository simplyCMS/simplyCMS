## 1. Ухвалено

### 1.1 Рішення власника

1. **Мультимовність ДАНИХ, а не інтерфейсу.**
   - Що перекладається: товари, модифікації, властивості, розділи тощо.
   - Мов довільна кількість, «мов може бути багато і може бути більше».
   - На вітрині буде перемикач мови.
2. **Критерій вибору — подальша доробка, підтримка й розвиток,** а не «менше переробляти». Гірший варіант
   не обирається лише тому, що вже реалізований.
3. **Модель зберігання — повноцінна схема OpenCart (модель B):**
   - кожен текст кожної мови лежить рівно в одному рядку `<entity>_translations(entity_id, locale, …)`;
   - у базовій таблиці — лише мовонезалежне;
   - жодна мова не особлива в схемі;
   - думку власника підтримав фахівець з БД: «основна мова в колонках + накладки» — костиль, jsonb — ні
     (цілісність, ключі, індекси).
4. **Модель 1С зберігається:**
   - товар → модифікація (= характеристика 1С з власним GUID = `product_modifications.id`);
   - властивості товару й модифікації окремо;
   - види цін × (товар | модифікація);
   - складений id «товар#характеристика» не підтримуємо.
5. **Ідентифікатори.**
   - GUID 1С = наш `id`; зовнішніх id немає.
   - `id` генерує викликач, не БД — це вже інваріант.
6. **Імпорт і переклади.**
   - Імпорт (1С, API) може йти однією мовою.
   - Переклади — окремим рішенням у магазині, у майбутньому плагіном.
   - Обидва шляхи працюють разом.
7. **Перейменування через API підтримується коректно:** наслідки для перекладів, slug/URL, SEO, знімків і
   пошуку.
8. **Пріоритет — SEO і максимальна швидкодія:**
   - миттєві пошук і фільтри різними мовами;
   - пошук спирається на вже ухвалене дослідження: леми тощо.
9. **Цілісна система, а не «ізолєнта».** Надійна обробка в програмному контурі: сервер адмінки та API.
10. **Жодного зіставлення за назвою чи вільним текстом:** лише довідники й однозначний вибір у адмінці.
11. **API — наступний крок після пілоту.**
    - Основний канал для облікових систем.
    - CLI/MCP для агентів працюють на тому самому API.
    - Серверні функції однаково переписуються в цій хвилі, тому **протокол API проєктується в ній же**.
12. **Завантаження з 1С** власник розробить пізніше сам, на власній інфраструктурі (рішення 2026-10-14).
    Ми не досліджуємо модулі обміну й CommerceML. Для платформи 1С — один із клієнтів загального API:
    upsert за id, одна мова на запит, перейменування.
13. **Baseline у цій хвилі можна переписати.** Заморожування — крок релізу `1.0.0-rc.1` після хвилі. Пілот — після
    1.0.0-rc.1.
14. **Обсяг хвилі:** повна доробка вітрини й адмінки, не лише зберігання.

### 1.2 Рішення архітектора (з досліджень 30/40/60/70; переглядаються лише з новим доказом)

- **Рядок мови джерела позначено:**
  - `is_source` — рівно один на сутність (частковий унікальний індекс);
  - наявність рядка джерела гарантується (відкладена перевірка);
  - метадані однакові для всіх мов: `source_hash`, `updated_at`, статус;
  - переклад автоматично `outdated`, коли змінився текст джерела.
- **`languages` — єдине джерело мов:**
  - основна мова вітрини = `languages.is_default` (властивість магазину, а не форма даних);
  - мови не видаляються, лише деактивуються;
  - друге джерело (`VITE_LOCALE`) зноситься.
- **Вітрина читає з проєкції:**
  - мовонезалежний рядок на товар — розділ, статус, опції для фасетів;
  - ціни окремо;
  - текст на (товар, локаль) з уже застосованим fallback; форма ключа адреси (`UNIQUE(locale, slug)` чи інша) — за рішенням Р-ML-12;
  - проєкцію оновлює ядро в транзакції запису: set-based, детермінований порядок блокувань;
  - форму з окремими цінами переміряти.
- **Фасети — за id значень;** мова лише в підписах.
- **Пошук:** `search_documents` з локаллю в ключах і в черзі; `tokenize()` у `LanguagePack`.
- ~~Slug перекладені~~ — **знято власником 2026-10-14**, перенесено в розвилку Р-ML-12 (SEO-фахівці критикують прив'язку SEO-URL до мови в OpenCart 3; потрібне окреме дослідження).
- **Інкрементальна синхронізація — не по `updated_at`** (губить рядки на конкурентних записах, доведено).
  Натомість журнал змін або горизонт `pg_snapshot_xmin`.
- **Мова інтерфейсу адмінки ≠ мова контенту:** у формах — явний вибір мови контенту.
- **`orders.locale`** — у цій хвилі; листи покупцю — його мовою.
- **Порт перекладів і API не виставляють назовні деталей зберігання.** Ззовні — мапа мов або «переклад як
  ресурс».

### 1.3 Чекають підтвердження власника

- Усе про URL (префікс мови, перекладені slug, F2) — тепер у розвилці Р-ML-12, не тут.

## 2. Розвилки (брейншторм + дослідження)

Нумерація стабільна, на неї посилаються звіти.

- **Р-ML-1. Нові мультимовні реквізити картки товару.** Хто і як додає поле: розробник ядра міграцією,
  власник магазину в адмінці, плагін. Межа між «реквізитом» і «властивістю» (властивості 1С вже є довідником
  зі значеннями). Що з полями, які мають бути у фільтрах, пошуку, API й темі.
- **Р-ML-2. Розширення схеми плагінами (SDK).**
  - Чи може плагін додати колонку в таблицю ядра. Якщо ні — таблиця-розширення 1:1 і таблиця перекладів
    розширення.
  - Як розширення автоматично потрапляє у форму адмінки, API, проєкцію, пошук, експорт/імпорт і тему.
  - Що буде при видаленні плагіна.
- **Р-ML-3. Протокол API.**
  - Стиль: REST + OpenAPI, GraphQL, JSON:API.
  - Форма перекладних полів: мапа мов чи заголовок мови.
  - Часткові оновлення, bulk, ідемпотентність, версії рядків, журнал змін, вебхуки, токени й права.
  - Як серверні функції адмінки, API, CLI і MCP стають одним командним шаром, а не чотирма.
- **Р-ML-4. Перелік перекладних сутностей.**
  - Товари, модифікації, розділи, властивості та їхні значення, бренди.
  - Контент Е6д, банери, меню, SEO-поля.
  - Назви способів доставки й оплати, статуси замовлень, шаблони листів, системні довідники сіду.
  - Знімки в замовленні: назва мовою замовлення чи всіма мовами.
- **Р-ML-5. Операції з мовами:** додати мову, деактивувати, змінити основну мову магазину, змінити мову джерела
  сутності.
- **Р-ML-6. Fallback по полях:** яке поле можна показати мовою джерела, а яке ні (slug, SEO).
- **Р-ML-7. Процес перекладу:**
  - статуси, `outdated`;
  - порт плагіна-перекладача (машинний переклад, людина, агент);
  - повнота перекладу в адмінці.
- **Р-ML-8. Теми й плагіни на вітрині:** які дані теми отримують, як плагін вітрини читає перекладене.
- **Р-ML-9. Кеш і CDN** для кожної мови; HTML вітрини зараз не кешується.
- **Р-ML-10. Перехід даних:** переписування baseline, демо-сіди, showcase.
- **Р-ML-11. Незадані розвилки** — те, що знайдуть дослідження й рев'ю.
- **Р-ML-12. Архітектура URL багатомовного магазину.** Чи перекладати slug і чи прив'язувати SEO-URL до мови.
  Як мова потрапляє в URL: префікс, домен, піддомен. Чи потрібен id в URL. Історія адрес і 301 при
  перейменуванні через API. Canonical, hreflang, sitemap; що робити з неперекладеним товаром. Транслітерація.
  Окремо: що саме SEO-фахівці критикують в OpenCart 3 і як цього уникнути.
  Дослідження: `83-seo-url-architecture.md`.
- **Р-ML-13. Фільтри й каталог на сервері.** Сервер лише будує фільтри; застосовуються вони на клієнті, у пам'яті
  браузера. Працюють тільки за `option_id` і числовими діапазонами (`82` п.2). Пошуку на вітрині немає взагалі
  (`82` п.7). «Миттєві фільтри й пошук різними мовами» на такій основі неможливі, тому треба перенести
  фільтрацію в проєкцію/SQL і побудувати пошук з нуля.
- **Р-ML-14. Атомарне збереження картки товару.** Основні поля, властивості, модифікації, ціни й залишки
  зберігаються окремими операціями (`82` п.4). Для API і для перекладів (джерело + `source_hash`) потрібен
  складений ресурс «товар» з одним записом. Варіант — команди над агрегатом.
- **Р-ML-15. Події ядра для плагінів.** Імена хуків (`product.before_save`) є лише в типах; ядро їх не емітить
  (`82` п.5). Від цього залежать SDK розширень, плагін-перекладач, вебхуки API та інвалідація проєкції.
- **Р-ML-16. Мертві SEO-поля.** `meta_title` і `meta_description` товару, розділу та опції завантажуються, але
  в head не потрапляють (`82`, «Розбіжності»). Закрити в цій хвилі разом із багатомовним head.
- Факти до розвилок: усього близько 190 `createServerFn`, 125 з них — в одному модулі `admin-server`. Ресурсна
  фабрика `defineAdminResource` і `CoreActor` уже є основою командного шару (`82` п.3). `languages` нічим не
  читається. Локаль — змінна процесу, від запиту не залежить.

### Після верифікації Opus (`84-verify-code-extensibility.md`, 2026-10-14)

Карту коду (`82`) підтверджено повністю, спростованих тверджень немає. Нові факти, які мають увійти в цю хвилю:

- Сторінка `/catalog` вантажить усі товари без пагінації.
- Розділ показує лише власні товари, без товарів підрозділів.
- Стан фільтрів живе лише в `useState`, в адресі сторінки його немає. Усе це — Р-ML-13.
- Опис товару в rich-HTML потрапляє в `meta description`, `og:description` і JSON-LD без очищення від тегів.
  Безпеки це не стосується: JSON-LD екранує `<`. Але це вада SEO, її закриває Р-ML-16.
- `*_property_values.option_id` має `ON DELETE SET NULL` разом із UNIQUE `NULLS NOT DISTINCT`. Видалення опції
  лишає сиріт, а для multiselect друге видалення падає. Виправляється в переробці довідника властивостей
  (Р-ML-1); правильний FK — `CASCADE` або `RESTRICT`.
- `plg_faq_items.question` / `answer` — перекладний текст референс-плагіна. Це перший споживач конвенції Р-ML-2.

Нові розвилки:

- **Р-ML-17. Мова інтерфейсу вітрини при довільній мові контенту.** `Locale = 'uk' | 'en'` — замкнений тип
  (`i18n/types.ts:4`), на ньому стоять каталоги ядра, теми й плагінів. Магазин із контентом, наприклад,
  польською отримає змішану сторінку: контент польською, інтерфейс ні.
- **Р-ML-18. Мова джерела:** одна на агрегат «товар», включно з модифікаціями й значеннями, чи окремо для кожної
  таблиці.
- **Р-ML-19. Колекції `admin-data` у формі таблиці проти команд над агрегатом** (продовження Р-ML-14).
- **Р-ML-20. Внески плагінів у проєкцію.** Синхронно в транзакції запису чи через outbox. Наявний клієнтський
  `HookRegistry` для цього не годиться.
- **Р-ML-21. OpenAPI як артефакт збірки магазину:** склад API залежить від встановлених плагінів.
- **Р-ML-22. Політика видалення плагіна:** що робити з його даними.
- **Р-ML-23. Значення властивостей.** `value` змішує код (boolean, колір) і текст — розщепити. Одиниці виміру.
  Розділити назви, які бачить покупець, і назви лише для адмінки (`price_types`, `category_rules`).

Позиція верифікатора (75%) щодо Р-ML-1 і Р-ML-2. Це ще не рішення: на розгляд власнику.

- **Довідник властивостей 1С уже є шаром «атрибутів».** Другий паралельний EAV (`field_definitions`) не
  заводити.
- **Реквізит** — колонка ядра, яку додає міграція.
- **Властивість** — рядок довідника, який додає власник в адмінці або плагін декларацією.
- **Довідник розширюється:**
  - переклади назв, опцій і текстових значень;
  - `is_translatable`, зафіксований при створенні;
  - область дії «всі розділи»;
  - власник визначення та простір імен slug.
- **Структуровані дані плагіна (як FAQ)** лежать у його власних таблицях за конвенцією ядра `*_translations`.
  Ядро дає спільну функцію для `is_source` і `source_hash`. FK з `CASCADE` на таблиці ядра дозволено.
  Колонок у таблиці ядра плагін не додає, jsonb для перекладних даних не використовує.
- **`source_hash` рахується на рядок перекладу, а не на весь агрегат.** Інакше встановлення плагіна позначить
  усі переклади застарілими.

### Після верифікації Opus (`85-verify-api-seo.md`, 2026-10-14)

**URL (Р-ML-12).**

- Спростовано 83:
  - OpenCart 4 у SEO-режимі бере мову з префікса для всіх мов, включно з основною;
  - Shopware за замовчуванням тримає номер товару в URL і перебудовує slug при перейменуванні.
- Підтверджено вади OpenCart 3: мова береться з сесії, cookie й Accept-Language; розбір адреси не знає мови;
  через це заборонено однаковий keyword у різних мовах і з'являються кілька шляхів до товару без canonical.
- У нас проблеми «кількох шляхів» немає: товар резолвиться за slug, а неправильний розділ дає 301.
- **Нове обмеження.** «Основна мова без префікса», прив'язана до `languages.is_default`, суперечить Р-ML-5
  «змінити основну мову»: та сама `/x` почне віддавати іншу мову. Варіанти:
  - **A′** (верифікатор, ~65%): окрема, практично незмінна «мова кореня» (`url_root`), яка не залежить від
    основної мови;
  - **B** (~35%): префікс для всіх мов.
  - Рішення — за власником.
- Позиції верифікатора:
  - slug явний для кожної наявної мовної версії, без fallback під час запиту (~80%);
  - без id в URL (~75%), захоплення slug з історії — лише явною дією;
  - неіснуюча мовна версія — 404 з посиланнями на наявні мови, а не 302 (~70%);
  - розділ в URL товару прибрати — нахил ~60%, продуктове рішення.
- Нові підрозділи Р-ML-12:
  - інвалідація кешу на всіх мовах сутності (hreflang взаємний);
  - поріг «версія існує» для outdated-перекладу і для лістингу частково перекладеного розділу;
  - мовний контракт для роутів плагінів і `my/`, лінт на жорсткі `<Link>`;
  - зарезервовані сегменти: коди мов проти верхніх сегментів;
  - заборона `Vary: Accept-Language`;
  - `slugify` у `LanguagePack`;
  - slug лише при створенні (як Shopify) проти перебудови з назви (як Shopware) — явний вибір;
  - canonical — на сторінку тією ж мовою;
  - hreflang — лише коди ISO 639-1 (`uk`, а не `ua`).
- Конфлікти з «фасетами кодами» в нашому коді: посадкові `/properties/<властивість>/<опція>` за slug і `?mod=`
  (slug модифікації).

**API (Р-ML-3).**

- Командний шар — **В1, власний реєстр** (~70%; oRPC ~25%, Hono ~5%). Близько 60% уже написано:
  Zod-входи, ядра без HTTP, `CoreActor`, `runAdmin`.
- Бракує:
  - реєстру з іменами операцій;
  - суб'єкта з токена — зараз він береться лише з cookie (`authz-request.ts`, `getRequest()`), його треба
    передавати параметром;
  - статусу без `setResponseStatus` (`run.ts:61`);
  - мапінгу помилок в адаптерах;
  - схем виходу.
- Публічна поверхня — **командний RPC `POST /api/v1/<op>`** (~70%), а не REST поруч із ним.
- oRPC: Zod 4 лише через `@orpc/zod/zod4` (кореневий імпорт тягне `zod/v3`), мейнтейнер фактично один.
- MCP: `@modelcontextprotocol/sdk` 1.x реалізує протокол 2025-11-25, лінія v2
  (`@modelcontextprotocol/server`) — 2026-07-28. Транспорт уже є в SDK, Hono не потрібен.
- Мовні записи:
  - атомарна перевірка хеша (`FOR SHARE` на рядку джерела або один оператор);
  - хеш на поле (~65%), slug і SEO-поля поза хешем;
  - 409 з поточним хешем;
  - адмінка надсилає хеш, з яким відкрила форму;
  - `If-Match`, що не збігся, дає 412 — не плутати з 409 для `expectedSourceHash`.
- Плагін-перекладач працює через порти в процесі, HTTP-клієнтом не є.

## 3. Рішення власника 2026-10-14 (друга сесія брейншторму)

- **Р-ML-1 / Р-ML-23. Перекладність не обирається.**
  - Кожен текстовий реквізит, який бачать у магазині, мультимовний завжди, без вибору.
  - Числа, артикули, коди, ціни — загальні для всіх мов. Їх не перекладають, вони лежать у самій картці
    сутності.
  - Зразок — OpenCart.
  - Позначки `is_translatable` немає. Перекладність визначається ТИПОМ: текст перекладається, число, код і
    boolean — ні.
  - Колонку `value` значень властивостей розщеплюємо за типом (Р-ML-23).
- **Р-ML-2. Плагіни не додають власних властивостей.** Так у 1С, і це зручно. Плагіни використовують
  властивості, які є в довіднику.
  - Другого паралельного механізму полів (`field_definitions`, custom fields) немає.
  - «Власник визначення / простір імен slug для плагінів» знято.
  - Власні структуровані дані плагіна (як FAQ) лишаються в його таблицях `plg_<name>_*`, переклади — за
    конвенцією ядра.
- **Р-ML-17. Мовні пакети інтерфейсу вітрини.**
  - Їх постачає бібліотека i18n платформи, доробляються вони в межах платформи загалом.
  - Репозиторій відкритий, тож будь-хто може додати мову.
  - Наслідок: `Locale` перестає бути замкненим `'uk' | 'en'`, каталоги ядра, теми й плагінів відкриваються
    для нових мов.
- **Р-ML-12 / Р-ML-5. URL — варіант A.**
  - Основна мова магазину без префікса і НЕЗМІННА після створення магазину.
  - Решта мов — з префіксом (`/en/…`).
  - Операції «змінити основну мову магазину» немає. Р-ML-5 лишає додавання й деактивацію мов і зміну мови
    джерела окремої сутності.
- **Р-ML-3. Мовні записи через API — два сценарії, обидва підтримуються:**
  1. клієнт надсилає текст лише мовою джерела → решта мов не змінюється, їхні переклади стають `outdated`;
  2. клієнт (1С чи інший) надсилає текст джерела разом з перекладами в одному запиті → записуються всі мови.
     Надіслані переклади рахуються актуальними щодо нового тексту джерела: `source_hash` фіксується той самий.
     Мови, яких немає в запиті, стають `outdated`.
  - Окремий запис перекладу з `expectedSourceHash` (плагін-перекладач, адмінка) лишається третім шляхом.
- **Р-ML-3. Командний шар.** Власник не бачить, чому серверні функції TanStack Start не можна перевикористати
  для API. Призначено окреме поглиблене дослідження та пробну збірку oRPC (`86`, `87`).

### Командний шар (`86`, `87`, 2026-10-14) — рекомендація архітектора, чекає рішення власника

- Серверну функцію технічно можна викликати ззовні, але її адреса — хеш шляху файлу й імені змінної. У магазині
  шлях іде через `node_modules/.pnpm/simplycms@<версія>`, тож адреса змінюється з кожним релізом платформи (за
  формулою; живою збіркою магазину не перевірено). Тіло — формат seroval, а не JSON. Помилки повертаються в тілі
  відповіді, а не HTTP-статусом. Суб'єкт береться лише з cookie. Тобто це крихкий внутрішній протокол без
  контракту.
- Перевикористовується все, крім транспорту: Zod-схеми, операції, ядра `*In`, `CoreActor`, права.
- Рекомендація (~75%):
  - реєстр операцій `defineOperation` поверх `defineAdminResource` / `runAdmin`;
  - адмінка лишається на serverFn — тонкі топ-рівневі обгортки, відповідність реєстру стереже тест;
  - зовнішнім — один універсальний маршрут `POST /api/v1/<операція>` з токеном;
  - OpenAPI 3.1 і MCP генеруються з реєстру через `z.toJSONSchema` (дати — дротова форма, один раз на тип);
  - контрактний тест проганяє кожну операцію через HTTP-адаптер;
  - перший крок — винести суб'єкт і статус на межу транспорту.
- Альтернативи: «адмінка теж через HTTP» (~20%) і oRPC (~5%). Пробна збірка oRPC (`87`): працює, але потребує
  експериментального плагіна для дат, має одного мейнтейнера і додає ~10 кБ gzip до клієнта. Власний реєстр —
  ~100 рядків проти ~120.
- Відкрите: суб'єкт через `AsyncLocalStorage` чи явним параметром; плагін `api-key` Better Auth проти власної
  `api_tokens`.

**РІШЕННЯ ВЛАСНИКА 2026-10-14 (Р-ML-3):** погоджено.
- Спільний реєстр операцій.
- Адмінка — на серверних функціях як тонких обгортках над реєстром.
- Зовнішнім клієнтам — один вхід `POST /api/v1/<операція>` з токеном. OpenAPI і MCP генеруються з реєстру.

Захищати від обходу двома шарами: тести І лінт-правило (вимога власника, «щоб в подальшому важко було
порушити»). Що має ловити лінт:
- `createServerFn` в адмін-зоні, обробник якого не делегує операції реєстру;
- бізнес-логіку в тілі обгортки;
- прямий виклик ядер `*In` / `withActor` поза операцією реєстру.

Правило — з власним іменем плагіна і негативним контролем тестом, як усі кастомні правила (`AGENTS.md`). Точні
межі зон визначає план. Тест паритету «кожна операція реєстру має обгортку і проходить через HTTP-адаптер»
лишається.

## 4. Рішення власника по черзі (2026-10-14)

1. **Адреса мовної версії (Р-ML-12).**
   - У кожної мовної версії власний slug, записаний явно.
   - При створенні мовної версії slug дорівнює копії slug основної мови.
   - Змінюється лише явною дією: вручну або плагіном-перекладачем. Автоматичної перебудови немає, fallback під
     час запиту теж немає.
   - Однаковий slug у різних мовах дозволено. Унікальність — у межах мови.
2. **Форма URL (Р-ML-12).**
   - Плоскі адреси: товар `/<slug>`, розділ `/<slug>` (інші мови — з префіксом `/en/<slug>`).
   - Розділу в адресі товару немає.
   - Єдиний реєстр адрес на мову (на зразок `seo_url` у Shopware і `url_rewrite` у Magento) тримає:
     - поточну адресу кожної сутності (товар, розділ, сторінка, посадкова сторінка властивості);
     - історію старих адрес для 301 одразу на кінцеву.
   - Унікальність — у межах мови, через усі типи сутностей.
   - Конфлікт зі службовими сегментами (`cart`, коди мов тощо) блокується при створенні.
   - Адреса не змінюється при перенесенні товару між розділами.
3. **Неперекладена сутність (Р-ML-6, F2).**
   - Мовна версія існує в усіх сутностей одразу після увімкнення мови. Її slug — копія основного.
   - Поки перекладу немає, текст показується основною мовою, а інтерфейс — мовою версії. Сторінка має
     `noindex`, canonical на основну мову, у sitemap і hreflang її немає.
   - Після перекладу сторінка відкривається для пошуку автоматично, без зміни адреси.
   - «Перекладено» = заповнені обов'язкові поля мовою, щонайменше назва. Позначений `outdated` переклад
     лишається перекладеним, бо інакше масове перейменування з 1С деіндексувало б мовну версію.
4. **Обсяг хвилі (Р-ML-13).**
   - У цій хвилі: дані, адреси, адмінка і каталог на сервері — фільтри, пагінація, товари підрозділів, адреси
     фільтрів і посадкові сторінки. Задачу `docs/tasks/seo-ssr-faceted-navigation.md` узгодити з рішеннями 1–3.
   - Пошук — окремою хвилею одразу після, за спекою `2026-08-25-storefront-search-design.md`, з амендментом
     мов. У цій хвилі лише закладається місце: локаль у ключах `search_documents` і в черзі.
   - Чи потрібен пошук до пілоту — окреме рішення пізніше.
5. **Мова замовлення (Р-ML-4).**
   - `orders.locale` — мова оформлення. Листи щодо замовлення йдуть цією мовою.
   - Знімок позицій (назва товару й модифікації, назви знижок у `discount_data`) зберігає текст мовою покупця і,
     якщо вона відрізняється, ще й основною мовою магазину. Покупець бачить свою мову, адмінка — основну.
   - Назви статусів замовлень лишаються живими з довідника (перекладеного) і показуються мовою того, хто дивиться.
   - Перекладаються лише тексти, видимі в магазині. Внутрішні адмінські назви (`price_types`, `category_rules`
     тощо) — ні; точний перелік фіксує архітектор у повній спеці.
6. **Збереження картки товару (Р-ML-14 / Р-ML-19).**
   - Опис товару — основні поля, тексти всіма мовами, властивості, модифікації — це один агрегат. Він
     записується однією атомарною командою реєстру з перевіркою версії: чужа зміна дає конфлікт, а не мовчазне
     перезаписування. Адмінка й API користуються тією самою командою.
   - Ціни й залишки — окремі команди: масові оновлення, окремі права, часті оновлення з 1С.
7. **Процес перекладу (Р-ML-7).**
   - У цій хвилі:
     - статуси перекладу (перекладено / `outdated` / немає);
     - ручний переклад в адмінці: вкладки мов, повнота, позначка застарілих;
     - список «потребує перекладу»;
     - точка підключення плагіна-перекладача в `plugin-sdk`.
   - Плагін-перекладач на ШІ — окремою роботою пізніше. Він стане першим споживачем цієї точки підключення і може
     працювати також агентом через MCP на тому самому реєстрі операцій.
8. **Видалення плагіна (Р-ML-22).**
   - Видалення плагіна лишає його таблиці й дані; повторне встановлення відновлює їх.
   - Остаточне очищення — окрема явна команда («видалити разом із даними») з підтвердженням і нагадуванням
     про резервну копію.
   - `doctor` показує таблиці від видалених плагінів.

## 5. Технічні рішення архітектора (2026-10-14; власник бачить їх списком і може переглянути)

- **Р-ML-18. Мова джерела — одна на агрегат.** Товар разом із модифікаціями й значеннями властивостей, розділ,
  властивість разом з опціями. Імпорт з 1С іде однією мовою на агрегат. Змінити мову джерела — це явна команда
  над агрегатом.
- **Р-ML-20. Проєкція вітрини будується з даних ядра.** Плагіни своїх полів не додають (рішення власника), тому
  внесків плагінів у проєкцію немає. Плагін читає свої таблиці сам через порти. Оновлення проєкції — синхронне,
  у транзакції команди реєстру.
- **Р-ML-21. Склад API залежить від магазину.** Операції плагінів реєструються в тому самому реєстрі.
  OpenAPI-документ магазину генерується при його збірці й віддається на `/api/v1/openapi.json`.
- **Р-ML-23. Значення властивостей:**
  - `value` розщеплюється за типом: текст — у перекладах значень; boolean, колір і число — мовонезалежні
    колонки;
  - одиниця виміру — перекладний текст властивості;
  - FK `option_id` — `CASCADE` або `RESTRICT` замість `SET NULL`.
- **Slug — транслітерація** за офіційною українською схемою (КМУ 2010) через `slugify` у `LanguagePack`
  кожної мови. Ручне редагування дозволене.
- **Токени API** — власна таблиця `api_tokens` (хеш, права, термін дії, останнє використання) чи плагін
  `api-key` Better Auth — вирішує план за перевіркою через context7. Суб'єкт передається з межі транспорту
  явним параметром.
- **Кеш:** HTML вітрини кешується окремо для кожної мови; ключ — шлях, і префікс мови вже в ньому.
  `Vary: Accept-Language` не ставиться. Інвалідація зачіпає всі мови сутності, бо hreflang взаємний.
- **Перехід даних:**
  - baseline переписується; демо-сід і showcase оновлюються;
  - живих даних немає;
  - перекладні тексти переходять у `*_translations` з `is_source` для основної мови.

## 6. Рішення за рецензією дизайну (2026-10-14)

9. **Мова джерела = основна мова магазину завжди** (рішення власника). Це знімає Р-ML-18 і операцію «змінити мову
   джерела». Позначка `is_source` і колонка `source_locale` не потрібні: джерело — рядок основної мови.
   Формулювання про `is_source` в §1.2 і про «мову джерела» в рішенні 3 скасовано цим пунктом. Fallback — до
   основної мови.
- Решту відповідей на рецензію (мовні токени фільтрів, колізії адрес, обсяг проєкції, мова адмінки й листів,
  SEO-поля блоку A, кеш, запис усіх сутностей командами, медіа multipart, генератор стенду) вніс архітектор
  прямо в дизайн `2026-10-14-multilingual-wave-design.md`.
10. **Ціна каталогу** (рішення власника): вид ціни глядача + загальні знижки; персональні — лише на картці й у кошику.
11. **Публічний API в цій хвилі, мінімально** (рішення власника): токени з правами, адмінка токенів, вхід `/api/v1` увімкнений у магазині; MCP і CLI — після пілоту.

## 7. Уточнення власника 2026-10-14 (друга сесія)

12. **Фолбек інтерфейсу — основна мова магазину**, а не англійська. Пакет основної мови обов'язковий.
13. **Мова вітрини — лише з адреси.** Cookie чи localStorage для вибору мови немає. Мова адмінки й листів — з профілю.
14. **Стани мови:**
    - `draft`: адреси створено, вітрина закрита, перекладачі працюють;
    - `published`: власник вмикає вручну, поруч індикатор повноти по типах сутностей;
    - `disabled`: мову сховано, переклади збережено.
    Індексацію окремих неперекладених сторінок усередині `published` закриває `noindex`.
15. **Видимість товару одна для всіх мов.** «Ринок» (валюта, доставка за країною) — окреме майбутнє поняття, не
    мова.
16. **Масовий переклад — через API** (агент, плагін, 1С). Файлового експорту й імпорту (CSV/XLIFF) у хвилі немає,
    пізніше — плагіном на тому ж API.
17. **Зображення — по мовах** (рішення власника всупереч рекомендації «банери + alt»):
    - будь-яке зображення сутності (фото товару, банер, зображення розділу й опції) можна перевизначити для мови;
    - перевизначення лежить у рядку перекладу; NULL означає «спільне з основною»;
    - alt-текст зображень — перекладний.
18. **Відгуки:** відгук запам'ятовує мову написання (`product_reviews.locale` — з адреси сторінки). Показуються всі
    відгуки, мовою сторінки першими; рейтинг спільний. Перекладу відгуків у хвилі немає.
