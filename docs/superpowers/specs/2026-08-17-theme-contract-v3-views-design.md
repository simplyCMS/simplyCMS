# Контракт тем v3 — «theme views»: перевизначення view-шару канонічних сторінок

> Дизайн затверджено власником 2026-08-17 (брейнштормінг-сесія, гілка
> `claude/website-cloner-analysis-p7wf4z`). Джерело мотивації — лайв-тест
> механізму «редизайн за референсом» (його результат став нинішньою
> default-темою): картку товару неможливо наблизити до референсу, бо тема
> впливає на канонічні сторінки лише токенами.
> Це **ревізія рішень D3/D4** платформної спеки
> [`2026-07-30-platform-architecture-design.md`](2026-07-30-platform-architecture-design.md)
> і реалізація «Горизонту 2» ресерчу
> [`2026-08-15-theme-contract-expansion.md`](../research/2026-08-15-theme-contract-expansion.md) §5.
>
> Статус: **спека затверджена, у коді НЕ реалізовано.** Виконання — після
> інкремента Б.2 треку редизайну (порядок §12); імплементаційний план пишеться
> перед стартом (superpowers writing-plans).

## 1. Мотивація

Контракт v2.2 дає темі токени, шрифти, Header/Footer і дві секції головної.
Цього досить, щоб «перефарбувати» магазин, але структурно всі магазини
платформи — клони: та сама верстка каталогу, картки товару, кошика. Для
платформи масового використання це слабка диференціація тем і слабкий
маркетплейс; для механізму клонування дизайну — стеля якості (референсну
картку товару відтворити нічим).

Водночас причини, з яких сторінки переїхали в ядро (Фаза 0, D3/D4), нікуди
не зникли: оновлення сторінок мають їхати всім магазинам npm-пакетом,
SEO/AI-якість — централізована, магазин не має ставати форком (біль
OpenCart/WooCommerce). v3 розвʼязує цю напругу **розділенням сторінки на два
шари**: дані/логіка/SEO — непорушне ядро; презентація — перевизначувана.

## 2. Зафіксовані рішення власника (2026-08-17)

| # | Рішення |
|---|---------|
| V1 | **Межа перевизначення — view-шар.** Роути, лоадери, server fns, SEO, URL-структура лишаються в ядрі назавжди. Тема може постачати опційні view-компоненти на типізовані view-model-и; канонічний view — завжди fallback. Повне володіння сторінкою (модель Shopify) відхилено — це відкат до форк-моделі |
| V2 | **Обсяг v3 — пʼять сторінок вітрини:** `Home`, `Catalog`, `CatalogSection`, `ProductDetail`, `Cart`. Checkout/auth/profile — кандидати v3.1 після обкатки (найвищий ризик конверсії/коректності, найменша потреба в диференціації) |
| V3 | **Conformance — жорсткий гейт.** Обовʼязкові реквізити асертяться машинно; провал = червоні тести/CI автора теми і блок публікації в маркетплейс-індекс. Рантайм-fallback на канонічний view при невалідному — НЕ робиться (маскував би дефект) |
| V4 | **Адмінська кастомізація в v3 — через settings** (доведення наявного механізму до кінця). Drag-and-drop секцій — окремий трек B поверх v3, після обкатки |
| V5 | **Порядок виконання:** ревʼю-цикл PR #32 → трек C (інкременти механізму клонування, Б.2) → трек A (ця спека) → трек B. Послідовно, без паралелі |

Ревізія платформних рішень: **D3′** — «не перевизначаються» звужується до
даних/роутингу/SEO; **D4′** — тема, як і раніше, не володіє сторінками, але
може постачати view. **D2 чинне без змін** (плагіни й адмінка сторінок не
перевизначають).

## 3. Форма контракту

`ThemeModule` отримує опційне поле `views`:

```ts
// packages/theme-system/src/types.ts
interface ThemeViews {
  Home?: React.ComponentType<HomeViewModel>;
  Catalog?: React.ComponentType<CatalogViewModel>;
  CatalogSection?: React.ComponentType<CatalogSectionViewModel>;
  ProductDetail?: React.ComponentType<ProductDetailViewModel>;
  Cart?: React.ComponentType<CartViewModel>;
}
```

Кожна з пʼяти канонічних сторінок `@simplycms/storefront-routes/src/pages/`
розкладається на **container** (усе, що є сьогодні: хуки, query, серверні
дані → збирає view-model) і **canonical view** (чиста презентація на тій
самій view-model). Container рендерить
`theme.views?.<Name> ?? Canonical<Name>View` через наявний
`useActiveThemeModule`. View живе **всередині каркаса**: `StorefrontShell`
(Header/Footer/токени/шрифти) лишається навколо, як для сторінок сьогодні —
view перевизначає контент сторінки, не каркас. Побічний виграш:
`ProductDetail.tsx` (~700 рядків) розкладається під канонічний ліміт файлів.

## 4. View-model: принципи

- **Типи — у контрактному шарі** `@simplycms/objects` (T0, нуль залежностей):
  їх споживають і ядро, і теми, без залежності теми від `storefront-routes`.
- **Секційна структура** (форвард-сумісність із треком B): view-model групує
  поля за майбутніми секціями, а не плоским мішком — напр.
  `ProductDetailViewModel` = `gallery` / `summary` / `description` /
  `characteristics`, `HomeViewModel` = `hero` / `sections` / `featured`.
  Точний склад — робота імплементаційного плану.
- **YAGNI-правило:** поле додається лише коли його споживає канонічний view.
  Роздування view-model «на майбутнє» — анти-патерн.

## 5. Slot-компоненти реквізитів

Комерційні реквізити їдуть у view не «сирими даними», а **готовими
прибіндженими компонентами ядра**:

```ts
interface ProductDetailViewModel {
  product: { /* назва, ціни, описи, фото, характеристики, наявність */ };
  slots: {
    AddToCart: React.ComponentType<SlotAppearanceProps>;
    QuantityPicker: React.ComponentType<SlotAppearanceProps>;
    PriceBlock: React.ComponentType<SlotAppearanceProps>;
    StockBadge: React.ComponentType<SlotAppearanceProps>;
  };
}
```

Тема **розставляє** `<slots.AddToCart />` у своєму лейауті (стилізація —
appearance-пропси + токени), але логіку купівлі, стани loading/error,
інтеграцію з кошиком зламати темою неможливо — вона в ядрі. Це механічна
відповідь на «обовʼязкові реквізити»: свобода лейауту максимальна,
коректність воронки гарантована ядром. Slot-компоненти рендерять маркер
`data-simplycms-requisite="<name>"` — асерт conformance стає тривіальним і
нефальсифікованим.

Альтернатива «дані + колбеки, тема малює кнопку сама» відхилена для v3:
робить conformance слабким і дозволяє темі зламати покупку.

Мінімальний склад реквізитів по сторінках (уточнює план): ProductDetail —
назва, PriceBlock, AddToCart, StockBadge; Cart — список позицій, сума,
перехід до checkout; Catalog/CatalogSection — картки товарів з лінками,
пагінація; Home — без обовʼязкових комерційних реквізитів (Header/Footer дає
каркас).

## 6. Межа даних, SSR, i18n

**View — чиста функція від view-model.** Жодних власних фетчів (на відміну
від `HomeSections`, який свідомо тягне дані сам). Це несуча вимога, не
смакова: conformance-гейт мусить рендерити view на фікстурній view-model
**без БД** — фетчі всередині зробили б це неможливим. SSR працює автоматично
(container уже SSR-сумісний). i18n — як у v2.1+: `useThemeT` + власний
каталог теми; сканери i18n уже покривають `themes/` і референс-пакети цілком.

## 7. Conformance-гейт

- **Механіка:** розширення conformance-kit у `@simplycms/themes` рендерить
  кожен заявлений view на фікстурних view-model-ах (jsdom) і асертить:
  (а) всі обовʼязкові реквізити сторінки присутні (маркери
  `data-simplycms-requisite`); (б) рендер не падає на крайніх станах
  (товар без фото, порожній кошик, порожня секція).
- **Фікстурні view-model-и** живуть у ядрі поруч із типами й оновлюються тим
  самим PR, що міняє тип — дрейф структурно неможливий.
- **Де червоніє:** тести магазину / CI автора теми (шаблон
  `simplycms create theme` отримує ці тести з коробки); референс-теми
  монорепо — у `pnpm test`; маркетплейс-індекс приймає лише зелений
  conformance.
- **Рантайм:** без fallback і без валідації — магазин рендерить те, що тема
  дала (V3). Дефект видно на гейтах, а не маскується в проді.

## 8. Settings: довести наявний механізм до кінця

Що вже є: `ThemeSettingDefinition` (`type: color|boolean|select|text|number`),
адмін-сторінка `packages/admin/src/pages/ThemeSettings.tsx`, колонка
`themes.settings` (jsonb). Чого бракує — і що входить у v3:

1. **`useThemeSettings()`** у `@simplycms/themes`: типізоване читання значень
   (БД поверх default-ів із definitions) у компонентах і view теми.
2. **Інвалідація SSR-кешу теми** при зміні settings — та сама механіка, що
   для активації теми (урок лайв-тесту: SQL-активація повз інвалідацію
   лишила стенд на старих токенах).
3. **Conformance-рендер із default-ами:** фікстурний рендер обгортається
   провайдером settings із default-значеннями — view, що читає settings,
   тестований без БД.

View-model settings **не** возить: дані магазину і конфіг оформлення — різні
канали; settings — легальний render-контекст (як токени).

## 9. Вплив на механізм клонування дизайну

Фаза «Шліфування» скіла `redesign-from-reference` (інкремент Б.2) при появі
v3 отримує повну драбину рішень для кожної розбіжності side-by-side:

**токен** → **setting теми** → **view теми** (клон лейауту картки / каталогу
/ кошика) → **кастомна сторінка `src/routes/my/`** → **свідомо прийняти
канонічний вигляд**.

- Дисципліна спека-файлів розширюється на сторінки:
  `docs/design-references/<slug>/views/<PageType>.spec.md` — той самий
  шаблон, що для компонентів (interaction model first, усі стани, точні
  значення, responsive, секція Motion з Б.2).
- Пари «наш канонічний тип ↔ їхня сторінка» від дискаверера — прямий вхід
  view-спек.
- Conformance-гейт страхує агента-клонувальника: загубив `slots.AddToCart`
  у гонитві за піксельною схожістю — падають тести, а не продажі.

Інкременти Б.2 **не чекають** на v3 — драбина рішень просто подовжиться,
коли v3 приземлиться.

## 10. Сумісність, міграція, верифікація

- **Повна зворотна сумісність:** `views` опційне; теми v2.2 (`default`,
  `solarstore`) працюють без жодної правки. Сумісність тут — властивість
  дизайну, а не вимога: реальних магазинів ще немає (уточнення власника
  2026-08-17; D5 чинне — breaking дозволений), тож якщо імплементація
  знайде місце, де чистіше зламати, — ламаємо. Номер v3 — через нову
  велику поверхню і conformance-вимоги.
- **Найбільший обсяг** — рефакторинг пʼяти сторінок на container + canonical
  view. Кожна сторінка — окрема фаза плану з гейтами; критерій — канонічний
  вигляд не змінився (side-by-side тим самим `inspect.mjs` проти дев-стенда:
  інструмент клонування стає інструментом регрес-контролю ядра).
- **Хвіст оновлень:** `docs/architecture/themes.md` + `docs/guides/themes.md`
  (описати v3 як фактичний стан), conformance-kit, шаблон
  `packages/cli/template-theme/` (conformance-тести з коробки),
  `pnpm template:sync`, амендмент платформної спеки (D3′/D4′ — зроблено
  разом із цією спекою), роадмап.
- **Перший реальний споживач** views — тема `default` (дизайн знято
  лайв-тестом клонування, шліфування — інкремент Б.2): вона ж валідація
  всього ланцюга «інспекція → view-спека → view теми → conformance →
  side-by-side».

## 11. Ризики (прийняті свідомо)

| Ризик | Чому прийнятний |
|-------|-----------------|
| View усіх зареєстрованих тем їдуть у білд | Як і `components` сьогодні; магазин тримає 1–2 теми. Code-splitting по роутах лишається |
| Дрейф фікстурних view-model-ів від реальних даних | Фікстури в ядрі поруч із типами, оновлюються тим самим PR (§7) |
| Роздування view-model | YAGNI-правило §4; ревʼю-лінза architecture |
| Розсинхрон канонічного view після спліту | Side-by-side регрес-контроль `inspect.mjs` у DoD кожної фази плану |

## 12. Порядок виконання і межі

**Порядок (V5):** ревʼю-цикл PR #32 → мерж → трек C (Б.2, включно зі
шліфуванням default-теми повторним прогоном механізму) →
**трек A: імплементаційний план цієї спеки → виконання** → трек B.

**Що v3 свідомо НЕ обіцяє:**

- перевизначення Checkout / OrderSuccess / auth / profile (кандидати v3.1
  після обкатки);
- секційну композицію сторінки як дані в БД і drag-and-drop в адмінці
  (трек B; v3 лише тримає двері відчиненими секційною структурою
  view-model-ів, §4);
- встановлення/оновлення тем без rebuild (чинне D1);
- зміну межі довіри тем (Р10 Фази 4 чинне: theme-sdk із портами — окрема
  історія, якщо колись знадобиться).
