# Пілот пакування: крок install з `npm` на `pnpm` — імплементаційний план

> **For agentic workers:** Кроки використовують чекбокс-синтаксис (`- [ ]`) для трекінгу. План сумісний із `/виконай-задачу` (Етапи = Tasks, кроки = `- [x] **Step N:**`).

**Goal:** Пілот пакування має ставити скретч-магазин тим самим пакетним менеджером, яким його ставить кінцевий користувач (`pnpm 11.20`), — щоб політики pnpm 11 (`allowBuilds`, `minimumReleaseAge`) і суворий ізольований резолв уперше опинилися всередині гейта, а не за його межами.

**Architecture:** Механізм примусу локальних tarball-ів (`overrides`) переїжджає з npm-івського top-level поля в `package.json` у top-level ключ `overrides:` файлу `pnpm-workspace.yaml` скретча — **мерджем у копію, що приїхала з шаблону**, а не окремим файлом оверлею (інакше затерся б `allowBuilds`). Оскільки помилка в цьому механізмі під pnpm **мовчазна**, разом із міграцією вводиться гард провенансу: після install пілот доводить по lockfile-у, що кожен пакет ядра приїхав із локального tarball-а, а не з реєстру.

**Tech Stack:** Node ≥20 ESM (`.mjs`, без збірки), pnpm 11.20, Vitest 4. Нових залежностей не додається — YAML-блок пишеться текстом (карта пласка).

**Джерело правди пріоритету:** [`docs/architecture/test-contours.md`](../../architecture/test-contours.md) §7, п.2 — «Пілот з `npm` на `pnpm`» стоїть другим за співвідношенням ціна/цінність, одразу після вже зробленого Gate E.

## Довідка для виконавця — емпірично перевірені факти (2026-08-08)

Усе нижче доведено прогонами на pnpm 11.20.0 на цій машині, а не взято з доки.

**Де pnpm 11 читає overrides**

- ✅ Працює: top-level ключ `overrides:` у `pnpm-workspace.yaml`. Діє транзитивно на будь-якій глибині (доведено ланцюгом A→B→C, де споживач залежить лише від A).
- ⚠️ Ігнорується з попередженням: `pnpm.overrides` у `package.json` → `[WARN] The "pnpm" field in package.json is no longer read by pnpm`.
- 🔴 **Ігнорується МОВЧКИ: npm-івський top-level `overrides` у `package.json`** — рівно те, що сьогодні пише `scaffold.mjs:101`. Нуль попереджень.
- `file:`-tarball за абсолютним шляхом приймається; для scoped-імен теж. У lockfile pnpm нормалізує шлях у відносний.
- Override самодостатній навіть для прямих залежностей: якщо в `dependencies` стоїть версія, override усе одно підставить tarball.
- Для одиночного (не-workspace) проєкту ключ `packages:` у `pnpm-workspace.yaml` не потрібен.

**🔴 Чому потрібен гард провенансу.** Раніше помилка в механізмі overrides була голосною: пакетів `@simplycms/*` у реєстрі не існувало, тож install падав `ERR_PNPM_FETCH_404`. **Тепер у реєстрі лежить `0.2.1`** — той самий номер версії, що й у tarball-ах. Отже мовчазна деградація overrides дасть **зелений пілот, який перевірив опубліковані пакети замість тих, що йдуть на публікацію.** Це руйнує сенс пілота, і жоден наявний гейт цього не побачить.

**Політики pnpm 11 у скретчі**

- `allowBuilds` шаблону (`esbuild`, `sharp`, `unrs-resolver`) — **достатній**: перевірено, що **жоден** пакет ядра не має `preinstall`/`install`/`postinstall`/`prepare`. Для реєстрових пакетів ключ — голе ім'я; `dangerouslyAllowAllBuilds` не потрібен.
- 🔴 Для НЕ-реєстрових (`file:`) залежностей ключ `allowBuilds` — це **повний package id з ВІДНОСНИМ шляхом** (`pkg@file:../../tarballs/pkg-1.0.0.tgz`), навіть якщо в override шлях абсолютний. Нас це не зачіпає (див. вище), але при появі install-скрипта в пакеті ядра — зачепить.
- `minimumReleaseAge` **не чіпає** `file:`-tarball-и взагалі (перевірено значенням у 10 років). Б'є лише по реєстрових залежностях скретча.
- При **дефолтному** `minimumReleaseAge` (нічого не задано — стан шаблону) pnpm на свіжу залежність **не падає**: він дописує `minimumReleaseAgeExclude` у `pnpm-workspace.yaml` і йде далі, exit 0. Падіння (`ERR_PNPM_NO_MATURE_MATCHING_VERSION`) дає лише **явно заданий** `minimumReleaseAge`.
  → **Рішення: у скретчі нічого не перевизначаємо.** Пілот лишається вірним тому, що отримує користувач, і не набуває часової крихкості.
- 🔴 pnpm **мутує** `pnpm-workspace.yaml` під час install (дописує `minimumReleaseAgeExclude`, підказки до `allowBuilds`). У скретчі це нешкідливо (тека одноразова), але генератор не має вважати файл своєю незмінною власністю.

**Версія pnpm у скретчі**

- 🔴 corepack бере версію з найближчого `package.json` із полем `packageManager`. Оверлей `tests/pilot/store-template/package.json` цього поля **не має** (воно є лише в `template/package.json.tpl`, який оверлей затирає). Заміряно: у теці з полем — `pnpm 11.20.0`, без нього — `10.33.0`.
- Різниця смислова: **pnpm 10 ще читає поле `pnpm` у package.json, pnpm 11 — ні.** Тобто помилкова форма overrides пройшла б зелено на 10 і зламалась би в користувача на 11.

**Lockfile скретча**

- overrides записуються в lockfile окремою секцією і звіряються при frozen-install: зміна значень → `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH`.
- Пілот щоразу підставляє нові абсолютні шляхи, а режим `--reuse` перевикористовує `STORE_DIR` зі старим lockfile → **frozen-режим у скретчі використовувати не можна**, потрібен явний `--no-frozen-lockfile`.

**Розкладка `node_modules` і гейти**

- `STORE_DIR` = `os.tmpdir()/simplycms-pilot/store` — поза репо, тож всмоктування батьківським workspace не загрожує (а власний `pnpm-workspace.yaml` у скретчі страхує додатково).
- Gate A (`gate-a.mjs:44-49`, підрядок `node_modules/@simplycms/`) — виживає в обох випадках: генератор пише сконфігурований у `routes.ts` шлях, а якщо раптом realpath — хвіст віртуального стору теж містить `.../node_modules/@simplycms/x`.
- Gate A `suspicious` (`:51-53`, підрядки `packages/` і `/src/`) — хибних спрацювань не дає: імена тек стору використовують `+` і `@`.
- Gate C (`gate-c.mjs:23-36`) — регулярки неякорені, матчать хвіст realpath. Побічний ефект: лічильник «у бандлі N» може зрости (той самий пакет у кількох теках стору через варіанти peer-ів); інваріант «в initial 0» не змінюється.
- Gate D — найкрихкіше місце. Глоби `template/tailwind.config.ts:14-15` під pnpm розкриваються в симлінки. Прямий прогін сканера `@tailwindcss/oxide@4.3.3` на симлінк-фікстурі показав, що симлінки він проходить і класи знаходить — але це **перше, що треба звірити** на прогоні.
- Gate B / Gate E — уперше виконуються під суворим ізольованим резолвом. Очікувати **новий клас падінь** `ERR_MODULE_NOT_FOUND` у пакета з недекларованою залежністю, яку плоске дерево npm ховало хойстингом. Це не регресія міграції, а її ціль.

**Що НЕ чіпати**

- `scripts/pilot-pack/pack.mjs:4-7` — коментар «саме `pnpm pack`, а не `npm pack`» стосується кроку **pack** і лишається правдивим.
- `vitest.config.ts:42` — коментар `// витяги npm/pnpm pack` уже покриває обидва менеджери.
- `docs/tasks/platform-roadmap.md:162` — історична фіксація DoD Фази 1; заднім числом не переписуємо.

(98 модулів) і tiptap (22) в initial-чанку. Причина не в пілоті, а в магазині:
code-splitter TanStack Router шукає роут у `TSR_ROUTES_BY_ID_MAP` за module-id
від Vite (realpath через `.pnpm/`), а генератор заповнив мапу шляхами через
симлінк. Ключі не збігаються — сплітінг не застосовується, мовчки.

Отже **кожен магазин, поставлений через pnpm, віз увесь застосунок одним
чанком**, і жоден контур цього не бачив, поки пілот ганяв npm. Виправлено
`realpathSync` у `template/routes.ts`; після фікса — точний паритет із плоским
деревом: 207 чанків, 2453 модулі, initial 19/303, адмінка й tiptap в initial 0.

Це найкраще можливе підтвердження гіпотези задачі: міграція окупилась на
першому ж прогоні.
