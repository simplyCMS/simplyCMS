## 1. Звіт орієнтації: що збіглося з описом задачі, що ні

Перевірено командами, не пам'яттю.

### Збіглося

| Факт | Перевірка |
|------|-----------|
| `main` = `1484cc7`, PR #25 змерджено | `git log --oneline origin/main -3` |
| Репо і реєстр обидва на `0.2.1` | `packages/objects/package.json` → `0.2.1`; `npm view @simplycms/objects version` → `0.2.1`; `npm view create-simplycms-store version` → `0.2.1` |
| Публікованих пакетів рівно 22, усі на одній версії, `private` — жодного | скан `packages/*/package.json` |
| У remote є **тільки** тег `v0.1.0` | `git ls-remote --tags origin` |
| Немає Docker-демона → `pilot:e2e` неможливий | `docker info` → `dial unix /var/run/docker.sock: no such file or directory` |
| Немає `.env.local` → `pnpm pilot` проти живої БД неможливий | `ls -la .env*` → лише `.env.example` |
| Склад релізу: pnpm-міграція пілота + гард провенансу, `realpathSync` у `template/routes.ts`, README 22 пакетів, актуалізація доків | `git log ef277ab..HEAD`, `git diff --stat` |

### 🔴 Розійшлося — факти, що впливають на план

1. **Комітів не 15, а 18** (`git rev-list --count ef277ab..HEAD` = 18, рахуючи
   3 merge-коміти). Опис задачі назвав 15. На обсяг релізу не впливає, але
   означає, що список змін треба брати з `git log`, а не з опису.

2. **У релізі є ще один рантайм-фікс, не названий в описі задачі:**
   `cf2ba11 fix(admin): перемикання теми інвалідовує і клієнтський кеш роутера`
   — це зміна **сирців опублікованого пакета** `@simplycms/admin`
   (`packages/admin/src/lib/revalidateTheme.ts` — новий файл,
   `packages/admin/src/pages/{Themes,ThemeSettings}.tsx`).
   Тобто теза «для споживачів `@simplycms/*` рантайм-поведінка не змінилась»
   **невірна**: вона змінилась рівно в одному пакеті, і це фікс дефекту.
   Це посилює аргумент за patch (див. §2), а не за minor.

3. **Supabase CLI доступний** (`npx supabase --version` → `2.113.0`), всупереч
   таблиці обмежень у задачі. Практичного наслідку немає: без Docker-демона
   `supabase start` усе одно не підніметься, тож Gates B/E лишаються
   недосяжними — але з іншої причини, ніж записано.

4. **graphify не встановлено** — `orient --doctor` каже, що працює через
   rg-fallback. Це норма для cloud-сесії, окремого кроку не потребує.

5. **Робоча гілка вже існує і дорівнює `main`:**
   `claude/simplycms-release-complex-mdxqbp`, `git rev-list --left-right --count
   origin/main...HEAD` = `0 0`. Наслідок для `pnpm release`: `ensureReleaseBranch`
   бачить гілку ≠ `main` і **лишається на ній**, гілки `release/v0.2.2` не
   створює. Це збігається з вимогою задачі (розробка на призначеній гілці) — але
   означає, що назва релізної гілки буде не канонічна `release/vX.Y.Z`, і в
   `release-process.md` це варто відзначити як допустимий випадок.

6. **`src/routeTree.gen.ts` — файл трекається git-ом** (не в `.gitignore`;
   в `.prettierignore` — так). Отже гейт `pnpm build`, який його генерує, може
   забруднити дерево. Порядок дій це враховує (§6): спершу прогін гейтів
   вручну, комміт можливої дельти, і лише тоді `pnpm release` із його гардом
   чистого дерева.

7. **`pnpm install --frozen-lockfile` уже прогнано — зелений**, дерево після
   нього чисте. Тобто lockfile синхронний з манифестами; ризику
   `ERR_PNPM_OUTDATED_LOCKFILE` на старті немає.

## 2. Рішення 1: версія — `0.2.2` (patch)

### Що фактично змінилось у публікованому вмісті

| Пакет | Зміна | Клас |
|-------|-------|------|
| `create-simplycms-store` | `template/routes.ts` — `realpathSync`; `template/pnpm-workspace.yaml`; `template/README.md` | **фікс дефекту** |
| `@simplycms/admin` | `src/lib/revalidateTheme.ts` + два виклики | **фікс дефекту** |
| `@simplycms/runtime` | поле `description` у манифесті | косметика |
| решта 19 | тільки `README.md` (картка в реєстрі) | документація |

Публічного API не додано й не змінено **в жодному** пакеті: нових `exports`,
нових експортованих символів, змінених сигнатур немає.

### Аргументи, зважені в обидва боки

**За `0.3.0` (minor):** фікс `routes.ts` міняє шаблон суттєво і лагодить
дефект, що ламав збірку кожного магазину під pnpm; наявні магазини мусять
зробити ручний крок. Хочеться голосного сигналу «оновись».

**За `0.2.2` (patch) — обрано:**

1. **Semver-сигнал тут не той інструмент.** Minor означає «додано
   функціональність назад-сумісно». Нічого не додано. Сигнал «ти маєш зробити
   ручний крок» несе **міграційна нота**, а не номер версії — і ми її пишемо
   (рішення 3). Якщо підняти minor заради гучності, ми витрачаємо єдиний
   сигнал, який лишається для справжньої фічі, і наступний реліз ядра з новими
   API стане неоднозначним.
2. **Ручний крок стосується вже створених магазинів, а не тих, хто ставить
   пакет.** Оновлення `create-simplycms-store` до `0.2.2` не чіпає наявних
   магазинів взагалі: скаффолдер запускається один раз. Тобто версія пакета —
   не той канал, яким ця новина доходить до постраждалих.
3. **Прецедент проєкту.** `0.2.1` був саме таким релізом — `8c88511
   fix(create-store): шаблон під pnpm 11` плюс оновлення залежностей і доків.
   Тобто в цьому репо patch-слот уже означає «фікси шаблону + чори», а minor
   (`0.2.0`) — завершену фазу з новими можливостями (`create-simplycms-store`,
   owner-invite). Тримаємо ту саму семантику.
4. **Синхронна модель робить minor дорожчим.** Версію отримують усі 22 пакети,
   у 19 з яких змінився тільки README. Minor для них — брехня в обидва боки.

**Висновок: `0.2.2`.** Якщо власник обере `0.3.0`, у плані міняється рівно
одне число і формулювання в `CHANGELOG.md`; решта кроків тотожна.

## 3. Рішення 2: теги — окрема задача

### Що встановлено по коду

`scripts/release.mjs:58` викликає `tagExists(version)` і падає, якщо тег є.
`scripts/release/git.mjs:49-52` реалізує це як `git tag --list` — **локальні**
теги. Ніде в `scripts/release/` немає `git tag` на створення. Отже:

- **дефект A:** тег не створюється ніколи → в remote лежить лише `v0.1.0`,
  а `0.2.0` і `0.2.1` не протеговані. Історія релізів відновлюється лише по
  комітах `chore(release): vX.Y.Z`;
- **дефект B:** гард сліпий у свіжому клоні. Перевірено просто зараз:
  `git tag --list` у цьому клоні порожній, хоча `v0.1.0` у remote є. Тобто
  гард пропустив би навіть повторний випуск `0.1.0`.

Реальний захист від повторного випуску дає не він, а `compareVersions` проти
версії в манифестах (`release.mjs:51`) — вона в git, тож у свіжому клоні
працює. Плюс `pnpm publish -r` мовчки пропускає вже опубліковані версії.
**Тобто дефект A/B — це втрачена зручність, а не діра в безпеці релізу.**

### Чому не лагодити зараз

1. Правка `git.mjs` — це зміна релізного тулінгу **всередині релізу, який цим
   тулінгом і робиться**. Якщо вона виявиться неточною, ми дізнаємось про це
   на середині прогону гейтів, і причина буде змішана з релізом.
2. Ретроактивне проставляння `v0.2.0`/`v0.2.1` — окрема операція над remote
   (push тегів), яку не покриває жоден гейт і яка не має стосунку до вмісту
   цього PR.
3. Правильний фікс не однорядковий: треба вирішити, чи тег ставить людина
   локально, чи CI після успішної публікації (логічніше друге — тег тоді
   означає «опубліковано», а не «підготовлено»), і чи гард питає remote
   (`git ls-remote --tags`) замість локальних тегів. Це дизайн-рішення.

**Дія в цьому релізі:** записати обидва дефекти в
`docs/tasks/platform-roadmap.md` (розділ «Що НЕ зроблено») і в
`docs/architecture/release-process.md` (розділ про `pnpm release`), щоб борг
не загубився. Кода не чіпаємо.

## 4. Рішення 3: `CHANGELOG.md` + міграційна нота

### Проблема, яку треба закрити

`realpathSync` живе в `packages/create-simplycms-store/template/routes.ts`.
Шаблон розгортається **один раз**, у момент `pnpm create simplycms-store`.
Наслідок: кожен магазин, створений із `0.2.0`/`0.2.1` і поставлений через
pnpm, має свій зламаний `routes.ts` і **не отримає фікс з оновленням пакетів**
— бо файл належить магазину, а не ядру. Симптом мовчазний: збірка зелена,
просто весь застосунок (включно з адмінкою і tiptap) їде одним initial-чанком.

Місця, де цю новину сьогодні ніде прочитати: `CHANGELOG.md` у репо немає,
GitHub Releases не ведуться (тегів немає), README пакета про це не каже.

### Що робимо

1. **Завести `CHANGELOG.md` у корені**, формат Keep a Changelog, українською.
   Записи: `0.2.2` (повний), плюс стислі `0.2.1` / `0.2.0` / `0.1.0`, зібрані
   з `git log` — щоб файл не виглядав так, ніби історія почалась сьогодні.
   У записі `0.2.2` — секція **«Міграція наявних магазинів»** з точним
   діффом, який власник магазину має внести у свій `routes.ts`, і з ознакою,
   за якою він перевірить, що постраждав:
   `ls dist/client/assets/*.js | wc -l` — одиниці замість ~200.
2. **Короткий блок «Оновлення наявного магазину»** у
   `packages/create-simplycms-store/README.md` із посиланням на CHANGELOG:
   README — це картка пакета на npm, єдина сторінка, яку власник магазину
   реально побачить.
3. `.prettierignore` виключає **всі** `*.md`, тож `format:check` на це не
   реагує — окремого форматування не треба.

Обидва файли комітяться **до** `pnpm release` (гард чистого дерева), окремим
комітом `docs`.

## 5. Рішення 4: смок із реального реєстру — одразу, з обходом `minimumReleaseAge`

Дефолт pnpm 11 — `minimumReleaseAge: 1 доба` (див. `pnpm-workspace.yaml`
монорепо, коментар). Тобто щойно опубліковані `0.2.2` перші 24 години не
резолвляться. Два шляхи:

- **чекати добу** — чисто, але смок відкладається, а саме він ловить те, чого
  не бачить пілот (сліпа зона №1 у `test-contours.md`);
- **`minimumReleaseAge: 0` у скретчі** — смок одразу, ціна: політика
  supply-chain-затримки в цьому одноразовому магазині вимкнена.

**Обрано другий.** Скретч живе в `/tmp`, викидається одразу після перевірки,
і сама політика — не предмет цього смоку (його предмет — чи резолвиться й
збирається магазин із реєстру). 🔴 Нюанс, який треба врахувати: сам
`pnpm create simplycms-store` теж піде в реєстр по свіжий скаффолдер і
впреться в ту саму політику **до** того, як з'явиться куди писати
`minimumReleaseAge: 0`. Тому скаффолдити — через npm, який такої політики не
має:

```bash
npm exec -y create-simplycms-store@0.2.2 -- /tmp/smoke-store   # скаффолд повз політику
printf '\nminimumReleaseAge: 0\n' >> /tmp/smoke-store/pnpm-workspace.yaml
cd /tmp/smoke-store && pnpm install && pnpm build
ls dist/client/assets/*.js | wc -l    # ~200, а НЕ одиниці
```

Точний синтаксис аргументів CLI звірити з `packages/create-simplycms-store/src/`
у момент виконання.

## 6. Порядок виконання

### Крок A — передрелізна верифікація (до будь-яких правок)

Канонічний порядок, перший червоний — стоп:

```
pnpm install --frozen-lockfile   ✅ уже зелений
pnpm format:check
pnpm lint            # 0 errors; ~961 warnings — НОРМА, не глушити
pnpm build           # перед typecheck: генерує src/routeTree.gen.ts
pnpm typecheck
pnpm test
pnpm build:packages
pnpm test:packaging
pnpm pilot:pack      # A / C / D / CLI + гард провенансу
```

🔴 У `pilot:pack` звіряються **числа**, не лише «PASS»:

| Що | Очікування | Що означає розбіжність |
|----|-----------|------------------------|
| клієнтських чанків (Gate C) | ~207 | одиниці → code-splitting знову зламано |
| initial | 19/303 | ріст → у initial потрапило зайве |
| `@simplycms/admin` в initial | 0 | >0 → адмінка їде всім відвідувачам |
| `@tiptap/*` в initial | 0 | >0 → редактор їде всім відвідувачам |
| провенанс | усі 20 пакетів ядра з `file:` | будь-який з реєстру → пілот перевіряє не те, що публікуємо |

Після `pnpm build`: `git status --porcelain`. Якщо `src/routeTree.gen.ts`
змінився — окремий коміт `chore: перегенерований routeTree`, інакше гард
чистого дерева в `pnpm release` впреться.

### Крок B — документація релізу

- `CHANGELOG.md` (новий) — §4;
- `packages/create-simplycms-store/README.md` — блок оновлення;
- `docs/tasks/platform-roadmap.md` — борг по тегах (§3);
- `docs/architecture/release-process.md` — борг по тегах + примітка, що
  релізна гілка може бути не `release/vX.Y.Z`, якщо реліз готується не з `main`.

Коміт: `docs(release): CHANGELOG + міграційна нота для наявних магазинів`.

🔴 `package.json` тут не чіпається, отже `pnpm install` для lockfile не
потрібен. Якщо це зміниться — звичайний `pnpm install` і lockfile у той самий
коміт (пастка `ERR_PNPM_OUTDATED_LOCKFILE`).

### Крок C — реліз

```bash
pnpm release 0.2.2
```

Гарди → бамп 22 манифестів → повний прогін 8 гейтів → коміт
`chore(release): v0.2.2`. Лишається на гілці
`claude/simplycms-release-complex-mdxqbp` (§1, п.5).

Далі вручну:

```bash
git push -u origin claude/simplycms-release-complex-mdxqbp
```

і **draft PR** у `main`. Мерж — рішення власника, не робиться автоматично.

### Крок D — публікація

Мерж у `main` тригерить `publish-packages.yml`: гейт `NPM_TOKEN` →
`install --frozen-lockfile` → `build:packages` → `test:packaging` →
`pnpm publish -r --access public --no-git-checks`.

Перед мержем PR має бути зелений по трьох job-ах: `typecheck`, `test`,
`packaging`.

### Крок E — післярелізна верифікація

1. **Через ~5 хв** (CDN-лаг — саме він дав один із дефектів `0.2.0`):
   ```bash
   npm view @simplycms/objects version
   npm view create-simplycms-store version
   ```
2. **Усі 22, а не частина** — прогін міг упасти на середині. Скриптом по
   списку з `packages/*/package.json`, з явним переліком тих, хто не на `0.2.2`.
3. **Смок магазину з реального реєстру** — §5.
4. **Роадмап**: версія в «Поточний стан» → `0.2.2`, дата оновлення.
   Це окремий коміт **після** мержу; він поїде наступним PR, бо реліз-коміт
   уже змерджено.

## 7. Відкат

npm **не дає** перевипустити ту саму версію. Тому:

| Ситуація | Дія |
|----------|-----|
| Гейт у `pnpm release` червоний | нічого не сталось: бамп у робочому дереві, коміту немає. `git checkout -- .`, лагодити, повторити |
| CI на PR червоний | звичайний фікс-коміт у гілку; реліз-коміт лишається |
| `publish` упав **до** кроку Publish (install/build/parity) | нічого не опубліковано → `workflow_dispatch` після фіксу |
| `publish` упав **на середині** публікації (частина пакетів у реєстрі) | 🔴 **не бампати версію.** `workflow_dispatch` — `isAlreadyPublished` пропустить уже опубліковані, доллє решту |
| Опубліковане виявилось зламаним | `0.2.3` із фіксом + `npm deprecate @simplycms/<pkg>@0.2.2 "…"`. `npm unpublish` — тільки в межах 72 год і тільки якщо ніхто не встиг залежати; версія при цьому вигорає назавжди |

🔴 Ситуація «частково опубліковано» **розсинхронізує реєстр із моделлю
синхронних версій** до успішного ретраю. Це не привід бампати — це привід
ретраїти, поки не доллється.

## 8. Що це оточення довести НЕ може

Називаю наперед, щоб у звіті це не виглядало як недогляд.

| Не перевіряється | Причина | Наслідок |
|------------------|---------|----------|
| Gate B (запити до живої БД) | немає `.env.local` | регресія в предикатах запитів пройде непоміченою |
| Gate E (owner-invite наживо) | немає Docker-демона → локальний стек Supabase не підняти | invite-флоу не перевірено цим релізом |
| Клікові смоки (плагін, тема, `/profile`) | немає браузера | фікс `cf2ba11` (інвалідація кешу теми) перевірено **лише** юніт-тестом `revalidate-storefront.test.tsx`, не руками |
| Сам `publish-packages` до мержу | тригер — push у `main` | перший доказ, що токен і права ще живі, — сам реліз |
| Смок із реального реєстру | пакетів `0.2.2` ще немає | Крок E, п.3 — після мержу |

Ці зони збігаються зі сліпими зонами, вже описаними в
`test-contours.md` §4 — нових не з'являється.
