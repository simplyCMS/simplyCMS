**Дата:** 2026-08-09
**База:** `main` = `ee7f62d`, версія пакетів `0.2.2`
**Гілка:** `claude/simplycms-i18n-migration-63khns`
**Борг:** роадмап Фази 0, п. 4

## 0. Рішення, які треба ухвалити ДО роботи

### Рішення №1 — рантайм-перемикання мови: **НІ (варіант A)**

Локаль лишається build-time вибором власника магазину (`simplycms.config.ts` →
`locale: 'uk-UA'`). Ми робимо повний `en.ts`, але **не** робимо `/en/`-роутів,
`hreflang`, canonical на локаль і перемикача в UI.

Чому:

- варіант B чіпає canonical і sitemap, тобто **перетинається** з невиконаною
  задачею `docs/tasks/seo-ssr-faceted-navigation.md`. Робити двічі одну й ту саму
  правку canonical — гарантований конфлікт;
- B вимагає локалізації **даних** (назви товарів, секцій, властивостей у БД), а
  схема ядра одномовна: `products.name` — один `text`. Без міграції схеми
  двомовна вітрина показує англійський каркас із українськими товарами. Це не
  «трохи більша задача», це інша задача;
- A уже дає всю цінність, заради якої борг заводили: жодного хардкоду в коді,
  магазин англійською збирається зміною одного рядка конфіга.

**Наслідок:** B лишається окремою фазою й має бути записаний як борг у роадмапі,
з явною передумовою «локалізація даних у схемі».

### Рішення №2 — структура каталогу: **неймспейсні модулі, зведені spread-ом**

913 унікальних текстів у один файл не влізуть (ліміт 150 рядків на файл).

```
packages/i18n/src/catalogs/
├── uk/
│   ├── index.ts          # export const messages = { ...common, ...cart, … }
│   ├── common.ts         # спільні для обох пакетів рядки
│   ├── validation.ts     # повідомлення Zod
│   ├── nav.ts · cart.ts · checkout.ts · catalog.ts · product.ts
│   ├── auth.ts · profile.ts · order.ts
│   └── admin/            # ~13 модулів за доменами адмінки
│       ├── index.ts · common.ts · products.ts · orders.ts · …
└── en/                   # ДЗЕРКАЛЬНА структура, файл у файл
```

`MessageKey` лишається замкненим union-ом, бо `index.ts` зводить модулі в один
обʼєкт:

```ts
export const messages = {
  ...common,
  ...validation,
  ...admin,
} satisfies Record<string, string>;
```

`keyof typeof messages` після spread-у дає повний union літеральних ключів —
контракт `types.ts` не змінюється, публічний API пакета теж (`exports` — тільки
`.`, каталоги не експортуються назовні окремо).

🔴 Ризик спреду: дублікат ключа у двох модулях **мовчки** перетирається. Гасить
тест `catalog-integrity.test.ts` (див. §4).

**Конвенція ключів** — плоскі крапкові, як зараз, з дисципліною:

| Сегмент | Правило |
|---|---|
| `common.*` | рядок трапляється в **≥2 доменах** («Зберегти», «Скасувати», «Помилка», «Назва») |
| `validation.*` | повідомлення Zod («Назва обовʼязкова» — 8×, «Мінімум 2 символи» — 4×) |
| `<домен>.*` | сторфронт: `cart`, `checkout`, `catalog`, `product`, `auth`, `profile`, `order`, `nav`, `breadcrumbs` |
| `admin.<домен>.*` | адмінка: `admin.products`, `admin.orders`, `admin.discounts`, `admin.shipping`, `admin.users`, `admin.settings`, `admin.plugins`, `admin.themes`, `admin.banners`, `admin.properties`, `admin.reviews`, `admin.prices` |
| `…​.toast.*` | повідомлення toast живуть у своєму домені: `admin.products.toast.saved` — не окремий кореневий неймспейс |

Неймспейс — **за доменом, а не за файлом**: 108 текстів повторюються ≥3 разів
(587 входжень сумарно), розкладка за файлами дала б їм 587 ключів замість ~108.

**Динамічні ключі** (мапи `Record<StatusCode, Label>` — 46 таких властивостей):
ключ не будується конкатенацією (`t(\`status.${code}\`)` зламає замкнений union),
а мапиться явно:

```ts
const STATUS_KEYS: Record<ReviewStatus, MessageKey> = {
  pending: 'admin.reviews.status.pending',
  approved: 'admin.reviews.status.approved',
  rejected: 'admin.reviews.status.rejected',
};
```

Так додавання статусу в БД без ключа — помилка типізації, а не порожній рядок.

### Рішення №3 — ціна в бандлі: **лишаємо статичний імпорт обох каталогів**

Заміряно на реальних даних census-у: 913 унікальних текстів = 34 KiB тексту
(кирилиця — 2 байти на символ) + ~25 KiB ключів. `uk` ≈ 60 KiB, `en` ≈ 45 KiB,
разом ≈ **105 KiB сирих ≈ 25–30 KiB gzip** у клієнтському бандлі.

Чому не ліниве вантаження:

- `createTranslator` — **синхронний**, і `useT()` викликається під час рендера.
  Ліниве вантаження робить його асинхронним, а це або `await` у кореневому
  лоадері (сповільнює SSR кожного запиту), або Suspense навколо всього дерева;
- `tsup` для `@simplycms/i18n` стоїть із `splitting: false` — динамічний
  `import()` він **вбудує назад**, тож економії не буде без правки збірки пакета;
- за рішенням №1 локаль — константа збірки, тож правильна оптимізація тут не
  «ліниво», а «дати збірнику викинути невживаний каталог». Але реєстр
  `const catalogs: Record<Locale, Catalog> = { uk, en }` — статичний обʼєкт,
  обидві гілки досяжні, tree-shaking їх не прибере.

**Що робимо натомість:** заміряємо розмір клієнтського бандла `pnpm build` **до**
і **після** міграції, число кладемо у звіт. Якщо приріст вийде більшим за ~35 KiB
gzip — заводимо окремий борг «lazy-локаль» із правкою `tsup`-конфіга. Робити це
всередині цієї міграції — змішувати дві незалежні зміни.

### Що не є UI і мігрувати не треба

- **`console.error` — 4 входження** (`server/auth.ts` ×2, `server/themes.ts`,
  `seo/interceptor.ts`): це логи розробника, не інтерфейс. Лишаються українськими
  за правилом «коментарі й документація українською». Йдуть в allowlist тесту
  повноти.
- **Фікстури й дані в тестах** (`'Товар p1'`, `'Іван'`, `'Секція C'`) — це дані,
  не рядки інтерфейсу.
- 🔴 **`name: 'Новий тариф'` у `supabase.from('shipping_rates').insert`**

  показується. Мігруємо через `t()` (адмін бачить саме його при створенні), але
  фіксуємо в звіті: зміна локалі магазину змінить назву новостворених тарифів.
  Уже наявні рядки в БД не чіпаються.

## 2. Порядок зрізів

🔴 **Відхиляюсь від пропозиції в постановці в одному місці:** toast і Zod — **не**
окремий фінальний прохід, а частина кожного файлу.

Чому: окремий прохід означає торкнутися всіх 76 файлів **двічі** й подвоїти
поверхню рев'ю. Гірше — рефактор Zod-схеми у фабрику змінює сигнатуру всередині
компонента; робити його окремо від решти рядків того самого файлу — це два
конфліктні дифи на один файл. **Одиниця роботи — файл, мігрований повністю.**
Окремим лишається не прохід редагування, а прохід **перевірки** (§4).

| Етап | Обсяг | Що саме |
|---|---|---|
| **E0. Фундамент** | ~0 файлів UI | Перерозкладка каталогу на неймспейсні модулі (uk + en) без зміни набору ключів; `common.*` і `validation.*` наповнюються 108 повторюваними текстами; тести цілісності каталогу (§4). Гейти зелені, поведінка не змінилась. |
| **E1. storefront-routes** | 255 входжень, 21 файл | Менший пакет, і його бачить покупець. Дає шаблон рішень (мапи, фабрики Zod, toast) до того, як заходити в 1240 входжень адмінки. |
| **E2. admin — каркас** | ~120 входжень | `AdminLayout`, `AdminSidebar`, `adminLinks.ts`, `Dashboard`, `PlaceholderPage`, `usePluginToggle`, `revalidateTheme` — навігація й спільні ярлики, від яких залежить решта. |
| **E3. admin — довідники** | ~430 входжень | `Properties*`, `Sections*`, `PriceType*`, `PickupPoint*`, `Shipping*`, `OrderStatuses`, `Banners*`, `Themes*`, `Plugins*`. |
| **E4. admin — товари й ціни** | ~350 входжень | `Products`, `ProductEdit`, `ProductModifications`, `ProductPricesEditor`, `ProductPropertyValues`, `SimpleProductFields`, `StockByPointManager`, `PriceValidator`, `AllProductProperties`. |
| **E5. admin — комерція й люди** | ~340 входжень | `Orders`, `OrderDetail`, `AddProductToOrder`, `Discount*`, `UserCategory*`, `User*`, `Review*`, `Settings`. |
| **E6. Замикання** | — | `en.ts` добивається до 100 %; warn→error на обидва пакети; тест повноти вмикається на повну; `pnpm pilot:pack`; заміри бандла. |

Після **кожного** етапу — повний гейт-ланцюг і окремий коміт.

## 3. Технічні рішення всередині файлу

**Zod поза React → фабрика.** Було:

```ts
const formSchema = z.object({ name: z.string().min(1, "Назва обовʼязкова") });
```

Стало:

```ts
const buildFormSchema = (t: Translator) =>
  z.object({ name: z.string().min(1, t('validation.name.required')) });
```

у компоненті: `const formSchema = useMemo(() => buildFormSchema(t), [t]);`
`type FormValues` виводиться з `z.infer<ReturnType<typeof buildFormSchema>>`.
`t` стабільний (мемоїзований по локалі в `I18nProvider`), тож перебудови схеми на
кожен рендер не буде.

**Мапи ярликів на рівні модуля → мапи ключів.** `Record<Code, string>` стає
`Record<Code, MessageKey>`, значення резолвиться на місці рендера через `t()`.
Мапа лишається на рівні модуля — вона більше не містить тексту.

**Тернарники в JSX** — переносяться в тернарник ключів, коли обидві гілки
статичні: `t(isNew ? 'admin.banners.titleNew' : 'admin.banners.titleEdit')`.

**Шаблонні літерали (33 шт.)** — переходять на інтерполяцію `{name}`, яку
транслятор уже підтримує: `t('admin.plugins.toggleFailed', { name })`.

**Обробка (щоб не знищити коментарі — пастка №1).** Правки роблю **вручну через
`Edit`**, файл за файлом, читаючи його цілком. Масової sed/regex-заміни не буде.
Автоматичний тут лише **пошук** (AST-census) і **перевірка** (тест повноти) —
запис завжди ручний. Контроль: після кожного етапу `comments.mjs` перераховує
рядки кириличних коментарів; число має лишатись **325**.

## 4. Як доводиться повнота (пастка №2)

Зелений `warn→error` **не** доводить завершеність — він покриває 64 % роботи.
Незалежну гарантію дають **три committed-тести**:

1. **`tests/i18n-coverage.test.ts`** — AST-скан обох пакетів (той самий обхід, що
   й census). Падає, якщо знайдено кириличний `JSXText`, `StringLiteral`,
   `NoSubstitutionTemplateLiteral` або `TemplateExpression` поза явним
   allowlist-ом. Allowlist — точковий, із поясненням на кожен запис (4 виклики
   `console.error`). Це і є перевірка, якої лінт дати не може.
2. **`tests/i18n-catalog-parity.test.ts`** — `Object.keys(en)` дорівнює
   `Object.keys(uk)`. Закриває пастку №4: `Catalog = Partial<…>` за типом дозволяє
   дірки, тож повноту `en` може гарантувати лише тест.
3. **`packages/i18n/src/__tests__/catalog-integrity.test.ts`** — сума довжин
   ключів усіх неймспейс-модулів дорівнює довжині зведеного обʼєкта (немає
   мовчазного перетирання при spread-і) + кожен ключ модуля має префікс свого
   неймспейсу.

Плюс перевірка, яку тест не дає і яку я назву чесно: **збіг перекладу зі змістом**
(чи «Вид ціни» справді `Price type`, а не `Price kind`) — це людське рев'ю, і
воно лишається за замовником.

## 5. Що лишиться недоведеним

- **Візуально нічого не перевірено.** Браузера в оточенні немає — 913 рядків
  ніхто не побачив у верстці. Ризик: обрізані кнопки, розʼїхані шапки таблиць
  адмінки, переповнені бейджі. Наприкінці дам список місць під очі.
- **`pilot` і `pilot:e2e` не запустяться** (немає Docker/Supabase/`.env.local`).
  Прогониться лише `pilot:pack` — він доводить пакування, не поведінку.
- **Якість англійського перекладу** — мій, не носія. Термінологія е-комерсу
  (Price type / Pickup point / Shipping zone / Discount group) потребує звірки.

## 6. Реліз

**Рекомендую `0.3.0` (minor), але окремим кроком після мержу.**

Чому minor, а не patch: `MessageKey` — публічний тип пакета
`@simplycms/i18n`, і union розширюється з ~35 до ~913 членів. Формально це
адитивна зміна, але поведінка опублікованих `@simplycms/admin` і
`@simplycms/storefront-routes` змінюється видимо для споживача (рядки тепер ідуть
через провайдер; магазин без `I18nProvider` тепер падає значно ширше, ніж падав
на 6 файлах). Patch це б приховав.

Чому окремим кроком: `pnpm release` — свідоме рішення людини (див.
`docs/architecture/release-process.md`), і мерж у `main` публікує. Пропоную:
спершу PR із міграцією, після твого рев'ю — окремий `pnpm release 0.3.0`.

## 7. Оцінка

913 ключів × 2 каталоги ≈ 1830 рядків каталогу + правки в 76 файлах, з них 61
довший за 150 рядків. Це не механічна заміна: ~46 мап ярликів і 10 Zod-схем
вимагають структурного рефактора. Реалістично — **6 великих комітів**, кожен із
власним прогоном гейтів; найбільший ризик несе E4–E5 (адмінка, ~690 входжень),
де немає жодного автотесту на рендер.
