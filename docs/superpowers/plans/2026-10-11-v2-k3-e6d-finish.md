# К3-Е6д-доробка: закриття боргів К3-Е6д-1…9 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Закрити в гілці `claude/k3-e6d-content` (від `0e1f28f7`) усі дев'ять боргів К3-Е6д до мержу Е6д. Кожен борг закривається кодом або остаточним рішенням, без жодного запису «на потім».

**Architecture:** Чотири нові рішення архітектора:
- **Е6д-20.** Транзакційний outbox `media_erasures` для другої фази стирання.
- **Е6д-21.** `serveMedia` перевіряє рядок `media` і видимість сутності через ін'єкцію від маршруту. Персональні медіа отримують `private, no-cache`.
- **Е6д-22.** Sweep неприв'язаних рядків `media` через спільну `findMediaReferences`.
- **Е6д-23.** Покупець редагує свій відгук. Будь-яка правка повертає відгук у `pending`. Модерація приймає рішення лише проти версії, яку бачив модератор.

Решта задач розширює чинні механізми: опцію `media` фабрики (на jsonb-масиви), двофазне стирання (на аватар, логотип і `deleteMedia`), request middleware (стеля тіла) і контракт тем (банер).

**Tech Stack:** TanStack Start 1.168 / start-server-core 1.169, Drizzle + PostgreSQL 17 (RLS, гранти), React 18/19, Vitest + Testing Library, PG-харнес (`pnpm test:schema`), `live:smoke`.

**Spec:** `docs/superpowers/specs/2026-10-10-content-banners-reviews-design.md` разом із попереднім планом `docs/superpowers/plans/2026-10-10-v2-k3-e6d-content.md` (рішення Е6д-1…19). Повний перелік боргів із причинами — `docs/tasks/platform-roadmap.md`, розділ «Борги К3-Е6д». Рішення Е6д-20…23 ухвалені архітектором (`dashboard-design-spec`) 2026-10-11 і **записані тут**. ## Рішення

- **Е6д-20 — outbox стирання.**
  - **Таблиця** `media_erasures`, Категорія A (`id` задає викликач, без DEFAULT). Колонки:
    - `id uuid pk`;
    - `storage_key text unique not null`;
    - `requested_at timestamptz not null default now()`;
    - `attempts integer not null default 0`;
    - `last_error text`.

    Гранти — лише `app_admin` (select, insert, update, delete); RLS увімкнено з політикою `app_admin` ALL, як у сусідніх службових таблиць.
  - **Вставка.** `eraseMediaRows` у ТІЙ САМІЙ транзакції видаляє рядки `media` і вставляє рядки outbox (`on conflict (storage_key) do nothing`). Повертає ключі, як і зараз.
  - **Друга фаза** — `completeMediaErasures(keys)` після COMMIT. Для кожного ключа `driver.delete`:
    - успіх → рядок outbox видаляється;
    - збій → `attempts + 1`, `last_error`; назовні нічого не кидається.

    Після цього функція опортуністично добирає до `MEDIA_ERASURE_RETRY_BATCH = 5` найстаріших хвостів (`requested_at < now() - interval '1 minute'`, `FOR UPDATE SKIP LOCKED`).
  - **Адмін-операції** під `media.write`: «повторити стирання» і список/лічильник. Фонового шедулера немає. `simplycms doctor` не чіпаємо.
  - **`discardMedia`** зноситься (Е6д-20б). Будь-яке стирання файлу йде через outbox.
- **Е6д-20а — облік outbox поза транзакцією користувача.** `completeMediaErasures` відкриває власну коротку транзакцію службового актора в `simplycms/storage`.
  - Перевір у `db/actor.ts`, чи є системний актор (С-15 `{ kind: 'system' }`). Якщо є — бери його. Якщо немає — `withActor({ role: 'app_admin' })` без `userId`, і в JSDoc чесно напиши «системний актор, не адмін-користувач».
  - Окремої DB-ролі `operator` НЕМАЄ. Ескалація `operator` (`storefront/loaders/escalation.ts:55`) робить `set local role app_admin` у транзакції покупця. Тому всі нинішні викликачі `eraseMediaRows` з контексту `app_user` уже виконуються під `app_admin`:
    - видалення відгуку покупцем — `reviews-write.ts:146`;
    - аватар.

    Т9 мусить кликати `eraseMediaRows` так само через `operator`.
  - Вставка outbox іде в тій самій транзакції й під тією самою роллю, що й DELETE `media`.
- **Е6д-20б — відкат щойно опублікованого файлу теж іде через outbox.** У `catch` будь-якого шляху після `writeMedia` (подача й правка відгуку, upload адміна, аватар) кличеться `scheduleMediaErasures(keys)`: власна коротка транзакція службового актора вставляє рядки outbox. Далі `completeMediaErasures(keys)`. `discardMedia` як окремий шлях без outbox ЗНОСИТЬСЯ.
  - Межа лишається одна, і вона записується в `storage.md` одним рядком: БД недоступна саме в момент відкату → файл без рядка `media`. Він не роздається (Е6д-21), але й не видимий як хвіст.
- **Е6д-21 — роздача.**
  - **Сигнатура:** `serveMedia(ctx, { lookup })`, де `lookup(key, request) => Promise<MediaServeVerdict>` ін'єктує маршрут. Відповідь:
    - `'missing'` → 404;
    - `'hidden'` → 404 (не 403, щоб не підтверджувати існування);
    - `{ personal: boolean }` → файл.
  - **Кеш:**
    - персональні (`PERSONAL_MEDIA_ENTITY_TYPES = ['review', 'avatar']` у `domain/media.ts`) — `cache-control: private, no-cache`;
    - решта — як зараз, `public, max-age=31536000, immutable`.
  - **Видимість відгуку** делегується RLS: запит «чи бачу я рядок `product_reviews` з цим id». Із сесією — `withCustomerDb(subject.userId)`, без сесії — `withStorefrontDb`. Адміну з `can(subject, 'review.moderate')` видно все.
  - **Резолвери** — ЯВНА константа `MEDIA_VISIBILITY: Partial<Record<string, MediaVisibilityResolver>>` у модулі вітрини, яку `lookupMediaForRequest` бере напряму. Ніякої реєстрації побічним ефектом імпорту. Тип без резолвера видимий, якщо рядок `media` є.
  - **Доступ до БД:** гість іде через `withStorefrontDb` = `app_user` без `app.user_id` (`storefront/loaders/db.ts:23-27`), тобто та сама роль. `app_user` має табличний SELECT на `media` (`0002_grants.sql:132`), RLS на `media` немає. Нового гранту не потрібно; PG-тест це доводить саме гостем.
  - **304:** ключ незмінний (новий файл = новий ключ), тож чинний `etag: "<key>"` — сильний валідатор. На `If-None-Match` зі збігом віддаємо 304 без `driver.open`, але ПІСЛЯ `lookup`: персональний файл ревалідується з перевіркою видимості, а не повним перезавантаженням.
- **Е6д-22 — sweep.**
  - `findMediaReferences(db, key)` поверх `MEDIA_COLUMNS` повертає `{ table, column, id }[]`. Для jsonb перевіряється членство в масиві (`col ? key`), для text — рівність.
  - Ця сама функція дає:
    - 409 `media_in_use` у `deleteMedia`;
    - sweep (порожній результат = неприв'язаний);
    - інваріант сідів (Task 6).
  - **Sweep** (адмін-операція, `media.write`) прибирає рядки `media` старші за `MEDIA_SWEEP_MIN_AGE_HOURS = 24` без референсу: `eraseMediaRows` з власником рядка → outbox → `completeMediaErasures`.
  - **Інвентаризація записувачів (факти 2026-10-11, М2 архітектора).** Файли пишуть лише три шляхи:
    - адмінський `uploadMedia` — тільки через `ImageUpload`, шість споживачів: `product`, `product_modification`, `section`, `property_option`, `banner`, `store_logo`;
    - аватар — `storefront/loaders/avatar.ts:95`, тип `avatar`;
    - фото відгуку — `reviews-write.ts:95`, тип `review`.

    Ключів сховища в rich HTML немає: `RichTextEditor.addImage` бере довільний URL через prompt і нічого не вантажить. Плагіни, теми й налаштування сайту порт сховища не імпортують (grep 2026-10-11). Тож кожен тип, крім `store_logo`, живе в колонці `MEDIA_COLUMNS`. Логотип живе в `system_settings.value->>'logo'`, і `findMediaReferences` перевіряє його окремою гілкою.
  - **Гейт** `media-sweep-coverage` (Task 7). Множина типів, що вантажаться (`MEDIA_ENTITY_TYPES` + `'avatar'` + `REVIEW_MEDIA_ENTITY`), має збігатися з множиною типів, для яких `findMediaReferences` має гілку. Якщо тип не sweep-иться, він записується явно з причиною. В обидва боки.
  - **Вставлений вручну в rich HTML URL `/media/<key>`** чужого файлу не захищається. Обмеження одним рядком записується в `storage.md`: редактор не вантажить файли, а посилання на чужий файл — не референс.
- **Е6д-23 — редагування відгуку покупцем.**
  - **Політика** (перейменування `product_reviews_update_own_pending` → `product_reviews_update_own`): `USING (user_id = actor) WITH CHECK (user_id = actor AND status = 'pending')`. Колонковий грант `UPDATE (rating, title, content, images, status, updated_at)`, без `admin_comment`. Код явно пише `status: 'pending'`, `updated_at` ставить сервер.
  - **Фото:**
    - збережені референси ⊆ поточних `images` цього відгуку;
    - нові — лише через `writeMedia` з власником `review/<id>`;
    - разом ≤ `MAX_REVIEW_IMAGES`;
    - прибрані → `eraseMediaRows` з власником → outbox → `completeMediaErasures` після COMMIT;
    - при збої транзакції щойно опубліковані файли прибираються через `scheduleMediaErasures` + `completeMediaErasures` (Е6д-20б).
  - **Модерація проти побаченої версії:** `setReviewsStatus` приймає `items: { id, updatedAt }[]`. Розбіжність `date_trunc('milliseconds', updated_at) <> $updatedAt` під `FOR UPDATE` → 409 `review_changed` на весь пакет атомарно. Порівняння саме з `date_trunc`, як у keyset, бо `isoTs` віддає мілісекунди, а БД тримає мікросекунди. UI на 409 перечитує дані й показує тост «відгук змінився».
  - **Наслідок:** схвалений відгук після правки зникає з публічного показу до повторної модерації.
- **К3-Е6д-1:**
  - опція `media` фабрики приймає jsonb-масив (через `normalizeMediaRefs`); `assertMediaColumns` пропускає `PgText` і `PgJsonb`, усе інше валить;
  - `cascadeMedia` — на `sections` і `section_properties` (`property_options.image_url`), на `products` (`product_modifications.images`);
  - EXEMPT гейта лишається лише для аватара.
- **К3-Е6д-2 — стеля тіла.**
  - Константа `MAX_REQUEST_BODY_BYTES = max(MAX_REVIEW_IMAGES × MAX_REVIEW_IMAGE_BYTES, MAX_UPLOAD_BYTES, MAX_AVATAR_BYTES) + MULTIPART_OVERHEAD_BYTES` (`1 MiB`) у `domain/media.ts`.
  - Request middleware `bodyLimitMiddleware` у `simplycms/runtime/body-limit.ts` для будь-якого POST на `/_serverFn/`:
    - `Content-Length` > стелі → 413;
    - multipart без `Content-Length` → 411;
    - JSON без заголовка — як є.
  - Припущення «Node-раннер не читає тіло далі за `Content-Length`» записується в `ENVIRONMENT.md` і `upstream-workarounds.md` (маркер `UPSTREAM:START-BODY-1`).
- **К3-Е6д-3:**
  - аватар, логотип і `deleteMedia` переходять на `eraseMediaRows` + `completeMediaErasures`;
  - логотип отримує власника `{ entityType: 'store_logo', entityId: STORE_LOGO_OWNER_ID }` (константа в `domain/media.ts`, фіксований uuid), який пишеться при upload;

- Відповіді, коментарі й доки — українською; коментар пояснює **чому**.
- Жодних трейлерів `Co-Authored-By`/`Generated with` у комітах. Після задачі: `git log --format=%B 0e1f28f7..HEAD | grep -ciE "co-authored|generated with"` = `0`.
- Схема: `schema.ts` → правка baseline `packages/simplycms/migrations/0001_init.sql` / `0002_grants.sql` (точкова, без нового файлу `0005`, як Е6д-8) → `pnpm template:sync` → `pnpm test:schema`.
- Ключ `id` генерує викликач; у нових таблицях немає `DEFAULT gen_random_uuid()`.
- Двофазне стирання — єдиний канон. Транзакція видаляє лише рядки `media` (і пише outbox), файли — після COMMIT.
- Норма `pnpm lint` = 0 errors / 7 warnings.
- Задача, що зносить файли чи змінює схему, ганяє й `pnpm test:schema`. Харнес потребує `PG_HARNESS_URL`: `docker run -d --rm -p 54330:5432 -e POSTGRES_HOST_AUTH_METHOD=trust pgvector/pgvector:pg17` → `PG_HARNESS_URL=postgres://postgres@localhost:54330/postgres`.
- Тест «після COMMIT» розрізняє порядок лише через збій саме на COMMIT (deferred constraint trigger `blockCommit`, прецедент Е6д).
- Нові рядки UI — через `useT`, ключі в усіх локалях ядра (тест парності).
- ~150 рядків на модуль; великий файл ділити.
