# V2-К3 · Етап Е6д: контент — банери й відгуки на серверному шарі

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Чотири останні легасі-сторінки адмінки (`Banners`, `BannerEdit`, `Reviews`, `ReviewDetail`) переходять на `simplycms/admin-server` + `simplycms/admin-data`. Власник веде банери з повним розкладом і безпечними картинками й модерує відгуки: бачить лічильник «очікують», схвалює або відхиляє масово, бачить фото. Покупець додає до відгуку до 5 фото. Внутрішня примітка адміна з вітрини зникає. Доводить це `pnpm live:smoke`.

**Architecture:**
- **Банери.** Банери — ресурс фабрики `defineAdminResource` з eager-колекцією. Фабрика отримує декларативну опцію `media` (Е6д-1). Вона читає старий рядок один раз (`FOR UPDATE`), перевіряє нові референси як `media` цієї сутності, а для заміненого файлу транзакція видаляє лише рядок `media`; сам файл стирається ПІСЛЯ COMMIT (Е6д-14). Той самий знімок рядка бачить guard банерів для перехресних правил (Е6д-2). Предикати форми банера (кнопка, безпечне CSS-значення) живуть у T1 і спільні для вітрини й сервера (Е6д-3, Е6д-4).
- **Відгуки в адмінці.** Відгуки читаються іменованими операціями без колекції: keyset-список, лічильник, картка. Модерує одне ядро `setReviewsStatus` (одиночна й масова дія, сід). Статус і рейтинг тримають CHECK-и в baseline (Е6д-8).
- **Фото у відгуках.** Покупець подає фото в ОДНОМУ FormData-serverFn за зразком аватара: перевірка до запису, `writeMedia` у транзакції, `discardMedia` при відкаті (Е6д-5, Е6д-6).

**Tech Stack:** TanStack Start 1.167, React Query, `@tanstack/react-db` (eager-колекція банерів), Drizzle, Zod 4, Vitest, PostgreSQL 17 (`pnpm test:schema`), Playwright (`pnpm live:smoke`).

**Spec:** [`docs/superpowers/specs/2026-10-10-content-banners-reviews-design.md`](../specs/2026-10-10-content-banners-reviews-design.md) (Д-1…Д-4; правки за Е6д-1…Е6д-9 — коміт плану f888655e, за Е6д-14 — коміт правок аудиту р1).

## Ухвалені рішення етапу

| № | Рішення | Причина |

| Е6д-1 | *(архітектор)* **Опція фабрики `media: { entityType: MediaEntityType; columns: readonly W[] }`**. Порядок у транзакції insert/update/remove: лок → знімок старих рядків (`SELECT … WHERE id = ANY($ids) ORDER BY id FOR UPDATE`, ОДИН раз; на insert знімка немає) → guard (бачить знімок, Е6д-2) → перевірка НОВИХ референсів → запис → `eraseMediaRows` заміненого чи видаленого (лише рядки `media`) → після COMMIT `discardMedia` (Е6д-14). Новий референс перевіряється, лише якщо він непорожній і відрізняється від знімка: це рядок `media` з `entity_type = cfg.entityType AND entity_id = <id рядка>` під `FOR SHARE`, інакше 409 `media_ref_invalid`. Стирається лише референс, що задовольняє ту саму умову (чужий файл фабрика не стирає ніколи). Незмінений `data:`/`https:` референс (демо) не перевіряється. В Е6д опцію отримують лише банери; `sections`/`products`/`property_option` — беклог (Task 10) | «Прибрав картинку → скасував форму» лишає мертвий референс (`ImageUpload` з `eraseOnRemove` за замовчуванням стирає файл одразу). Декларативна опція закриває цей клас бага одним механізмом, а не кодом у кожному ресурсі. Умова `entity_id` не дає стерти чужий файл підсунутим референсом, бо стирання йде за `storage_key` |

Кожна операція з `discard` має у харнесі три кейси:
  1. після успіху файлів і рядків `media` немає;
  2. транзакція впала → файли й рядки на місці, `driver.delete` не викликано;
  3. `driver.delete` впав після COMMIT → запис у БД виконано, рядків `media` немає, файл лишився орфаном, битих референсів 0.

**Interfaces:**
- `AdminResourceConfigBase` отримує `media?: { entityType: MediaEntityType; columns: readonly NoInfer<W>[] }` (КАНОН). Колонки — лише writable `text`.
- `ResourceGuardWrite` для update отримує знімок: `{ kind: 'update'; updates: readonly { id: string; patch: Patch; before?: Insert }[] }`. `before` заповнюється, коли ресурс має `media`. Для insert форма не змінюється. Наявні guard-и не змінюються: поле опційне.
- `resource-media.ts`:
  - `type ResourceMedia = { readonly entityType: MediaEntityType; readonly columns: readonly string[] }` — рантайм-форма опції;
  - `readSnapshot(db: ActorDb, ctx: ResourceWriteContext, ids: readonly string[]): Promise<Map<string, Record<string, unknown>>>` — `FOR UPDATE`, `ORDER BY id`;
  - `assertMediaRefs(db: ActorDb, media: ResourceMedia, rows: readonly { id: string; next: Record<string, unknown>; before?: Record<string, unknown> }[]): Promise<void>` — для кожної колонки з непорожнім `next[col] !== before?.[col]` перевіряє `media` за умовою Е6д-1 під `FOR SHARE`; інакше `stateConflict(ADMIN_STATE_CONSTRAINT.mediaRefInvalid)`;
  - `eraseReplacedMedia(db: ActorDb, media: ResourceMedia, pairs: readonly { id: string; before: Record<string, unknown>; after: Record<string, unknown> | null }[]): Promise<string[]>` — для кожного рядка бере МНОЖИНУ `refs(before) \ refs(after)` по всіх колонках `media` (аудит Codex р1 B3: одна картинка може стояти у двох колонках, і заміна однієї колонки не має стерти файл, на який досі вказує інша). Береться лише ключ, що задовольняє умову Е6д-1; відібрані ключі кожного рядка йдуть в окремий виклик `eraseMediaRows(db, keys, { entityType: media.entityType, entityId: <id рядка> })` (Е6д-16), а функція повертає обʼєднаний результат — ключі для `discard`. `after: null` означає remove.
- **Discard у фабриці (Е6д-14):** операції `update`/`remove` ресурсу з `media` кличуть `discardMedia` кожного ключа ПІСЛЯ `run` (тобто після COMMIT). Db-варіанти `updateIn`/`removeIn` отримують обовʼязковий для `media`-ресурсу третій параметр `discard: string[]` (колектор): ключі дописуються в нього, а `discardMedia` кличе ВИКЛИКАЧ після своєї транзакції. Виклик `updateIn`/`removeIn` media-ресурсу без колектора кидає помилку програміста, щоб сід чи порт не лишали орфанів мовчки.
- Порядок (КАНОН Е6д-1) у `defineWriteOps`. Без `media` шлях байт у байт колишній.
  - insert: lock → guard → `assertMediaRefs` → запис;
  - update: lock → `readSnapshot` → guard (з `before`) → `assertMediaRefs` → запис → `eraseReplacedMedia` → COMMIT → `discardMedia`;
