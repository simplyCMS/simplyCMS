**Чи можна викликати серверну логіку з server route без дублювання — так, і в нашому коді це вже можливо.**
`defineAdminResource` повертає звичайні async-функції (`list/insert/update/remove`) і ядра без HTTP
(`insertIn/updateIn/removeIn`). `admin-server/index.ts` лише обгортає їх: `createServerFn().validator(adminInput(ops.insertSchema)).handler(ops.insert)`
(126 таких обгорток). Server route може викликати `productsOps.insert({ data })` напряму. Документація
TanStack цього не забороняє, бо це не виклик serverFn, а виклик звичайної функції.

Реальна перешкода не в TanStack, а у **двох прив'язках до транспорту всередині `runAdmin`** **[НОВЕ]**:
1. `requireGrant → resolveRequestGrant → readSessionSubject(getRequest().headers)` (`auth/authz-request.ts:36`):
   суб'єкт береться **лише** з cookie-сесії Better Auth. Bearer-токен API туди не потрапить.
2. `setResponseStatus(409/400/403)` (`admin-server/impl/run.ts:61-62`, `authz-request.ts:53`): статус ставиться
   через контекст відповіді Start. У server route, що сам повертає `Response`, цей статус не діє (обробник
   повертає власний `Response`), тож мапінг помилок у статус мусить перейти в адаптери.

Обидві прив'язки знімаються одним рефакторингом: передавати суб'єкта/грант параметром, а мапінг помилок
перенести на межу транспорту. Механізм TanStack тут не потрібен.

Звіт 81 оцінює «клей» В1 як «великий». Ця оцінка майже цілком випливає з припущення про **ресурсний REST**
(маршрути, query-парсинг, PATCH-семантика, кеш). Для командного HTTP (`POST /api/v1/<op>` з JSON) адаптер займає кількасот рядків.

### Моя позиція

- **В1, еволюційно з `defineAdminResource`/`runAdmin`, ~70 %.** Конкретні кроки:
  1. `runAdmin(operation, fn)` перетворити на `runAdmin(grant, operation, fn)`: грант приходить від адаптера
     (адмінка — з cookie, API — з токена, CLI/MCP — з токена). `setResponseStatus` винести в адаптер serverFn.
  2. Реєстр `defineOperation({ name, permission, input, output, kind, handler })`. Обгортки serverFn лишаються
     **топ-рівневими const**, бо компілятор Start інакше мовчки їх не трансформує. Їх паритет із реєстром стереже тест,
     а не генерація.
  3. HTTP-адаптер — один catch-all server route `/api/v1/$`, виняток у `CSRF_EXEMPT_PREFIXES` лише для Bearer-запитів
     (cookie-запити на `/api/v1` мають і далі проходити CSRF, інакше це діра).
  4. OpenAPI 3.1 — з `z.toJSONSchema` на кожну операцію. MCP — через SDK v2 на `WebStandard…Transport` у тому самому
     server route. CLI — з реєстру.
- **В2 (oRPC), ~25 %.** Технічно сумісний: Zod 4 через `@orpc/zod/zod4`, OpenAPI 3.1 задається явно. Проти:
  - він **замінює** `createServerFn` як транспорт адмінки, а це 126 обгорток і клієнтські хуки;
  - bus factor 1;
  - ще один контекстний механізм поверх нашого гранта;
  - пастка з кореневим імпортом конвертера.

  Його головна сила — REST-маршрутизація з OpenAPI — нам не потрібна, якщо HTTP командний (див. нижче).
- **В3 (Hono), ~5 %.** MCP-транспорт є в самому SDK, а розщеплення визначень serverFn і Hono — якраз та дубль-проблема,
  яку треба прибрати.

### Ресурсний REST проти командного RPC для **наших** споживачів

Хто реально ходить по HTTP:
- **Завантажувач 1С власника.** HTTP-сервіси 1С однаково легко шлють `POST` з JSON. Власник пише клієнт сам: йому
  потрібна стабільна документована операція, а не «REST-звичність».
- **CLI і MCP** — природно командні (звіт це сам визнає, §3.3).
- **Адмінка** ходить через serverFn, не через публічний HTTP.
- **Плагін-перекладач — НЕ HTTP-клієнт [НОВЕ, виправлення 81].** За інваріантом `AGENTS.md` плагін працює лише через порти
  `simplycms/plugin-sdk` у процесі. Він споживач **порту**, а не протоколу. Звіт 81 зараховує його до споживачів API.

Переваги REST, на які спирається 81 (кеш, ETag, CDN), для автентифікованого API запису нерелевантні.

**Висновок: командний RPC — єдина публічна форма, ~70 %.**
- `POST /api/v1/<op>` для записів;
- безпечні читання дозволено віддавати й через `GET /api/v1/<op>?…`;
- без паралельної ресурсної REST-поверхні.

Публікувати обидві поверхні з одного реєстру (пропозиція 81) означає подвоїти контракт, тест-поверхню і семвер-зобов'язання.

### Правило мовних записів «запис джерела не чіпає інших мов; переклад з `expectedSourceHash` → 409»

Ядро правила правильне. Але в поточному формулюванні є **дірки [НОВЕ]**:
1. **TOCTOU.** Перевірка `expectedSourceHash` і запис перекладу мусять бути атомарні щодо запису джерела:
   - або `SELECT … FOR SHARE` рядка джерела в транзакції перекладу;
   - або один оператор `INSERT … SELECT … WHERE src.source_hash = $expected`.

   Інакше паралельна правка джерела між перевіркою й комітом дасть «свіжий» переклад застарілого тексту. Звіт лише
   постулює 409 і не каже, як його гарантувати.
2. **Що таке «запис джерела» в API.** Варіанти: мова запиту = `is_source` сутності, або явний режим. Якщо 1С пише `uk`,
   а джерело сутності вже `en` (Р-ML-5 «змінити мову джерела»), запит має або **відхилитися** (`not_source_locale`),
   або стати записом перекладу, тобто вимагати хеш. Мовчазне трактування неприпустиме.
3. **Гранулярність хеша.** Рекомендую **на поле**, як Shopify, ~65 %:
   - рядковий хеш робить застарілою назву через правку опису;
   - плагін машинного перекладу платить за повторний переклад усього рядка.

   Slug і SEO-поля **не входять** у хеш (див. 83 нижче).
4. **Відповідь 409** має нести в extension members RFC 9457 поточний хеш і (опційно) поточне джерело, щоб MCP-агент
   виправився без зайвого читання, як радить специфікація MCP (`isError` з дієвим текстом).
5. **Адмінка-перекладач** мусить відправляти хеш, проти якого відкрила форму. Інакше вона пише за правилом last-write-wins
   і правило обходиться через власний UI.
6. `If-Match`/`version` для рядка — **окремий** захист (412), не змішувати з 409 джерела (див. 1(д)).

## 4. Критична оцінка рекомендацій 83

### 4.1. «Основна мова без префікса (A)», ~75 % у звіті → **у формулюванні звіту відхиляю**

Звіт сам називає мінус «зміна основної мови = масовий 301». Але рамка (Р-ML-5) **планує** операцію «змінити основну мову
магазину», а в 1.2 `is_default` визначено як властивість магазину. Прив'язка безпрефіксного простору до `is_default`
перетворює плановану операцію на катастрофу. Масовий 301 — ще не найгірше. Гірше **перевикористання адрес [НОВЕ]**:
- після зміни `uk → en` шлях `/x` (раніше український) починає віддавати англійську;
- старий український URL неможливо зредіректити, бо він тепер валідна адреса іншої мови;
- однакові латинські slug (бренди, моделі) у двох мовах гарантують такі колізії.

Варіанти, що витримують Р-ML-5:
- **A′ (моя рекомендація, ~65 %).** Безпрефіксний простір — окрема, практично незмінна властивість
  `languages.url_root` (одна мова), **не** `is_default`.
  - Зміна `is_default` (fallback, x-default, мова адмінки за замовчуванням) не рухає жодного URL.
  - Зміна `url_root` — окрема рідкісна міграція зі згенерованою 301-картою.
  - `/uk/x` для root-мови → 301 на `/x`.
  - Одномовний магазин має чисті URL.
  - Додавання другої мови нічого не рухає. Тобто **не** правило PrestaShop «префікс лише коли мов > 1»: воно саме
    є антипатерном, бо друга мова зсуває всі адреси.
- **B (префікс усюди, ~35 %).** Симетрія, зміна основної мови — нуль змін URL; так зробив і OC4 (`/en-gb/…`).
  - Ціна: `/uk/` у кожному URL одномовного магазину.
  - `/` мусить бути 302 (не 301, бо ціль залежить від конфігурації) або сторінкою вибору мови як `x-default`.

**Розвилка для власника:** A′ проти B. A у формі звіту (прив'язка до `is_default`) — ні.

Технічно обидва варіанти здійсненні в нашому роутері. TanStack Router підтримує `/{-$locale}/…` (опційний сегмент,
приклад i18n — у документації path-params), а `params.parse` відсіює неактивні коди. Статичні роути мають
пріоритет над опційними.

### 4.2. «Slug по мовах, опційний, fallback на slug основної мови», ~85 % у звіті → **знижую до ~40 % у такій формі**

Runtime-fallback slug створює дві дірки, яких звіт не бачить **[НОВЕ]**:
1. **Колізія ефективних slug.** Унікальність «`(тип, мова, slug)`» стосується лише *збережених* slug. У просторі
   `/en/` живуть і явні en-slug, і fallback-slug джерела.
   - en-slug товару B може збігтися з fallback-slug товару A.
   - Зміна джерельного slug A може зіткнутися з явним en-slug B у кожній мові, де діє fallback.

   Перевірка стає O(мов) на кожен запис і не виражається одним `UNIQUE`.
2. **Зміна URL при появі перекладу.** Коли en-slug з'являється, адреса `/en/<fallback>` змінюється.
   - Fallback-адреса мусить потрапити в історію slug і отримати 301.
   - Отже, історія має фіксувати не лише явні зміни, а й «материалізацію».

Плюс неоднозначність «основної мови»: `is_default` магазину чи `is_source` сутності? Вони різні (Р-ML-5).

**Моя рекомендація (~80 %):** slug **зберігається явно для кожної існуючої мовної версії** — без runtime-fallback.
- Значення за замовчуванням обчислюється **один раз при створенні версії**: транслітерація перекладеної назви засобами
  `LanguagePack` мови або копія slug джерела.
- Тоді `UNIQUE(locale, slug)` у проєкції/таблиці slug — звичайне обмеження БД, а «fallback» — лише UX форми.
- Це прямо відповідає Saleor (`unique(language_code, slug)`) і Shopify (`INVALID_VALUE_FOR_HANDLE_TRANSLATION`).
- Slug і SEO-поля **поза** `source_hash`: slug — не переклад, а адреса, і «застарілим» не буває.

### 4.3. «Без id в URL + історія slug», ~70 % → **погоджуюсь, з поправкою**

Звіт пропускає, що наш `id` = **GUID 1С** (36 символів) **[НОВЕ]**. Варіант PrestaShop (`/123-slug`) з ним дає
`/p/0f8c…-slug`, а саме цього Google не радить («long ID numbers»). Id в URL можливий лише через новий короткий
сурогат (послідовний номер), а це ще одна сутність ідентичності. Тому чисті slug + історія — правильний вибір (~75 %).

Не погоджуюсь із формулюванням звіту «історичний запис знімається при захопленні slug іншою сутністю». Тиха
переадресація трафіку на іншу сутність гірша за відмову. Пропоную: **захоплення історичного slug — явна дія з
попередженням**, за замовчуванням заборонене, а історія живе безстроково (Google: «consider keeping redirects
indefinitely»).

### 4.4. «URL товару без категорії» → **у нас ця вада вже знешкоджена; змінювати — за бажанням, не з необхідності**

Звіт (§4.8, антипатерн 9) не дивився код. Що є насправді (`domain/product-path.ts`, роут `catalog/$sectionSlug/$productSlug.tsx`):
- товар резолвиться **лише за slug товару** (`getProduct({ slug })`), сегмент розділу — декоративний;
- будь-який неканонічний сегмент → **301 на поточний** (`productRedirectTarget`, Р25);
- товар без розділу → зарезервований `all`.

Тобто проблема OC3 «кілька шляхів без канону» у нас **не відтворюється**. Переміщення товару між розділами або
перейменування розділу не потребує історії: старий шлях сам дає 301 без ланцюжка.

Залишковий аргумент «проти» сегмента в багатомовності: перейменування slug розділу в мові X міняє URL **усіх** його
товарів у мові X. Це тисячі 301 і переіндексація від однієї правки. Мій нахил — **прибрати сегмент розділу з URL
товару** (~60 %), але як продуктове рішення власника, а не як усунення вади.

Пропозиції звіту `/p/…`, `/c/…` суперечать чинним `/catalog/…`. Злам дозволений (клієнтів немає), але це окрема зміна контракту тем
(`productPath` — єдина точка побудови, тож злам локалізований).

### 4.5. «302 на основну мову для неіснуючої версії», ~65 % → **відхиляю**

Google (301-redirects): за тимчасового редіректу ціль **не** вважається канонічною, тобто `/en/x` може лишитися в індексі
з українським контентом. Це той самий дубль, якого звіт хоче уникнути. Крім того, 302 на адресу іншої мови — фактично
«редірект за мовою», а Google радить так не робити.

**Рекомендую (~70 %):** неіснуюча мовна версія → **404** із посиланнями «доступно: Українська, …» (сторінка 404 у
мові URL). Перемикач мови ніколи не веде на неіснуючу версію: він веде на ту саму сутність у наявних мовах або на
головну/розділ цільової мови. Якщо версія колись існувала і переклад видалили чи деактивували — так само 404, бо
повернення перекладу поверне URL. 301 тут хибний, бо він постійний.

### 4.6. «Фасети в query кодами» → **погоджуюсь (~85 %), але звіт не бачить двох наших конкретних конфліктів**

- **Перемикач мови зберігає фільтри без перекладу** лише якщо коди мовонезалежні. Це сильний аргумент «за».
- **[НОВЕ] Конфлікт 1: `/properties/$propertySlug/$optionSlug`.** У нас уже є **індексовані посадкові сторінки властивостей**
  на slug (`section_properties.slug` глобально унікальний, `property_options` унікальний у межах властивості). Тому:
  - або slug опції — **мовонезалежний код** (для query фасетів), і посадкові сторінки мають окремий перекладний slug;
  - або slug перекладається, і тоді для фасетів потрібен окремий код.

  Одне поле не може бути і тим, і іншим. GUID 1С як код у query допустимий лише тому, що фасетні URL не
  індексуються, але читабельність гірша.
- **[НОВЕ] Конфлікт 2: `?mod=<slug модифікації>`** на картці товару: `product_modifications.slug` унікальний у межах
  товару. Якщо slug модифікації перекладний, `?mod=` залежить від мови й ламається перемикачем. Рекомендація:
  `?mod=` — мовонезалежний код (або id), slug модифікації — не перекладати.

### 4.7. Незадані розвилки й антипатерни, яких у 83 немає [НОВЕ]

1. **Інвалідація hreflang-кластера.** Через взаємність hreflang поява чи зникнення перекладу мовою X змінює HTML
   сторінки **в усіх інших мовах** і sitemap. Для Р-ML-9 (кеш/CDN) ключ інвалідації — сутність, а не (сутність, мова).
2. **Поріг «версія існує»** (назва чи назва+опис):
   - чи рахується `outdated`-переклад існуючим (так; інакше правка джерела в 1С миттєво ховає мовні версії з індексу);
   - як поводиться **лістинг розділу** в мові, де частина товарів не перекладена: показувати лише перекладені
     (розділ може стати порожнім → за Google 404) чи змішувати мови (погано за Google).
3. **Мовний контракт для роутів плагінів і `my/`.** Кожен роут вітрини (ядро, плагіни, кастомні роути магазину)
   мусить жити під мовним сегментом, а теми й плагіни будувати посилання лише через мовно-свідомі хелпери
   (`productPath(…, locale)`).
   - Жорсткий `<Link to="/cart">` у темі — тихий витік у root-мову.
   - Потрібні лінт і (або) тест паритету, як для інших контрактів тем.
4. **Зарезервовані слова.**
   - Коди мов не можуть збігатися з верхніми сегментами (`catalog`, `cart`, `auth`, `api`, `media`, `properties`) і зі
     slug сторінок контенту Е6д.
   - `NO_SECTION_SLUG = 'all'` — зарезервоване слово, яке тепер має бути зарезервоване в кожній мові.
5. **`Vary`.** Мова визначається лише URL, тож **жодного `Vary: Accept-Language`/cookie** на HTML вітрини. Інакше
   CDN-кеш розщеплюється, а Google бачить різний контент на одній адресі (повтор вади OC3 на рівні кешу).
6. **Коди hreflang.** Лише ISO 639-1 (+ ISO 15924). `languages.code` треба валідувати на це, якщо мова претендує на
   hreflang; `uk`, а не `ua`.
7. **Транслітерація per-language.** КМУ №55 стосується лише `uk`. Для інших мов — свої таблиці або перекладена назва
   латиницею, тобто `slugify()` у `LanguagePack` поруч із `tokenize()`. Плюс NFC і нижній регістр, бо Google
   case-sensitive.
8. **Регенерація slug: Shopware проти Shopify.**
   - Shopware регенерує slug з перекладеної назви (історія — неканонічні записи).
   - Shopify генерує handle лише при створенні, далі явна зміна з `redirectNewHandle`.

   Звіт подає «не регенерувати» як безальтернативне. Альтернатива існує, і вибір між ними — продуктове рішення
   (рекомендую модель Shopify: рішення власника №7 і сценарій 1С).
9. **Перемикач мови на сторінках кошика, чекауту й профілю:** мова з URL і там, а мова листів — з `orders.locale`.
   Розрізнити «мову сесії UI» і «мову замовлення» при зміні мови посеред чекауту.

## 5. Підсумок вердиктів

- **81, підтверджено:** TanStack (усі три цитати), Idempotency-Key -07 (статус і коди), RFC 9457, Standard Webhooks,
  Shopify digest required / `outdated`, ts-rest стоїть, trpc-openapi архівовано, Hono zod-openapi 3.1, oRPC OpenAPI 3.2
  за замовчуванням / 3.1 задається, адаптер TanStack Start.
- **81, частково або уточнено:**
  - Zod 4 в oRPC є лише на `@orpc/zod/zod4`, корінь — v3;
  - bus factor oRPC = 1 людина;
  - відхилення застарілого digest у Shopify не задокументоване, тож 409 — наш вибір;
  - RFC 9110: If-Match → 412, а не 409;
  - плагін-перекладач — споживач порту, а не HTTP;
  - SDK MCP 1.32.1 не реалізує специфікацію 2026-07-28.
- **83, підтверджено:** OC3 startup/seo_url/адмінка, усі сторінки Google (з датами), Magento, Saleor, поля Shopware.
- **83, спростовано:** «OC4 — мова не з path, префікси лише модулями» (у SEO-режимі ядро OC4 має `/en-gb/`);
  «Shopware без id в URL» (дефолт `{name}/{productNumber}`).
- **83, рекомендації, які відхиляю:**
  - A, прив'язане до `is_default` (суперечить Р-ML-5) → A′ або B;
  - runtime-fallback slug → явний slug для кожної версії;
  - 302 для неіснуючої версії → 404 з посиланнями.
