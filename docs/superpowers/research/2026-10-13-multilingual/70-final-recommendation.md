# 70. Підсумкова рекомендація архітектора — багатомовність даних, довідники, API (2026-10-13)

Джерела: 01 (вимоги власника), 10/11 (зіставлення за назвою, верифіковано Opus), 20 (API/1С), 30 (SEO,
швидкодія, пошук — виміри), 40 (експерименти Postgres 17, 50k/5k товарів, 5 мов), 50 (рішення головного
аналітика, Fable), 60 (адверсаріальна верифікація, Opus: «прийняти з правками»).

## 1. Головне, що змінює рамку рішення

**Вибір моделі зберігання НЕ замикається запуском пілоту.** Перехід між моделями «основна мова в колонках +
переклади» (A/A″) і «усі мови в таблицях перекладів» (B) на 50k товарів — 1–2 с копіювання даних
(expand/contract, без простою; 40 §9, підтверджено 60 §1). Дорога частина — переписування запитів, і вона
однакова зараз чи пізніше. Після 1.0 зміна моделі не ламає semver, якщо порт перекладів і API не
виставляють назовні «базова колонка проти накладки» (60 §1) — це правило ми фіксуємо зараз.

Отже до пілоту треба зафіксувати лише те, що справді незворотне, а модель зберігання обрати свідомо — і
реалізувати її хвилею мультимовності (Е9), не відкладаючи пілот.

## 2. Модель зберігання: позиція аналітиків і моя

- **Fable (50) і Opus (60): A″** — «джерело + накладки»: текст мови джерела в колонках базових таблиць,
  `source_locale` на сутності, переклади в `<entity>_translations`. Перевага над B оцінена ≈60/40. Сильні
  аргументи: `NOT NULL` джерела як факт схеми; нуль накладних для одномовного магазину.
- **Opus знайшов у A″ три класи дефектів, яких B не має за побудовою** (доведено на Postgres): текст однієї
  мови може лежати у двох місцях (накладка в мові джерела мовчки перекриває базу); мова запису через API
  неявна (текст іншої мови тихо лягає в базу); зміна мови джерела / основної мови — це перенос тексту між
  базою й накладками, а не прапорець. A″ закриває їх лише правилами ядра.
- **Аргументи проти B, що не втрималися** (60 §1): «+1 JOIN назавжди» — вітрина читає готову проєкцію, різниця
  на сторінці товару — планування запиту (0,3–0,5 мс виконання в обох); «B — 3–4 тижні» — упереджено поточним
  кодом: хвиля Е9 переписує лоадери вітрини в будь-якій моделі.

**Моя рекомендація як архітектора — B як цільова модель** (OpenCart/PrestaShop/Sylius/Shopware): кожен текст
кожної мови живе рівно в одному рядку `<entity>_translations(entity_id, locale, …)`; рядок мови джерела
позначений (`is_source`, рівно один на сутність — частковий унікальний індекс + відкладена перевірка
наявності в ядрі запису); метадані однакові для всіх мов (`source_hash`, `updated_at`, статус).
Чому — саме за критеріями власника, а не за ціною:
1. **Розвиток:** нове перекладне поле — одна колонка в одній таблиці (в A″ — дві: база й накладка).
2. **Підтримка й ризик помилок:** один інваріант «мова L сутності E — один рядок» замість набору правил ядра,
   що закривають три класи дефектів A″.
3. **API, 1С, агенти, плагін-перекладач:** мапа мов `name: {uk, en}` і «переклад як ресурс» — природні;
   імпорт однією мовою — запис рядка джерела; перейменування — зміна рядка джерела → решта мов
   автоматично `outdated` за `source_hash`; зміна мови ведення — перенос позначки `is_source`.
4. **Багато мов:** жодна мова не є «особливою» в схемі; основна мова вітрини — властивість магазину
   (`languages.is_default`), а не форма даних.
Ціна B: складеніша основна форма адмінки (один складений ресурс замість плаского — одна форма на
сутність) і відкладена перевірка наявності рядка джерела. Швидкодія вітрини однакова (проєкція).

Якщо власник обере A″ — обов'язкові правки з 60 (П2–П4): явна `locale` в кожному текстовому записі,
заборона накладки в мові джерела, `source_locale NOT NULL` без DEFAULT з FK на `languages`, операція
«змінити мову джерела».

## 3. Спільне для будь-якої моделі (рішення 50 + правки 60)

- **Вітрина читає з проєкції R2:** мовонезалежний рядок на товар (розділ, статус, опції для фасетів);
  ціни окремо; текст на (товар, локаль) з уже застосованим fallback і `UNIQUE(locale, slug)` — реєстр slug.
  Оновлюється ядром у транзакції запису set-based на пакет, з детермінованим порядком локів (ризик
  дедлоку з чекаутом — 60 §3). Форму з окремими цінами ПЕРЕМІРЯТИ до Е9 (48 мс виміряно з цінами всередині).
- **Фасети — за id значень;** мова лише в підписах (підтверджено вимірами 30/40).
- **Пошук:** `search_documents` з локаллю в ключах індексів і в черзі; `tokenize()` у `LanguagePack`
  (амендменти спеки пошуку 2026-08-25).
- **Slug:** перекладені; історія slug — upsert «останній власник» + 301; колізія fallback-slug джерела в
  мові, якою 1С не оперує, розводиться детерміновано, а не відмовою всього пакета (60 §4).
- **URL і SEO:** основна мова без префікса, інші — `/en/…`; hreflang/sitemap per locale; неперекладений
  товар — F2 (canonical на основну мову, поза hreflang і sitemap); «перекладено» = заповнені обов'язкові поля.
- **API:** server routes з токенами (власна `api_tokens`), upsert за id (GUID 1С = наш id, `z.guid()`),
  ідемпотентність, версія рядка; інкрементальна синхронізація — НЕ по `updated_at` (губить рядки на
  конкурентних записах, доведено в 60), а журнал змін / горизонт `pg_snapshot_xmin`.
- **Мова інтерфейсу ≠ мова контенту:** у формах адмінки — явний вибір мови контенту.
- **`languages`** — єдине джерело мов і основної мови (до першого не-`uk` магазину); мови не видаляються,
  лише деактивуються.

## 4. До пілоту — лише незворотне й дефекти (≈3–5 днів)

1. **ADR (без коду):** основна мова без префікса, перекладені slug, F2, правило «порт/API не виставляють
   базу проти накладки», амендменти спеки пошуку.
2. **Доставка — підтверджені major-дефекти (11):** самовивіз бере зону з обраної точки
   (`pickup_points.zone_id`, NULL → дефолтна зона), а не з прихованого поля міста; гарантія рівно однієї
   дефолтної зони (створення при онбордингу, заборона зняти/видалити); fail-closed `shipping_unavailable`
   лише для способів з тарифами по зонах (не ламає Нову Пошту як перевізника); запис
   `orders.shipping_zone_id/shipping_rate_id` і перерахунок в адмінці з них.
3. **Зіставлення за назвою міста (`cities`/`regions`):** рішення власника — прибрати зараз (пілот на
   дефолтній зоні + НП + самовивіз) або тримати до довідника населених пунктів у Е9 (див. питання 3).
4. **boolean-фільтр** вітрини (порожній каталог) — виправити.
5. **`orders.locale`** — дешево (0,5 дня), стандарт галузі; бекфіл пізніше теж точний, але колонка однаково
   знадобиться для листів мовою покупця.

Свідомо після пілоту (Е9): модель зберігання (B), таблиці перекладів, проєкція R2, історія slug, пошук з
локаллю, довідник населених пунктів (КАТОТТГ як структура ядра), API (токени, upsert, журнал змін, вебхуки,
MCP/CLI), решта знахідок 10/11.

## 5. Питання власнику

1. **Цільова модель зберігання:** B (моя рекомендація) чи A″ (рекомендація Fable й Opus, ≈60/40)?
2. **Коли:** у хвилі Е9 після пілоту (рекомендую — дані переносяться за секунди, код коштує стільки ж) чи
   до пілоту з відкладенням rc.1 на ~2–4 тижні?
3. **Доставка в пілоті:** чи потрібні alterenergy різні тарифи кур'єра за містами? Якщо ні — прибираємо
   зіставлення за назвою міста зараз; якщо так — тримаємо до довідника населених пунктів у Е9.
4. **URL:** основна мова без префікса, перекладені slug, F2 — підтвердити.
