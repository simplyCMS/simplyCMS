## 1. OpenCart 4: факти з коду

### 1.1 Що таке мова магазину

`system/helper/db_schema.php:3219-3266` — таблиця `language`:
`language_id` int AI, `name` varchar(32), `code` varchar(5), `locale` varchar(255), `extension` varchar(255),
`status` tinyint (default 0), `sort_order`. Поля `directory` (як в OC 2/3) у 4.x немає.

- `code` (`en-gb`, `ru-ru`) — одночасно ключ мови даних і ім'я теки каталогу інтерфейсу.
- `extension` — ім'я language-extension, з якого брати каталоги (порожнє — ядро, `catalog/language/<code>`).
- **Одна таблиця на обидві ролі.** Окремого реєстру «мов інтерфейсу» немає.

### 1.2 Чи можна додати й увімкнути мову без пакета — ТАК

`admin/controller/localisation/language.php:223-276` (`save`) перевіряє лише довжину `name` (1–32), `code` (2–5),
`locale` (2–255) і унікальність `code` (`:259-262`). **Наявність теки `<code>` чи extension не перевіряється.**
`status` задається з тієї ж форми, тож мову без пакета можна одразу ввімкнути.

`admin/model/localisation/language.php:35-75…` (`addLanguage`) вставляє рядок і **копіює описи всіх сутностей**
(атрибути, банери, категорії, …) з `config_language_id` — тобто з мови, якою зараз працює адмін (див. 1.3).
Тексти нової мови — копія, а не порожнеча.

### 1.3 Як визначається мова вітрини й адмінки

Вітрина — `catalog/controller/startup/language.php:19-55`:
- список — `catalog/model/localisation/language.php:109-110` (`WHERE status = '1'`);
- код: `?language=` → перший сегмент SEO-URL (`:31-34`) → `config_language_catalog` (`:36-43`);
- `config_language_id` = id мови (`:51`) — ним фільтруються всі `*_description`;
- якщо в мови є `extension` — додається шлях `extension/<ext>/catalog/language/` (`:46-48`).

Адмінка — `admin/controller/startup/language.php:19-52`:
- список — `admin/model/localisation/language.php:591` (усі мови, без фільтра `status`) [з коду];
- мова: налаштування магазину `config_language_admin` (`:32-34`), перекрите cookie `language` (`:37-39`);
- та сама `config_language_id` (`:47`) — тож **мова інтерфейсу адміна = мова, з якої копіюються описи** при
  `addLanguage`. Мова даних, яку адмін редагує у формі, — окремо (вкладки мов у формах) [не підтверджено кодом
  форм, загальновідома поведінка OC].
- Видалити мову, що є `config_language` чи `config_language_admin`, не можна (`language.php:381, 385`); з
  замовленнями — теж (`:399`).

Налаштування: `admin/controller/setting/setting.php:136-138` — `config_language_catalog`, `config_language_list`,
`config_language_admin`; список вибору — та сама `getLanguages()` (`:134`).

### 1.4 Fallback — ПОКЛЮЧОВИЙ, на `en-gb`, а не на мову магазину

- `system/config/default.php:6` — `$_['language_code'] = 'en-gb';`
- `system/framework.php:146-149` — `new Language($config->get('language_code'))`, `addPath(DIR_LANGUAGE)`,
  `load('default')`: об'єкт мови створено з кодом `en-gb`.
- `system/engine/loader.php:205-217` — `$this->load->language($route, $prefix, $code)` → `language->load(…)`
  з `$code` (зазвичай `''`) → потім подія `language/*/after`.
- `system/library/language.php:136-183` — `load()`: при `$code === ''` бере `$this->code` (тобто `en-gb`);
  файл відсутній → `$_ = []` без помилки (`:163-167`); результат `array_merge` у `$this->data` (`:180`).
- `catalog/controller/startup/language.php:69-93` (`after`, зареєстровано `system/config/catalog.php`, блок
  `'language/*/after'`) — повторно вантажить той самий файл кодом поточної мови (`config_language`) і, якщо є
  `extension`, шляхом розширення. `array_merge` перекриває ключі.
- `system/library/language.php:71-77` — відсутній ключ → повертається сам ключ.

**Наслідок [з коду]:** спершу `en-gb`, потім перекриття поточною мовою. Немає теки `pl`, немає файлу чи ключа →
рядок англійською. Те саме для модулів і тем-розширень: їхні каталоги вантажаться тим самим `load()` з тим самим
порядком (спершу `en-gb`). Тобто вітрина польської мови без пакета в OC — **польські дані + англійський
інтерфейс**: той самий «змішаний» стан, що в нашій §19, лише fallback — англійська, а не основна мова.

### 1.5 Мова листів замовлення

`catalog/controller/mail/order.php:110-123` (новий), `:389-402` (зміна): код мови — з `order.language_id`
(fallback — `config_language`), далі `load->language('default', 'mail', $code)` і `('mail/order_add', 'mail',
$code)`. Тут `$code` непорожній, тож база `en-gb` **не** вантажиться: для мови без пакета листа ключі
лишаються сирими (`mail_text_subject`) [з коду, не прогнано]. Статус замовлення в листі — з
`order_status` мовою замовлення (`:165`). Лист-сповіщення магазину (`:501-506`) — без явного коду, статус —
мовою `config_language_id` [з коду].

### 1.6 Як постачається мовний пакет

- Ядро кладе в репо `catalog/language/{en-gb,fr-fr}`, `admin/language/{en-gb,es-es,fr-fr}` (GitHub API, `master`)
  — пакети ядра неповні за набором мов.
- Тип розширення `language`: `admin/controller/extension/language.php:80-134` — встановлення вимагає
  `extension/<ext>/admin/controller/language/<code>.php` (`:101`), реєструє шляхи (`:120-131`) і кличе його
  `install` (`:134`).
- Реальний приклад — `ruOpenCart/opencart-language-russian-4`, `ocn_language_russian.ocmod/admin/controller/
  language/russian.php`: `install()` (`:985-1006`) **сам створює рядок `language`** (`code ru-ru`,
  `extension ocn_language_russian`, `status 1`), `uninstall()` (`:1013-1021`) його видаляє, а окремий крок
  (`:660`) перекладає системні довідники (статуси замовлень, країни, зони, групи покупців, …).
- Отже зв'язок «мова ⇔ пакет» в OC — **конвенція екосистеми** (пакет створює мову), а не інваріант ядра.
  Ядро мову без пакета пропускає мовчки (1.2). Модулі третіх сторін часто не мають каталогу мови й лишаються
  англійськими (issue opencart#13833) [не підтверджено кодом].

### 1.7 OpenCart 3.x (гілка `3.0.x.x`, коміт `f8606857eda493676a10c80f42ce66f8f5d8a47a`)

Файли — від `upload/`.

- **Таблиця** `install/opencart.sql:1749-1760` — `oc_language`: `language_id`, `name`, `code` varchar(5),
  `locale`, `image`, `directory` varchar(32), `sort_order`, `status`. Колонка `directory` в 3.x — залишок:
  форма й `addLanguage` її не пишуть (`admin/model/localisation/language.php:3-4` — лише `name, code, locale,
  sort_order, status`), а завантажувач бере теку за `code` (нижче).
- **Мова без пакета дозволена.** `admin/controller/localisation/language.php:370-399` (`validateForm`) — лише
  довжина `name`, `code`, непорожній `locale`, унікальність `code`. Теки не перевіряє, як і OC4.
  `addLanguage` так само копіює описи з `config_language_id` (`model…/language.php:11-15…`).
- **Fallback поключовий на `en-gb`, жорстко зашитий у клас:** `system/library/language.php:14`
  (`private $default = 'en-gb'`) і `:60-76` — `load()` ЗАВЖДИ спершу вантажить `en-gb/<file>.php`, потім
  `<directory>/<file>.php`, `array_merge`; файлу немає — пропуск без помилки. Відсутній ключ → сам ключ (`:35-37`).
  `system/config/default.php:10-11` — `language_directory`/`language_autoload` = `en-gb`.
- **Мова вітрини:** `catalog/controller/startup/startup.php:61-129` — сесія → cookie → **`Accept-Language`
  браузера** (за `locale`, потім за кодом) → `config_language`; далі `new Language($code)` (`:123-126`), тобто
  тека = код. Список — `catalog/model/localisation/language.php:15` (`status = '1'`). SEO-URL з мовним
  префіксом у ядрі 3.x немає [з коду startup; модулі SEO — не перевірено].
- **Мова адмінки:** `admin/controller/startup/startup.php:26-36` — ОДНЕ налаштування магазину
  `config_admin_language`, без cookie й без профілю: усі адміни бачать одну мову.
- **Листи:** `catalog/controller/mail/order.php:59-62` — `new Language($order_info['language_code'])`,
  `load(code)`, `load('mail/order_add')` → завдяки `$default` листи мовою без пакета йдуть **англійською**
  (а не сирими ключами, як у OC4 — див. 1.5).
- **Постачання пакетів:** у ядрі лише `en-gb`; пакет — набір файлів, які власник кладе в
  `catalog/language/<code>` і `admin/language/<code>` (вручну чи через `.ocmod.zip`-інсталятор), а мову додає
  руками в «Локалізація → Мови» [не підтверджено кодом інсталятора; загальновідомий шлях OC3].

### 1.8 OC3 проти OC4 — відмінності

| Аспект | OC 3.x | OC 4.x |
|---|---|---|
| Колонки мови | `code`, `locale`, `image`, `directory` (мертва) | `code`, `locale`, `extension` |
| Звідки каталоги | `catalog|admin/language/<code>/` у ядрі (файли кладуть поверх) | ядро або language-extension (`extension/<ext>/…/language/`) |
| Хто створює рядок мови | власник руками | зазвичай `install()` розширення (1.6) |
| Перевірка пакета при додаванні | немає | немає |
| Fallback рядка | `en-gb`, зашито в клас (`$default`) | `en-gb` з `system/config/default.php` (`language_code`), той самий порядок «спершу en-gb» |
| Листи мовою без пакета | англійською (fallback працює) | сирі ключі (явний `$code` обходить базу) [з коду] |
| Мова вітрини | сесія/cookie/`Accept-Language`/налаштування | `?language=`/URL-префікс/налаштування |
| Мова адмінки | одна на магазин (`config_admin_language`) | налаштування + cookie браузера |

### 1.9 Підсумок для сумніву власника

| Твердження власника | Факт OC 3 і 4 |
|---|---|
| «Є перелік мов, якими можна відображати адмінку, і цими ж мовами створюють дані» | **Так** в обох: одна таблиця `language` на обидві ролі (1.1, 1.3, 1.7) |
| Мова без пакета інтерфейсу неможлива | **Ні** в обох: ядро дозволяє, показує `en-gb` поключово (1.2, 1.4, 1.7); в OC4 мову зазвичай створює сам пакет (1.6) |
| Fallback | На `en-gb` (константа), не на мову магазину |
| Мова адмінки | OC3 — одна на магазин; OC4 — налаштування + cookie; ніде не профіль користувача |

## 3. Що вирішували ми і чому

1. **Журнал рішень** `docs/superpowers/specs/2026-10-14-content-multilingual-design.md`:
   - рішення 1 (`:13`): «Мультимовність ДАНИХ, а не інтерфейсу»;
   - розвилка Р-ML-17 (`:155-157`) прямо назвала проблему: магазин із польським контентом отримає змішану
     сторінку. Відповідь (`:258-262`): пакети постачає платформа, «будь-хто може додати мову» через репозиторій.
     Тобто намір був **прибрати змішану сторінку пакетами**, а не узаконити її;
   - рішення 12 (`:410`, друга сесія 2026-10-14): «Фолбек інтерфейсу — основна мова магазину, **а не англійська**.
     Пакет основної мови обов'язковий». Питання стояло «на що fallback», а не «чи дозволяти мову без пакета».
2. **Аудит Codex** `research/…/88-codex-audit.md:49, :99` (major): `Locale` визначено через пакет, а контент
   дозволено без пакета → «розділити код мови контенту та доступність каталогів». Звідси §18.4 «код мови контенту
   ≠ наявність пакета» і далі §19.
3. **Чому так (доповнення архітектора, звірено з кодом):** передумова — постачання.
   - пакети є лише `uk`, `en` (`packages/simplycms/src/i18n/packs/index.ts:10-13`, реєстр закритий на збірці);
   - пакет додається лише через репозиторій платформи; npm-пакетів рівно 5 (AGENTS.md);
   - магазин, якому потрібна `pl`, сам пакета зробити не міг; розведення осей дало польські дані зараз, інтерфейс —
     коли з'явиться пакет.
   - Друга причина технічна (§19.1): `useLocale()` подавав мову інтерфейсу в ключі даних. Її закривають брендовані
     типи (`ContentLocale`/`UiLocale`) **за будь-якої моделі**.
4. **Зв'язок «мова магазину ⇔ пакет» як правило публікації ніколи не розглядався явно.** Близькі місця:
   майстер-план Р7 (`plans/2026-10-15-multilingual-wave-master.md:39, :296`) вимагає пакет лише для ОСНОВНОЇ мови;
   `admin-server/impl/languages/view.ts:38` уже віддає `hasPack` у список мов адмінки, але
   `languages/status.ts:78-80` перевіряє перед `published` лише повноту даних, не пакет.

## 4. Вплив на SimplyCMS моделі «опублікувати можна лише мову з пакетом; на вітрині UI = контент»

### 4.1 T1–T4 (зроблено)

| Що | Доля |
|---|---|
| `ContentLocale`, `LocaleSet`, `useContentLocale`, ключі кешу лише на `ContentLocale` (T1, `contracts/content-locale.ts`, `runtime/content-locale.ts`) | **лишається без змін**: адмінка однаково має дві осі (мова інтерфейсу адміна ≠ мова форми), листи користувачу — теж |
| `UiLocale`, `toUiLocale`, `lookupMessage` (T2) | лишається |
| `resolveUiLocale` / `resolveUiLocalePair` (`i18n/ui-locale.ts:43-68`) | **спрощується**: на вітрині — строгий `toUiLocale(content)` (точний код, можливо + базова мова `pt-BR→pt`) і гучна помилка при порушенні. Але міст повністю не зникає: потрібен для історичних даних (лист за старим замовленням мовою, яку потім вимкнули/чий локальний пакет прибрали; `profiles.locale` такої мови) — там fallback на основну лишається, тільки в одному місці (T6) |
| `fallback` у `UiLocalePair` (провайдер несе дві мови) | для **ядра** на вітрині стає зайвим; для тем і плагінів — потрібен, якщо їхній fallback рядка лишається (див. 4.4) |
| Ліниві частини `base/admin/mail`, реєстр `loadUiCatalog`, прогрів, гейти складу графа (T3–T4) | **без змін** |
| `LANGUAGE_PACKS` — закритий `Map` ядра (`packs/index.ts:10`) | **змінюється**, якщо джерело (б): реєстр = пакети ядра + пакети магазину (4.5) |
| Тест І41 «вітрина `pl` без пакета: дані `pl`, інтерфейс основною» (майстер `:346`), SSR-гейт «мова без пакета» (§19.5) | **переписується**: стан «published без пакета» стає неможливим; натомість тест відмови публікації і тест «draft `pl` → 404» |
| `storefront-routes/locale/root-data.ts:42`, `useRequestTranslator.ts:31`, `routes/admin/admin.tsx:66` | точки заміни моста на строгий вибір (вітрина); адмінка — без змін |
| `languages/status.ts:78` | **нова перевірка**: `published` вимагає пакет із частинами `base` і `mail` |

### 4.2 T5–T8 (план)

- **T5 (`profiles.ui_locale`)** — без змін по суті. Уточнення: список вибору — пакети з частиною `admin`
  (якщо локальним пакетам дозволено її не мати — `ui.admin` стає опційним у `LanguagePack`, `types.ts:161`).
- **T6 (листи)** — гіпотеза архітектора **підтверджена частково**:
  - `order-customer`: мова листа = `orders.locale` = мова інтерфейсу, коли мова опублікована з пакетом —
    так; але для замовлень мовою, що згодом втратила пакет (локальний пакет видалено), потрібен fallback на основну;
  - `user`: `toUiLocale(ui_locale) ?? toUiLocale(profiles.locale) ?? primary` — та сама форма, що в плані;
  - `store`, `invitee` — основна, без змін;
  - **нове:** CLI `owner:invite` (`template/package.json.tpl:14`, `node scripts/owner-invite.mjs`) працює поза
    Vite. Якщо основна мова магазину — локальний пакет (`pl`), CLI мусить його бачити: потрібен шлях
    завантаження пакета поза збіркою вітрини (JSON-каталоги або виклик через зібраний сервер). Це ризик
    варіанту (б), не наявний у плані.
  - форматування (§19.8) на вітрині стає тривіальним (UI = контент).
- **T7 (множина)** — без змін; для локальних пакетів тест категорій CLDR має їхати в магазин (див. 4.5).
- **T8 (канон)** — переписати §4/§18.4/§19.4/§19.12 п.5 у спеці, І41/І42 у майстрі, `i18n.md`.
- **Нова задача** (якщо (б)): реєстр пакетів магазину + `simplycms language add <code>` + скіл перекладу +
  перевірки в `doctor` і `bootstrapStore`.

### 4.3 Адмінка: чи потрібні дві ролі мови — ТАК

- Мова інтерфейсу адміна (кнопки, меню) і мова даних, яку він редагує (вкладка форми, §12) — різні речі
  в КОЖНІЙ платформі, навіть в OC (вкладки мов у формах). Об'єднати їх неможливо: адмін редагує переклад `en`,
  не перемикаючи свою адмінку на англійську.
- **Чи можуть набори бути різними — так, і це краще за OC:**
  - «мови, якими редагують дані» = рядки `languages` (усі, включно з `draft`);
  - «мови інтерфейсу адмінки» = пакети з частиною `admin`.
  Приклад з §19.6 (англомовний адмін в українському магазині без мови `en`) в OC неможливий без додавання `en`
  мовою магазину. Shopify/Magento/WordPress — як ми (профіль користувача). `profiles.ui_locale` без FK лишається.
- Строгість «UI = контент» стосується ЛИШЕ вітрини.

### 4.4 Нові продуктові питання

1. **Звідки пакет** для мови, якої платформа не постачає (головне, див. 5 і питання 1).
2. **`draft` без пакета** — дозволено (перекладачі заповнюють дані, вітрина 404) — узгоджено з OC (мову-без-пакета
   OC також не блокує) і з нашою машиною станів §18.4. Публікація — з перевіркою пакета.
3. **Теми й плагіни без каталогу мови.** OC: поключово `en-gb`. У нас зараз — рядок → мова основної (§19.4).
   Якщо ядро на вітрині строго `pl`, а тема без `pl` падає на основну `uk`, сторінка знову змішана (менше, але
   саме те, на що скаржиться власник). Варіанти — питання 3.
4. **Розсинхрон локального пакета після оновлення ядра.** Нові ключі ядра: тип `satisfies Record<BaseKey,string>`
   зламає typecheck магазину (чесно, у дусі §19.12 п.1 «один повний каталог, без fallback ядра») — тоді скіл
   `simplycms-update` мусить мати крок «доперекласти нові ключі». Альтернатива — поключовий fallback для
   локальних пакетів, що суперечить §19.12 п.1. Питання 4.
5. **Пакет зник** (видалено локальний пакет, мова `published`) — що робить вітрина. Питання 5.
6. **`content`-частина пакета** (`slugify`, `tokenize`): для публікації НЕ обов'язкова — без неї діє загальна
   транслітерація (§18.4, `packs/index.ts:29-33`). Але переклади системних довідників (статуси замовлень тощо,
   майстер §3.6 `:295`) з пакета мають дозаповнюватись і тоді, коли пакет з'явився ПІСЛЯ мови — так робить
   розширення OC (`russian.php:660`). Потрібна операція «дозаповнити довідники з пакета».

### 4.5 Технічна перевірка джерела (б) — локальний пакет у магазині

| Аспект | Висновок |
|---|---|
| Підключення до `LANGUAGE_PACKS` | Прецедент є: теми й плагіни магазину оголошуються в `simplycms.config.ts` лінивим `import()` через аліаси `@themes`/`@plugins` (`template/simplycms.config.ts`), сервер дізнається про них `declareBuiltThemes(...)` (`template/src/server.ts:28`), клієнт — `theme-registry.ts`. Аналог: `languages: { pl: () => import('@languages/pl') }` або синхронний опис `{ code, name, ui: { base: () => import(...) } }`. 🔴 `resolveUiLocale`/`toUiLocale` читають реєстр синхронно, тож метадані пакета (код, назва, лоадери частин) мусять бути зареєстровані ДО першого запиту і на сервері (`server.ts`), і на клієнті (`client.tsx`) — синхронний об'єкт із лінивими лоадерами, а не лінивий пакет цілком |
| Ліниві `import()` частин | Працює як у тем: Vite магазину сам розріже `base/admin/mail` на чанки; гейт складу графа (Task 4) треба поширити на пакети магазину (знаходиться в пілоті, не в монорепо) |
| Gate C | Каталоги — чисті дані, клієнтобезпечні; ризику server-only імпорту немає, якщо пакет не тягне `slugify` з server-only модулів |
| typecheck шаблону | Типи `BaseKey`, `AdminKey`, `MailKey`, `LanguagePack` уже публічні (`i18n/index.ts`); `satisfies Record<BaseKey,string>` дає повноту ключів компілятором — `typecheck:template` ловить пропуск/зайвий ключ |
| Парність і категорії множини | Тести парності ядра (`tests/i18n-catalog-parity.test.ts`) у магазин не їдуть; категорії CLDR (`Intl.PluralRules`) — лише рантайм. Потрібна перевірка в магазині: `doctor` або `simplycms language check` |
| CLI | `owner:invite` — чистий node без Vite (4.2): пакет має бути доступний і там |
| Відповідність AGENTS.md | Узгоджено з «магазин — мінімумом кроків, далі агент» і зі скілами, що їдуть у пакеті; не порушує «рівно 5 npm-пакетів» |
| Внесок назад | Добрий локальний пакет можна запропонувати PR у платформу — тоді він стає пакетом ядра (а) |

(в) npm-пакет мови — суперечить «рівно 5 пакетів», лише окремим рішенням власника; плюс — маркетплейс
(спека маркетплейсу) як канал, аналог language extension OC.

## 5. Варіанти

### A. «OC-строго + локальний пакет» (рекомендація архітектора)

`published` вимагає пакет (`base`+`mail`); джерело — пакет ядра або локальний пакет магазину (б); вітрина
UI = контент; адмінка — окрема `ui_locale`; теми/плагіни — fallback рядка (див. питання 3).
- Плюси: знімає «змішану сторінку» на рівні ядра; міст на вітрині зникає; `<html lang>`, форматування і листи
  стають однозначними; дає реальний шлях до `pl`/`de` без релізу платформи; відповідає принципу «агент веде».
- Мінуси: нова робота (реєстр пакетів магазину, команда, скіл, `doctor`, CLI); оновлення ядра може вимагати
  доперекладу (typecheck); якість перекладу локального пакета — на агенті магазину.
- Ціна переробки зробленого: мала — T1–T4 лишаються; переписати І41/SSR-тест «мова без пакета», вітринні виклики
  моста (3 місця), додати перевірку в `status.ts`. Нова задача (б) — середня (≈1 задача плану).

### B. Чинна §19 + дешевий пакет

Лишити дозвіл `published` без пакета (fallback на основну), але додати (б), щоб пакет був досяжний, і попередження
в адмінці при публікації без пакета.
- Плюси: нуль переробки T1–T4; гнучкість (мову можна відкрити до перекладу інтерфейсу).
- Мінуси: стан, яким незадоволений власник, лишається допустимим; міст і `fallback` у провайдері живуть далі.
- Ціна: лише (б).

### C. OC-буквально

Один реєстр мов на дані й адмінку, без перевірки пакета, поключовий fallback на `en`.
- Мінуси: суперечить рішенню 12 (fallback — основна, не англійська) і §19.12 п.1 (один повний каталог ядра);
  втрачає «англомовний адмін в українському магазині»; ніякої переваги перед A, крім схожості з OC.
- Не рекомендую.

### Залежність від вибору фреймворка i18n

- Рекомендація `research-i18n-libs.md` §4 стоїть на вимогах (1) осі мови, (2) каталоги тем/плагінів без
  компіляції в магазині, (6) типізація трьох рівнів. За варіанту A вимога (1) **слабшає** на вітрині (одна мова на
  запит), але лишається в адмінці.
- (б) додає нову вимогу: **формат каталогу, який агент магазину перекладає і магазин перевіряє** (TS/JSON із
  типом ключів ядра). Lingui/Paraglide вимагають компіляції — у магазині вона є (Vite), тож заперечення (2)
  для ЛОКАЛЬНИХ пакетів не діє, але для пакетів тем/плагінів з npm — діє далі.
- Висновок: стратегію мов варто ухвалити першою (як і пропонує власник); вона не скасовує рекомендацію «власний
  механізм», але змінює критерії спайків use-intl/Lingui: додати сценарій «пакет мови в магазині, повнота
  ключів після оновлення ядра».

## 6. Питання власнику (продуктові)

1. ~~Звідки береться пакет~~ — **ВИРІШЕНО власником 2026-11-04:** мову, якої бракує, додають PR у репозиторій
   платформи (а); механізм постачання ззовні (npm чи інший) — пізніше. Що закласти зараз — §8.
2. **Чи можна опублікувати мову без пакета інтерфейсу?**
   (а) ні — публікація лише з пакетом (варіант A);
   (б) так, з попередженням, інтерфейс основною (чинна §19, варіант B).
3. **Тема чи плагін не мають рядків мови вітрини (`pl`).**
   (а) рядок теми/плагіна — основною мовою магазину (як зараз);
   (б) рядок — англійською (як OC), якщо в теми є `en`, інакше основною;
   (в) публікацію мови блокує неповний каталог активної теми й плагінів;
   (г) лише попередження на сторінці мов + `doctor`.
4. **Оновлення платформи додало нові рядки, а локальний пакет їх не має.**
   (а) збірка магазину падає, скіл оновлення перекладає нові рядки до деплою;
   (б) збірка проходить, бракуючі рядки — англійською/основною, `doctor` попереджає.
5. **Опублікована мова втратила пакет (видалили локальний пакет).**
   (а) магазин не стартує з поясненням;
   (б) стартує, мова автоматично стає недоступною (404), `doctor` — помилка;
   (в) стартує, мова працює з інтерфейсом основною + гучний лог.
6. **Мова інтерфейсу адмінки.**
   (а) окремий список (пакети з частиною `admin`), вибір у профілі — як зараз (§19.6);
   (б) як в OC — лише з мов магазину.
   Рекомендую (а): ролі різні в усіх платформах, крім OC.
7. **Чи обов'язкова частина `admin` у локальному пакеті?**
   (а) ні — достатньо `base`+`mail` для публікації вітрини;
   (б) так — пакет завжди повний.

## 8. Постачання пакетів ззовні: що закласти зараз, а що в беклог

Рішення власника: зараз — лише PR у платформу; механізм постачання ззовні (npm чи інший) — пізніше. Питання:
закладати щось зараз чи досить беклогу. Передумова архітектора: «rc.1 заморожує baseline БД, а не API; пакет живе
лише в коді; механізм постачання — це minor-додавання; зараз закласти (1) публічний тип `LanguagePack`, не
прив'язаний до місця, (2) читання реєстру через одну функцію».

### 8.1 Перевірка передумови

| Пункт | Звірка | Вердикт |

### 8.2 Що справді стане зламом після 1.0, якщо не закласти зараз

Схема БД тут ні до чого — ламається лише **публічний API коду** `simplycms/i18n` (semver з 1.0: злам коду
магазину, тем чи плагінів → мажорна, AGENTS.md «Принципи»):

1. **`export const LANGUAGE_PACKS: ReadonlyMap<string, LanguagePack>`** (`i18n/index.ts:9`). Після 1.0 це
   контракт: форма «`Map` з усім одразу». Реєстрація ззовні вимагатиме або мутувати експортовану константу
   (`Map` живий, тож технічно можливо, але читачі, що кешували `[...values()]`, побачать застарілий список), або
   замінити її функцією — мажорна. **Закласти зараз:** прибрати константу з публічного барелю; читати через
   функції — `toUiLocale`/`resolveUiLocale`/`hasUiPack` (вже є) і одна нова для списку (`listUiPacks()`:
   код + назва + наявні частини) для `UiLocaleSelect` T5. Ціна зараз — ≈3 файли; потім — мажорна.
2. **Форма `LanguagePack`** (`i18n/types.ts:158-168`): `ui: Record<'base'|'admin'|'mail', …>` — усі три частини
   обов'язкові. Якщо майбутній пакет ззовні матиме лише `base`+`mail`, зробити `admin` опційним — злам для
   тих, хто читає `pack.ui.admin` без перевірки. **Вирішити зараз** (питання 7 §6): обов'язкова чи опційна.
   Якщо читачі пакета — лише функції `i18n` (п.1), то й ця зміна стає внутрішньою, і рішення можна відкласти.
3. **Контракт повноти ключів.** `BaseKey`/`AdminKey`/`MailKey` виводяться з каталогу `uk` (`types.ts:141-144`),
   а §19.12 п.1 каже «каталог ядра повний, fallback ядра — лише на рівні вибору мови». Для пакетів ядра це
   тримає тест парності. Для зовнішнього пакета кожен новий рядок ядра (minor) ламає його `satisfies Record<…>`,
   тобто або кожен minor ядра — мажорний для пакетів, або для зовнішніх пакетів вводять поключовий fallback
   (внутрішня зміна `lookupMessage`, не злам). **Не закладати зараз** — це політика механізму постачання, яка
   додається без зламу; записати в беклог як першу розвилку механізму.
4. **Реєстрація до першого використання.** `toUiLocale`/`resolveUiLocale` синхронні над закритим набором.
   Майбутня `registerLanguagePack()` (до старту сервера й клієнта, як `declareBuiltThemes`) — адитивна.
   **Не закладати** — лише беклог.

### 8.3 Рекомендація

- **Передумову архітектора підтверджено** — у БД, в OpenAPI, у шаблоні й CLI нічого не залежить від джерела
  пакета; механізм постачання — minor.
- **Закласти зараз (у межах блоку, дешево):**
  (1) `LanguagePack` — публічний `export type`, без прив'язки до місця (вже так, `i18n/index.ts` експортує тип);
  (2) прибрати **константу** `LANGUAGE_PACKS` з публічного барелю й дати одну функцію списку для `UiLocaleSelect`
  (T5); перевірка «`published` лише з пакетом» — через `hasUiPack` (уже функція);
  (3) явно вирішити обов'язковість `ui.admin` — або сховати форму пакета за функціями (п.1), і тоді відкласти.
- **У беклог** (`docs/tasks/multilingual-wave-backlog.md`, адресат «після rc.1»): реєстрація пакетів ззовні
  (npm/інше), контракт повноти ключів зовнішнього пакета і поключовий fallback, доступність пакета для CLI поза
  Vite, перевірка парності/категорій множини в магазині, дозаповнення системних довідників при появі пакета.
- Якщо НЕ зробити п.(2) до 1.0: перетворення константи на реєстр — мажорна версія лише через одну публічну
  константу; магазинів це торкнеться тільки якщо тема/плагін її імпортували (референсні — ні, перевірено grep
  по шаблону). Тобто злам малий, але неминучий і безпідставний — дешевше прибрати зараз.

Упевненість: **≈85 %** у висновку «БД і API не блокують»; ≈70 % в оцінці ризику п.3 (залежить від того, яким
буде механізм).
