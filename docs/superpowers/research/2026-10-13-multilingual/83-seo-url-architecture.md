# 83. Архітектура SEO-URL багатомовного магазину (SimplyCMS)

Дата дослідження: 2026-10-14. Дослідник: субагент. Репозиторії не змінювались; поточний код SimplyCMS (роути, схема slug) у цьому дослідженні НЕ аналізувався — лише зовнішні джерела.

Умовні позначки: **[Факт-Google]** — офіційна документація Google; **[Код]** — прочитано у вихідному коді (raw.githubusercontent.com); **[Думка]** — окремі SEO-фахівці/вендори/форуми; **[Висновок]** — моя інференція, не джерело.

---

## 0. Підсумок за 10 рядків

1. Твердження «прив'язка SEO-URL до мови в OpenCart 3 — найгірше рішення платформи» **дослівно в жодному джерелі не знайдено**. Знайдено інше, точніше: вада не в тому, що keyword зберігається по мовах (так роблять усі зрілі платформи), а в тому, що **мова запиту НЕ виводиться з URL** (сесія/cookie/Accept-Language), а розбір URL ігнорує `language_id`. Це вада архітектури, а не реалізації.
2. Google прямо: окремі URL на кожну мову; cookie/параметри/авто-редірект за мовою — не рекомендовано; локалізовані слова в URL дозволені; non-ASCII — percent-encode; слова, а не довгі ID, бажані.
3. Усі порівнювані платформи (Shopify, Shopware, Magento, PrestaShop, Saleor, Sylius) мають мову в URL і per-language slug; відрізняються id в URL та історією редіректів.
4. Рекомендація: мова з URL-префікса (default без префікса), per-language slug з fallback, окремий незмінний id сутності, **slug не змінюється автоматично при перейменуванні (1С)**, таблиця історії slug з 301 на актуальну адресу, транслітерація в латиницю, hreflang/canonical/sitemap лише для реально існуючих мовних версій.

### 1.3. «Справжня архітектурна вада» vs «вада реалізації»

| Клас | Що | Чому |
|------|----|------|
| **Архітектурна** | Мова запиту не є функцією URL (сесія/cookie/Accept-Language) | Одна адреса → різний контент за станом клієнта; краулер бачить одну мову. Суперечить Google (§2). Виправлення потребує зміни контракту маршрутизації, а не латки |
| **Архітектурна** | Розбір URL не знає мови (`WHERE keyword AND store_id`), генерація знає | Асиметрія: будь-який keyword будь-якої мови резолвиться в сесійну мову → потенційні дублі «в усіх комбінаціях» [Висновок] |
| **Архітектурна (слабше)** | Унікальність keyword на рівні «store», а не «store+language»; нема унікального індексу в БД | Блокує однаковий slug у різних мовах (законний випадок для латинських назв/брендів) і не гарантує цілісності |
| **Реалізація** | Redirect перемикача до зміни мови; нема canonical/hreflang; нема 301 з `index.php?route` | Лагодиться модулями (SEO Pro, ocStore), хоч і з вартістю підтримки |
| **Реалізація / продуктова** | Нема історії slug і 301 при перейменуванні | Властиво більшості «простих» ядер; Magento/Shopware мають |
| **Не вада** | Сам факт `language_id` у `seo_url` | Shopware, Magento (store view), Saleor, Sylius, commercetools — теж per-language slug |

Що змінилося в OC4: таблиця стала `key/value` + `sort_order` (шлях можна складати з кількох сегментів), мова — GET-параметр. Архітектурний недолік №1-2 лишився [Код]. Як у OC4 роблять префікси мов — це сторонні модулі (huntbee, stsn-dev, opencartbot): «default без префікса, інші `/fr/…`» — **[Думка вендорів]**, не ядро.

**Чесна оцінка твердження власника:** сформульованого «найгірше рішення» я не знайшов; найближче — критика «мова не в URL / однакові slug заборонені». Можливо, фахівці мали на увазі саме це. Рекомендую уточнити в них, що саме вони мали на увазі.

## 2. Офіційні рекомендації Google та інших

| Тема | Твердження | Тип, джерело, дата |
|------|-----------|--------------------|
| Окремі URL | «Google recommends using different URLs for each language version of a page»; не покладатися на cookie/налаштування браузера; Googlebot зазвичай краулить із США без Accept-Language | [Факт-Google] https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites — оновлено 2025-12-10 |
| Структури | ccTLD, піддомен, підкаталог (`/de/`) — перелік плюсів/мінусів без ранжування; URL-параметри (`?loc=de`) — «Not recommended» | там само |
| Авто-редірект | Не перенаправляти за «уявною» мовою користувача; давати посилання для вибору | там само |
| Локалізовані слова | «It's fine to use localized words in the URL»; UTF-8 і правильне екранування | там само |
| Часткові переклади | Лише шаблон перекладено, основний текст ні — погано; мова сторінки визначається за видимим контентом, не за `lang`/URL | там само |
| hreflang | Взаємні посилання обов'язкові («If two pages don't both point to each other, the tags will be ignored»); посилання на себе; `x-default`; HTML/HTTP-заголовок/sitemap еквівалентні | [Факт-Google] https://developers.google.com/search/docs/specialty/international/localized-versions — оновлено 2026-09-21 |
| Дублі | «Localized versions of a page are only considered duplicates if the main content of the page remains untranslated» | там само |
| URL-структура | Non-ASCII — percent-encode; «use readable words rather than long ID numbers»; «Use words in your audience's language in the URL (and, if applicable, transliterated words)»; дефіси замість підкреслень | [Факт-Google] https://developers.google.com/search/docs/crawling-indexing/url-structure — оновлено 2025-12-10 |
| 301 | «Keep the redirects for as long as possible», мінімум ~1 рік; без ланцюжків — «redirecting to the final destination directly»; ланцюжок ≤3 бажано, <5 завжди; Googlebot проходить до 10 хопів | [Факт-Google] https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes — оновлено 2026-08-20 (це сторінка про переїзд сайту; для окремих товарів — застосування за аналогією) |
| Фасети | robots.txt disallow; canonical на нефільтровану сторінку лише поступово зменшує краулінг; `nofollow` на всі посилання; стандартний роздільник `&` | [Факт-Google] https://developers.google.com/search/docs/crawling-indexing/crawling-managing-faceted-navigation — оновлено 2025-12-18 |
| x-default для сайтів, що підлаштовуються за мовою/локацією | блог Google 2013 | [Факт-Google, старий] https://developers.google.com/search/blog/2013/04/x-default-hreflang-for-international-pages |
| Кирилиця | Mueller: нелатинські URL допустимі, escaped/Unicode еквівалентні, умова — валідні й унікальні | [Заява Google-представника, у переказі] https://searchengineland.com/google-using-non-english-urls-non-english-websites-fine-294758 — сторінка віддала 403, дату не підтверджено; переказ через пошуковик |
| Ключове слово в URL | Mueller: «very small ranking factor», не варто перебудовувати сайт заради цього | [Заява у переказі Search Laboratory, дата невідома, Google+ Hangout] https://www.searchlaboratory.com/?p=2862 — **слабке джерело, не верифіковано** |
| Geo-IP редірект | Mueller: загалом не рекомендує; якщо `/` редіректить, це має бути `x-default` | [Переказ] searchenginejournal.com (стаття 482113) — не відкривав повністю, лише з пошуку |

**Не знайдено:** прямої заяви Google, що *переклад slug* підвищує ранжування. Єдине є «fine to use localized words». Дослівної теми «translate content and URLs» на сторінці Google немає.

**Bing:** офіційну сторінку не знайдено; сторонні джерела розходяться (hreflang слабкий сигнал vs. рекомендований; Content-Language/`lang` як основний сигнал). Висновок: ставити `<html lang>` і `Content-Language`, узгоджені з hreflang. [Думка]
**Yandex:** офіційна довідка (https://yandex.ru/support/webmaster/ru/yandex-indexing/locale-pages) за переказом пошуковика: підтримується `hreflang` з `x-default` (рекомендація — коли мова визначається за Accept-Language/IP чи вибором); sitemap для мовних версій більше не підтримується. Дату сторінки не перевірено. Окремий Webmaster-сайт на кожну мовну версію — лише думка користувачів Хабру.

## 4. Варіанти для SimplyCMS і компроміси

### 4.1. Мова в URL

| Варіант | Плюси | Мінуси |
|---------|-------|--------|
| A. Основна мова без префікса, решта `/en/…` | Нуль зміни для UA-магазину, чисті URL основної мови, норма PrestaShop/Shopify/OC-модулів | Зміна «основної» мови потім = масовий 301; `/uk/x` треба 301→`/x`, щоб уникнути дубля |
| B. Усі мови з префіксом (`/uk/…`, `/en/…`) | Симетрія, зміна default безболісна, простіше правила | `/` потребує вибору (редірект або мовна сторінка = `x-default`); для UA-ринку менш звично |
| C. Окремі домени/піддомени | Чітке геотаргетування | Інфраструктура, SSL, окремі авторитети; слабо підходить багатьом малим магазинам |
| D. Параметр/cookie | — | Google: «Not recommended»; OC-антипаттерн |

Рекомендація: **A** з політикою «префікс = код мови у БД, `/uk/…` 301 на канон». Впевненість середня-висока (~75%). Варіант B — обґрунтована альтернатива, якщо власник очікує зміну основної мови.

### 4.2. Slug

| Варіант | Оцінка |
|---------|--------|
| Спільний для всіх мов | Просто; кирилична/нелатинська назва в `/en/` виглядатиме чужою; Google не вимагає перекладу slug |
| Перекладений обов'язково | Дороге: кожен товар вимагає перекладу, інакше порожньо |
| **Перекладений опційно з fallback на slug основної мови** | Баланс; відповідає Saleor/Sylius (translation slug + fallback) [Код/Док] |

Рекомендація: **per-language slug, опційний, fallback на slug основної мови** [Висновок]. Унікальність: `(тип сутності-простір, мова, slug)`, а не глобально і не «між мовами». Важливо: резолвінг строго по мові, що прийшла з URL-префікса (на відміну від OC). Впевненість висока (~85%).

### 4.3. Id в URL

| | Чистий slug | `/p/<id>-slug` (PrestaShop) |
|---|---|---|
| Стабільність при перейменуванні | Потребує історії slug + 301 | Автоматична: невірний slug → 301 на канонічний за id |
| Колізії | Потрібна унікальність + суфікси | Немає |
| Google | «readable words rather than long ID numbers» — коротка id не забороняється | |
| UX/брендинг | Чистіше | Менш «чисте» |

Рекомендація: **чистий slug + незмінна сутність id у БД + таблиця історії**, а головне — **автоматичного перегенерування slug від імені товару немає**: slug створюється один раз, 1С-перейменування slug НЕ чіпає; зміна slug — лише явна дія в адмінці (або явне поле в API). Це прибирає найчастіше джерело ланцюжків 301 у сценарії 1С. Впевненість середня (~70%): id-в-URL — нижчий ризик і слід залишити як запасний варіант, якщо власник не захоче вести історію.

### 4.4. Транслітерація vs кирилиця

Google: обидва допустимі, переваги «слова мовою аудиторії (і, якщо доречно, транслітеровані)». Percent-encoded кирилиця в логах/месенджерах/копіюванні стає нечитабельною (`%D0%BA…`) [Висновок]. Рекомендація: **латинська транслітерація** (українська національна 2010, КМУ №55) з ASCII-fold, дефіси, нормалізація до нижнього регістру; кирилиця в slug — не за замовчуванням. Для «ідентичних назв» — суфікс `-2` або короткий хеш id. Впевненість висока щодо технічної безпеки, середня щодо «найкращого для ранжування» (даних про відмінність немає).

### 4.5. Історія адрес і 301

Структура (пропозиція): `slug_history(entity_type, entity_id, language, slug, retired_at)`; поточні slug в окремій таблиці або з прапором. Правила:
1. Зміна slug → старий у історію; запит старого slug → **301 на актуальну адресу відразу (final destination)**, без ланцюжків: при кожній новій зміні перенаправляти всі історичні на поточний (Google: «redirecting to the final destination directly»).
2. Зберігати «якомога довше» (Google: ≥1 рік; краще безстроково).
3. **Конфлікт «стара адреса A = нова адреса B»:** актуальний slug завжди перемагає; історичний запис знімається при захопленні slug іншою сутністю (журнал в адмінці з попередженням). Альтернатива — забороняти захоплення історичного slug без підтвердження. [Висновок]
4. Видалений/деактивований товар: 410/404 або 301 на категорію — рішення власнику (soft-404 ризик при редіректі на нерелевантне; Google-доки в цьому дослідженні не перевірені).
5. Зміна префікса мови / структури — окремий клас 301 (глобальне правило, не рядки).

### 4.6. Неперекладена сторінка

| Варіант | Оцінка |
|---------|--------|
| Показувати мовою джерела на `/en/…` з canonical на основну | Google: сторінка з оригінальним текстом = дубль (https://developers.google.com/search/docs/specialty/international/localized-versions), змішана мова = «poor experience» |
| noindex на неперекладених | Дозволяє бути доступною, але засмічує краул |
| **Мовної версії немає, доки немає перекладу ключових полів** | Чисто для SEO: URL не існує → не потрапляє в hreflang/sitemap |
| 404 | Для прямого входу — жорстко |

Рекомендація [Висновок]: версія мови «існує» лише якщо переведено мінімум (назва, опис — конфігуровано). Для неіснуючої: **302 (не 301) на версію основної мови**, щоб при появі перекладу URL запрацював; перемикач мови не веде туди (веде на еквівалент батьківської категорії або приховує мову). Hreflang і sitemap — лише для існуючих. Впевненість середня (~65%): 302-поведінка Googlebot для таких сторінок не верифікована.

### 4.7. Перемикач мови й автовизначення

- Перемикач — звичайні `<a href>` на **відповідні** адреси (рендер на сервері з карти альтернатив), не форма/JS/cookie. [Факт-Google: окремі URL, посилання на інші версії]
- Автоматичний редірект за Accept-Language/IP — **не робити**: Google прямо «avoid automatically redirecting». Допустимо: ненав'язлива клієнтська пропозиція («Перейти на English?») з запам'ятовуванням вибору в localStorage — пропозиція, не редірект. [Висновок]
- Збереження вибору користувача (cookie) допустимо лише як UI-підказка, не як визначник контенту.

### 4.8. Розділи та фасети

- Категорії: **плоский унікальний slug**, не ієрархічний шлях (`/c/laptops`); ієрархія — для хлібних крихт. Ієрархічні URL ламаються при переміщенні/перейменуванні батька (множинні 301) [Висновок]. OC-проблема «товар у кількох категоріях має кілька шляхів» (Habr) обходиться тим, що URL товару не містить категорії.
- Фасети: значення — **мовонезалежні коди/id у query** (`?color=red&size=m`), стандартний `&` [Факт-Google]; індексація за замовчуванням вимкнена (canonical на нефільтровану, за потреби robots-disallow; `nofollow` лише якщо на всіх посиланнях).
- Прибуткові комбінації (бренд+категорія) — окремі курировані «SEO-посадкові» сторінки з власними slug по мовах, а не відкриті фасети. [Думка/практика, джерела не наведено]
- Пагінація: канонічний self, не canonical на 1-шу (Google: рекомендації не перевірялись у цьому дослідженні; **перевірити**).

|---|------------|-------------------------|
| 1 | Мова з cookie/сесії/Accept-Language замість URL | Контракт маршрутизації; після індексації решта мов невидима; зміна = перенесення всіх адрес (OC3, §1.1) |

| 3 | Параметр `?lang=` | Google: not recommended |

| 7 | hreflang на неіснуючі/нереципрокні версії; відсутній self-reference; неузгоджений canonical | Google ігнорує (§2) |
| 8 | Ланцюжки 301 (A→B→C) та тимчасові 302 для постійних переїздів | Google: напряму на фінальну адресу |
| 9 | Ієрархічні URL категорій; категорія в URL товару | Масові 301 при реорганізації; дублі |
| 10 | Відкриті для індексації фасетні URL; кома/`;` як роздільник | Краул-бюджет, дублі |
| 11 | Змішана мова на сторінці (шаблон мовою A, контент мовою B) | Google: «poor experience» |
| 12 | Зміна «основної» мови/префіксної політики після запуску | Глобальний 301 усього сайту; тому рішення A/B — зараз |

## 6. Рекомендація для SimplyCMS

**Схема.** `/…` — основна мова, `/<код>/…` — інші мови (A); мова виводиться з URL і лише з URL. Тип-сегменти ASCII-нейтральні (`/p/<slug>`, `/c/<slug>` — пропозиція, не перевірено проти поточних роутів SimplyCMS). Slug per-language, опційний з fallback на основну мову, транслітерований, унікальний за `(тип, мова, slug)`, незмінний без явної дії. Окрема таблиця історії slug з 301 на актуальну адресу без ланцюжків. Мовна версія існує, лише коли є переклад мінімального набору полів. Перемикач = посилання на відповідні версії; без авто-редіректу за мовою. На кожній існуючій версії: `<html lang>`, self-canonical, hreflang (reciprocal+self+`x-default` → основна мова), sitemap з `xhtml:link` по існуючих версіях. Фасети — коди в query, не індексуються за замовчуванням.

**Рівень упевненості:** 
- висока (≈85-90%): мова з URL-path; per-language slug з fallback; hreflang лише на існуючі версії; відмова від авто-редіректу; slug не перегенеровується автоматично;
- середня (≈65-75%): default без префікса (A проти B); чистий slug + історія замість id-в-URL; 302 для неперекладених; плоскі категорії;
- низька: розв'язання «стара адреса A = нова B»; 410/404 vs редірект для видалених; пагінація/фасети-посадки (не перевірялось на первинних джерелах).

**Відкриті питання власнику:**
1. Основна мова без префікса (A) чи префікс усюди (B)? Чи можлива зміна основної мови в майбутньому?
2. Чи прийнятні в URL товару id (`/p/123-slug`) заради нульового ризику колізій, чи вимагаємо чисті slug?
3. Хто володіє slug: 1С-імпорт не повинен його змінювати — підтверджуєте політику «slug лише за явною дією»?
4. Мінімальний набір полів для «існуючої» мовної версії (назва? назва+опис?)? Що робити з прямим заходом на неіснуючу версію (302 на основну / 404)?
5. Поведінка для видалених товарів: 404/410 чи 301 на категорію?
6. Чи потрібні окремі домени для мов (кейс клієнтів з ccTLD)?
7. Підтвердіть у SEO-фахівців, що саме вони називають «найгіршим рішенням OC3» — мій аналіз коду це розкладає на пп. 1-3 з §1.3.

**Невизначено/не перевірено:** точні тексти Shopify про редіректи при зміні handle; hreflang у Shopware/Magento/PrestaShop ядра; поведінка Googlebot на 302 для неперекладених; офіційна позиція Bing; поточні роути SimplyCMS (`docs/architecture/rendering-and-routing.md` не читався).
