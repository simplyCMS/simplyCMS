## 0. Підсумок для архітектора (одна сторінка)

1. **Теза «фільтри по id/кодах, мова — лише відображення» підтверджується** `[В]`, з сімома винятками
   (§4.6): вільний текст значень, сортування назв, слаги лендингів, пошук у фасеті, одиниці, видимість
   неперекладеного, лексика атрибутів у FTS. Для enum-фасетів (`select`/`multiselect`/`color`/`boolean`)
   запит фасетів ідентичний при будь-якому N мов; приєднання назв значень у `uk` або `de` додає ≤ ~1 мс
   (в межах шуму).
2. **Фасети на 1k–100k товарів у чистому Postgres вкладаються у бюджет без розширень** `[В]`:
   10k — 6 мс (відфільтрований) / 19 мс (весь каталог без фільтра) на наївному EAV-join; 100k — 15–83 мс
   на EAV, 5–17 мс на `uuid[]`+GIN, 1–7 мс на roaring-бітмапах, 0,09 мс на препорахованих лічильниках
   розділу. Roaring не потрібен для цільового обсягу; препорахунок «розділ без фільтра» — потрібен
   (це перше, що бачить гість і краулер).
3. **Багатомовний FTS у Postgres** `[В]`: документ на (товар, мова) із `tsvector('simple')` масштабується
   лінійно за числом мов (100k товарів: 18 MB GIN на 1 мову, 104 MB на 6), запити — 1–6 мс. Вбудовані
   конфігурації PG17 — лише 28 мов + `simple`, без польської, чеської, української, CJK, тайської
   `[В]`; тож мовний шар у застосунку (за спекою) — правильний вибір. **Прогалина в спеці:** контракт
   `LanguagePack` не має `tokenize()`; для CJK/тайської `simple` не ділить текст на слова `[В]`, а
   `Intl.Segmenter` у Node 24 — ділить `[В]`.
4. **SEO:** Google прямо рекомендує окремі URL на мову, не cookie й не параметр `[П]`; `hreflang` =
   взаємні посилання + самопосилання `[П]`; мови-версії дублікати, лише якщо основний контент однією
   мовою `[П]` — отже неперекладений товар на `/en/` з українським текстом **є дублікатом**.
   Google не дає окремої інструкції для fallback `[П]`; обґрунтована політика — §1.5.
5. **Швидкодія:** у коді зараз HTML вітрини не має `Cache-Control` (крім `private, no-store` для
   залогіненого) `[П: код]`. TanStack Start не має вбудованого ISR — це патерн `Cache-Control` +
   CDN-purge `[П]`. Мова в шляху URL робить ключ кешу правильним без `Vary` (а Cloudflare `Vary`
   ігнорує, крім `accept-encoding`) `[П]`.
6. **Модель даних:** при читанні вітрини з окремої проєкції **жодна** модель зберігання (A/B/D) не дає
   переваги ні для швидкодії, ні для фасетів, ні для FTS — це залежить від реалізації читання `[В]`.
   Модель зберігання важить лише для **цілісності слагів** і **лічильника «переклад існує/свіжий»**
   (§6.3). Найважливіша структурна вимога — **розділити проєкцію на мовно-нейтральну (1 рядок на
   товар: фасети, ціни-індекс, розділи) і мовно-залежну (1 рядок на товар×мову: слаги, тексти,
   статус перекладу, FTS)**.

## 1. Багатомовне SEO e-commerce

### 1.1. Структура URL

| Варіант | Позиція Google `[П]` | Примітка |
|---|---|---|
| підтека `/de/` (gTLD) | «Easy setup, low maintenance on the same host»; мінус — одна локація сервера, важче розділити сайти | дефолт індустрії нижче |
| піддомен `de.example.com` | «Easy setup, allows different server locations»; користувач не зрозуміє, мова це чи країна | потребує DNS/сертифіката на мову |
| ccTLD | найсильніший гео-сигнал, дорого, одна країна | не для «довільної кількості мов» |
| параметр `?loc=de` | **«Not recommended»**; сегментація складна | відкидаємо |

Також `[П]`: «using different URLs for each language version … rather than using cookies or browser
settings»; «It's fine to use localized words in the URL»; UTF-8 і коректне екранування в посиланнях
(<https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites>).

Практика: Shopify — підтеки як найпростіше й за замовчуванням, піддомени «some search engines treat as
separate sites», домени — найсильніший локальний сигнал `[П]`
(<https://help.shopify.com/en/manual/markets/seo>). Saleor storefront: ADR 0001 відхилив
«Cookie / `?lang=` only» («Not shareable, weak SEO, ambiguous cache keys») і піддомени («operational
overhead»), прийняв `/{locale}/{channel}/…` з правилом «Canonical URLs always include locale — no
hidden default» `[П]`
(<https://github.com/saleor/storefront/blob/main/docs/adr/0001-locale-channel-url-routing.md>).

**Розвилка для SimplyCMS (драфт §6 п.3 — основна мова без префікса):** це сумісно з Google, але має ціну
`[Н]`: (а) шлях `/<основна-мова>/…` мусить 301 вести на безпрефіксний (інакше дублікат); (б) зміна
`languages.is_default` після запуску = масова зміна URL. Saleor обрав «префікс завжди». Для магазинів,
що вже мають безпрефіксні URL (пілот), безпрефіксна основна мова зберігає адреси. Рішення продуктове;
технічна вимога — заборонити змінювати `is_default` після публікації без міграції редиректів.

### 1.2. `hreflang`

Джерело: <https://developers.google.com/search/docs/specialty/international/localized-versions> `[П]`.

- Три способи (HTML `<link>`, HTTP-заголовок, sitemap `xhtml:link`) — «equivalent from Google's
  perspective»; поєднання «no benefit».
- «Each language version must list itself as well as all other language versions»; без взаємності
  теги **ігноруються**.
- `x-default` — для випадку, коли жодна мова/регіон не збіглись; приклад — селектор мови або загальна
  сторінка.
- Лише ISO 639-1 + ISO 3166-1 Alpha 2; код країни сам по собі заборонений; голу мову (`de`) можна.
- «Google doesn't use hreflang or the HTML lang attribute to detect the language of a page» — мову
  визначає з видимого контенту.
- Для sitemap: `xhtml:link` діти **не** рахуються у ліміт 50 000 URL.

Bing: джерела розходяться (одні кажуть «слабкий сигнал», інші — що покладається на
`Content-Language`/`lang`) `[Вт]`; офіційної позиції не перевіряв `[Н]`.

**Наслідок для моделі:** кластер hreflang — це множина мов, де переклад **опублікований**, а не всіх
увімкнених. Кластер має обчислюватись з проєкції (§6), різний для кожної сутності.

Спостереження за кодом Saleor storefront `[П: код]`: `buildLocaleHreflangAlternates` ітерує **усі
сконфігуровані** локалі й будує альтернати для кожної, без перевірки, чи є переклад саме цієї сутності
(`src/lib/seo/hreflang.ts`); чи робить це виклик вище — не перевіряв `[Н]`.

### 1.3. Перекладені slug vs спільний

- **Shopify:** handle перекладається в Translate & Adapt для товарів, колекцій, статей, блогів, сторінок;
  sitemap оновлюється, з дефолтних URL створюються редиректи на перекладені; слово-сегмент `products`
  не перекладається; handle не можна кастомізувати «per market»
  (<https://shopify.dev/changelog/resource-url-handles-are-now-translatable>) `[П/Вт]`.
- **Saleor (3.21+):** `ProductTranslation.slug` — nullable; обмеження
  `UniqueConstraint(language_code, slug)` **лише серед рядків перекладів**; пошук
  `product(slug, slugLanguageCode)` **без автоматичного fallback** — клієнт пробує переклад, потім
  primary; ADR 0004: «Primary slug remains identity», канонічний редирект 308, кеш-теги по primary slug,
  `TRANSLATION_*` вебхуки; структурні сегменти (`/products/`) лишаються англійськими `[П: код]`
  (<https://github.com/saleor/saleor/blob/main/saleor/product/models.py>,
  <https://github.com/saleor/storefront/blob/main/docs/adr/0004-translatable-slugs.md>).
  Цей ADR описує **ту саму діру**, що драфт §4 п.1: `UNIQUE(locale, slug)` на таблиці перекладів не
  бачить колізії з базовим slug неперекладеного товару.
- **Shopware 6:** слаги винесені з `product_translation` в окрему таблицю `seo_url` з полями
  `sales_channel_id`, `language_id`, `foreign_key`, `route_name`, `path_info`, `seo_path_info`,
  `is_canonical`, `is_modified`, `is_deleted` (видалений URL лишається в таблиці і відновлюваний)
  `[П: код]` (`src/Core/Content/Seo/SeoUrl/SeoUrlDefinition.php`). Тобто це **матеріалізована
  проєкція «розв'язаних» адрес** на (канал, мова, сутність). Унікальні індекси цієї таблиці не
  перевіряв `[Н]`.

**Висновок:** три зрілі платформи сходяться в тому, що slug — окрема від тексту сутність з власною
ідентичністю (primary = ідентичність, переклад = подання), а розв'язання `(locale, slug) → entity` — це
одна таблиця/один індекс. Рекомендація для SimplyCMS (§6.3) — **реєстр слагів на мову**.

### 1.4. Canonical, sitemap, `<html lang>`, JSON-LD

- **Canonical на кожну мову.** `[П]`: «Different language versions of a single page are considered
  duplicates only if the primary content is in the same language»; canonical — «a strong signal»;
  для сторінок з hreflang canonical має бути тією ж мовою
  (<https://developers.google.com/search/docs/crawling-indexing/canonicalization>). Shopify: самопосилальний
  canonical на кожну ринкову версію `[П]`.
- **Не плутати noindex і canonical.** `[П]`: `noindex` для вибору canonical не радять («will completely
  block the page»), `rel=canonical` — «preferred solution»
  (<https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls>). Крім того
  Mueller (переказ SEJ) — не блокувати robots.txt уже створені мовні сторінки, бо Google тоді не зможе
  їх канонікалізувати `[Вт]`.
- **Sitemap.** `[П]` ліміт 50 MB / 50 000 URL на файл, індекс sitemap опційний; **Google ігнорує
  `<priority>` і `<changefreq>`**; `<lastmod>` береться лише якщо «consistently and verifiably»
  точний, відбиває «last significant update» (<https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap>).
  Поточний `renderSitemapXml` (`src/storefront/seo/sitemap.ts`) пише `changefreq`/`priority` — безкоштовний
  шум; альтернатив `xhtml:link` немає `[П: код]`. 100k товарів × N мов = N×100k URL → потрібен
  sitemap index із чанками ≤ 50k (кластер hreflang можна дати в кожному `<url>`).
- **`<html lang>`.** Google його не використовує для мови `[П]`, але WCAG 2.2 SC 3.1.1 (Level A):
  «default human language of each web page can be programmatically determined»
  (<https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html>). Зараз
  `src/routes/__root.tsx:95` ставить `lang={locale}` з однієї глобальної локалі `[П: код]` — для
  багатомовності потрібна локаль запиту в SSR (Saleor витратив на це окремий розділ ADR: lang має бути
  в початковому HTML, не `useEffect`).
- **JSON-LD.** `inLanguage` у schema.org має домен CreativeWork, Event тощо; `Product`/`Offer` у
  переліку **немає** (<https://schema.org/inLanguage>) `[П]`; для `WebPage`/`CollectionPage` застосовне
  через успадкування від CreativeWork `[Н: ієрархію не перетягував]`. Сторінка Google про Product-структуровані
  дані, яку я отримав, не містить настанов про мову/локалізацію `[П]`. Практично: `name`/`description`
  в JSON-LD — мовою сторінки; окремий `inLanguage` на Product не потрібен.

### 1.5. Неперекладений товар у мові — політика

Що **доведено** `[П]`: (1) дублікат лише при однаковій мові основного контенту; (2) перекладати лише
«boilerplate» (шаблон) і лишати основний контент іншою мовою Google прямо називає ризиком, особливо для
UGC (<https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites>);
(3) canonical — сильний сигнал; (4) noindex ≠ інструмент вибору canonical.

Що **не** сказано `[П]`: окремого правила «що робити з fallback-сторінкою» немає. Два пошуки
(Mueller/SEJ, Shopify) не дали авторитетної відповіді `[Вт]`; думка «noindex непереклад»
належить коментатору, не Google.

Три варіанти (вибір — продуктовий; технічно всі виражаються статусом в проєкції):

| Варіант | Поведінка в `/en/` | hreflang | sitemap | Ризик |
|---|---|---|---|---|
| **F1. Не існує** | товар відсутній у каталозі/пошуку `en`, URL → 404 (або 301 на основну мову за явним вибором) | немає | немає | втрата каталогу в `en`; погано для UX |
| **F2. Показ з canonical** | показуємо fallback-контент; `rel=canonical` → URL основної мови | **не** входить | **не** входить | дублікати скануються (crawl budget), але індексація консолідується |
| **F3. Показ + noindex** | як F2, але `noindex,follow` без canonical | не входить | не входить | сторінка зникає з індексу; посилальна вага не передається canonical-ом |

F2 найкраще узгоджується з цитованими фактами Google (canonical — рекомендований інструмент, у кластер
hreflang входять лише справжні переклади). Позначаю як **умовивід** `[Н]`: перевірити Search Console на
пілоті. Критично: **один** механізм на сторінку (canonical АБО noindex), не обидва.

Вимога до моделі: статус `translated | fallback` (§6.2) мусить бути обчислюваним у проєкції без
запиту в декілька таблиць, бо від нього залежать `<link rel=canonical>`, `<link rel=alternate>`,
sitemap, robots-meta.

### 1.6. Автоперенаправлення за `Accept-Language`

`[П]` Google: «Avoid automatically redirecting users from one language version of a site to a different
language version», «the crawler sends HTTP requests without setting Accept-Language», «Don't use IP
analysis to adapt your content»; локаль-адаптивні сторінки Google може не сканувати/не ранжувати повністю
(<https://developers.google.com/search/docs/specialty/international/locale-adaptive-pages>);
рекомендація — окремі URL + hreflang. Shopify редиректить клієнтів на їхній ринок, **виключаючи
краулерів** `[П]`. Saleor ADR: редирект лише кореня `/` на `/{defaultLocale}/…` + cookie для вибору.

Рекомендація `[Н]`: на контентних URL редиректу немає; максимум — неблокувальна підказка (банер) на
клієнті. Якщо основна мова безпрефіксна, кореня-редиректу взагалі немає (відповідає рекомендації
Google за побудовою). Якщо все ж редирект кореня за `Accept-Language` — тоді 302 і `Vary: Accept-Language`
на цій відповіді.

## 2. Фасетна навігація і SEO

Що каже Google `[П]` (<https://developers.google.com/crawling/docs/faceted-navigation>):

- Фасетна навігація «can generate infinite URL spaces». Для непотрібних в пошуку URL — **robots.txt
  disallow** як основний інструмент; фрагменти `#` на краулінг не впливають; `rel=canonical` і
  `nofollow` — «may, over time, decrease the crawl volume» і «generally less effective in the long
  term».
- Для сканованих: 404 на порожню комбінацію; стандартний роздільник `&`; у шляхових фільтрах —
  **незмінний порядок** і без дублів.
- Сторінка **не згадує `noindex`**. Crawl-budget гайд: «Don't use noindex to manage crawling» —
  Google усе одно робить запит; блокований robots URL довше стоїть у черзі
  (<https://developers.google.com/crawling/docs/crawl-budget>). Цей гайд адресований сайтам ~1M+
  сторінок/тиждень або 10k+ що змінюються щодня, «rough estimates»: 100k товарів × 5 мов — на межі.
- Dec 2024: faceted nav — «by far the most common source of overcrawl issues» (<https://developers.google.com/search/blog/2024/12/crawling-december-faceted-nav>)
  `[П через пошукові сніпети; тіло сторінки через WebFetch не отримав]`. Цифри «50 % faceted + 25 %
  action-параметри» з підсумкового звіту 2025 — лише `[Вт]` (Search Engine Land дав 403); першоджерела
  не бачив.

**Внутрішня неузгодженість у `seo-ssr-faceted-navigation.md`** (знайдено при читанні): §4.2/Блок C
дають multi-facet query-URL `noindex,follow` + `canonical → секція`, а Блок E додає robots-disallow
лише для sort/page/view/price. Комбінації на кшталт `?brand=nike&color=red` лишаються **скановними**
і ловлять той самий overcrawl, який Google називає головною проблемою; `noindex` crawl budget не
економить. Узгодити: або disallow усіх фільтр-параметрів (крім білого списку), або свідомо прийняти
витрату краулінгу.

### 2.1. Локалізовані slug значень фільтрів

Дві різні задачі, їх варто розвести `[Н]`:

1. **Індексовані лендинги** (секція × одна опція/ознака) — чисті шляхові слаги, локалізовані
   (`/en/catalog/panels/power-400w`), самоканонічні, у sitemap, у hreflang-кластері, з порогом
   «не thin». Це продовжує тезу консенсусу в проєктному документі (§2.3) — ID у URL є антипатерном.
   Слаги — з реєстру слагів (§6.3), причому слаг опції в мові має бути унікальний у межах властивості
   в цій мові.
2. **Робочий стан фільтра** (комбінації, сортування, пагінація) — query-параметри, `robots.txt`
   disallow. Пропоную в параметрах використовувати **мовно-нейтральні ключі** (primary slug/код
   властивості й опції), а не локалізовані: (а) перемикач мови зберігає query без перекладу (Saleor
   ADR 0004 правило 7 саме для цього зберігає query-рядок і заміняє лише шлях); (б) нормалізація
   ключа кешу не залежить від мови; (в) ці URL не індексуються, ключове слово в них не потрібне.

Зарезервовані сегменти (`filter`, `all`, …) мають перевірятись у **кожній** мові для перекладених
слагів розділів (драфт §4 п.1).

Shopify (для порівняння): фільтр-параметри `?filter.p.…`, стабільні ідентифікатори замість тексту з
квітня 2026 — за проєктним документом `[Вт]`; першоджерело `shopify.dev/changelog` не перевіряв.

## 3. Швидкодія вітрини

### 3.1. Метрики й пороги (web.dev `[П]`)

- Core Web Vitals, 75-й перцентиль, мобільні/десктоп окремо: **LCP ≤ 2,5 с**, **INP ≤ 200 мс**
  (погано > 500 мс), **CLS ≤ 0,1** (<https://web.dev/articles/vitals>,
  <https://web.dev/articles/inp>).
- TTFB — не Core Web Vital; «good» ≤ 0,8 с, «poor» > 1,8 с; для SSR він допустимо вищий, якщо
  FCP/LCP кращі за клієнтський рендер (<https://web.dev/articles/ttfb>).
- Розкладка LCP: TTFB ≈ 40 %, затримка завантаження ресурсу < 10 %, тривалість ≈ 40 %, затримка
  рендеру < 10 %; `fetchpriority="high"` на LCP-зображенні, **не** lazy-load, `src/srcset` у початковому
  HTML (<https://web.dev/articles/optimize-lcp>).
- Google: «Core Web Vitals are used by our ranking systems», але хороші показники не гарантують топ,
  а релевантність має пріоритет (<https://developers.google.com/search/docs/appearance/page-experience>).

### 3.2. Поточний стан у коді `[П: код]`

- HTML вітрини: жодного `Cache-Control`, окрім `private, no-store` для залогіненого (бо ціни
  персоналізовані: `storefront/loaders/viewer.ts`). Гостьова відповідь «однакова для всіх».
- `sitemap.xml`/`robots.txt`: `public, max-age=3600, stale-while-revalidate=86400` лише на 200
  (`storefront-routes/seo/interceptor.ts`).
- Є процесний `createReadCache` з лічильником поколінь (`site/read-cache.ts`) — готовий патерн
  інвалідації без «старого значення на TTL».
- Нема hreflang, нема TTFB/Lighthouse-вимірів у `docs/` (grep).

### 3.3. Кеш HTML на краю і мова

- **Ключ кешу.** Мова у шляху = окремий URL = окремий ключ без жодного `Vary`. Це принципово, бо
  Cloudflare за замовчуванням **ігнорує** `Vary` (враховує лише `vary: accept-encoding` та
  налаштовані випадки) `[П]`
  (<https://developers.cloudflare.com/cache/concepts/cache-control/>).
  Ключ на `Accept-Language`/cookie мови — погана ідея (Saleor ADR: «ambiguous cache keys»).
- **Гість vs сесія.** Кеш-публічна лише гостьова відповідь; з сесійною cookie — `private, no-store`
  (вже реалізовано для цін). CDN має обходити кеш при наявності сесійної cookie `[Н: правило CDN]`.
  Cloudflare: `Set-Cookie` при дефолтному рівні кешу знімається, при Origin Cache Control — відповідь
  не кешується `[П]`.
- **SWR.** `stale-while-revalidate` підтримується Cloudflare; `s-maxage` «implies proxy-revalidate,
  which disables stale-while-revalidate» — за його ж документацією; приклади TanStack поєднують
  `s-maxage` і SWR для Vercel `[П]` → поведінка залежить від CDN, перевіряти заголовками (`curl -I`,
  `Age`, `cf-cache-status`).
- **Інвалідація.** `Cache-Tag` у відповіді + purge за тегом; Cloudflare відкрив purge за тегом на
  **всіх тарифах** (changelog 2025-04-03) `[П]`; ліміти: заголовок ≤ 16 KB (~1000 тегів), 100 тегів на
  purge у дашборді `[П]`
  (<https://developers.cloudflare.com/cache/how-to/purge-cache/purge-by-tags/>). Теги для багатомовності:
  `product:<id>` (змінилась мовно-нейтральна частина: ціна, наявність, фасети → усі мови),
  `product:<id>:<locale>` (змінився переклад), `section:<id>`, `i18n:<locale>` (зміна перекладу
  інтерфейсу/меню). Приклад Saleor: теги по primary slug, а вебхук `TRANSLATION_*` додано окремо, бо
  `PRODUCT_UPDATED` на зміну перекладу **не спрацьовує** `[П: код]` — той самий клас пропуску в нас
  виникне, якщо інвалідація підписана на подію товару, а не на подію проєкції.
- **Самохостинг без CDN** (Dokploy/Traefik — типовий магазин за вимогою «$1–3/міс на магазин»):
  чи має Traefik OSS HTTP-кеш — **не перевірено** `[Н]`. Альтернатива — процесний мікрокеш HTML
  для гостьових запитів, ключ `(locale, нормалізований path+query)`, TTL у секунди + SWR, скидання
  лічильником поколінь (патерн уже є). Обмежувати за **байтами**, не за записами: N мов × сторінки ×
  50–150 KB `[Н: розмір не міряв]` швидко з'їдає бюджет 400–600 MB.
- **ISR/prerender.** `[П]` TanStack Start: «page doesn't claim built-in ISR»; ISR — це `headers()` на
  роуті + CDN + on-demand purge; `prerender` (Vite) — build-time, `crawlLinks`
  (<https://tanstack.com/start/latest/docs/framework/react/guide/isr>). Prerender 100k×N динамічних
  сторінок на білді — не варіант; лише статичні (головна, інформаційні).
- **Селективний SSR / стрімінг.** `ssr: false | 'data-only' | fn` на роуті `[П]`. Чи впливає потоковий
  SSR на краулерів — гайд Start мовчить; не перевірено `[Н]`.
- **hreflang/alternates** у SEO-гайді Start **не описані** `[П]` — це наш код (`head()` роуту).
- **304/ETag.** Crawl-budget гайд Google просить підтримувати `304 Not Modified` `[П]`; у нас —
  `[Н]` не перевірено.

### 3.4. Бюджет TTFB для SSR з Postgres

Не міряв повний SSR-запит (потрібен запущений магазин) — **прогалина**. Розрахунок на основі цитованого:
LCP ≤ 2,5 с, TTFB ≈ 40 % → ≈ 1,0 с загальна стеля; «good» TTFB ≤ 0,8 с у полі (включає мережу). Вимірювані
мною серверні часи БД для каталожних запитів (1–6 мс FTS, 3–17 мс фасети на 100k, Додаток А) — малі
порівняно з рендером React і мережею; тобто **вузьке місце SSR — не Postgres, а кількість послідовних
запитів лоадерів і рендер** `[Н]`. Пропонований гейт (умовивід): TTFB p75 гостьової сторінки каталогу/PDP
з кешу ≤ 200 мс, без кешу ≤ 600 мс; вимірювати в пілоті A/B через Lighthouse/CrUX.

### 3.5. Фільтри й INP

Фільтри в URL (проєктний документ Блок C) + `loaderDeps` дають кеш лоадера на валідовані search-параметри
`[П]` (<https://github.com/tanstack/router/blob/main/docs/router/guide/data-loading.md>),
`defaultPreloadStaleTime`/preload «intent» дають миттєву навігацію для передбачуваних кліків `[П]`.
Для INP ≤ 200 мс: клік має негайно перемалювати стан (pending/оптимістичний), а не чекати SSR-відповіді;
це інженерна вимога до теми `[Н]`. Зараз фільтрація — клієнтський `useMemo` (миттєва, але без URL/SSR);
переведення на сервер **додає** мережеву затримку на кожен клік — компенсувати (а) бюджетом фасетів
(§4), (б) preload, (в) pending-станом.

## 4. Фільтри й фасети «миттєво» в Postgres (1k–100k × N мов)

### 4.1. Виміряно (Додаток А): час SQL фасетних лічильників

Схема: `products`, `product_options(product_id, option_id)` (EAV, як у `product_property_values`),
10 властивостей, 340 опцій, ~1,06 M зв'язків на 100k товарів, розділи зі зміщеним розподілом.
Час = `EXPLAIN ANALYZE` серверний, гарячий кеш, медіана з 9, один клієнт.

| Сценарій (100k товарів) | A EAV join | B `int[]`+GIN | C roaring | D препорахунок |
|---|---:|---:|---:|---:|
| S1: розділ 6,9k, без фільтра | 19,5 мс | 15,9 мс | 2,6 мс | **0,09 мс** |
| S2: розділ + 1 опція (817) | 9,1 | 5,0 | 4,1 | — |
| S3: весь каталог + 1 опція (11k) | 31,4 | 16,6 | 3,4 | — |
| S4: весь каталог, без фільтра (97k) | 82,8 | 103,2 | 1,2 | 7,3 |
| S5: каталог + 2 опції (2,8k) | 15,1 | 8,6 | 6,8 | — |

| 10k товарів | A EAV | B array | C roaring |
|---|---:|---:|---:|
| S4 весь каталог без фільтра | 19,0 мс | — | — |
| S3 каталог + 1 опція | 6,4 | 2,7 | 1,2 |

Розміри: roaring-бітмапи 340 опцій — 2,0 MB + 0,34 MB розділи; `facet_cnt(section, option)` — 4,5 MB;
EAV-таблиця зі зв'язками й індексами — 80 MB; GIN на `option_ids` — 2,4–2,8 MB.

`uuid[]` GIN (стандартний `array_ops`) дає 16,7 мс (S3) і 10,5 мс (S5) — тобто **у схемі з UUID-ключами
пристойно працює без сурогатних int** (`int[]` з `array_ops` — 21 мс, `intarray`-oparator
`gin__int_ops` — 17 мс). Roaring вимагає 32-бітних ключів → потрібен сурогатний int на товар
(pg_roaringbitmap `[П]`, pgfaceting: «Only 32-bit integer ID columns»).

**Читання результату:** на цільовому обсязі навіть «наївний EAV» ≤ 83 мс у найгіршому випадку (весь
каталог без фільтра), а це саме той запит, який можна препорахувати. Масштаб 1k–10k не потребує нічого.
Roaring виграє на великих відфільтрованих наборах (S3: 3,4 мс проти 16,6), але на селективних
(S2: 4,1 проти 5,0) майже нічого — вартість визначається числом опцій (340 AND-операцій).

Обмеження вимірів: один клієнт, без конкурентності; синтетичний розподіл Zipf-подібний; множинні
вибрані властивості (дизюнктивні фасети, де лічильники властивості рахуються без її власного
фільтра) множать вартість на число вибраних властивостей — **не міряв** `[Н]`.

### 4.2. Підходи й джерела

| Підхід | Що підтверджено | Застереження |
|---|---|---|
| Просто `GROUP BY` по EAV/масиву | мої виміри вище | O(кількість збігів × властивості) |
| Препорахунок лічильників `(section, option)` | мій D: 0,09–7 мс | не покриває довільні фільтри; тримати оновлення в тій самій черзі проєкції |
| Матеріалізоване в'ю | Postgres: `REFRESH` «completely replaces the contents», `CONCURRENTLY` потребує UNIQUE-індексу без `WHERE`, одночасно лише один refresh `[П]` (<https://www.postgresql.org/docs/17/sql-refreshmaterializedview.html>) | немає інкрементального оновлення в ядрі; для точкових змін адміна — неадекватно |
| `pg_ivm` (інкрементальні в'ю) | інкрементально через AFTER-тригери; ліцензія PostgreSQL; PG 13–19 `[П]` (<https://github.com/sraoss/pg_ivm>) | обмеження: зовнішні з'єднання з агрегатами заборонені, база — лише звичайні таблиці (не партиційовані), накладні витрати на запис; доступність у managed-PG не перевірена `[Н]` |
| Roaring: `pg_roaringbitmap` + `pgfaceting` | є пакет PGDG `postgresql-17-roaringbitmap 1.2.0` і `postgresql-17-pgfaceting 0.2.0` (встановив `apt` в `postgres:17` `[В]`); pg_roaringbitmap — Apache-2.0, активний (push 2026-10-03), pgfaceting — BSD-3, **останній push 2024-03-19**, лише 32-бітні id, дельти зливаються періодично (лічильники відстають до `run_maintenance`) `[П]` (<https://github.com/cybertec-postgresql/pgfaceting>); автор: 100M рядків — 155 мс проти 18,4 с паралельного скану (власне залізо) `[Вт-автор]` | у 2023 pg_roaringbitmap «Not available on AWS RDS, Google Cloud SQL or Azure» (<https://www.postgresql.eu/events/pgconfeu2023/sessions/session/4762/slides/408/roaring.pdf>) — актуальність не перевіряв; **базовий образ тенанта `pgvector/pgvector:pg17` цього розширення не містить** (спека П14) |
| ParadeDB `pg_search` (`pdb.agg`) | вендор: 42 M результатів — 1 013 мс проти 11 849 мс ручного фасетингу `[Вт-вендор]` (<https://www.paradedb.com/blog/faceting>) | **AGPL-3.0** (`gh api`) `[П]` — сумісність із MIT-ядром — питання власнику/юристу; зайве на цьому обсязі |
| Instacart | перейшли з Elasticsearch на Postgres; «denormalized data model» і часті часткові оновлення цін/залишків були проблемою, писальне навантаження −10×, вартість сховища/індексації −~80 % `[Вт: InfoQ 2025-08-25]` (<https://www.infoq.com/news/2025/08/instacart-elasticsearch-postgres>; першоджерело tech.instacart.com повернуло 403); лексика — GIN + змінений `ts_rank` + `pg_trgm`; семантика — pgvector | про фасети стаття мовчить; **урок про проєкцію:** летючі поля (ціна/залишок) не денормалізувати в рядок, який перебудовується |

### 4.3. Рекомендація (лише з виміряного)

1. **Рівень 0 (усі обсяги):** лічильники «розділ без фільтра» препорахувати (таблиця або кеш процесу з
   поколіннями). Це перший екран для гостя й краулера — найдорожчий і найкешованіший.
2. **Рівень 1:** відфільтровані лічильники — з проєкції `option_ids uuid[]` + GIN (без розширень, без
   сурогатних ключів, 5–17 мс на 100k).
3. **Рівень 2 (тригер — каталог > ~100k або p95 фасетів > 50 мс, як уже записано в спеці):** roaring
   як опційний драйвер з образом, що містить розширення, і сурогатним int — не базовий стек.
4. Не вводити `pg_search`/AGPL і матв'ю як основний механізм.

### 4.4. Теза «фільтри по id/кодах, мова — лише відображення»: вердикт

**Підтверджується для enum-фасетів** `[В]`: підрахунок і фільтрація йдуть по `option_id`; при N мов
SQL фасетів не змінюється (проєкція мовно-нейтральна); приєднання назв значень: 16,2 → 17,5 мс (`uk`),
16,2 мс (`de`) проти 16,1 мс без назв, roaring + назви — 3,2 мс (різниця в шумі).

### 4.5. Що з цього залежить від мови (винятки з тези)

1. **Вільний текст значень** (`property_type = text`; `product_property_values.value` — у схемі є й
   `value` text, і `option_id`): значення — рядок мовою; фасет по ньому = групування по `(locale,
   value)`, лічильники різні на мову. Рішення: або заборонити фасетувати `text` (лише `select`/`multiselect`),
   або перевести такі значення в довідник опцій (з id).
2. **Сортування значень у фасеті** — за назвою в мові: потрібна колація мови. Postgres підтримує ICU-колації
   `CREATE COLLATION … (provider = icu, locale = 'de-DE')` і `COLLATE` на вираз `[П]`
   (<https://www.postgresql.org/docs/17/collation.html>); для списку з кількох сотень значень простіше
   `Intl.Collator` у застосунку `[Н]`.
3. **Слаги й підписи лендингів** (§2.1) — мовні.
4. **Пошук усередині фасета** (`searchForFacetValues` з контракту спеки) — мовний шар
   (нормалізація/лематизація назви значення).
5. **Одиниці й формат чисел** (400 W vs 400 Вт) — відображення, числове значення лишається `numeric_value`.
6. **Видимість неперекладеного** (§1.5): якщо політика F1 (товар відсутній у `en`), то в **усі фільтри
   лічильників `en`** додається предикат «товар доступний у локалі» — мова входить не в схему фасетів, а
   в WHERE. Для F2/F3 (fallback) — не входить. Тобто це продуктове рішення, яке змінює запит.
7. **Текстові атрибути в FTS** (`attrs_lex` у `search_documents`) — мовні за побудовою (спека).

## 5. Багатомовний повнотекстовий пошук у Postgres

### 5.1. Вбудоване vs мовний шар у застосунку

`[В]` `select cfgname from pg_ts_config` на PG 17.11: arabic, armenian, basque, catalan, danish, dutch,
english, finnish, french, german, greek, hindi, hungarian, indonesian, irish, italian, lithuanian,
nepali, norwegian, portuguese, romanian, russian, serbian, **simple**, spanish, swedish, tamil, turkish,
yiddish. Нема: українська, польська, чеська, перська, естонська, CJK, тайська.
Snowball (BSD-3-Clause `[П]`, <https://snowballstem.org/license.html>) має Czech, Polish, Persian,
Estonian та ін.: `gh api repos/snowballstem/snowball/contents/algorithms` `[П]`, а в самого Snowball є
офіційний JS-бекенд (`javascript/base-stemmer.js`, `stemwords.js`) `[П]`. Тобто для деяких мов, яких
нема в PG, є алгоритм — але **не у вбудованих конфігураціях**; мовний шар у застосунку (рішення спеки П2)
знімає це обмеження.

Обґрунтування `simple` + generated column `[П: спека, перевірено на живому PG]`: per-row `regconfig` у
generated column не `IMMUTABLE`. Документація Postgres підтверджує, що конфігурація задає парсер і
словники (<https://www.postgresql.org/docs/17/textsearch-configuration.html>); про `immutable`/generated
сама сторінка мовчить `[П]`.

### 5.2. Ємність і швидкодія на N мов `[В]`

Синтетика: 100k товарів, по 5 токенів у заголовку (вага A) + 30 у тілі (вага C) на документ, 15 % спільних
токенів між мовами (бренди/артикули), решта — словник мови зі Zipf-розподілом.

| Мов | Документів | Heap | GIN(tsv) | Побудова GIN |
|---:|---:|---:|---:|---:|
| 1 | 100 000 | 60 MB | 18 MB | 1,6 с |
| 6 | 600 000 | 360 MB | 104 MB | 10,6 с |

Ріст майже лінійний за числом документів (5,8× GIN на 6× документів); `to_tsvector` по 600k документів —
21 с. Документи потрібні лише для **перекладених** комбінацій (за політики F2/F3 пошук fallback-товарів
краще вести з документа основної мови, а не дублювати текст).

Запити (2 слова, `locale = 3`, `ORDER BY ts_rank LIMIT 24`, 600k документів, мс):

| Запит (хітів у мові) | GIN(tsv) + btree(locale) | GIN(locale, tsv) через `btree_gin` |
|---|---:|---:|
| `x3_30 & x3_100` (14) | 1,7 | 1,8 |
| `s10 & x3_100` (9; `s10` спільний) | 1,1 | 1,4 |
| `s10` (1 226 у мові, 6 882 усього) | 5,9 | **21,8** |
| `x3_5000` (171) | 1,3 | 1,6 |

Висновок: **простий GIN(tsv) з фільтром за `locale` кращий за композитний `btree_gin`**; найдорожчий —
широкий спільний токен (бренд), що збирає кандидатів з усіх мов. Спека вже вимагає верхньої межі
кандидатів перед ранжуванням. Не тестував: партиціювання за `locale` (LIST) `[Н]`.

Триграми: `gin_trgm_ops(title_norm)` — 44 MB на 600k заголовків ~37 символів, побудова 3,9 с. Мій
запит `%` на синтетиці дав 530 мс, але дані виродженні (усі токени мають префікс `x3_`, ділять
тригрими) — **цифру до уваги не брати**; реалістичні 6,7–15,8 мс на 10k — у дослідженні спеки.
Увага: `%` з порогом 0,3 на низькоселективних даних може бути повільним — потрібен бенчмарк на реальних назвах.

### 5.3. Не-пробільні мови (CJK, тайська)

`[В]` Postgres `to_tsvector('simple', …)`: `吾輩は猫である 名前はたぬき` → дві лексеми-фрази;
`太阳能电池板 400瓦` → `'太阳能电池板'`, `'400瓦'`; тайська `ไฟฟ้า แผงโซล่า` ділиться лише по пробілах.
`Intl.Segmenter` (Baseline 2024 `[П]`, MDN) у Node v24.15 / ICU 78.2 `[В]`: `吾輩 は 猫 で ある 名前 は たぬき`;
`太阳 能 电池 板 400 瓦`; `ไฟฟ้า แผง โซ ล่า`. Тобто контракт `LanguagePack` треба доповнити
`tokenize(text): string[]` (дефолт — Unicode-слова, CJK/тайська — `Intl.Segmenter`), а в індекс і запит класти
токени через пробіл — архітектура спеки (симетрично) це дозволяє. Альтернативи в БД: `zhparser` (SCWS),
`pg_bigm`, PGroonga — розширення, не для базового образу `[Вт]` (2015-ті порівняння; чи актуальні — не
перевіряв). `pg_trgm` для CJK історично не підходить `[Вт]`.

## 6. Синтез: вимоги до моделі даних

### 6.1. Головний архітектурний висновок

Читання вітрини має йти з **двох проєкцій з різним ключем**:

- **`catalog_facets` (мовно-нейтральна), ключ `product_id`:** `section_ids uuid[]` (розділ + предки),
  `option_ids uuid[]` (з `product_property_values` ∪ значення активних модифікацій — у схемі значення
  живуть у двох таблицях), числові значення для діапазонів, `is_active`, агрегат наявності. **Не** містить
  мовних рядків і ціни (ціна — окремий вузький індекс по `product_prices`, бо є типи цін/категорії
  покупців). Один рядок на товар, незалежно від числа мов → N мов фасетам нічого не додає `[В]`.
- **`catalog_i18n` (мовно-залежна), ключ `(product_id, locale)`:** розв'язані `name`, `slug`,
  `short_description`, `meta_*`, `h1`, `translation_status`, `canonical_locale`, `content_updated_at`;
  разом із `search_documents (entity_type, entity_id, locale)` зі спеки. Аналогічні таблиці для
  розділів, властивостей, опцій.

Причини: (а) принцип П8 спеки «порт повертає id, гідрація окремо» з цього випливає; (б) урок Instacart —
летючі поля не денормалізувати в рядок, який перебудовується `[Вт]`; спека вже виносить ціни з
індексованої таблиці й міряє: UPDATE ціни −0,13 % проти −8,8 % для тексту; (в) ключ `(product_id, locale)` збігається з ключем документів пошуку й черги
індексації.

### 6.2. Конкретні вимоги

1. **Реєстр мов — єдине джерело:** `languages(code BCP47, hreflang_code, is_default, is_active,
   fallback_code, dir, lang_pack)`; `is_default` незмінний після публікації без міграції редиректів
   (§1.1).
2. **Статус перекладу на (сутність, мова):** `status ∈ {translated, outdated, fallback}` + `published`;
   «translated» = обов'язкові поля заповнено й опубліковано (NULL-поле = fallback, як у драфті §3).
   Від нього залежать canonical/hreflang/sitemap/robots-meta (§1.5) і предикат видимості (§4.5 п.6).
3. **Слаги:** реєстр `slug_registry(locale, entity_type, slug) UNIQUE → entity_id, is_canonical,
   redirect_from…` — Shopware-подібна розв'язана таблиця (§1.3). Заповнюється в одній транзакції із
   зміною сутності під наявним `lockCatalogTarget` `[П: драфт]`. Включає **і** перекладені слаги, **і**
   fallback-слаги (бо `/en/<український-слаг>` теж маршрутизується). Збіг перекладеного слага з чужим
   fallback — правило: переклад має пріоритет, конфліктний переклад відхиляється з помилкою валідації.
   Історія старих слагів → 301 (Shopify створює редиректи; Shopware зберігає `is_deleted`).
   Зарезервовані сегменти — в кожній мові.
4. **Довідник значень:** кожна фасетна властивість — `select`/`multiselect`/`color`/`boolean` із `option_id`;
   переклад назви — рядок на (опція, мова); для лендингів — `slug` у реєстрі; вільний текст (`text`) не
   фасетується або мігрує в опції (§4.5 п.1). Ключ опції в query-параметрах — primary slug/код,
   мовно-нейтральний (§2.1).
5. **`content_updated_at` на (сутність, мова)**, а не `updated_at` базової таблиці: Google використовує
   `<lastmod>` лише якщо він «consistently and verifiably» точний `[П]`, а `products.updated_at` змінюється
   від будь-якої правки (наявність, ціна). Обчислюється при ребілді проєкції порівнянням вмісту.
6. **Черга індексації з локаллю:** `search_index_queue` у спеці має `PRIMARY KEY (entity_type,
   entity_id)` — без `locale`. Якщо ключ лишається так, зміна перекладу однієї мови перебудовує всі мови
   (зайве N×), а дедуплікація не розрізняє «весь товар» і «один переклад». Додати `locale` (nullable =
   усі мови) — **знайдено при читанні**, потребує узгодження зі спекою.
7. **Події інвалідації кешу = події проєкції**, а не події товару (клас пропуску Saleor `TRANSLATION_*`,
   §3.3). Теги: `product:<id>`, `product:<id>:<locale>`, `section:<id>`.
8. **Sitemap/hreflang генеруються з `catalog_i18n`** (`status = translated`, `published`), не з базових
   таблиць; кластер hreflang — множина `locale` з `translated` для даної сутності.
9. **`orders.locale`** (драфт §4.4) — не SEO, але читається із того ж реєстру.
10. **Мовний шар:** `LanguagePack` + `tokenize()` (§5.3) + версія в рядку індексу (П4 спеки).

### 6.3. Чи має модель зберігання (A / B / D) перевагу для SEO/швидкодії, якщо читання йде з проєкції

**Коротко: ні, для читання — ні; різниця лише в цілісності запису.** `[В]` показав, що швидкодія
фасетів/FTS визначається структурою проєкції, а не місцем зберігання вихідного тексту; sitemap, кеш і
hreflang читають проєкцію.

| Аспект | (A) дефолт у колонках + `*_translations` | (B) усе в `*_translations` | (D) JSONB-мапа на поле |
|---|---|---|---|
| Швидкодія читання вітрини / фасети / FTS | залежить від проєкції, не від моделі | те саме | те саме |
| Побудова проєкції | дві гілки (база для основної мови + переклади) | одна гілка | вибірка з JSONB (як окрема гілка) |
| Унікальність слага «в мові» | базовий slug у `products`, переклади в іншій таблиці → міжтабличне обмеження/тригер або реєстр | `UNIQUE(locale, slug)` нативно для явних перекладів; fallback-колізію **усе одно** лікує реєстр | жоден нативний механізм; лише N індексів по виразах `(jsonb->'en'->>'slug')` |
| «Переклад існує/свіжий» | основна мова завжди «існує» (немає рядка) → статус та `outdated` особливі | рівномірно: рядок є/нема, `status` у рядку | потребує метаданих у JSON на ключ |
| `content_updated_at` на мову | основна мова ділить `updated_at` з нестосовними правками | у кожного рядка свій | у одному рядку, треба зберігати мітки в JSON |
| Зміна основної мови пізніше | міграція даних (поміняти базу й переклад) | запис `is_default` | запис `is_default` |
| Міграція існуючих даних | адитивна (драфт) | перенос колонок | `text → jsonb` переписує таблицю (драфт) |

Єдине місце, де модель має вагу для SEO: **(1) слаги, (2) точність `lastmod`, (3) вартість зміни
основної мови**. Тут B/A з явними таблицями перекладів і реєстром слагів рівноцінні для функціоналу, B
чистіше; D гірший. Вибір між A і B — це питання вартості міграції пілоту та складності побудови проєкції,
**а не** швидкодії вітрини. Це відповідає висновку драфту (патерн A адитивний) і не суперечить йому.

### 6.4. Продуктові розвилки власнику (не технічні)

1. Основна мова з префіксом чи без (§1.1).
2. Політика неперекладеного: F1/F2/F3 (§1.5).
3. Чи показувати підказку-банер за `Accept-Language` (§1.6).
4. Яку підтримку обіцяємо кожній мові: «базова» (нормалізація + тригрим) чи «морфологічна» (§5.4).
5. CJK/тайська — входять у скоуп першої хвилі чи ні (§5.3).
6. Чи припускається CDN (Cloudflare тощо) як рекомендована частина, чи лише процесний кеш (§3.3).
7. Чи фасетувати вільний текст (§4.5 п.1).

  чи є HTTP-кеш у Traefik OSS; підтримка `304` у Start.

- Реальні багатомовні дані для FTS і тригрим-запитів (мій корпус синтетичний).
