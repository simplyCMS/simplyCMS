# Вимоги власника до мультимовності даних і суміжного (дослівно зведено, 2026-10-13)

1. Мультимовність ДАНИХ (не інтерфейсу): товари, властивості, розділи тощо — довільна кількість мов, «мов може бути багато і може бути більше»; перемикач мови на вітрині (може з'явитись пізніше).
2. Критерій вибору моделі — не «менше переробляти», а подальша доробка, підтримка, розвиток. Не обирати гірший варіант лише тому, що вже реалізовано. Власник готовий відкласти перший реліз (1.0.0-rc.1) і пілот, якщо треба змінити структуру БД (зокрема на варіант «усі мови в таблицях перекладів», як OpenCart). Врахувати всі можливі варіанти не лише на зараз, а на майбутнє.
3. Робота з магазином через API — наступний крок одразу після пілоту; для деяких випадків основний канал (інтеграції з 1С та іншими обліковими системами). Потенційні CLI/MCP для AI-агентів — на тому самому API.
4. Ідентифікатори: зовнішні id НЕ потрібні — GUID 1С ідентичні нашим id і є ідентифікатором сутності (не лише для 1С). Узгоджено з інваріантом «id генерує викликач, не БД».
5. Завантаження товарів (з 1С чи по API) може відбуватись ОДНІЄЮ мовою; переклади можуть робитись окремим рішенням у магазині (у майбутньому — плагін чи щось подібне). Це має працювати разом.
6. По API може приходити команда на ПЕРЕЙМЕНУВАННЯ (зміна назви/текстів/slug) — це має підтримуватись коректно (наслідки для перекладів, slug/URL, SEO, знімків, пошуку).
7. Пошукова оптимізація і максимальна швидкодія: максимум у бенчмарках SEO/швидкодії; моментальна робота пошуку й фільтрів різними мовами з урахуванням уже ухваленого дослідження пошуку (леми тощо).
8. Усе має працювати як одна цілісна досконала система, а не «шматки, зліплені ізолєнтою».
9. Продумати, як інтерфейс підтримувати в програмному контурі звернення до адмінки (серверний шар адмінки / API) і як обробляти максимально якісно й надійно у всіх випадках.
10. Зіставлення за назвою/вільним текстом (напр. зони доставки за назвою міста) — помилка рішення: лише довідники й однозначний вибір користувачем того, що додано в адмінці. Подібні патерни шукати по всій системі.
11. Складений ідентифікатор «товар#характеристика» (CommerceML) НЕ підтримуємо. Модель SimplyCMS свідомо повторює концепцію 1С: товар → модифікація (= характеристика 1С, власний GUID = `product_modifications.id`), властивості товару й властивості модифікації окремо, види цін і ціни на (товар | модифікацію) × вид ціни. Ця структура — перевага платформи (саме її бракує в OpenCart), її зберігаємо; багатомовність і API мають лягти на неї, а не міняти її.
