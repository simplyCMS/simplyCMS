## 1. Базлайн: що наш механізм уже вміє (і чого не вміє)

Стан після Б.3/треку A: дискаверер v2 (sitemap-proposal, visit-проби
JSON-LD + сімʼя карток, чесний `unresolved` з 3 причинами, блокування пар),
інспекція v3 (canvas-семплер кольорів — CSS Color 4; motion-капчер:
transitions-кластери, keyframes + `inaccessibleSheets`, reveal-diff,
hover-sweep, JS-бібліотеки, триставний `jsDrivenSuspected`), мапінг v2
(merge N сторінок, структурований `unmapped` з `belowAA`), контракт тем v3
(23 кольори + radius + 2 шрифти + `fonts` + components + **views 5 сторінок**
+ slot-реквізити + conformance-гейт), скіл із 7 фаз, каналами чесності й
драбиною шліфування.

**Єдиний великий внутрішній геп:** side-by-side (фаза 5) — парні інспекції
тим самим `inspect.mjs`, але саме ПОРІВНЯННЯ — очі агента по полях JSON і
скріншотах; жодної числової метрики схожості в коді немає.

## 2. Що знайдено в інструментах (тільки дельта проти нашого)

### 2.1 JCodesMore/ai-website-cloner-template (свіжий стан)

Один новий механізм з середини серпня (коміт `92872bc`): **Atlas-фолбек
ассетів** — коли оригінальний ассет невідновлюваний і не є
брендом/логотипом, за явною згодою користувача генерується заміна через
image-gen API, з ОБОВʼЯЗКОВИМ маркуванням у `ARTIFACT_MANIFEST.md` як
fallback. Решта скіла без змін — наш interaction sweep/motion-капчер уже
покриває і перевищує їхній (у них — інструкції агенту, у нас —
детерміністичні скрипти).

### 2.2 Perfect-Web-Clone (ericshang98: skill + повний продукт)

- **«Three Principles» секціонування** (`chunk_content.py`, 642 рядки, і
  дубль у `component_analyzer.py` — правило-орієнтований, без AI попри
  README): детерміністичний геометричний розподіл сторінки на секції —
  extract → split (>N токенів, рекурсивно) → horizontal-layout detect
  (vertical overlap >30%) → remove overlaps → merge gaps → **машинна
  валідація** (no-overlap / coverage ≥80% / size-bound) з JSON-звітом і
  exit 1 при порушенні.
- **Bounded self-healing loop** (`self_healing_tools.py`, 646 рядків): збір
  помилок з 3 джерел (overlay/console/terminal) → дедуп за хешем →
  пріоритезація за severity → `max_attempts=5` → детекція «застряг на тій
  самій помилці».
- Слабкості (анти-приклади): ассети хотлінком на оригінальні URL; QA-фази
  фактично немає; поведінковий sweep значно бідніший за наш.

### 2.3 OpenKombai — переносити нічого

Одно-комітний MVP: скріншот → vision-опис → код, без екстракції, збірки,
верифікації. Розрив README ↔ код підтверджує правило «читай код».

### 2.4 abi/screenshot-to-code

- **Self-refine як інструмент у tool-loop**: `screenshot_preview` рендерить
  поточний HTML (Playwright, desktop+mobile, чекає `document.fonts.ready`)
  і повертає PNG прямо В КОНТЕКСТ моделі; system prompt: «завжди клич після
  create/edit і виправляй точковими edit_file». Без метрик — оцінює VLM
  очима; межа циклу — `max_steps=30`.
- **Ассет-конвеєр**: `extract_assets` (bbox-crop через vision із partial
  success), `generate_images` (лише для невитягуваних; заборона копіювати
  весь скріншот), `edit_images`/`remove_backgrounds`.
- **Відео-режим**: запис екрана (`getDisplayMedia`) → base64 → нативно у
  мультимодальний вхід (Gemini) — модель сама «дивиться» взаємодії; промпт
  вимагає відтворити ту саму поведінку.
- Промпт-дрібниці: піновані версії CDN-бібліотек (Babel 7.25.6 з поясненням
  чому), targeted-element edits через outerHTML-локатор.

### 2.5 Stanford Design2Code (метрики — головна знахідка раунду)

Пʼять обчислюваних скорів схожості (`metrics/visual_score.py`), без
жодних кастомних вагів:

1. **OCR-free детекція текст-блоків**: маючи HTML обох сторін,
   перефарбувати текстові елементи в унікальні кольори з пулу, зняти 2
   скріншоти з offset-палітрами, по піксель-диффу знайти bbox кожного
   блоку + справжній колір з оригінального скріншоту.
2. Matching блоків — угорський алгоритм по текстовій схожості (поріг 0.5).
3. Скори: **Block-Match** (площі matched/усіх — карає пропуски й
   галюцинації), **Text** (Sørensen-Dice), **Position** (1−max|Δцентрів|),
   **Color** (CIEDE2000 delta-E тексту), **CLIP** (косинус ембедінгів
   ViT-B/32 по скріншотах із заінпейнченим текстом).
4. Портованість: перші 4 — легкі (Playwright + геометрія/рядки, секунди на
   сторінку); CLIP — важкий (torch, ГБ вагів). Жорстка вимога — HTML ОБОХ
   сторін (у нашому кейсі є завжди: референс живий, наш магазин наш).
5. Промпт-режими: text-augmented (дай тексти списком — модель робить лише
   layout), layout-marker (`[1]`,`[2]`… замість тексту; вставка тексту
   другим LLM-проходом краща за автозаміну: 0.538 vs 0.512),
   visual-revision (реф + поточний рендер як 2 підписані зображення + «зроби
   однаковим» — single-shot, циклюється зовні).

### 2.6 tweakcn

- **Дельта поверхні токенів** проти наших 26: тіні як **6 компонентів**
  (color/opacity/blur/spread/offset-x/y), **letter-spacing**,
  **spacing**-одиниця (опційна), `font-serif`/`font-mono` окремо,
  `chart-1..5`, `sidebar-*` (у нас sidebar свідомо поза темою).
- **Затвердження теми — багатосценна галерея** (mail/dashboard/marketing/
  cards/typography + повний компонент-шоукейс), light/dark-перемикач,
  inspector-overlay «звідки цей колір», contrast-checker з живими
  «Aa»-семплами по 10 парах і фільтром «лише проблемні».
- Імпорт теми: paste-CSS (regex) і vision-LLM у Zod-схему; **з URL чужого
  сайту не вміє взагалі** — нашого детерміністичного інспектора не має.

### 2.7 Onlook

- DOM↔код через `data-oid`-інструментацію Babel-проходом; каскадне
  перейменування кольору по всіх .tsx (AST). Релевантно ЛИШЕ майбутньому
  треку B (візуальна композиція) — зафіксувати як референс для його спеки.
- «Зроби як сайт X» — делегує **Firecrawl API** (`formats: ['branding']`),
  власного екстрактора не має. Підтвердження унікальності нашого підходу.
