## 1. Що таке ai-website-cloner-template насправді

**Не парсер і не програма.** Кодова частина тривіальна: Next.js 16 +
shadcn/ui + Tailwind v4 стартер (один `page.tsx`, один `button.tsx`). Уся
цінність — один файл `.claude/skills/clone-website/SKILL.md` (~500 рядків),
розтиражований скриптом (`scripts/sync-skills.mjs`) у формати 13
AI-середовищ. «Двигун» — сам агент із браузерним MCP (Chrome/Playwright);
скіл — методологія, що змушує агента клонувати дисципліновано.

### 1.1 Пайплайн скіла (5 фаз)

1. **Reconnaissance** — повносторінкові скріншоти 1440/768/390px; витяг
   шрифтів/палітри/фавіконів; обовʼязковий **interaction sweep** (повільний
   скрол + клік по всьому інтерактивному + ховер + 3 viewport-и) із
   фіксацією у `BEHAVIORS.md`; топологія сторінки в `PAGE_TOPOLOGY.md`.
2. **Foundation** — глобальні токени/шрифти в CSS, скачування всіх ассетів
   генерованим скриптом (enumerate через DOM-скрипт: img/video/
   backgroundImage/svg/favicon).
3. **Component specs** — на кожну секцію `*.spec.md` ДО будь-якої збірки:
   точні значення з `getComputedStyle()` (не «на око»), модель взаємодії,
   усі стани, дослівний контент, responsive-поведінка, ассети.
4. **Parallel build** — по одному builder-агенту на секцію в git worktrees,
   спека інлайном у промпті; ліміт складності ~150 рядків спеки на агента;
   кожен агент верифікує `tsc --noEmit`.
5. **Assembly & QA** — складання сторінки, side-by-side порівняння з
   оригіналом на 1440 і 390, ітерація по розбіжностях (спека винна →
   ре-екстракція; білдер винен → фікс по спеці).

### 1.2 Найцінніші прийоми (переносимо дослівно)

- **Спека-файл як контракт** перед диспетчем будь-якого білдера
  (аудитований артефакт; білдер без спеки = вгадування).
- **«Визнач модель взаємодії ДО коду»** (static/click/scroll/time-driven) —
  їхня помилка №1: click-таби замість scroll-driven = повний переписон.
- **Витяг усіх станів, не лише дефолтного** (клікнути кожен таб; стилі на
  скролі 0 і 100+; дифф двох станів = специфікація поведінки).
- **Layered assets** (фон + оверлей + іконка в одному контейнері) — окремий
  чекліст, бо пропущений оверлей робить клон «порожнім».
- **Complexity budget**: спека понад ~150 рядків → секцію ділити.
- **Візуальний QA як обовʼязкова фаза**, а не «здається схоже».
- Список анти-патернів «What NOT to do» як частина скіла.

### 1.3 Обмеження оригіналу (наші переваги)

- Жорстко вимагає браузерний MCP — без нього не працює взагалі. У нас уже є
  Playwright (`@playwright/test`, `scripts/e2e.mjs`) → детерміністичний
  скрипт інспекції працює в будь-якому середовищі, браузерний MCP —
  опційне підсилення (interaction sweep).
- Нульова i18n-дисципліна (у нас — обовʼязкові каталоги тем + лінт).
- Клонує довільну сторінку з нуля — у нас структура канонічна, тож чесне
  позиціювання інше (§3).

## 2. Ландшафт подібних інструментів

Ринок ділиться на дві різні задачі: **pixel-clone** (відтворити чужу
сторінку 1:1) і **style-extraction** (витягти дизайн-систему і будувати
своє). Для SimplyCMS релевантна друга.

- [dembrandt](https://github.com/dembrandt/dembrandt),
  [extract-design-system](https://github.com/arvindrk/extract-design-system) —
  Playwright + computed styles → токени JSON/CSS; є і CLI, і Claude-скіл.
- [taste-skill](https://github.com/senlindesign/taste-skill) — витяг не лише
  значень, а «смаку» (чому такі трейд-офи); одиничний прохід
  `getComputedStyle` на елемент, ліміт пейлоада 60KB.
- Firecrawl website-design-clone — два паралельні scrape (бренд-токени +
  повний скріншот) → структурований markdown; потребує їхнього API.
- Комерційні (CopyWeb, Superdesign, same.dev, Clonesite) — закриті.

Джерела: [огляд клонерів 2026](https://copyweb.net/blog/website-cloner-best-top-10-in-2026),
[порівняння підходів](https://miromiro.app/blog/best-ai-website-cloners-compared),
[reverse-engineering дизайн-систем](https://www.context.dev/blog/how-to-reverse-engineer-any-websites-design-system),
[гайд Superdesign](https://superdesign.dev/blog/clone-a-website).

## 3. Позиціювання для SimplyCMS

**Не «клонер», а «редизайн за референсом» (design transfer):** з референсу
витягається дизайн-система і переноситься на наш каркас. Fidelity
нерівномірна, і це кажеться користувачу прямо на старті:

- головна сторінка — може бути дуже близькою до референсу
  (HeroBanner + HomeSections + власні сторінки в `src/routes/my/`);
- воронка покупки (16 канонічних сторінок) — «в кольорах, шрифтах і
  настрої» референсу; структуру диктує ядро (рішення D3/D4 — обґрунтування
  в парному ресерчі).

Після контракту v2.2 (типографіка + шрифти + розчинення brand-*) стеля:
«перефарбувати + шрифти + повністю власні Header/Footer/Hero/HomeSections».

## 4. Концепт скіла (актуалізований після Фази 4)

Форма: **скіл + детерміністичні скрипти**. Все, що можна зробити скриптом —
скрипт (повторюваність); усе, що потребує судження — агент за правилами
скіла. Спирається на штатний лайфсайкл тем Фази 4, нічого не дублює.

- **Фаза 0 — діалог-кларіфай:** URL(и) референсу і які сторінки дивитись;
  глибина (токени-only / повна тема / + власні сторінки); мапінг «блок
  референсу → наш слот» (hero → HeroBanner, секції → HomeSections); ключ
  теми; правові межі (§5).
- **Фаза 1 — інспекція (скрипт, Playwright):** скріншоти 1440/768/390;
  семплінг computed styles; кластеризація палітри з частотами; шрифти/ваги;
  radius/тіні/spacing; dark-mode за наявності → JSON + скріншоти в
  артефакт-теку. Interaction sweep — агентом через браузерний MCP, якщо
  доступний; без нього — чесна деградація до статичної інспекції.
- **Фаза 2 — мапінг токенів (скрипт пропонує, агент+користувач
  затверджують):** палітра → 23 семантичні ключі + типографічні токени
  v2.2 + `dark`-блок + перевірка контрасту пар `*`/`*-foreground` (WCAG).
- **Фаза 3 — скаффолд:** `pnpm simplycms create theme <name>` (штатний
  CLI; скаффолд + запис у конфіг) → заповнення `tokens.ts`/`fonts`.
- **Фаза 4 — компоненти за спеками:** дисципліна §1.2 (спека-файл →
  збірка → всі стани) для Header/Footer/HeroBanner/HomeSections; всі рядки
  UI — через `useThemeT` + каталог uk/en (контракт v2.1; парність-тест і
  eslint-глоб підхоплять автоматично). Темі дозволено тягнути дані хуками
  `@simplycms/core`/`@simplycms/supabase` — межі довіри на теми немає
  свідомо (Р10 Фази 4). Кастомні сторінки — `src/routes/my/`.
- **Фаза 5 — верифікація:** порядок гейтів репо + side-by-side скріншоти
  «референс vs локальний магазин» (наш Playwright) + активація в адмінці
  (`bootstrapThemes` робить рядок БД сам).

**Доставка кінцевим користувачам:** скіл + скрипти живуть у монорепо
(джерело правди), у шаблон `create-simplycms-store` їдуть через
`pnpm template:sync` (та сама механіка, що в решти тулінгу). У монорепо той
самий скіл слугує для розробки демо-тем.

## 5. Правові межі (частина діалогу Фази 0)

Переносимо: токени, лейаут-ідеї, настрій. НЕ переносимо: логотипи,
бренд-ассети, тексти, фото товарів (замість них — контент магазину
користувача). Заборонено використовувати для фішингу/імперсонації.
Аналог «Not intended for» оригінального шаблону, але вбудований у діалог.

## 6. Відкриті питання до етапу імплементації скіла

1. Playwright у шаблоні магазину: devDep шаблону чи on-demand установка
   при першому запуску скрипта інспекції.
2. Куди складати артефакти інспекції в магазині користувача
   (`docs/research/` комітом — аудитований слід, як у оригіналу — чи
   gitignore).
3. Мова/імʼя скіла для кінцевих користувачів шаблону (укр. конвенція
   команд монорепо vs англомовні користувачі скаффолда).
4. Обсяг MVP: фази 1–3 (токени+шрифти, без браузерного MCP) окремим
   релізом, фази 4–5 — другим.
