# codebase-memory-mcp — код-шар пошуку

Індекс коду репозиторію: символи, файли й **розділені** типи звʼязків
(`CALLS` окремо від `IMPORTS`). Обслуговує питання «де оголошено символ»,
«хто його викликає», «що зачепить зміна».

Документацію цей індекс **не** обслуговує — `*.md` виключені навмисно. Пошук по
канону робить `orient --map "<тема>"` (скіл `codebase-research`); це другий шар,
з власним двигуном і власним корпусом.

**Джерело:** `DeusData/codebase-memory-mcp`, реліз **v0.11.0**.
**Одне сховище на акаунт** — інші репозиторії на цій машині індексуються тим
самим інструментом і тим самим бінарником, без окремої установки.

Це заміна graphify, який тут працював до жовтня 2026: його AST-хуки лишали в
графі «привидів» після rename, зламались мовчки (`could not locate a Python with
graphify installed`), а `orient` при цьому тихо падав на греп — що на питанні
«хто кличе» дає хибну відповідь (див. «Чесна деградація»).

## Установка

Інструмент ставиться **глобально, не в репо**: один інструмент на машину.

```bash
# 1. Архів релізу v0.11.0 з GitHub (не `curl … | bash`):
#    так інсталятор можна прочитати ДО запуску, а це потрібно, щоб знати,
#    що саме він пише поза git.
# 2. Установка з розпакованого архіву:
<шлях-до-архіву>/bin/codebase-memory-mcp install -y --force \
  --dir="$HOME/.local/bin" --clients=claude
```

Перед запуском корисно подивитись, що саме буде дописано:

```bash
codebase-memory-mcp install -n --dry-run --dir="$HOME/.local/bin"
```

🔴 **Пастка установки: group-writable тека.** Інсталятор відмовляється ставити
бінарник у теку з правами `0775` і падає з
`install_dir_group_or_world_writable`. Це стосується і теки призначення, і теки,
з якої запускається бінарник:

```bash
chmod g-w ~/.local ~/.local/bin
```

Сам shell-скрипт `install.sh` пише лише бінарник і копію себе як updater, а
**конфігурацію агентів виконує бінарник** (`"$DLBIN" install -y --force --dir=…`).
Тобто читання `install.sh` повного переліку дописок не показує — його показує
`--dry-run`.

### Що дописується поза git

`~/.local/bin/codebase-memory-mcp` і `install.sh`; PATH у `~/.bashrc`; MCP-запис у
`~/.claude.json`; скіл `codebase-memory` і **три агенти** (`codebase-memory`,
`-scout`, `-auditor`) у `~/.claude/`; хуки Claude Code — `PreToolUse` на
`Grep|Glob|Bash`, `PostToolUse` на `Read`, `SessionStart`, `SubagentStart`.

У **репозиторій інсталятор не пише нічого**, і `.mcp.json` не створює. Так і має
лишатись: у cloud-сесіях бінарника немає, і закомічений конфіг давав би там
постійну помилку підключення. Єдиний закомічений артефакт — `.cbmignore`.

## Де що лежить

| Що | Шлях |
| --- | --- |
| бінарник | `~/.local/bin/codebase-memory-mcp` |
| сховище індексів (усі проєкти) | `~/.cache/codebase-memory-mcp/` |
| індекс цього репо | `~/.cache/codebase-memory-mcp/<проєкт>.db` |
| логи | `~/.cache/codebase-memory-mcp/logs/` |
| скоуп індексації | `.cbmignore` у корені репо |

Імʼя проєкту — не імʼя репо, а **слаг абсолютного шляху** (`/a/b/simplyCMS` →
`a-b-simplyCMS`); актуальне дає `list_projects`. `orient` шукає проєкт за
`root_path`, а не за імʼям.

🔴 **Індекс прив'язаний до шляху.** Кожен git-worktree і кожен другий клон — це
окремий проєкт, який треба проіндексувати окремо; без цього `orient <Символ>`
чесно відмовить (`orient --doctor` покаже «цей корінь не проіндексовано»), а
головна сесія, яка бачить MCP по основному клону, відповідатиме про ІНШУ гілку.

## Дві поверхні доступу

**MCP** — для головної сесії й субагента `codebase-research` (`.claude/agents/`).
Інструменти видно в переліку на кожному кроці: `search_graph`, `trace_path`,
`get_code_snippet`, `query_graph`, `get_architecture`, `search_code`,
`get_graph_schema`, `list_projects`, `index_status`, `detect_changes`,
`check_index_coverage`.

🔴 MCP-сервери підхоплюються **на старті сесії**. Сесія, відкрита до установки,
інструментів не побачить — потрібен рестарт.

**CLI** — той самий двигун із bash, для ролей без MCP (і для `orient`):

```bash
codebase-memory-mcp cli --quiet <tool> '<json-аргументи>'
codebase-memory-mcp cli --quiet search_graph '{"project":"<проєкт>","name_pattern":"<Символ>"}'
```

🔴 **Вивід стискає спільні префікси шляхів, і обрізається по-різному залежно від
інструмента.** Рядок `@13+suffix` означає `prefix[13] + suffix`; саме правило
приходить у виводі — але поле зветься **по-різному**: `rows_ref_rule` у
`query_graph`, `results_ref_rule` у `search_graph` (є ще посекційні
`file_tree_ref_rule`, `impacted_ref_rule`, `qn_rule`). Хто його ігнорує — рахує
неправильно. Скрипти (`orient`) просять `"format":"json"` і цієї пастки не мають.

Межа виводу теж не одна: `query_graph` віддає сторінками по 200 із курсором
(`next_cursor`, `next_offset`, `truncation_reason: page_limit`), а `search_graph`
ріже за бюджетом виводу (`truncation_reason: output_budget`). Завжди звіряй
`returned` із `total`, перш ніж вважати відповідь повною.

## Індексація й свіжість

```bash
codebase-memory-mcp cli --quiet index_repository '{"repo_path":"<абсолютний шлях>"}'
```

Повна індексація цього репо — **кілька секунд** (≈9,5 тис. вузлів, ≈36 тис.
звʼязків). Далі свіжість тримає watcher, тож ребілдити руками не треба.

Переіндексація потрібна в одному випадку: **після зміни `.cbmignore`**. Інакше в
індексі лишаються вузли з файлів, які щойно виключені, — відповідь двигуна стає
неправдивою, не показуючи цього у виводі. `orient --doctor` порівнює час
останньої зміни `.cbmignore` із часом індексації й каже про розбіжність.

### `.cbmignore`

Той самий синтаксис, що й `.gitignore`. Поверх нього діє сам `.gitignore`:
файл, ігнорований git, до індексу не потрапляє (у звіті індексації такі файли
мають `reason: gitignore`). Саме тому `.env.local` із реальними секретами в
індекс не потрапляє. Що виключено й навіщо (кожен блок має коментар у файлі):

- `*.md`/`*.mdx` — доки обслуговує інший шар;
- білд-артефакти й генерат (`dist/`, `routeTree.gen.ts`, `.output/`, …);
- 🔴 `.claude/worktrees/` — вкладені git-worktree агентів лежать всередині теки
  репо; без виключення основний індекс тягнув би повну копію коду на кожен;
- 🔴 **копії монорепо**, які синхронізує `pnpm template:sync` під тестом парності:
  `packages/create-simplycms-store/template/` і `packages/cli/host/`. Кожен
  символ host-а мав би двійника, і `orient adminRequestGuard` показував би
  оголошення в копії нарівні зі справжнім. Ціна рішення: символ, який існує
  ТІЛЬКИ в шаблоні (немає в `src/`), індекс не побачить — для шаблону працюють
  `Grep`/`Read`;
- `packages/simplycms/{drizzle,seed-migrations}/` — SQL-знімки, не код, який хтось
  викликає. (Канонічні міграції `packages/simplycms/migrations/` лишаються.)

## Конфігурація

```bash
codebase-memory-mcp config list
codebase-memory-mcp config set <ключ> <значення>
```

`ui_enabled` вимкнено навмисно: HTTP-візуалізація графа цьому репо не потрібна.
Ембединг-підсистеми в конфігурації немає взагалі — вектори й семантичний пошук
тут не використовуються: на корпусі MetaHub (де це заміряно) ембединг коду дав
score 0.17 на український запит і 0.042 на англійський, у топі стояв шум із
тестів, тож лексичний пошук виграє на порядок.

## Шар доків: опційна лематизація

`orient --map "<тема>"` шукає по канону власним BM25 (`scripts/map-search.py`) і
**не залежить** від код-шару. Корпус: `docs/architecture`, `docs/development`,
`docs/guides`, `docs/tasks`, `AGENTS.md`, `packages/README.md` — **без**
`docs/superpowers/{plans,specs}` (історія засмічує видачу). Скрипт — копія
MetaHub-ового, адаптована під цей корпус (не спільний пакет: зчеплення двох репо
гірше за розходження копій); параметри BM25 (`k1=1.5`, `b=0.3`) — заміри MetaHub,
власного заміру на корпусі SimplyCMS ще немає.

Два режими нормалізації, обидва робочі:

| режим | коли | влучання в топ-5 (заміряно в MetaHub) |
| --- | --- | --- |
| **леми** (`pymorphy3`) | є venv нижче | 100% |
| сирі токени | venv немає (cloud, свіжий клон) | 87% |

Фолбек не поломка, але локально леми варті 34 МБ:

```bash
uv venv ~/.local/share/simplycms-doc-search/venv
uv pip install --python ~/.local/share/simplycms-doc-search/venv/bin/python \
  pymorphy3 pymorphy3-dicts-uk
```

🔴 Чому venv, а не `pip install`: більшість дистрибутивів позначають системний
Python як `externally-managed`. `orient` сам знаходить venv за шляхом вище;
інше місце задається `ORIENT_DOC_VENV`.

Рівень видно у виводі праворуч від шляху (`леми` / `сирі токени`); якщо venv не
знайдено, `--map` сам це скаже наприкінці виводу з командами. Мовчазної
деградації тут немає навмисно.

## Чесна деградація

`orient` має три режими, і деградують вони по-різному — за одним правилом:
**деградація дозволена лише там, де лексика (греп) чесна.**

| режим | без cbm | чому |
| --- | --- | --- |
| `orient <Символ>` | **відмовляє** (код виходу 1) | греп через барелі бреше на «хто кличе» |
| `orient --plan` | шляхи/рядки — файлова система; символи — `rg`/`grep` лише по ОГОЛОШЕННЮ, з явним застереженням | оголошення або збігається з патерном, або ні |
| `orient --map` | працює так само | cbm не використовує |

Заміряно на цьому репо (`withActor`): старий греп-фолбек `orient` показував
**49 «споживачів-файлів»** (README, тести, реекспорти, самі оголошення), cbm — **15
прямих викликів** (`trace_path`, `mode: calls`, `depth: 1`). Дефолтна глибина —
1: транзитивний обхід (`--depth N`) додає hop 2+ і розбивається за hop, щоб
2-хопового викликача не прийняли за прямого.

## Заміряні межі двигуна

У відповідь треба дивитись, а не приймати число:

**Кратні виклики схлопуються.** Ребро `CALLS` зберігає один `line`-атрибут на пару
«викликач → викликаний», тож два виклики символа з тієї самої функції дають одне
ребро. Двигун сам сигналізує про невпевненість: `trace_path` з `include_evidence`
віддає на кожному ребрі `confidence` і `strategy` (`orient` друкує їх; евристичне
ребро ≈0.55, резолвлене ≈0.95).

**Перейменований імпорт може випасти.** На `import { X as Y }` у багаторядковому
імпорт-блоці файл-імпортер може не потрапити у відповідь. Питання «хто кличе» це
не зачіпає, але **«хто імпортує» варто перевіряти грепом**:

```bash
git grep -nE 'import\s*\{[^}]*\bСимвол\b'   # однорядкові
git grep -n  'Символ as '                   # перейменування
```

**`CALLS` — це виклики.** Змінна чи константа, яку передають як значення
(middleware в масиві, конфіг, токен), споживачів у цій осі не має: на
`adminRequestGuard` (middleware в `requestMiddleware`) cbm чесно показує «0
кличуть». `orient` додає попередження для символів, що не є функцією/класом.

🔴 Правило з усього вище: **порожній або круглий результат — привід перевірити, а
не підстава стверджувати.** Саме тому агент `codebase-research` зобовʼязаний
кликати `check_index_coverage` перед твердженням «такого немає».

## Оновлення

```bash
codebase-memory-mcp update
```

🔴 **`update` виконує `install` наново — і повертає все, що той ставить.** Три
вендорські субагенти (`codebase-memory`, `-scout`, `-auditor`), хуки й активаційні
вказівники зʼявляться знову, навіть якщо їх прибрали. Після кожного оновлення
перевіряй `ls ~/.claude/agents | grep codebase-memory`.

## Відкат

```bash
codebase-memory-mcp uninstall            # додай -n --dry-run, щоб спершу подивитись
```

Знімає бінарник, MCP-запис, скіл, агентів і хуки; про індекси питає окремо.

🔴 **Чого uninstall НЕ знімає: PATH-дописку в `~/.bashrc`.** Рядок
`export PATH="$HOME/.local/bin:$PATH"` лишається сиротою — прибирати вручну.

## Перевірка після установки

```bash
codebase-memory-mcp --version                     # має бути 0.11.0
codebase-memory-mcp cli --quiet list_projects '{}'
.agents/skills/codebase-research/scripts/orient --doctor
```

У `get_graph_schema` має бути видно **окремі** типи ребер `CALLS` і `IMPORTS` —
це і є властивість, заради якої двигун обрано: відповідь на «хто кличе» не
змішується з реекспортами через барелі.
