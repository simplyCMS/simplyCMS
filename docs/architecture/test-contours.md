# Тестові контури: що який рівень доводить

> Джерело правди про **межі тестування**. Заведено 2026-08-04 після того, як
> два дефекти опублікованого `0.2.0` виявились у зоні, яку не покриває жоден
> автоматичний контур. Схема-компаньйон (візуальна) —
> [артефакт «Тестові контури SimplyCMS»](https://claude.ai/code/artifact/ae1b9379-b2af-41ea-bcdd-8a3c91541d89).

## 1. Різниця, заради якої існує пілот

Код ядра потрапляє в магазин **двома різними шляхами**, і вони перевіряють
різні речі:

| | Монорепо (`pnpm dev`, `pnpm test`) | Справжній магазин |
|---|---|---|
| Рядок у коді | `import '@simplycms/ui'` | той самий |
| Резолв | `vite resolve.alias` + `tsconfig paths` | node-резолв + `exports`-мапа |
| Куди веде | `packages/ui/src/button.tsx` — **сирці** | `node_modules/@simplycms/ui/dist/button.js` — **збірка** |

🔴 Усе, що лежить між цими двома шляхами, у монорепо **не виконується жодного
разу**: збірка `tsup`, коректність `exports` і `publishConfig.exports`,
повнота `dependencies`, peer-діапазони, вміст tarball (`files`), робота
`bin`. Тому зелений `pnpm test` **нічого не каже** про те, чи працює
опублікований пакет.

Звідси головний принцип: **кожен контур покриває префікс конвеєра**, а не
окрему точку. Дефект живе там, де префікс закінчився.

## 2. Конвеєр і покриття

```
монорепо → build:packages → pnpm pack → npm registry → create-store → магазин
└── pnpm test ┘
└──────── pilot:pack (A/C/D/CLI) ────────┘
└──────────── pilot:e2e (+B/E) ───────────────────────────┘
                                        └── НЕ ПОКРИТО ────────────────┘
```

| Контур | Команда | Доходить до | Потребує |
|---|---|---|---|
| Юніти | `pnpm test` | сирців | — |
| Пакувальність | `pnpm pilot:pack` | локальних tarball-ів | — |
| Проти живої БД | `pnpm pilot` | + HTTP-відповіді | `.env.local` |
| Локальний стек | `pnpm pilot:e2e` | + БД із нуля, owner-флоу | **Docker** |
| Реальний реєстр | **немає** | — | мережа |

## 3. Що доводить кожен гейт

| Гейт | Доводить | Джерело |
|---|---|---|
| **A** | Генератор роутів зібрав те саме дерево, скануючи `node_modules/@simplycms/*/routes`, а не `packages/`; import-и генерату ведуть у `node_modules` | `gate-a.mjs` |
| **B** | `createServerFn` працює в PRODUCTION-манифесті, а не лише в dev-режимі монорепо; SSR-рендер, guard `/admin`, sitemap/robots/health | `gate-b.mjs` |
| **C** | Серверний код не тече в клієнтський бандл; code splitting живий. Джерело — модульний граф (`bundle-stats.client.json`), не vite-manifest | `gate-c.mjs` |
| **D** | Tailwind v4 бачить компоненти пакетів: у зібраному CSS є утиліти, що зустрічаються **виключно** в `@simplycms/*` | `gate-d.mjs` |
| **E** | Перший signup НЕ отримує `admin` (міграція в живій схемі); `owner:invite` ідемпотентний; `/auth/confirm` ставить cookies і редиректить | `gate-e.mjs` |
| **CLI** | Упакований скаффолдер живий: `template/` у tarball, `bin` запускається, плейсхолдери підставлені, `@clack/prompts` у `dependencies` | `create-pkg-smoke.mjs` |

🔴 Gate E — **єдине** місце, де взагалі виконується міграція
`first_user_no_auto_admin` і invite-флоу.

✅ **Перший успішний прогін — 2026-08-04** (Docker встановлено того ж дня):
```
OK  перший signup БЕЗ ролі admin — ролей у покупця: 1
OK  owner-invite ідемпотентний + роль admin — 2 прогони → 1 користувач, рядків admin: 1
OK  GET /auth/confirm — 302 → .../auth/set-password, auth-cookies: true
```
Третій рядок — живий доказ фікса blocker-а з код-рев'ю: до заміни
`Response.redirect` на `redirectResponse` ця перевірка дала б 500.

## 4. Сліпі зони (станом на 2026-08-08)

1. **Установка з реального реєстру.** Пілот ставить *локальні* tarball-и;
   користувач бере пакети з реєстру. Після міграції на `pnpm` (2026-08-08)
   різниця лишилася **тільки по джерелу**, не по менеджеру — сліпа зона
   звузилась, але не закрилась. Вона дала один із двох дефектів `0.2.0`: 404 на
   tarball (CDN-лаг ~5 хв після публікації). Ручний прогін 2026-08-04 після
   `0.2.1` пройшов наскрізь (install exit 0 + build exit 0, `dist/` 3.1 MB),
   але автоматичного гейта на це досі немає — це Gate F, §7 п.3.
2. ~~**Пакетний менеджер.**~~ — **закрито 2026-08-08.** Пілот ставить скретч
   через `pnpm install` (`scripts/pilot-pack/build.mjs`, `pnpmInstall`), тим
   самим, який декларує магазин. Що тепер **покрито**: `allowBuilds` реально
   виконується (це його відсутність дала другий дефект `0.2.0`); ізольована
   розкладка `node_modules` — тобто недекларована залежність більше не
   резолвиться хойстингом. Що **не покрито**: `minimumReleaseAge` — він не
   чіпає `file:`-tarball-и взагалі, тож ядро повз нього проходить, а на
   третьосторонні залежності діє дефолт, який pnpm тихо обходить
   авто-винятком. Свідома втрата: плоске дерево як **незалежний** спосіб
   довести самодостатність пакета більше не використовується — цю роль
   тримає статичний `scripts/audit-deps.mjs`.
3. **Мовчазна відмова механізму tarball-ів.** Примус локальних пакетів —
   `overrides` у `pnpm-workspace.yaml` скретча; npm-івську форму того самого
   поля pnpm ігнорує без жодного попередження. Раніше поламка була голосною
   (пакетів у реєстрі не існувало → `ERR_PNPM_FETCH_404`), тепер у реєстрі
   лежить та сама версія, тож пілот мовчки перевіряв би **вже опубліковані**
   пакети замість тих, що йдуть на публікацію. Закрито гардом провенансу
   (`scripts/pilot-pack/provenance.mjs`): він читає lockfile скретча й падає,
   якщо хоч один пакет ядра приїхав не з `file:`. Негативний контроль
   пройдено — з вимкненим механізмом 17 із 20 пакетів приїхали з реєстру.
4. **Живі клікові смоки** — частково закрито 2026-08-04 (див. §8): плагін,
   тема і `/profile` перевірені руками; лишився invite-лист через Mailpit.
   Автоматичних браузерних тестів досі немає.
5. **Owner-флоу цілком:** лист від GoTrue за нашим шаблоном → перехід за
   `token_hash` → установка пароля в браузері. Gate E перевіряє роут напряму
   через `generateLink`, обходячи сам лист.
6. **Версії локального стеку відстають від хмари** (спіймано на першому
   прогоні e2e): `gotrue v2.186.0` проти `v2.195.0` у linked-проєкті,
   `storage-api v1.35.3` проти `v1.67.26`. Для перевірки власної логіки не
   блокер, але e2e ганяється не на прод-версіях — або підтягувати, або
   свідомо зафіксувати розбіжність.

## 5. Роль `src/` і план `apps/dev-store`

`src/` — це **не окремий продукт, а найтонший можливий host**: 13 файлів,
жодної сторінки. Роути й сторінки в пакетах, host лише монтує їх через
`routes.ts` і склеює `EngineContext`; `src/routes/my/` — порожня тека під
кастомні сторінки магазину.

Тобто `src/` уже виконує роль **референсного магазину** — просто не названий
цією роллю. Спека платформи (§4.1) описує цільову розкладку як
`packages/*` + `apps/dev-store` («референс/тестовий магазин для розробки
платформи; сьогоднішній `src/`»).

🔴 **Переїзд сам по собі нічого не тестує.** Його цінність в іншому: щойно
магазин стає текою в `apps/`, поруч можна покласти **другий** — той, що
збирається з `node_modules`, а не з aliasів. Тоді нинішній одноразовий скретч
у `/tmp` стає постійним і відкриваним в IDE, і аж тоді стають можливі
браузерні смоки: сьогодні клацати просто нема де.

## 6. Політики pnpm 11, що впливають на контури

- **`allowBuilds`** (наступник `onlyBuiltDependencies`, формат — мапа, місце —
  `pnpm-workspace.yaml`). Без нього install обривається
  `ERR_PNPM_IGNORED_BUILDS`, а `pnpm build` перезапускає install і теж падає.
- **`minimumReleaseAge`**, дефолт **1 доба**: pnpm не резолвить пакети,
  опубліковані менш ніж добу тому. Наслідок для контурів — будь-який гейт, що
  ставить *щойно опубліковані* пакети, падатиме перші 24 години після релізу.
  Тому гейт «проти реального реєстру» має ганятись **за розкладом або
  вручну**, а не в PR-конвеєрі.

🔴 З 2026-08-08 обидві політики діють **усередині** пілота — він ставить скретч
через `pnpm`. Виміряні наслідки (прогони на pnpm 11.20.0):

- `allowBuilds` шаблону (`esbuild`, `sharp`, `unrs-resolver`) тепер реально
  виконується. Для реєстрових пакетів ключ — голе ім'я; для `file:`-залежностей
  це **повний id з ВІДНОСНИМ шляхом** (`pkg@file:../../tarballs/pkg-1.0.0.tgz`),
  навіть якщо в override шлях абсолютний. Нас це не зачіпає лише тому, що жоден
  пакет ядра не має install-скриптів — щойно зʼявиться, зачепить.
- `minimumReleaseAge` **не чіпає `file:`-tarball-и взагалі** (перевірено
  значенням у 10 років), тож ядро проходить повз. Часової крихкості пілот не
  набув: при ДЕФОЛТНОМУ значенні pnpm на свіжу залежність не падає, а сам
  дописує `minimumReleaseAgeExclude` і йде далі. Падіння
  (`ERR_PNPM_NO_MATURE_MATCHING_VERSION`) дає лише **явно заданий** параметр —
  тому в скретчі його свідомо не перевизначаємо.
- 🔴 pnpm **мутує** `pnpm-workspace.yaml` під час install. У скретчі це
  нешкідливо (тека одноразова), але генератор не має вважати файл своєю
  незмінною власністю.

## 6.1. Оточення для e2e (перевірено 2026-08-04)

Без цього `pnpm pilot:e2e` не запуститься, і кожна нова сесія витратить
години на ті самі граблі.

**Docker.** Ubuntu 24.04, офіційний репозиторій Docker (не `docker.io` з
Ubuntu). Ключ і репо — [docs.docker.com/engine/install/ubuntu](https://docs.docker.com/engine/install/ubuntu/).
🔴 Після `sudo usermod -aG docker $USER` членство в групі **не діє в уже
відкритих сесіях**. Або перелогінитись (для SSH — розірвати й підняти
з'єднання; нове вікно термінала того самого сеансу не допоможе), або ганяти
через `sg docker -c '<команда>'` — це працює одразу й без перелогіну.

**Диск.** Стек Supabase — 13 образів, **10.27 GB** (виміряно
`docker system df` після прогону). Плюс скретч-магазин і томи БД. На 38 GB
диска, з яких 29 GB уже зайнято, прогін падає на середині з `ENOSPC`, і
харнес втрачає можливість писати stdout — виглядає як повне зависання.
Мінімум — ~15 GB вільних. Звільнити: `pnpm store prune`,
`npm cache clean --force`, `docker system prune -af --volumes`.

**Версії стеку.** `supabase start` попереджає, що локальні образи старші за
linked-проєкт (2026-08-04: `gotrue v2.186.0` проти `v2.195.0`,
`storage-api v1.35.3` проти `v1.67.26`). Для перевірки власної логіки не
блокер — див. сліпу зону №5.

## 6.2. Як підняти локальний контур руками (для перегляду в браузері)

`pilot:e2e` гасить стек за собою (`supabase stop --no-backup` — томи
видаляються навмисно, щоб наступний прогін починався з чистої БД). Тому
«подивитись сайт після e2e» не вийде — контур треба піднімати окремо:

```bash
sg docker -c 'supabase start'
sg docker -c 'supabase db reset --yes'     # міграції + supabase/seed.sql
```

Далі `.env.development.local` (він у `.gitignore` і **перекриває**
`.env.local` лише для `vite dev`, тож робочі ключі не чіпаються) з
`API_URL`/`PUBLISHABLE_KEY` зі `supabase status -o json`, і `pnpm dev`.

🔴 Сід дає товари, секції, тему й плагін, але **жодного користувача**:
міграція `first_user_no_auto_admin` прибрала авто-адміна, тож власника
треба створити service_role-ключем — `auth.admin.createUser` +
upsert у `user_roles`. Це той самий шлях, що й `owner:invite`, лише з
паролем замість листа.

Порти локального стеку: API `54321`, БД `54322`, Studio `54323`,
Mailpit `54324` (усі листи GoTrue осідають там — invite-флоу видно очима).

🔴 **Якщо браузер не на тій машині, де стек** (VS Code Remote-SSH, `ssh -L`):
значення `VITE_*` вшиваються в **клієнтський** бандл, тож адресу резолвить
браузер. Прокинути треба **і `3002`, і `54321`** — інакше сайт відкриється,
а логін упаде з `ERR_CONNECTION_REFUSED` на `POST /auth/v1/token`, бо для
браузера `127.0.0.1:54321` — це його власна машина. Підставляти замість
localhost LAN-IP не варто: збірка прив'яжеться до конкретної адреси мережі,
і туди ж вестимуть посилання в листах GoTrue.

## 7. Куди рухатись (порядок за співвідношенням ціна/цінність)

1. ~~**Docker + Gate E**~~ — **зроблено 2026-08-04**. Побічний урок про
   середовище: стек Supabase важить рівно 10.27 GB образів, тож 38 GB диска
   не вистачало; довелось розширювати LVM до 48 GB.
2. ~~**Пілот з `npm` на `pnpm`**~~ — **зроблено 2026-08-08.** Підтверджена
   прогонами форма: overrides для pnpm 11 живуть у top-level ключі `overrides:`
   файлу `pnpm-workspace.yaml`; `pnpm.overrides` у `package.json` ігнорується з
   попередженням, а npm-івський top-level `overrides` — **мовчки**. Блок
   дописується у файл, скопійований із шаблону (оверлей затер би `allowBuilds`).
   Додано гард провенансу — див. сліпу зону №3.
   🔴 **Що прогін спіймав одразу.** Gate C упав: 3 клієнтські чанки замість 207,
   уся адмінка (98 модулів) і tiptap (22) в initial. Причина не в пілоті — в
   магазині: pnpm розкладає залежності симлінками, Vite їх резолвить, і
   code-splitter TanStack Router не впізнає роут, бо шукає його в
   `TSR_ROUTES_BY_ID_MAP` за realpath, а генератор заповнив мапу шляхами через
   симлінк. Тобто **кожен магазин, поставлений через pnpm, віз увесь застосунок
   одним чанком** — і жоден контур цього не бачив, поки пілот ганяв npm.
   Виправлено `realpathSync` у `template/routes.ts`; після фікса — точний
   паритет із плоским деревом (207 чанків, initial 19/303, адмінка й tiptap в
   initial 0).
3. **Gate F: установка з реального реєстру** — рідкісний, за розкладом
   (див. `minimumReleaseAge`).
4. **Переїзд у `apps/`** + браузерні смоки поверх постійного `e2e-store`.


## 8. Ручний смок повного розгортання магазину

Гейти A–E доводять механіку, але **не бачать нічого, що існує лише в
браузері**: гідратацію, застосування CSS-змінних теми, кліки без
перезавантаження, рендер листа GoTrue. Нижче — процедура, яка це закриває.
Проходити перед релізом, що чіпає тему, плагіни, auth або каркаси.

### 8.1. Який контур піднімати

Два різні сценарії, і плутати їх не можна:

| | **A. dev-store монорепо** | **B. магазин із реєстру** |
|---|---|---|
| Що перевіряє | поведінку UI, швидка ітерація | той самий UI **плюс** пакування |
| Резолв ядра | alias → сирці | `node_modules` → `dist` |
| Підняття | §6.2, потім `pnpm dev` | `pnpm create simplycms-store` + `pnpm install && pnpm build && pnpm start` |
| Коли | щоденно | перед релізом і після нього |

🔴 Сценарій A **не доводить нічого про опублікований пакет** (див. §1). Якщо
перевіряєш реліз — потрібен B, і саме на ньому спливли обидва дефекти `0.2.0`.

### 8.2. Підготовка (обидва сценарії)

1. Стек і БД — §6.2 (`supabase start`, `db reset`).
2. Власника створити service_role-ключем: сід користувачів **не дає**
   (міграція `first_user_no_auto_admin` прибрала авто-адміна).
3. 🔴 Якщо браузер не на машині зі стеком — прокинути **і порт застосунку,
   і `54321`**; інакше сайт відкриється, а логін упаде з
   `ERR_CONNECTION_REFUSED` (див. §6.2).

### 8.3. Чек-лист

**Вітрина (анонімно).** `/` і `/catalog` показують 4 товари `Pilot Seed …` з
цінами в ₴; `/admin` редиректить на `/auth`.
🔴 `curl` тут не доказ: каталог бере товари через `useQuery` **на клієнті**,
тож у HTML їх не видно, хоч сторінка й робоча.

**Плагін.** `/admin/plugins` → вимкнути `hello-world` → віджет зникає з
дашборду **без перезавантаження** → увімкнути → з'являється.

**Тема.** `/admin/themes` → активувати іншу тему → перейти на вітрину
**в межах застосунку** (не F5) → палітра змінилась.
Як переконатись, що теми взагалі різні, а не «однакові на вигляд»: у
`themes/*/tokens.ts` порівняти `primary`. Станом на 2026-08-04:
`default` = `4 58% 56%` (кораловий), `solarstore` = `203 85% 47%` (синій).
Перевірка з боку сервера — `curl -s <адреса>/ | grep -o -- '--primary: [^;]*'`:
токени інлайняться в `<style>` через `ThemeTokens`.
🔴 Пастка інструменту: HTML — це один рядок на 40+ КБ, тож `grep -oE` із
контекстом (`.{200}…`) мовчки нічого не знаходить. Шукати без контексту або
через `python3`.

**Профіль.** Логін → `/profile` під залогіненим користувачем.

**Invite-флоу (єдиний, що досі не пройдено).** `owner:invite` на новий email →
лист у Mailpit (`54324`) → перехід за посиланням має привести на
`/auth/set-password` із живою сесією. Gate E перевіряє цей роут напряму через
`generateLink`, **обходячи сам лист**, — тобто ланка «GoTrue рендерить наш
`invite.html`» не перевірена ніким.

**Знайдений дефект (виправлено).** Адмінка скидала лише СЕРВЕРНИЙ кеш
(`POST /api/revalidate-theme`), але не клієнтський: `_storefront` має
`staleTime: 5 * 60_000`, тож перехід на вітрину в межах застосунку до п'яти
хвилин показував стару тему, а тост стверджував «Зміни застосовані на сайті».
Ловилось лише hard-refresh-ем. Фікс — `useRevalidateStorefront()`
(`packages/admin/src/lib/revalidateTheme.ts`), яка робить обидва кроки;
гард — `packages/admin/src/__tests__/revalidate-storefront.test.tsx`.

Це і є аргумент за ручний смок: механіка була зелена в усіх гейтах, а
користувач бачив стару тему.
