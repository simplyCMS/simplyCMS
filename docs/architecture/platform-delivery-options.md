# SimplyCMS як платформа: варіанти механізму поставки ядра, плагінів і тем

> **Статус:** аналітичний документ для ухвалення напряму. Створено 2026-07-30.
> **База:** дослідження 9 напрямів (Medusa, Vendure, Payload, Nuxt Layers, Shopware/Saleor,
> OpenCart/WordPress/Magento, shadcn registry, TanStack Start внутрішньо, механіки поставки
> оновлень) + 2 адверсарні верифікації з живими експериментами на версіях пакетів цього репо
> + критик повноти. Повні матеріали досліджень — у сесійному scratchpad
> (`scratchpad/research/*.md`); ключові факти й джерела продубльовані тут.
> **Мета:** SimplyCMS має стати OpenCart-подібною платформою: ядро розвивається окремо,
> поверх нього збираються повні інтернет-магазини, плагіни й кастомні теми. Модель поставки
> вже ухвалена: **розробник встановлює через код + rebuild** (npm-пакети; без runtime-zip).

---

## 1. Від чого відштовхуємось: як влаштовано зараз і чому це не платформа

Сьогоднішній «магазин» — це **форк усього репозиторію**:

| Шар | Як зараз | Наслідок |
|---|---|---|
| Каркас (65 route-файлів, `src/server/*`, `__root.tsx`, `start.ts`) | Живе в репо магазину | Нова сторінка ядра **не доїжджає** до існуючих магазинів — її треба переносити руками (git merge форка) |
| Теми | Статичні імпорти в рукописному `src/theme-registry.ts`; активація прапорцем `themes.is_active` у БД | Додати тему = редагувати код магазину + rebuild. Контракт жорсткий: 3 лейаути + **16 обовʼязкових сторінок, жодної опційної** (`theme-system/src/types.ts`) |
| Плагіни | Runtime існує (`HookRegistry`, `PluginSlot` у 12+ місцях, таблиця `plugins`, адмін-сторінки), але `registerPluginModule()`/`loadPlugins()` **ніде не викликаються** | Усі слоти рендерять порожньо; «встановити плагін» неможливо в принципі |
| Ядро | Два канали одночасно: git subtree (`cms:pull/push`) і GitHub Packages (6 із 17 пакетів, тег v0.1.0) | Немає одного каналу правди; 10 з 17 пакетів `private: true` (зокрема core, admin, ui, theme-system, plugin-system) |
| Конфігурація | `simplycms.config.ts` (мінімальний) + стан у БД | Два джерела істини, режими розсинхрону не визначені |

**Фізика стека, яку не обійти:** TanStack Start — це Vite-збірка з file-based routing:
генератор сканує `src/routes`, пише `routeTree.gen.ts` (роути + типи + code-splitting).
На відміну від PHP-світу OpenCart, «покласти файл — і воно працює» без збірки не буває.
Тому платформа для нашого стека — це **правильна build-time композиція + npm-поставка +
інструменти оновлення**, а не runtime-довантаження.

## 2. Що дало дослідження: факти, на яких стоять варіанти

### 2.1. Головний технічний факт (верифіковано експериментально)

У TanStack Router є механізм **virtual file routes**: замість «скануй одну теку» host може
описати дерево програмно. Примітив `physical(urlPrefix, directory)` монтує **теку з
route-файлами** в задану гілку URL. Експерименти (прогін справжнього генератора з версій
цього репо, а потім незалежна адверсарна перевірка) підтвердили:

- ✅ `physical()` монтує теки **поза** `src/routes` — включно з `node_modules` і
  абсолютними шляхами. Це не хак: у апстрімі TanStack є **регресійні тест-фікстури**,
  що монтують теки поза routesDirectory (`tests/generator/virtual-physical-inside-nested`).
- ✅ Нова сторінка, додана в пакет ядра → після `pnpm update` зʼявляється в магазині
  **без жодного нового файлу в магазині** (генератор рекурсивно сканує теку пакета).
- ✅ Повна типізація зберігається: типи роутів пакета генеруються в `routeTree.gen.ts`
  магазину, `<Link to="/catalog/...">` типізується.
- ✅ Per-route code-splitting, SSR-стрімінг, гранулярні loader-и, server routes —
  зберігаються (для генератора це звичайні file-based роути з іншої теки).
- ⚠️ Пакет мусить **запікати route id під фіксований mount-prefix** (напр., усі роути
  storefront-пакета записані як `/_storefront/...`). Тоді генератор нічого не переписує
  в node_modules і збірка працює навіть на read-only ФС. Фіксований префікс = частина
  контракту пакета.
- ❌ **Перевизначення роуту ядра магазином — не shadowing, а фатальний конфлікт
  генератора** («Conflicting configuration paths»). Обхід через `routeFileIgnorePattern`
  крихкий (глобальний regex по basename). Висновок: у цій моделі кастомізація йде
  **не** через підміну роутів.
- ❌ Code-based routing як альтернатива — мертвий: TanStack Start його не підтримує
  (issue #5808 закрито «not planned», мейнтейнер: «code based routing is not supported»).

Відкриті ризики, які закриваються лише пілотом (у монорепо все резолвиться workspace-лінками,
тому «зараз працює» нічого не доводить про справжні npm-пакети):
`createServerFn` в опублікованому пакеті (відкритий баг #7213: server fn, що викликається
лише з server-side коду, випадає з prod-маніфесту), витік server-коду в клієнтський бандл
через `optimizeDeps.exclude` (#6361/#5738), Tailwind v4 content-scan крізь node_modules,
end-to-end splitting на реальних 65 роутах.

### 2.2. Уроки платформ (кожен — з верифікованих дайвів)

| Платформа | Урок для нас |
|---|---|
| **Medusa v2** | Плагін = npm-пакет із CLI-циклом (`create --plugin` → локальний dev-loop через Yalc-лінк → `plugin:build` → publish → `plugins:[]` у конфігу) — готовий шаблон для нашого CLI. Модулі повністю ізольовані по схемі БД (свої таблиці, нуль крос-модульних FK, звʼязки через link-таблиці за конвенцією) — модель для плагінних Supabase-міграцій. **Два попередження з первинних джерел:** (1) найкрихкіше місце — build-time збирання адмін-розширень через package.json `exports` map: плагіни, що працюють через локальний лінк, масово ламаються після справжньої npm-публікації (issues #12687/#12585/#12303) → тестувати реальний publish-шлях, не workspace-лінки (наш парity-guard розширити). (2) Skeleton-update **не вирішений і в Medusa**: сторфронт до v2.14 — форк з офіційним гайдом «Don't use git merge, diff file-by-file», після v2.14 — генерується в монорепо **взагалі без каналу оновлень**. Тобто наш варіант A вирішує задачу, яку індустрія ще не закрила. Антиурок: Medusa дозволяє breaking у **minor**-релізах — нам явно зафіксувати строгий semver. |
| **Vendure** (найближчий аналог мети) | Магазин = тонкий host: `vendure-config.ts` + тека міграцій + package.json. Ядро/плагіни — тільки npm, ніколи не форкаються. Плагін декларує `compatibility` (semver-діапазон) — bootstrap відмовляється стартувати з несумісним ядром. Міграції: плагіни декларують *схему*, а **host генерує одну зведену міграцію, яку ревʼюїть людина**. Антиурок: 6 років Angular-адмінки (плагіни мусили писати Angular, повна перекомпіляція адмінки на кожну зміну) → у 2025 переписали на React/Vite з `defineDashboardExtension`. Нам — закладати extension points адмінки одразу. |
| **Payload v3** | Довів «catch-all монтування»: адмінка+API живуть у npm-пакеті, host тримає 4-6 тонких файлів; minor-оновлення приносить нові адмін-сторінки без правок host (перевірено на v3.37.0). Але: «незалежна еволюція пакетів» — міф; peer deps запінені **точно** (`payload 3.86.0`), lockstep примусовий, і host-файли **ніколи не перегенеровуються** (на мажорі — ручні правки). Урок: реліз-потяг однією версією — чесна і робоча модель. |
| **Nuxt Layers** | Модель-мрія (`extends` + file shadowing: проєкт > тема > ядро, нові сторінки з оновленням шару). Механізм непереносний на Vite/TanStack (немає ні extends, ні shadowing, ні defu-merge), а npm-шари навіть у Nuxt другосортні (живий баг alias-резолву #31298). Забираємо **ментальну модель пріоритетів**, не механізм. |
| **Shopware 6 / Saleor** | Рамка «in-process плагін vs out-of-process app». Для нашої моделі «код+rebuild» правильний in-process npm-плагін (сила: схема БД, сервіси, глибокий UI). Попередження: зміна тулчейна ядра (їхній Vue2→Vue3 + Webpack→Vite у 6.7) — головна причина масових поломок плагінів → потрібні контрактні тести сумісності перед кожним релізом. Theme-as-app: «перемикабельність» теми — це поле маніфеста, незалежне від способу поставки. Saleor (webhooks + iframe) — модель для майбутнього опційного інтеграційного tier, не для основи. |
| **OpenCart / WordPress / Magento** | Чому маркетплейси виграли: низький поріг входу (zip, не форк) + **стабільне API-як-обіцянка** + оновлення в один клік. Каталог антипатернів 1:1 на нас: ніякого патчингу файлів ядра (OCMOD), ніякого глобального нетипізованого hook-супу (WP `$wp_filter`), ніякого «перехоплюй будь-який метод» (Magento interceptors → сертифікація як симптом), extend замість override для розмітки, міграції — трековані/неймспейснуті/централізовані, вузька перелічувана поверхня плагіна. |
| **shadcn registry** | Готовий формат для «власного CLI + маркетплейсу»: `registry.json` + `registry-item.json` + CLI `add`, децентралізовані неймспейси (`@acme/thing`), приватні реєстри з auth. Чесна слабкість: оновлень немає (add --overwrite/diff, і все). Тому copy-in годиться для **візуального** шару, але не для коду з бізнес-поведінкою (у наших темах є Checkout/Auth — їм потрібні апстрім-фікси). |
| **Angular `ng update`** | Єдиний у галузі механізм, **спроєктований редагувати файли споживача** при оновленні: пакет декларує `ng-update.migrations` → schematics правлять код застосунку, тестуються ізольовано (`--migrate-only`). Це готова модель для оновлення host-файлів магазину. Поруч: Strapi публікує чесну таблицю «яка breaking change покрита codemod-ом, яка ні». |

### 2.3. Знахідки критика, що обмежують будь-який варіант

1. **Контракт теми — справжнє вузьке місце.** 16 обовʼязкових сторінок без жодної
   опційної означає: будь-яка нова сторінка ядра **структурно ламає всі теми**. Мета
   «оновлення приносить нові сторінки» недосяжна, поки контракт не стане
   версіонованим: опційні сторінки + **fallback-сторінки з ядра** + декларація
   capabilities темою.
2. **Два джерела істини активації** (реєстрація в бандлі + `is_active` у БД) ніде в
   індустрії не зустрічаються; режими розсинхрону (staging/prod БД, відкат деплою,
   БД посилається на тему, якої немає в білді) треба спроєктувати явно.
3. **i18n відсутній повністю** (українська захардкоджена в темах). Ядро, що постачає
   сторінки, постачає й текст → без каталогів повідомлень core-сторінки непридатні
   для не-UA магазинів. Вирішити до відкриття платформи.
4. **Межа довіри плагіна:** зараз плагін отримує `SupabaseClient` напряму. Потрібна
   вузька перелічувана поверхня (ports-only API) + лінт імпортів у CI.
5. **Готовність до пакування:** 10/17 пакетів `private: true`, build-скрипт лише у 6;
   у корені репо **немає LICENSE**. GitHub Packages вимагає токен навіть на читання —
   барʼєр для сторонніх; канал для екосистеми — публічний npmjs.
6. **`supabase/types.ts`** — один згенерований файл, яким володіє host, а типізується
   проти нього все; плагін, що додає таблиці, змінює його. Регенерація після
   плагінних міграцій має бути частиною флоу CLI.

## 2bis. Рішення власника (зафіксовано 2026-07-30, уточнюють варіанти нижче)

1. **Розкладка «що де лежить»:** склад коду — **один, npmjs** (ядро, плагіни, теми);
   `simplycms` CLI — інструмент поверх pnpm (add/update/db:diff/doctor), НЕ окремий
   реєстр; маркетплейс — індекс-вітрина з метаданими, що вказує на npm-пакети;
   `@simplycms/plugin-sdk` — звичайний npm-пакет з типами/хелперами для авторів.
2. **Адмінка: перевизначення сторінок НЕ закладається взагалі** (модель OpenCart/WP —
   замінити сторінку products не можна навіть плагіном). Плагіни **додають** сторінки:
   пакет плагіна везе `admin-routes/`, монтується під `/admin/<plugin-slug>/…`,
   пункт меню — через слот у AdminSidebar. Тонкі route-обгортки сторінок адмінки — норма.
3. **Storefront: канонічні сторінки — невідʼємна частина ядра**, одразу зроблені
   правильно (SEO + придатність для AI-агентів) і **не перевизначаються**. Магазин
   вільно додає власні сторінки (потрапляють у роути й sitemap). Наслідок для тем:
   **тема НЕ володіє сторінками** — контракт теми звужується до
   `{ manifest, tokens, components (Header/Footer/…), settings }`; нова сторінка ядра
   нічого не ламає; «контракт v2 з опційними сторінками» з §3 замінюється цією
   простішою моделлю. Варіативність усередині канонічних сторінок — theme-компоненти,
   слоти, налаштування.
4. **Робочих сайтів ще немає** → міграційного тягаря немає: breaking-реструктуризація
   без перехідних шимів дозволена (re-export-шими core можна зносити).
5. **Міграції БД:** схема ядра і плагінів — типізований код (Drizzle, включно з RLS:
   `pgPolicy`/`pgTable.withRLS`/`drizzle-orm/supabase` — підтверджено актуальною
   документацією) → `simplycms db:diff` генерує одну зведену SQL-міграцію →
   у `supabase/migrations/` на людське ревʼю → застосування Supabase CLI. Саморобний
   `migrate.mjs` замінюється. Data-access лишається на supabase-js/PostgREST.
6. **Supabase-шар:** консолідувати в єдиний пакет `@simplycms/supabase` за зразком
   `metahub/packages/supabase` (@kit/supabase), звірено з офіційним quickstart Supabase
   для TanStack Start (два клієнти: browser + server на `getCookies`/`setCookie`;
   новий нейминг `VITE_SUPABASE_PUBLISHABLE_KEY`). Плагіни клієнт не отримують —
   тільки порти з SDK.

## 3. Варіант A — «Ядро володіє каркасом» (physical()-монтаж)

### 3.1. Механіка

Репозиторій магазину стискається до тонкої збірки:

```
my-store/
├── package.json              # @simplycms/* як залежності (semver)
├── simplycms.config.ts       # ЄДИНЕ джерело істини: тема, плагіни, адаптери, SEO
├── routes.ts                 # монтаж каркаса ядра (нижче)
├── src/
│   ├── routes/
│   │   ├── __root.tsx        # тонкий: імпортує shell з ядра
│   │   ├── _storefront.tsx   # лейаут-обгортка (тонка)
│   │   ├── admin.tsx         # лейаут-обгортка (тонка)
│   │   └── my/               # ВЛАСНІ сторінки магазину (свій URL-простір)
│   ├── router.tsx, start.ts, client.tsx
│   └── theme-registry.ts     # реєстрація тем (генерується з config)
├── themes/                   # локальні/copy-in теми (опційно)
├── plugins/                  # локальні плагіни (опційно)
└── supabase/migrations/      # зведені, відревʼювані міграції
```

`routes.ts` — програмний монтаж (виконується генератором на етапі збірки, це справжній
TS-модуль):

```ts
import path from 'node:path'
import { rootRoute, layout, physical } from '@tanstack/virtual-file-routes'

// symlink-шлях (НЕ require.resolve — pnpm-реалпат запікає версію в імпорти)
const pkg = (name: string) => path.join('node_modules', name, 'routes')

export const routes = rootRoute('__root.tsx', [
  layout('_storefront.tsx', [ physical('/', pkg('@simplycms/storefront-routes')) ]),
  physical('/admin', pkg('@simplycms/admin-routes')),
  physical('/', 'my'),                       // власні сторінки магазину
  // плагіни зі своїми сторінками адмінки:
  physical('/admin/reviews-plus', pkg('@simplycms-plugins/reviews-plus/routes')),
])
```

Route-файл ядра — **тонкий**: loader (через порт/EngineContext) + рендер сторінки
активної теми. Вся варіативність вигляду — в темі; вся вставна логіка — у PluginSlot.

**Контракт пакета з роутами:** фіксований mount-prefix (route id запечені під нього),
peer dep на `@tanstack/react-start` (вмикає авто-noExternal через vitefu), `sideEffects`
описані, Tailwind-сумісні класи (див. ризики).

### 3.2. Ключові сценарії

**Створення магазину:** `pnpm create simplycms-store` → генерує тонку збірку вище
(6-8 файлів + конфіг), `pnpm dev` — повний магазин працює.

**Оновлення ядра:** `pnpm update "@simplycms/*"` → генератор при наступному dev/build
підхоплює нові route-файли пакета → нові сторінки/фікси зʼявляються. Якщо реліз позначений
як такий, що міняє host-файли (рідко: ~6 файлів), — `simplycms update` доганяє їх
schematics-міграцією (модель `ng update`). CI магазину: `install → build (генерація) →
typecheck → test` — компілятор є гарантом сумісності.

**Встановлення плагіна:** `simplycms add @vendor/plugin-nova-poshta` →
(1) `pnpm add` пакета; (2) запис у `simplycms.config.ts.plugins[]`; (3) міграції-кандидати
плагіна копіюються з перештампованим timestamp у `supabase/migrations/` **на ревʼю**
(git diff), таблиці плагіна — з префіксом `plg_novaposhta_*`; (4) `pnpm db:migrate` +
`db:generate-types`; (5) rebuild. В адмінці плагін вмикається/налаштовується
(`is_active` + config за Zod-схемою плагіна) — **без** перезбірки.

**Кастомна сторінка магазину:** кладеться у `src/routes/my/` (власний URL-простір) або
монтується окремою текою; потрапляє в роути й sitemap штатно. Перевизначення URL ядра
**не підтримується** (технічно — конфлікт генератора; архітектурно — рішення власника:
канонічні сторінки — невідʼємна, SEO/AI-оптимізована частина ядра, як в OpenCart/WP).

**Тема (за рішенням власника — БЕЗ володіння сторінками):**

```ts
interface ThemeModule {
  manifest: { name; version; engines: { simplycms: '^X' } }  // сумісність
  tokens: DesignTokens                       // кольори/типографіка/радіуси (CSS vars)
  components: { Header; Footer; HeroBanner?; /* брендові компоненти */ }
  settings?: ZodSchema                       // налаштування (themes.settings у БД)
}
```

Сторінки рендерить ядро; тема дає токени, брендові компоненти й налаштування.
Нова сторінка ядра нічого не ламає. Поставка теми — на вибір автора: **npm-пакет**
(отримує фікси, semver) або **copy-in через реєстр** (shadcn-модель: повне володіння,
без апстрім-фіксів). Реєстрація тем генерується з `simplycms.config.ts`; активація
з БД (перемикання з адмінки серед установлених) лишається.

**CLI + маркетплейс:** `simplycms add/update/doctor/validate-theme` + авторський цикл
плагіна за зразком Medusa (`simplycms create plugin` скаффолд → `simplycms plugin:dev`
локальний dev-loop через workspace-лінк → build → publish). Реєстр —
shadcn-подібний індекс (JSON) над npm: пошук/вітрина/сумісність версій; сторонні
публікують у свій npm-scope + подають у індекс. Це і є «власний пакетний менеджер»,
але на плечах npm (вирішені проблеми: авторизація, версії, lockfile, provenance).

**Версіонування:** реліз-потяг — усі UI-звʼязані пакети (`core`, `ui`, `admin`,
`*-routes`, `theme-system`, `plugin-system`, `*-ui`) виходять однією платформенною
версією (урок Payload: чесний lockstep замість фіктивної незалежності); чисті
`objects`/`domain` — незалежний semver. Плагіни/теми декларують `engines.simplycms`
діапазон (урок Vendure), CLI/bootstrap перевіряє.

### 3.3. Переваги

- Буквально досягає OpenCart-мети: **оновлення ядра приносить нові сторінки/фікси
  в існуючі магазини** без ручного переносу.
- Host ≈ 6-8 файлів → schematics-міграції host-а тривіальні; «дрейф форка» зникає
  як клас проблеми.
- Зберігає все, заради чого брали TanStack Start: SSR-стрімінг, типізовані Link,
  per-route splitting, server routes.
- Компілятор — гарант сумісності (breaking ядра видно як помилки типів у магазині).
- Плагін-контур нарешті замикається природно: build-time встановлення + runtime
  активація, одне джерело істини в конфігу.

### 3.4. Недоліки і ціна

- Спираємось на **недодокументовану** (хоч і покриту апстрім-тестами) поведінку
  `physical()` поза routesDirectory. Мітигація: пін версій роутера + власний
  регрес-тест механізму в CI ядра; план Б — варіант B (роути матеріалізуються в
  магазин генератором, решта архітектури не міняється).
- Немає route-override → уся варіативність мусить пройти крізь контракт теми, тобто
  контракт v2 (опційність + fallbacks) — **обовʼязкова передумова**, не опція.
- `routeTree.gen.ts` не портабельний між менеджерами пакетів → регенерація після
  кожного install (жорсткий інваріант CI: build перед typecheck).
- Пілот обовʼязковий до перенесення 15k LOC адмінки: server fns у справжньому пакеті
  (#7213), витік у клієнтський бандл (#6361), Tailwind-scan, e2e splitting.
- Розробка самого ядра — тільки через workspace-лінк (dev-watcher ігнорує node_modules);
  для нас це і так поточний режим.

### 3.5. Ризики → мітигації

| Ризик | Мітигація |
|---|---|
| Апстрім змінить поведінку `physical()` | Пін версій + регрес-тест у CI ядра + план Б = варіант B без зміни решти архітектури |
| #7213: server fn за middleware випадає з prod-маніфесту | Пілот; правило контракту: server fns пакетів викликаються з route-файлів (де баг не проявляється), не з чужих server-fn |
| Витік server-коду в клієнт (#6361) | Пілот + перевірка бандла в CI (bundle-guard тест) |
| Tailwind не бачить класи пакетів | `@source` директиви в globals.css магазину (генерує CLI з конфігурації) |
| Нова сторінка ядра ламає теми | Контракт v2: опційні сторінки + core-fallbacks + capabilities |
| Плагін «бачить» усе (blast radius WP) | Ports-only API поверхня + dependency-lint у CI + заборона прямого SupabaseClient у плагінному SDK |
| Exports-map пакетів ламається після справжньої публікації (головний DX-провал Medusa: працює через лінк — падає з npm) | Пілот через `npm pack` + install у чистий проєкт; розширити `published-exports-parity.test.ts` на всі пакети з роутами/адмін-розширеннями; CI-джоба, що збирає магазин зі справжніх tarball-ів |

### 3.6. Поетапність (кожен крок цінний сам по собі)

- **Фаза 0 (безризикова, вже можлива):** перевести `src/routes` монорепо на
  `routes.ts` + `physical()` до **workspace-тек** (`packages/simplycms/storefront-routes`,
  `admin-routes`). Нічого не публікуємо; перевіряємо типи/splitting/DX на реальних
  65 роутах. Заодно: замкнути плагін-контур (loadPlugins на старті), LICENSE, i18n-скелет.
- **Фаза 1:** npm pack пілот — 1 пакет із 2-3 роутами + server fn → чистий проєкт;
  закрити відкриті ризики. Контракт теми v2 + fallbacks.
- **Фаза 2:** `create-simplycms-store` + `simplycms` CLI (add/update/doctor);
  публікація реліз-потяга на npmjs.
- **Фаза 3:** плагінний SDK (ports-only) + міграційний конвеєр + перші плагіни.
- **Фаза 4:** реєстр/маркетплейс (індекс тем і плагінів), conformance test-kit для
  авторів тем.

## 4. Варіант B — «Роути в магазині + CLI-codemods» (Angular-модель)

### 4.1. Механіка

Каркас лишається файлами магазину, але **ним володіє інструмент, а не людина**:

- `create-simplycms-store` генерує 65 тонких route-файлів (кожен: 3-5 рядків,
  re-export з пакетів ядра) зі stamp-коментарем «generated by simplycms@X».
- Кожен реліз ядра публікує **migrations manifest** (`upgrade-migrations.json`):
  перелік schematics-трансформацій «додай файл роута N», «переименуй import», з
  діапазонами версій — точна модель `ng update`.
- `simplycms update` виконує: `pnpm update` → прогін schematics по файлах зі stamp-ом
  (незмінені — перезаписуються; змінені користувачем — 3-way diff з інтерактивним
  вирішенням) → звіт «покрито codemod-ом / потребує рук» (чесна таблиця, як у Strapi).

### 4.2. Переваги

- Нуль залежності від недокументованих поведінок генератора TanStack — тільки
  стандартний file-based routing.
- Магазин може вільно правити **будь-який** роут (повний контроль, як зараз).
- Найзрозуміліша модель для стороннього розробника («всі файли — ось вони»).

### 4.3. Недоліки

- 65 файлів у кожному магазині → **дрейф неминучий**. Це рівно та модель, з якої
  Medusa втекла: їхній фінальний гайд для форкнутих стор-фронтів — «не робіть git
  merge, дифайте і переносьте руками». Codemod по зміненому користувачем файлу —
  вічна боротьба (3-way merge, конфлікти, довіра до інструменту).
- Нові сторінки приносить не `pnpm update`, а окремий крок `simplycms update`,
  який може конфліктувати.
- Інвестиція в powerful codemod-runner (це найскладніша частина `ng update`) — велика
  і постійна: кожен реліз ядра мусить везти міграції.
- «API-як-обіцянка» слабшає: поверхня контракту = вміст 65 файлів, а не інтерфейси.

### 4.4. Коли він правильний

Як **план Б** для варіанта A (та сама архітектура пакетів; роути просто
матеріалізуються в магазин, а не монтуються) і як джерело інструменту
(schematics-runner потрібен навіть у A — для ~6 host-файлів).

## 5. Варіант C — «Payload-splat лише для адмінки»

### 5.1. Механіка

`src/routes/admin/$.tsx` — один catch-all, який рендерить `AdminApp` з
`@simplycms/admin`; внутрішній роутинг адмінки — усередині пакета. Оновлення
адмінки = `pnpm update`. Storefront лишається як зараз (форк).

### 5.2. Переваги

- Найменший крок; адмінка (15k LOC, найстабільніший UI-контур без per-store
  кастомізацій) одразу отримує npm-оновлення.
- Для адмінки втрати splat-підходу неважливі: вона вже client-only SPA
  (`ssr:false`), SSR-стрімінг/сплітинг там не працюють і так.

### 5.3. Недоліки

- **Мети не досягає:** вітрина — головна цінність платформи — лишається форком-снімком.
- Для storefront splat неприйнятний (верифіковано): один splat = один чанк на секцію,
  втрата типізованих `<Link>`, гранулярних loader-ів, SSR-стрімінгу по роутах,
  server routes.
- Два різні механізми роутингу в одному застосунку — постійна когнітивна ціна.

## 6. Порівняння

| Критерій | A: ядро володіє каркасом | B: роути + codemods | C: splat адмінки |
|---|---|---|---|
| «Оновлення приносить нові сторінки» | ✅ буквально, через `pnpm update` | 🟡 через `simplycms update`, з конфліктами | 🟡 лише адмінка |
| Дрейф магазинів | ✅ зникає (host ~6 файлів) | ❌ неминучий (65 файлів) | ❌ storefront дрейфує |
| Ризик залежності від стека | 🟠 недодокументована (але тестована апстрімом) поведінка | ✅ мінімальний | ✅ мінімальний |
| SSR/типізація/splitting вітрини | ✅ повні | ✅ повні | ✅ (storefront не чіпається) |
| Свобода правити роут ядра | ❌ (навмисно; через тему/конфіг) | ✅ повна | ✅ (storefront) |
| Обсяг першої фази | 🟡 середній (фаза 0 — дні, не тижні) | 🟠 великий (codemod-runner) | ✅ малий |
| Обсяг постійної підтримки | ✅ низький | ❌ міграції на кожен реліз | 🟡 |
| Шлях відступу | → B без зміни архітектури пакетів | → A пізніше (дорожче) | → A/B |

## 7. Рекомендація

**Варіант A як цільова архітектура**, з двома свідомими запозиченнями:
- із B — schematics-runner для host-файлів (при host ~6 файлів це малий інструмент,
  а не платформа codemod-ів) і як задокументований план Б;
- із C — послідовність пілота: перший `physical()`-монтаж природно робити з адмінки
  (найменші SSR-ризики), потім storefront.

Причина: A — єдиний варіант, що досягає сформульованої мети («ядро розвивається
окремо, оновлення доїжджають до магазинів, плагіни й теми — встановлювані одиниці»),
і при цьому його головні ризики (а) перевіряються дешевим пілотом до точки
неповернення, (б) мають план Б, що не ламає архітектуру пакетів.
