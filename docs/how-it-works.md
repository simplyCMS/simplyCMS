# Як працює платформа SimplyCMS (пояснення «на пальцях»)

> Доступний виклад затвердженої архітектури. Технічне джерело правди —
> [специфікація](superpowers/specs/2026-07-30-platform-architecture-design.md);
> трекінг робіт — [роадмап](tasks/platform-roadmap.md). Створено 2026-07-31.

## Карта дійових осіб (аналогія з OpenCart)

| В OpenCart | У SimplyCMS | Що це фізично |
|---|---|---|
| Ядро OpenCart (zip з сайту) | Пакети `@simplycms/*` | npm-пакети, які магазин ставить як залежності |
| Папка магазину на хостингу | Репозиторій магазину (~8 файлів + конфіг) | Git-репо розробника магазину |
| «Модулі» в адмінці (upload zip) | **`simplycms` CLI** в терміналі | Команда встановлення/оновлення розширень |
| OpenCart Marketplace | Маркетплейс SimplyCMS | Сайт-каталог, що вказує на npm-пакети |
| MySQL на хостингу | Supabase-проєкт магазину | БД + auth + storage, окремо від коду |

Головна відмінність: в OpenCart «встановити» = закинути файли на працюючий сервер.
У Vite/React/SSR-світі «встановити» = додати залежність + перезібрати. Тому роль
«менеджера розширень» переїжджає з адмінки в термінал розробника, а адмінці
лишається **активація й налаштування** вже встановленого — без перезбірки.

## Де лежить код і пакети

- **GitHub** — вихідний код і розробка (монорепо платформи, репо авторів розширень).
  Магазини наш репозиторій **не форкають**.
- **npmjs.com** — опубліковані пакети. Ланцюжок: код на GitHub → CI публікує реліз
  на npmjs → магазини тягнуть через pnpm. GitHub Packages не використовується
  (вимагає токен навіть на читання публічних пакетів — барʼєр для екосистеми).
- Сторонні автори публікують під **своїм** npm-scope
  (`@vendor/simplycms-plugin-*`, `@vendor/simplycms-theme-*`).

## «Наш пакетний менеджер» = CLI-оркестратор, не заміна npm

Власний реєстр/lockfile/розвʼязання версій ми не будуємо — це вже зробив npm.
`simplycms` CLI — розумна обгортка поверх pnpm, яка робить те, чого pnpm не вміє:

```
simplycms add @vendor/simplycms-plugin-novaposhta
├─ pnpm add …                          ← звичайний npm-механізм
├─ запис у simplycms.config.ts         ← реєстрація (якірна вставка)
└─ підказки: pnpm build; якщо плагін привіз міграції — simplycms db:diff

simplycms db:diff --write              ← окремий крок, ЛЮДСЬКЕ РЕВʼЮ обовʼязкове
├─ N канонів: міграції ядра + кожного встановленого плагіна
├─ SQL-лінт межі довіри: плагін чіпає лише свої таблиці plg_<name>_*
└─ далі: git diff → supabase db push → регенерація типів БД
```

Стан після Фази 3: `create plugin` (скаффолд власного плагіна в `plugins/`
магазину) і конвеєр міграцій плагінів працюють; перевірка
`engines.simplycms` — на bootstrap-і магазину (warn-режим до v1.0); монтаж
сторінок адмінки плагіна — рядок `physical()` у `routes.ts` за
якір-коментарем (автоматизація в `add` — попереду). Механізм цілком —
[`architecture/plugins.md`](architecture/plugins.md).

## Анатомія працюючого магазину

Один Node-процес + Supabase як окремий сервіс:

- **Storefront (SSR)** — канонічні сторінки з `@simplycms/storefront-routes`
  (головна, каталог, категорія, товар, кошик, checkout…) + власні сторінки магазину.
  Повний HTML для Google та AI-агентів. Сторінки не перевизначаються — вигляд дає
  активна **тема** (токени + Header/Footer + налаштування), вставки — слоти плагінів.
- **Admin (SPA, `/admin`)** — сторінки з `@simplycms/admin-routes` + сторінки
  встановлених плагінів (`/admin/<plugin>/…`). Перевизначення сторінок адмінки
  не існує (як в OpenCart/WP) — лише доповнення.
- **Server functions** — дані для сторінок → Supabase (Postgres/Auth/Storage).

Межа відповідальностей: **усе, що змінює код — CLI + rebuild (розробник);
усе, що змінює поведінку встановленого — адмінка, миттєво (власник).**

## Сценарії

**Новий магазин:**
```bash
pnpm create simplycms-store my-shop   # тонка збірка: конфіг + ~8 файлів
# створити Supabase-проєкт, вписати ключі в .env.local
pnpm db:migrate                        # схема ядра з коробки
pnpm dev                               # повний магазин: вітрина + адмінка + default-тема
```
Деплой — `pnpm build` + будь-який Node-хостинг, як звичайний TanStack Start застосунок.

**Оновлення ядра:**
```bash
pnpm update "@simplycms/*" && pnpm build   # нові сторінки/фікси приїхали самі
```
Генератор роутів сканує теки пакетів ядра — новий route-файл у пакеті стає новою
сторінкою магазину **без жодного нового файлу в репо магазину**. Рідкісні релізи,
що міняють host-файли (~8 штук), доганяються командою `simplycms update`
(CLI сам редагує ці файли). Breaking-зміни — тільки в major-версіях.

**Плагін для власника магазину:** знайшов у маркетплейсі → розробник виконав
`simplycms add …` + deploy → в адмінці зʼявився перемикач і форма налаштувань
(за Zod-схемою плагіна) → активував. Далі все керується з адмінки.

**Автор плагіна:** `simplycms create plugin` (скаффолд на `@simplycms/plugin-sdk`)
→ `simplycms plugin:dev` (локальний dev-loop) → `npm publish` під своїм scope
→ PR у індекс маркетплейсу. Доступ до даних — тільки через порти SDK
(прямого Supabase-клієнта плагін не отримує).

## Маркетплейс = каталог, не сховище

1. **Індекс** — JSON у git-репозиторії: npm-імʼя, версії, сумісність, категорія,
   скріншоти. Подача = pull request (це і є модерація).
2. **Вітрина** — сайт, що рендерить індекс (пошук, категорії, картки).
3. **Інтеграція** — `simplycms add <імʼя>` шукає в індексі → npm-пакет → стандартний
   флоу; адмінка може показувати каталог «доступних розширень» з того ж індексу.

## Хто що робить

| Дія | Хто | Інструмент |
|---|---|---|
| Створити магазин | Розробник | `pnpm create simplycms-store` |
| Товари, замовлення, ціни | Власник | Адмінка |
| Встановити плагін/тему | Розробник | `simplycms add` + rebuild + deploy |
| Увімкнути/налаштувати встановлене | Власник | Адмінка, без перезбірки |
| Перемкнути тему серед встановлених | Власник | Адмінка |
| Оновити ядро | Розробник / CI | `pnpm update` + deploy |
| Своя сторінка/лендинг | Розробник | Файл у `src/routes/my/` |
| Написати й опублікувати розширення | Сторонній автор | SDK → `npm publish` → PR в індекс |
| Реліз ядра | Мейнтейнери | GitHub → CI → npmjs |
