## 1. Головне за 30 секунд

**Магазин працює на чистому Postgres. Адмінка — ні, і це очікувано.**

🔴 **К2-Е0 (2026-09-13):** покупний демо-магазин (`pnpm db:demo`) проходить
повну воронку одним прогоном — `pnpm live:smoke`: картка → кошик → чекаут →
рядок в `orders` зі списанням залишку, скасування в кабінеті повертає і
залишок, і статус. Подробиці — §2.2.

🔴 **К3-Е2 (2026-09-13):** файли теж живі — порт `simplycms/storage` із
драйвером `local-fs`, і той самий прогін доводить наскрізний ланцюг аватара
покупця: завантаження → `/media/<key>` → референс у БД → видалення. Подробиці
— §2.3 і §3.2.

🔴 **К3-Е3 (2026-09-24):** каталог адмінки — жива перша `on-demand`-колекція
TanStack DB. `/admin/products` (список, фільтри, «Показати ще»),
`/admin/products/new` і `/admin/products/$productId` (картка, модифікації,
ціни, залишки з гвардованим статусом, властивості, зображення через порт
сховища) — на серверному шарі `admin-server`/`admin-data`. Зображення товару
(DoD К3 п.6) тепер ЖИВЕ. Подробиці — §2.4 і §3.1/§3.2.

🔴 **К3-Е4 (2026-10-03):** довідники каталогу живі на тому самому серверному
шарі — `/admin/sections*` (розділи плоским списком, зображення через порт
сховища, призначення властивостей «для товарів»/«для модифікацій» у картці
розділу), `/admin/price-types*` (атомарний дефолт `setDefault` під
advisory-lock, видалення дефолту заборонене, тип із цінами не видаляється —
`ON DELETE RESTRICT` → тост «використовується») і `/admin/properties*`
(властивості з незмінним після створення типом, глобальний slug, опції з
власною сторінкою). Живий прогін доводить: власник створює розділ,
властивість, опцію, призначення й тип ціни — вітрина їх показує. Подробиці
— §2.5 і §3.1.

🔴 **К3-Е5 (2026-10-04):** замовлення в адмінці живі — `/admin/orders`
(on-demand колекція, «Показати ще», фільтр за статусом, серверний ліміт
сторінки) і `/admin/orders/$orderId` (картка лише на читання: позиції,
суми, клієнт, отримувач, доставка; зміна статусу іменованою операцією
`changeOrderStatus`). «Скасоване» — кінцевий статус (Е5-2): скасування
повертає залишок рівно один раз — облік фактично списаного живе в позиції
замовлення (`order_items.stock_reserved`/`stock_point_id`, Е5-4′), вийти зі
«Скасованого» не можна (409 і тост). Живий прогін доводить: покупець
оформлює два замовлення, власник підтверджує одне й скасовує друге — склад
і кабінет покупця це бачать. Подробиці — §2.6, §3.1 і §3.5а.

🔴 **К3-Е5б (2026-10-04):** позиції оформленого замовлення редагуються в
картці — кількість (Enter/blur), додавання товару вузьким пошуком
(`searchProductsForOrder`, буквальний `ilike` за назвою й артикулом) і
видалення через AlertDialog; у будь-якому статусі, крім «Скасованого».
Наявні позиції зберігають свою ціну, нова отримує серверну ціну для
покупця замовлення (гість — дефолтний тип) тим самим рушієм, що й чекаут
(нова server-only тека `simplycms/commerce`). Залишок рухається дельтою по
позиції через `order_items.stock_reserved`, доставка перераховується за
тарифом після кожної зміни, `total = subtotal + shipping_cost` у цілих
центах. Живий прогін доводить: кількість +1, додано й видалено інший товар
— склад, суми й кабінет узгоджені, а скасування покупцем повертає рівно
актуально списане. 🔴 Межа (Е5б-2): замовлення, чий метод доставки відтоді
деактивовано, стає нередагованим (зміни методу в Е5б немає). Подробиці —
§2.7 і §3.1.

🔴 **Фундамент даних адмінки, Етап A (2026-10-05):** колекції адмінки на
TanStack DB 0.11.3 (react-db 0.5.3, query-db-collection 1.3.4). Обходи
TSDB-B1 (`preload()`) і `gcTime: 0` зняті; серверний subset приймає `Date` і
`sortable`-колонки для курсора пагінації (`eq/gt/gte/lt/lte`). Кожен запис в
on-demand-колекцію тепер ревалідує активні зрізи (ціна — `docs/architecture/
upstream-workarounds.md`, TSDB-1). Живий прогін доводить «Показати ще» обох
списків на рівних `created_at` без втрат/дублів (`live-smoke/
admin-lists-pagination.mjs`).

🔴 **Фундамент даних адмінки, Етап B (2026-10-05):** схеми ресурсів адмінки
(`defineAdminResource`) будує власний генератор `columnsToZod` (9 типів колонок,
невідомий тип — гучний throw) замість `drizzle-zod`; той лишився лише
devDependency як еталон постійного гейта паритету
(`admin-server/impl/__tests__/columns-to-zod-parity.test.ts`, межі —
`docs/architecture/test-contours.md` §11.3). Статичні типи схем оголошує один
хелпер `declareSchema` (`resource-schemas.ts`). DZOD-1 закрито; касти проєкції
Drizzle винесено в реєстр як DRZ-2.

🔴 **К3-Е6а (2026-10-06):** доставка в адмінці жива на серверному шарі —
`/admin/shipping/methods*` (спосіб = провайдер `core:address`/`core:pickup`,
незмінний після створення, + режим ціни `rates`/`provider`/`carrier`; тарифи
за зонами редагуються в картці способу), `/admin/shipping/zones*` (дефолтна
зона — іменованою операцією під advisory-lock, дефолтну не вимкнути й не
видалити) і `/admin/shipping/pickup-points*`. `/admin/shipping` перенаправляє
на способи. Режим `carrier`: `shipping_cost = 0`, `total = subtotal`, підпис
«За тарифами перевізника» в чекауті й замовленні. Замовлення зберігає знімок
доставки в `orders.shipping_data`, тож картка, `order-success` і кабінет
показують назву точки на момент оформлення (К3-Е5-2 закрито);
`orders.delivery_method` і фіктивної оплати `online` більше немає. Спосіб із
точками й точку із залишком видалити не можна — БД (`RESTRICT`) і тост 409.
Живий прогін доводить: власник створює обидва способи, тариф і точку, покупець
оформлює обома, а знімок переживає перейменування точки. Подробиці — §2.8 і
§3.1.

🔴 **К3-Е6б (2026-10-06):** система адмінки жива на серверному шарі —
`/admin/settings` (профіль магазину: назва, заголовок головної, опис, контакти,
логотип, соцмережі; перемикач «списувати залишок» зберігається одразу),
`/admin/themes` (активація й налаштування теми) і `/admin/plugins` (вмикання,
конфіг) під однією authz-операцією `settings.manage`. Профіль лежить у
`system_settings['store_profile']`; вітрина читає його через кеш процесу
`simplycms/site` (TTL 5 хв + покоління, скидає сама операція після COMMIT) і
кореневий лоадер host-а: `<title>` «Сторінка — Назва», Organization JSON-LD
головної, бренд і контакти в темах `default` і `solarstore`. `seo`/`siteUrl` з
`defineConfig` прибрано (URL сайту — env `VITE_SITE_URL`);
`/api/revalidate-theme`, `plugin_events` і `plugins.migrations_applied` знесено;
`/api/health` на будь-який метод, крім `GET`, відповідає 405. Живий прогін
доводить профіль на прогрітому кеші, заміну логотипа, склад, теми (і в тій самій
вкладці) та плагін. Подробиці — §2.9.

🔴 **К3-Е6в (2026-10-07):** знижки й категорії покупців живі на серверному
шарі, і покупець бачить ОДНУ ціну на картці, у кошику й у чеку — усі поверхні
рахують одним ядром `simplycms/commerce` (`loadPricingContext` + `priceCart`).
`/admin/discounts*` (дерево груп з операторами, атомарний `saveDiscount`,
цілі й умови з реєстру), `/admin/price-validator` (діагностика тим самим ядром,
що чекаут), `/admin/user-categories*` (категорії з атомарним дефолтом і явними
відмовами видалення, автоправила з «Запустити всі»). Кошик бере ціни із
серверної квоти, картки — із середовища цін (`staleTime: 0`); порогові підказки
«від 3 шт — … (−10%)». Автоправила спрацьовують після оформлення замовлення
окремою транзакцією. Хуки знижок і порт `getDiscounts` знесено. Живий прогін
доводить поріг у картці, кошику й `order_items`, вимкнений батько стримує
активну дитину, а друге замовлення переводить покупця у «VIP» і змінює ціну.
Подробиці — §2.10 і §3.1.

Браузер більше не ходить у базу. Раніше сторінка сама зверталась до БД через
HTTP-посередника Supabase (PostgREST); тепер із базою говорить **тільки
сервер**, а браузер отримує готові дані. Це і є суть рішення B1.

Наслідок, який ще треба прийняти свідомо: **більшість адмінки досі не має
серверного шару** — 9 файлів (`rg -l useSupabaseClient packages/simplycms/src/admin`,
виміряно 2026-10-07 після Е6в) працюють із браузера і на чистому Postgres не
звертаються нікуди. Живі розділи — статуси замовлень (Е1б), каталог (Е3),
довідники каталогу (Е4), замовлення з редагуванням позицій (Е5, Е5б),
доставка (Е6а), система — налаштування, теми, плагіни (Е6б) і знижки з категоріями
покупців (Е6в, описано вище); решта адмінки
віддає каркас і застигає на «Завантаження».

Це не поломка, внесена неакуратно, а **неминучий наслідок** переходу: решті
адмінки потрібен той самий серверний шар, посторінково (Е6–Е7) — план
власника 2026-08-24.

### 2.1. Контур 0.4.1 — ПІДТВЕРДЖЕНО живим прогоном 2026-08-29

🔴 Прогін 2026-08-24 (таблиця вище) робився з `.env.local`, у якому Supabase-ключі
ще лежали, тож доказом для нового контракту він не був. Контур 0.4.1 зняв їх
зовсім: шар `data-supabase` знесено, `CMSProvider` більше не монтує
`SupabaseProvider`, `/api/health` пінгує Postgres, роут `/api/guest-order`
видалено, генератор типів і онлайн-перевірки `doctor` знято, аватар чесно
відмовляє. Нижче — результат ОКРЕМОГО прогону, зробленого саме під новий
контракт.

**Поза прогону.** П'ять tarball-ів зібрано з гілки (`pnpm pack` кожного пакета),
магазин розгорнуто скаффолдером із них у чисту теку, залежності ядра —
`file:`-посилання на ці tarball-и (не реєстр). База — окрема ЧИСТА `store041`,
канон накатано `psql -f` по кожному файлу `supabase/migrations/*.sql`
(45 таблиць). `.env.local` — рівно три ключі, `DATABASE_URL` під роллю
**`app_runtime`** (продакшн-поза, не суперюзер). Запуск — `pnpm build &&
node server.mjs`.

🔴 **Одне уточнення, без якого доказ читався б ширше, ніж він є.** Накат канону
робився **привілейованим** підключенням (власник кластера), а не тим
`DATABASE_URL`, який README магазину друкує власнику: усі 45 таблиць у
`store041` належать суперюзеру. Це не недбалість прогону, а обхід реального
дефекту — під роллю `app_runtime` канон не котиться за жодного стану БД
(`permission denied for database`, або `permission denied to alter role` на
безумовному `alter role` у `0000_prelude.sql:74`, або роль ще не існує на
чистому кластері). Тобто доведено саме **рантайм** магазину під `app_runtime`;
надрукований онбординг-крок накату лишається зламаним — борг 0.4.1-9.

| Твердження контуру 0.4.1 | Статус |
|---|---|
| Магазин збирається й піднімається БЕЗ жодного `VITE_SUPABASE_*` | ✓ (у файлах магазину — нуль збігів `SUPABASE`) |
| `/`, `/catalog`, `/cart`, `/auth`, `/sitemap.xml`, `/robots.txt` → 200 | ✓ усі шість |
| `/admin`, `/profile` анонімом → 307 | ✓ обидва |
| `/api/health` → 200 (пінг Postgres, не Supabase) | ✓ `{"status":"healthy","checks":{"database":{"ok":true,"error":null}}}` — тіло без hostname і назви ролі |
| Браузер: нуль `console.error`, `h1` із реальним контентом | ✓ `/`, `/catalog`, `/cart`, `/auth` — нуль `console.error`, нуль `pageerror`, нуль 4xx; `h1` = «Виважений вибір…», «Каталог», «Кошик» |
| `simplycms doctor` без `DATABASE_URL` падає саме на ньому | ✓ `✗ env: DATABASE_URL + BETTER_AUTH_SECRET → Не задано: DATABASE_URL`; онлайн-перевірки — видимий `?` зі скоупом К3 |

**Додатково — на монорепо-хості проти `pnpm db:demo` (порт 3141), той самий
контракт із трьох ключів:** реєстрація через Better Auth наживо ✓;
`/profile/settings` залогіненим — 200, `h1` «Налаштування», **нуль
`console.error`**, інпут аватара `disabled`, пояснення «тимчасово недоступне»
видиме (доказ Task 2 і того, що fallback `resolveDefaultClient()` більше

- **Фільтрація видимості — тепер обов'язок коду.** Політик «публічне

  база — тепер не ховає.
- **`userId` ніколи не параметр serverFn** — лише з сесії
  (`readSessionSubject`). RLS звіряє рядки з тим id, який їй назвав сервер;
  id, прийнятий від клієнта, вона перевірити не може за побудовою.

  у браузер.** Спіймано Gate C пілота: `withSessionDb` лежав у
  `storefront-routes/server/`, бандлер підняв його у спільний чанк, і разом
  із ним у клієнтський бандл поїхали drizzle і пул Postgres. Лікується
  перенесенням у модуль, який імпортується **bare-специфікатором**
  (`simplycms/storefront/loaders`) — такі бандлер лишає зовнішніми й у чанки
  не кладе. Після треку T (2026-09-02) гарантія ще сильніша: лоадери — це
  server-only дерево за декларацією `simplycms/contracts/server-only`, і
  збираються вони ОКРЕМОЮ збіркою, тож спільного чанка з клієнтом не може
  бути за побудовою. Це структурна гарантія, а не домовленість.

### 3.2. Сховище файлів — порт живий, зображення товару теж (К3-Е3, DoD К3 п.6 ЗАКРИТО)

**Працює наживо:** аватар покупця (Е2) і зображення товару (Е3). Порт

Доведено `pnpm live:smoke`: аватар — 2026-09-13 (§2.3), зображення товару
— 2026-09-24 (§2.4, крок адмінки: завантаження в `/admin/products/$productId`
→ `<img src="/media/...">` на вітрині → референс, не URL, у `products.images`).
Заміну (старий обʼєкт прибирається ОСТАННІМ, після COMMIT-безпечної точки)
смок не проходить — її доводить харнес `media-record` у `pnpm test:schema`.

**Не працює:** зображення банерів — `admin/components/ImageUpload.tsx`
переведено на порт (serverFn `uploadMedia`/`deleteMedia` з
`simplycms/admin-server`); його вже монтують картка товару (Е3), картки
розділу й опції властивості (Е4), а сторінки банерів лишаються на
`supabase-js` і на чистому Postgres не працюють.

**Не працює й лишається на Supabase:** `admin/pages/ReviewDetail.tsx` —
єдина виїмка ратчета `tests/storage-direct-calls.test.ts`. Сторінка мертва
цілком (читає й пише через `supabase-js`), тож переписується разом із
хвилею відгуків, а не «заодно» в storage-етапі.

**Що лишається К4:** драйвер `s3`, `transform`/srcset, presigned
direct-upload, облік невдалих видалень і sweep орфанів (обʼєкт без рядка
після обриву між `put` і COMMIT), привʼязка `entity_id` для медіатеки.

**Підґрунтя:** таблиця метаданих медіа (`src/schema/media.ts`) з
інваріантом незмінності колонок власності — він тримається **відсутністю
гранта UPDATE**, а не тригером; саме тому старий рядок аватара прибирається
через ескалацію оператора.

### 3.3. Листи не відправляються (рішення власника)

Запрошення власника і скидання пароля кличуть колбек відправки, але транспорт
— заглушка (`src/auth/send-email.ts`, `stubSendAuthEmail`): лист пишеться в
`console.warn` разом із посиланням. Рендер листа юніт-тестовний; доставки
немає. **Це навмисно** — тестується локально, де є SMTP.

### 3.4. Ціни позицій замовлення не перераховуються

✅ **Закрито К2-Е0 2026-09-13 (Е0-4).** Сервер рахує ціни позицій, суму й
доставку в ОДНІЙ функції (`prepareCheckout`), яку ділять і показ (квота
чекауту), і запис (`placeOrder`) — «показане = записане» тримається за
побудовою; підміна ціни в запиті клієнта більше не проходить. `placeOrder`
повертає доменну відмову (`PlaceOrderRejection`) замість throw. Наскрізний
доказ — `pnpm live:smoke`, перевірка «підсумок = замовлення» (§2.2); спека —
[`2026-09-03-k2-e0-storefront-live-contour-design.md`](../superpowers/specs/2026-09-03-k2-e0-storefront-live-contour-design.md).

### 3.5. `pnpm owner:invite` у шаблоні магазину

Скрипт переписаний без GoTrue й друкує посилання в консоль, але **з монорепо
не запускається**: він резолвить `simplycms` як залежність магазину. Це
нормально — він і призначений для скаффолдженого магазину. У монорепо
використовуй прямий виклик `issueOwnerInvite` (див. §5).

### 3.5а. Облік залишку замовлення — по позиції, без історичних замовлень (К3-Е5, Е5-4′/Е5-11)

З К3-Е5 облік замовлення живе в `simplycms/inventory` (`reserveOrderStock`,
`releaseOrderStock`), а фактично списане пишеться В ПОЗИЦІЮ:
`order_items.stock_point_id` (точка списання) і `order_items.stock_reserved`
(скільки реально знято; 0 — цілі без обліку). Скасування повертає рівно
`stock_reserved` у `stock_point_id` і обнуляє лічильник одним запитом —
повторне повернення бачить 0. Тумблер `decrease_on_order` на поверненні не
читається. Дві свідомі межі:

- **Замовлення, оформлені до К3-Е5, нічого не повертають.** Колонки
  приземлені правкою baseline, тож у таких рядків `stock_reserved = 0`;
  колишній fallback (точка з `orders.shipping_data.stock_point_id` або
  повторний резолв) прибрано — він давав фантомний залишок там, де облік був
  вимкнений, а відрізнити ці випадки даних немає (правило D5: реальних
  магазинів немає, демо-база перестворюється `pnpm db:demo`).
- **Точку списання ВИДАЛИЛИ (не деактивували) до скасування** — FK
  `ON DELETE SET NULL` обнуляє `stock_point_id`, рядки залишку точки зникають
  каскадом, і повертати кількість нікуди: вона не повертається, факт
  пишеться в `console.warn` (`[simplycms/inventory] … not returned`).
  Деактивована точка залишок отримує назад (кейс I1 `order-stock.test.ts`).

### 3.6. Контури, вимкнені рішенням B13

`pnpm test:e2e` і `pnpm pilot:e2e` — **decommissioned**, і з 0.4.1 команд
більше немає взагалі: знесено `scripts/e2e.mjs`, `scripts/e2e/`,

### 3.7. Відомі дефекти й борги, зафіксовані К3-Е5 (2026-10-04)

- ✅ **ЗАКРИТО 2026-10-04 (Е5б Task 8, рішення Е5б-15).** Токен
  гостьового замовлення захоплюється один раз при монтуванні й живе лише в
  памʼяті сторінки. Доказ — юніт `order-success-guest-token.test.tsx` і

  дефекту нижче.

  ручним прогоном Е5, дефект вітрини, а не адмінки. Код —

  Механізм такий:
  1. `token` входить у `queryKey` запиту замовлення.
  2. Після успішного завантаження `useEffect` прибирає `?token` з URL.
  3. Ключ змінюється, і запит повторюється вже без токена.
  4. Політика `orders_select_own_or_token` гостю рядка не віддає → `null` →

  Замовлення в БД є, адмінка його бачить. Ламається лише сторінка
  підтвердження гостя: вона блимає даними і падає в «не знайдено».

- ✅ **ЗАКРИТО 2026-10-06 (К3-Е6а, рішення Е6а-8).** Замовлення зберігає
  знімок доставки в `orders.shipping_data`; картка адмінки, `order-success` і

  перейменування чи видалення точки. Доказ — харнес `shipping-snapshot.test.ts`,
  рендер-тести трьох читачів і `live:smoke` (§2.8). Історія дефекту нижче.
  **Точка видачі в картці замовлення адмінки показувалась uuid-ом (К3-Е5-2).**

### 3.8. Борги К3-Е6в (2026-10-07) — свідомо поза хвилею

Повний перелік з причинами — роадмап, «Борги К3-Е6в». Коротко:
- SSR гостьовий: база списків — за типом ціни гостя (тип дефолтної категорії,
  інакше глобальний дефолтний — `loadGuestPriceTypes`, те саме правило, що

  рахує; `offers` у JSON-LD — гостьова база без знижки (F9; модифікації —

- Скасування замовлення категорію покупця не перераховує (Е6в-19).
- Автоправила не запускаються за розкладом — лише після оформлення й кнопкою.
- UI ручного призначення категорії й зняття `category_locked` — хвиля «покупці»
  (операція `assignCustomerCategory` вже є).
- Легасі `UserEdit.tsx` вставляє історію без `to_category_name` (`NOT NULL`) —
  сторінка мертва й переписується в хвилі «покупці».
- Головна бере ціну з `modificationId: null`: товар із цінами лише на
  модифікаціях показується без ціни.
- `staleTime: 0` — кожна карусель головної перезапитує середовище цін (мало б
  читатись раз на сторінку).
- Багатоінстансної інвалідації немає (без змін).
- Фінальне рев'ю (К3-Е6в-9…14 у роадмапі): реєстр умов до К5 (UI й підказки
  за літеральними типами, серверна реєстрація умов плагіна не спроєктована,

  у `PriceValidator` (`discount.manage`); холодний старт — два запити середовища
  й квоти замість одного; флейк бейджа зони в live-smoke доставки; `exceeds_price`
  для знижки, округленої до 0 коп., — окрема причина в поясненні. JSON-LD: гілка OutOfStock-fallback `AggregateOffer` без тесту. Хвиля «покупці»: `UserEdit` пише обидві
  назви категорій історії, знімає `category_locked`, без `auth_provider`.

  права **до** перемикання, і fail-closed зникає мовчки. Це реальний дефект,
  знайдений негативним контролем.
- RLS — **27 політик замість 93**, лише на user-scoped таблицях, у

### 4.3. Збірка: декларації типів більше не через tsup

кожну теку** entry і тримав їх усі живими: 36 програм, 9 ГБ, 191 с (розтин

🔴 Рішення виявилось ПОСТІЙНИМ, а не тимчасовим обхідом покинутого
інструмента: після міграції на tsdown (трек T) вимір повторили 2026-09-02 —

Запобіжники: кеп пам'яті в `scripts/build-packages.mjs` (діє в CI, релізі й
локально), стеля часу 300 с, структурний тест `tests/dts-toolchain.test.ts`.

## 5. Як підняти це локально (перевірено покроково)

```bash
pnpm install

# 1. База з демо-даними (потрібен локальний Postgres)
PG_HARNESS_URL=postgresql://<user>@127.0.0.1:5432/postgres pnpm db:demo
# віддасть готовий рядок DATABASE_URL

# 2. .env.local
DATABASE_URL=postgresql://<user>@127.0.0.1:5432/simplycms_demo
BETTER_AUTH_SECRET=<довгий випадковий рядок>
VITE_SITE_URL=http://localhost:3000
# BETTER_AUTH_URL=http://localhost:3000  # опційно: без нього база береться з
#   запиту, а WARN «Base URL is not set» у лозі — очікуваний. 🔴 Задавати лише
#   origin, з якого реально ходить браузер: з рядковим baseURL Better Auth
#   довіряє РІВНО цьому origin і відкидає інші з 403 INVALID_ORIGIN
# MEDIA_ROOT=/var/lib/simplycms/media  # опційно (К3-Е2): корінь драйвера
#   local-fs. Без нього — ./.data/media відносно робочої теки процесу; теку
#   створює сам драйвер при першому завантаженні, вона в .gitignore. У проді
#   задавати обовʼязково, і на том, що переживає деплой: дефолт лежить
#   усередині теки деплою, тож нова викладка почала б із порожнього сховища

# 3. Запуск
pnpm build && pnpm start        # або pnpm dev
```

**Перевірити весь контур одразу** (К2-Е0, DoD як скрипт): `PG_HARNESS_URL=…
pnpm live:smoke` — сам піднімає чисту демо-БД, збирає прод-білд, стартує
сервер і жене curl+SQL + Playwright-воронку (реєстрація → картка → кошик →
чекаут зі списанням → скасування з поверненням залишку) плюс крок аватара
(К3-Е2: завантаження → роздача `/media/<key>` → референс у БД → видалення).
Не чіпає `.env.local` розробника; потребує Postgres і Chromium (`pnpm exec
playwright install chromium`).

**Створити першого адміна** (у монорепо, бо скрипт шаблону резолвить
`simplycms` як залежність магазину):

```ts
// Зберегти як owner-invite.mts У КОРЕНІ репо (саме .mts: поза репо tsx бере
// CJS і падає на top-level await) і запустити з тими самими env:
//   set -a; . ./.env.local; set +a; npx tsx owner-invite.mts
const m = await import('./packages/simplycms/src/auth/index.ts');
const r = await m.issueOwnerInvite({
  email: 'admin@example.com',
  store: m.ownerInviteStore,
  siteUrl: 'http://localhost:3000',
  // Лист не несе поля `url` — посилання повертає сам issueOwnerInvite (r.url).
  sendEmail: async (mail) => console.log(mail.subject),
});
console.log(r.url);   // відкрити в браузері → форма пароля
```

🔴 `VITE_SUPABASE_*` **не потрібні й у `.env.example` їх більше немає** (0.4.1):
контракт магазину — рівно три ключі вище. Вітрина, вхід, воронка й
`/api/health` про Supabase не знають. Ключі знадобляться лише тому, хто
свідомо піднімає СТАРУ адмінку до треку К3, — тоді він додає їх у власний
`.env.local` сам, і це вже не контракт ядра.

## 7. Чого в цій карті свідомо немає

Числа, які застаріють за один PR (кількість тестів, файлів), — у розділах
вище вони наведені як **виміри на дату**, а не як контракт. Структурні
твердження («адмінці потрібен серверний шар», «фільтрація — обов'язок коду»)
переживуть рефакторинг; лічильники — ні. Це урок №8 роадмапу.
