## 1. Головне за 30 секунд

**Магазин працює на чистому Postgres. Адмінка — ні, і це очікувано.**

Браузер більше не ходить у базу. Раніше сторінка сама зверталась до БД через
HTTP-посередника Supabase (PostgREST); тепер із базою говорить **тільки
сервер**, а браузер отримує готові дані. Це і є суть рішення B1.

Наслідок, який треба прийняти свідомо: **адмінка не має серверного шару
взагалі** — усі 53 її файли (215 прямих звернень до таблиць) працюють із
браузера. На чистому Postgres звертатись нема куди — HTTP-посередника немає
й не буде. Тому адмінка віддає каркас і застигає на «Завантаження».

Це не поломка, внесена неакуратно, а **неминучий наслідок** переходу: адмінці
потрібен серверний шар, якого в неї ніколи не було. Її сесія має його
створити — це окремий трек із власним проєктуванням (serverFn + TanStack DB),
рішення власника 2026-08-24.

### 2.1. Контур 0.4.1 — ПІДТВЕРДЖЕНО живим прогоном 2026-08-29

🔴 Прогін 2026-08-24 (таблиця вище) робився з `.env.local`, у якому Supabase-ключі
ще лежали, тож доказом для нового контракту він не був. Контур 0.4.1 зняв їх
зовсім: шар `data-supabase` знесено, `CMSProvider` більше не монтує
`SupabaseProvider`, `/api/health` пінгує Postgres, роут `/api/guest-order`
видалено, генератор типів і онлайн-перевірки `doctor` знято, аватар чесно
відмовляє. Нижче — результат ОКРЕМОГО прогону, зробленого саме під новий
контракт.

**Поза прогону.** П'ять tarball-ів зібрано з гілки (`pnpm pack` кожного пакета),
магазин розгорнуто скаффолдером із них у чисту теку, залежності ядра —
`file:`-посилання на ці tarball-и (не реєстр). База — окрема ЧИСТА `store041`,
канон накатано `psql -f` по кожному файлу `supabase/migrations/*.sql`
(45 таблиць). `.env.local` — рівно три ключі, `DATABASE_URL` під роллю
**`app_runtime`** (продакшн-поза, не суперюзер). Запуск — `pnpm build &&
node server.mjs`.

🔴 **Одне уточнення, без якого доказ читався б ширше, ніж він є.** Накат канону
робився **привілейованим** підключенням (власник кластера), а не тим
`DATABASE_URL`, який README магазину друкує власнику: усі 45 таблиць у
`store041` належать суперюзеру. Це не недбалість прогону, а обхід реального
дефекту — під роллю `app_runtime` канон не котиться за жодного стану БД
(`permission denied for database`, або `permission denied to alter role` на
безумовному `alter role` у `0000_prelude.sql:74`, або роль ще не існує на
чистому кластері). Тобто доведено саме **рантайм** магазину під `app_runtime`;
надрукований онбординг-крок накату лишається зламаним — борг 0.4.1-9.

| Твердження контуру 0.4.1 | Статус |
|---|---|
| Магазин збирається й піднімається БЕЗ жодного `VITE_SUPABASE_*` | ✓ (у файлах магазину — нуль збігів `SUPABASE`) |
| `/`, `/catalog`, `/cart`, `/auth`, `/sitemap.xml`, `/robots.txt` → 200 | ✓ усі шість |
| `/admin`, `/profile` анонімом → 307 | ✓ обидва |
| `/api/health` → 200 (пінг Postgres, не Supabase) | ✓ `{"status":"healthy","checks":{"database":{"ok":true,"error":null}}}` — тіло без hostname і назви ролі |
| Браузер: нуль `console.error`, `h1` із реальним контентом | ✓ `/`, `/catalog`, `/cart`, `/auth` — нуль `console.error`, нуль `pageerror`, нуль 4xx; `h1` = «Виважений вибір…», «Каталог», «Кошик» |
| `simplycms doctor` без `DATABASE_URL` падає саме на ньому | ✓ `✗ env: DATABASE_URL + BETTER_AUTH_SECRET → Не задано: DATABASE_URL`; онлайн-перевірки — видимий `?` зі скоупом К3 |

**Додатково — на монорепо-хості проти `pnpm db:demo` (порт 3141), той самий
контракт із трьох ключів:** реєстрація через Better Auth наживо ✓;
`/profile/settings` залогіненим — 200, `h1` «Налаштування», **нуль
`console.error`**, інпут аватара `disabled`, пояснення «тимчасово недоступне»
видиме (доказ Task 2 і того, що fallback `resolveDefaultClient()` більше
нікого не тягне). Єдиний `console.error` за весь прогін — `404
/demo/banners/solar-home.jpg`: картинки демо-сіду фізично немає в
`dist/client`. Це борг демо-даних, не регресія 0.4.1 (на магазині зі
скаффолда 4xx нуль).

## 3. Що НЕ працює і чому саме

### 3.1. Адмінка — мертва до своєї сесії

🔴 **Виняток з Е1б (2026-09-02):** `/admin/order-statuses` уже живе на
серверному шарі (`simplycms/admin-server` + колекція TanStack DB з
`simplycms/admin-data`) — доведено живим браузерним прогоном (створення,
редагування, видалення, reorder, авто-rollback при зупиненому сервері).
Це референс-патерн для решти сутностей (хвилі Е3–Е6); опис нижче про
«нуль серверних функцій» стосується решти 49 файлів `src/admin/**`.
План — [`2026-08-30-v2-k3-e1b-server-layer.md`](../superpowers/plans/2026-08-30-v2-k3-e1b-server-layer.md).

**Симптом:** `/admin` віддає 200 і слово «Завантаження», далі нічого.

**Причина:** 53 файли, 215 звернень `.from(...)` з браузера через
`useSupabaseClient()`. Серверних функцій в адмінці **нуль**.

**Що потрібно зробити** (це і є її сесія):
1. Спроєктувати серверний шар: `createServerFn` + authz під `app_admin`.
2. Перевести 53 файли на нього. Патерн уже є — дивись, як зроблено вітрину:
   `src/storefront-routes/server/*.ts` (serverFn) + `src/storefront/loaders/*`
   (запити через `withActor`).
3. Кеш-шар (TanStack DB) — за планом власника.
4. Після цього зникає останній споживач `supabase-js` → можна зносити
   `src/supabase/` і сам `@supabase/supabase-js` із залежностей.
   🔴 `src/data-supabase/` знесено вже в 0.4.1 (шар мав нуль споживачів), а
   host-провайдера немає: `CMSProvider` більше не монтує `SupabaseProvider`.

🔴 **Три уроки вітрини, які зекономлять сесії адмінки дні:**

- **Фільтрація видимості — тепер обов'язок коду.** Політик «публічне
  читання» більше немає, `app_user` має грант SELECT на весь каталог. Кожен
  публічний запит МУСИТЬ явно фільтрувати `is_active`. Раніше чернетки ховала
  база — тепер не ховає.
- **`userId` ніколи не параметр serverFn** — лише з сесії
  (`readSessionSubject`). RLS звіряє рядки з тим id, який їй назвав сервер;
  id, прийнятий від клієнта, вона перевірити не може за побудовою.
- **Живий не-serverFn експорт у модулі поруч із serverFn тягне серверний граф
  у браузер.** Спіймано Gate C пілота: `withSessionDb` лежав у
  `storefront-routes/server/`, tsup підняв його у спільний чанк, і разом із
  ним у клієнтський бандл поїхали drizzle і пул Postgres. Лікується
  перенесенням у модуль, який імпортується **bare-специфікатором**
  (`simplycms/storefront/loaders`) — такі tsup вважає зовнішніми й у чанки не
  кладе. Це структурна гарантія, а не домовленість.

### 3.2. Сховище файлів — порту немає (контур К4)

**Не працює:** аватар користувача, завантаження зображень в адмінці, видалення
зображень відгуків. Три файли:
`profile-ui/AvatarUpload.tsx`, `admin/components/ImageUpload.tsx`,
`admin/pages/ReviewDetail.tsx`.

🔴 З 0.4.1 `AvatarUpload` **чесно відмовляє**: показує поточний аватар або
ініціали, тримає `input[type=file]` вимкненим і пояснює причину видимим
текстом із каталогу (`profile.avatar.unavailable`). Supabase він більше не
імпортує взагалі — тобто єдиний файл вітрини, який ходив у Storage, з
клієнтського графа вийшов. Два файли адмінки лишились як були (трек К3).

**Чому не полагодили:** порт `MediaProvider` має лише `url`/`upload`, без
`delete`/`transform`, а драйверів (`local-fs`, `s3`) ще немає — це контур К4.
🔴 Свідомо **не** підмінено заглушкою, яка «успішно» нічого не зберігає:
чесна поломка краща за тиху.

**Готове підґрунтя:** таблиця метаданих медіа вже в схемі
(`src/schema/media.ts`) з інваріантом незмінності колонок власності —
він тримається **відсутністю гранта UPDATE**, а не тригером.

### 3.3. Листи не відправляються (рішення власника)

Запрошення власника і скидання пароля кличуть колбек відправки, але транспорт
— заглушка (`src/auth/send-email.ts`, `stubSendAuthEmail`): лист пишеться в
`console.warn` разом із посиланням. Рендер листа юніт-тестовний; доставки
немає. **Це навмисно** — тестується локально, де є SMTP.

### 3.4. Ціни позицій замовлення не перераховуються

Сервер рахує **підсумки** з позицій (розбіжність «сума ≠ позиції» неможлива),
але саму ціну позиції приймає з кошика клієнта — тобто підміна ціни в запиті
ще проходить. Це не регрес (раніше браузер робив INSERT сам), але й не
закрито. Належить контуру чекауту.

### 3.5. `pnpm owner:invite` у шаблоні магазину

Скрипт переписаний без GoTrue й друкує посилання в консоль, але **з монорепо
не запускається**: він резолвить `simplycms` як залежність магазину. Це
нормально — він і призначений для скаффолдженого магазину. У монорепо
використовуй прямий виклик `issueOwnerInvite` (див. §5).

### 3.6. Контури, вимкнені рішенням B13

`pnpm test:e2e` і `pnpm pilot:e2e` — **decommissioned**, і з 0.4.1 команд
більше немає взагалі: знесено `scripts/e2e.mjs`, `scripts/e2e/`,
`scripts/pilot-pack/e2e.mjs` і `gate-e.mjs`, а прапорець `--e2e` падає з
поясненням. Спершу їх зламало рішення B13 (`supabase/config.toml` вимкнув
`[db.migrations]`, бо канон переїхав; стек піднімався з порожньою схемою і сід
падав), потім зникла й сама причина існувати: магазин не ходить у Supabase.
Специ `tests/e2e/**` і `playwright.config.ts` лишились без входу — основа для
відновлення на Postgres-стеку (трек К6).

## 4. Що змінилось в інфраструктурі (і чому це важливо знати)

### 4.1. Міграції: історія → чистий baseline

Теки `supabase/migrations/` **немає**. Канон — `packages/simplycms/migrations/`:

| Файл | Що робить |
|---|---|
| `0000_prelude.sql` | схема `app`, `app.current_user_id()`, ролі `app_runtime`/`app_user`/`app_admin` |
| `0001_init.sql` | таблиці, енами, індекси, RLS (генерат drizzle-kit) |
| `0002_grants.sql` | гранти як код |
| `0003_seed.sql` | сід чистого магазину |
| `demo/demo-seed.sql` | демо-каталог (поза каноном) |

### 4.2. Модель безпеки

- `app_runtime` — LOGIN-роль **без прямих грантів**; права дістає через
  `SET LOCAL ROLE app_user|app_admin`. Забудеш перемкнути → `permission
  denied`, а не тихий обхід RLS.
- 🔴 Членство видане з `WITH INHERIT FALSE` — інакше `app_runtime` успадковує
  права **до** перемикання, і fail-closed зникає мовчки. Це реальний дефект,
  знайдений негативним контролем.
- RLS — **27 політик замість 93**, лише на user-scoped таблицях, у
  initplan-формі.

### 4.3. Збірка: декларації типів більше не через tsup

Вендорений `rollup-plugin-dts` створює окрему повну `ts.Program` **на кожну
теку** entry і тримає їх усі живими: 36 програм, 9 ГБ, 191 с. Тепер декларації
емітить `tsc -p tsconfig.dts.json` — **39 с під кепом 3 ГБ**.

Запобіжники: кеп пам'яті в `scripts/build-packages.mjs` (діє в CI, релізі й
локально), стеля часу 300 с, структурний тест `tests/dts-toolchain.test.ts`.

### 4.4. Тестові контури

| Команда | Що доводить | Docker |
|---|---|---|
| `pnpm test` | юніти (лічильник змінюється щорелізу — дивись вивід) | ні |
| `pnpm test:schema` | накат канону, парність політик і грантів, **поведінкова матриця RLS** із трьома негативними контролями | **ні** |
| `pnpm test:packaging` | tarball-парність, форма `import.meta`, тулчейн декларацій | ні |
| `pnpm pilot:pack` | скретч-магазин зі справжніх tarball-ів: A/C/D/CLI/TOOL. 🔴 З 0.4.1 env скретча — рівно контракт магазину (без фіктивних Supabase-ключів), а Gate C стереже ще й `simplycms/dist/db`, `drizzle-orm`, `pg` | ні |
| `pnpm db:demo` | база з нуля + демо-каталог | ні |

## 5. Як підняти це локально (перевірено покроково)

```bash
pnpm install

# 1. База з демо-даними (потрібен локальний Postgres)
PG_HARNESS_URL=postgresql://<user>@127.0.0.1:5432/postgres pnpm db:demo
# віддасть готовий рядок DATABASE_URL

# 2. .env.local
DATABASE_URL=postgresql://<user>@127.0.0.1:5432/simplycms_demo
BETTER_AUTH_SECRET=<довгий випадковий рядок>
BETTER_AUTH_URL=http://localhost:3000
VITE_SITE_URL=http://localhost:3000

# 3. Запуск
pnpm build && pnpm start        # або pnpm dev
```

**Створити першого адміна** (у монорепо, бо скрипт шаблону резолвить
`simplycms` як залежність магазину):

```ts
// npx tsx цей файл, з тими самими env
const m = await import('./packages/simplycms/src/auth/index.ts');
const r = await m.issueOwnerInvite({
  email: 'admin@example.com',
  store: m.ownerInviteStore,
  siteUrl: 'http://localhost:3000',
  sendEmail: async (mail) => console.log(mail.subject, mail.url),
});
console.log(r.url);   // відкрити в браузері → форма пароля
```

🔴 `VITE_SUPABASE_*` **не потрібні й у `.env.example` їх більше немає** (0.4.1):
контракт магазину — рівно три ключі вище. Вітрина, вхід, воронка й
`/api/health` про Supabase не знають. Ключі знадобляться лише тому, хто
свідомо піднімає СТАРУ адмінку до треку К3, — тоді він додає їх у власний
`.env.local` сам, і це вже не контракт ядра.

---

## 6. Порядок робіт для наступної сесії

1. **Адмінка на серверний шар** (§3.1) — найбільший блок; після нього
   зникає `supabase-js` і можна зносити старий шар під корінь.
2. **Storage-порт К4** (§3.2) — оживляє аватар і зображення.
3. **SMTP + браузерний e2e** (§3.3, §3.6) — те, що недосяжне в CI-оточенні.
4. **Перерахунок цін позицій** (§3.4).
5. **Міграція на tsdown** — див. роадмап, окремим кроком; не змішувати з
   роботою над магазином.

---

## 7. Чого в цій карті свідомо немає

Числа, які застаріють за один PR (кількість тестів, файлів), — у розділах
вище вони наведені як **виміри на дату**, а не як контракт. Структурні
твердження («адмінці потрібен серверний шар», «фільтрація — обов'язок коду»)
переживуть рефакторинг; лічильники — ні. Це урок №8 роадмапу.
