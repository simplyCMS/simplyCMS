# Інкремент Б.2: шліфування механізму клонування дизайну після лайв-тесту

> Джерело скоупу — роадмап, «Інкремент Б.2 (трек C)» (рішення власника
> 2026-08-17) + підсумки лайв-тесту 2026-08-15/16 (повний пайплайн скіла
> `redesign-from-reference` проти реального референсу; результат-тема стала
> новою `themes/default`). Порядок треків — спека v3, рішення V5:
> ця задача йде ПЕРЕД треком A (контракт v3).
>
> 🔴 Жива валідація задачі — повторний прогін механізму проти того самого
> референсу (шліфування default-теми) — СВІДОМО поза цією задачею: то
> діалогова сесія з власником на стенді, не кодова робота. Ця задача
> має зробити так, щоб той прогін пройшов без жодної зі знайдених
> лайв-тестом прогалин.

## 1. Контекст — що саме показав лайв-тест

1. **Side-by-side QA зроблено лише для `home`** — по `listing`/`product`/
   `about` пар «референс ↔ наш» не було взагалі. Фаза 5 скіла формулює
   side-by-side одним рядком і не вимагає пару НА КОЖЕН підтверджений тип
   із `sitemap-proposal.json` — агент зробив мінімум, і скіл це дозволив.
2. **Анімації не зняті ніяк**: інспекція міряє лише статичні computed-стилі.
   Референс мав scroll-reveal секції і hover-переходи — усе це лишилось
   «дивись очима» без сліду в артефактах і спеках.
3. **Канонічна картка товару на стенді порожня**: сід пілота дає товарам
   лише `slug/name/section/price/oldPrice/isFeatured` — без фото, описів,
   властивостей. `ProductDetail` уміє все це рендерити
   (`ProductGallery`, `short_description`, HTML-опис,
   `ProductCharacteristics`, `StockDisplay`), але їй нічого показати —
   QA картки товару сліпе.
4. **Після базового клону нема процесного кроку «доганяти якість»**:
   розбіжності side-by-side не класифікуються і не отримують рішень.
5. **Беклог знахідок**: (а) `simplycms create theme` відмовляє в монорепо —
   `findStoreRoot` шукає магазин; (б) шрифт-евристика merge (голосування
   по сторінках) обрала моно-гарнітуру замість основної — span-мітки
   переважили body-текст.

## 2. Скоуп

### Блок A — фаза 5 скіла: обовʼязковий side-by-side по кожному типу

- Скіл (`.agents/skills/redesign-from-reference/SKILL.md`, фаза 5) вимагає:
  на КОЖЕН підтверджений тип зі `sitemap-proposal.json` — пара «інспекція
  референсу ↔ інспекція нашого стенда» тим самим `inspect.mjs`
  (`docs/design-references/<slug>/_ours/<pageType>/`), і по кожній парі —
  перелік розбіжностей із класифікацією:
  **токен-фіксабельна / дані / структурна-за-дизайном**.
- Продовжувати без пари по підтвердженому типу — заборонено текстом скіла
  (та сама модель, що обовʼязковий діалог фази 1.2); винятків рівно три, і
  кожен іде окремим рядком у підсумкову таблицю: тип, свідомо пропущений
  користувачем на фазі 1.2; `cart`/`checkout`, коли кошик нема чим
  наповнити (клієнтський стан; порожній `/checkout` редиректить на `/cart`,
  тож наївний знімок дав би мислабельований артефакт); і тип, у якого
  сторінки в магазині немає взагалі (`about`/`contact` без власної
  `src/routes/my/…`).
- Формат підсумку фази 5 — таблиця «тип → розбіжності → клас → рішення»,
  яку агент показує користувачу.

### Блок B — motion-капчер + секція «Motion» у спеках + hover-sweep

- `inspect.mjs` додатково знімає **motion-дані** (нова секція `motion` в
  `inspection.json`, bump `schemaVersion`):
  1. computed `transition-property/duration/timing-function` по семплованих
     елементах → кластери типових тривалостей/easing-ів;
  2. використані `@keyframes` із same-origin stylesheet-ів через CSSOM
     (cross-origin — чесний лічильник недоступних, не мовчазний дроп);
  3. reveal-дифи: під час наявного скрол-проходу — снапшоти
     `opacity`/`transform` секцій до/після кроків скролу → прапорці
     «секція анімується при скролі»;
  4. детект JS-анімацій (GSAP / Framer Motion / Lottie / anime.js) за
     script-src і глобалами → чесне поле «motion керується JS, статично
     незнімано».
- **Hover-sweep**: детерміністичний прохід Playwright `hover()` по
  навігації/кнопках/картках → дельти computed-стилів (background, color,
  transform, shadow) у `motion.hover`. Це закриває беклог-пункт
  «interaction sweep» детерміністично, без браузерного MCP.
- Шаблон спека-файлів компонентів (фаза 4 скіла) отримує обовʼязкову
  секцію **Motion** (тривалості/easing-и токенами виміру, reveal-поведінка,
  hover-переходи); компоненти реалізують її CSS-transitions.
- 🔴 Межа: контракт токенів теми НЕ розширюється (жодних motion-токенів у
  `ThemeTokenValues`) — рішення власника, перегляд можливий після обкатки.

### Блок C — demo-датасет діагностичного стенда

- Мета: канонічні сторінки стенда (насамперед картка товара) мають що
  рендерити — фото, описи, властивості, кілька секцій.
- Джерело — дамп КЛАУД-БД АльтерЕнерджі (санітизований: лише каталожні
  дані — products/sections/properties/зображення/ціни; БЕЗ користувачів,
  замовлень, персональних даних).
- Форма: окремий сід (напр. `scripts/dev-stand/` + згенерований SQL),
  який накочується на локальний стек ПОВЕРХ сіду пілота, ідемпотентно.
  🔴 `supabase/seed.sql` і `scripts/pilot-pack/seed-fixtures.mjs` НЕ
  чіпати — це контракт гейтів пілота (Gate B асертить точні назви).
  🔴 Стенд до клауд-БД напряму НЕ підключається (`bootstrapThemes`/адмінка
  писали б у живий магазин).
- Зображення: допустимо лишити публічні URL-и клауд-Storage (діагностичний
  стенд); локальне дзеркалення — опція, не вимога.
- Чесна деградація: без доступу до клауд-БД у сесії виконання — скрипт
  дампу/генерації і формат готові й покриті тестом на фікстурі, реальний
  дамп — дія власника перед прогоном.

### Блок D — фаза «Шліфування» у скілі + беклог

- Нова ОПЦІЙНА фаза скіла (після фази 5): посторінковий прохід по
  розбіжностях із драбиною рішень:
  **токен → setting теми → кастомна сторінка `src/routes/my/` → свідомо
  прийняти канонічний вигляд** (щабель «view теми» додасться треком A —
  у тексті скіла лишити позначку-місце). Кожне рішення фіксується в
  артефакті (розширення підсумкової таблиці фази 5), «мовчки лишити як є»
  — заборонено.
- Беклог: (а) `simplycms create theme` у монорепо — корінь монорепо
  (маркер: `pnpm-workspace.yaml` + `simplycms.config.ts`) визнається
  валідним коренем СКАФФОЛДУ (`findScaffoldRoot`, лише команда `create`) і
  скаффолдить у `themes/` кореня; для `doctor`/`add`/`update`/`db:diff`
  монорепо магазином не є — `findStoreRoot` там гучно відмовляє; (б) шрифт-
  евристика merge: голосування зважувати за обсягом текстового покриття
  сімʼї на сторінці (body/заголовки переважують мітки), тест на кейс
  лайв-тесту «span-мітки моно проти body-гарнітури».

## 3. Чого НЕ робимо (межі задачі)

- View-шар канонічних сторінок, view-model-и, conformance-гейт — трек A
  (спека `2026-08-17-theme-contract-v3-views-design.md`), не тут.
- Повторний живий прогін механізму і шліфування default-теми — окрема
  діалогова сесія після цієї задачі (її жива валідація).
- Motion-токени в контракті теми, drag-and-drop, секційна модель — ні.
- Зміни сіду пілота і будь-чого в контурі гейтів пілота — ні.
