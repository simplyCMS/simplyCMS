# Доставка скіла redesign-from-reference у клієнтські магазини: окремий репо + стандартний механізм скілів

> Рішення власника 2026-08-19: скіл розповсюджується **окремим репозиторієм
> в організації GitHub** (модель `supabase/agent-skills`) і ставиться в
> магазини «звичайним для скілів механізмом». Власник знає два стандарти —
> `npx skills add <owner/repo>` (skills.sh) і TanStack Intent — і всі свої
> поточні скіли ставив через `npx skills add`, тож він йому зрозуміліший;
> фінальний вибір стандарту — предмет Фази 0 цієї задачі (з рекомендацією
> нижче). Джерело фактів — три розвідки 2026-08-19 (кодова база + веб),
> ключові результати вбудовані сюди, щоб задача була самодостатньою.

## 1. Контекст — фактичний стан доставки (звірено кодом)

- Свіжий магазин скіл **отримує**: `scripts/sync-create-store-template.mjs`
  (пара `SYNCED_DIRS`, рядки 63-66) кладе РЕАЛЬНУ копію
  `.agents/skills/redesign-from-reference` → `template/.claude/skills/…`;
  скаффолдер копіює dot-теки (`scaffold.mjs:57`, `cpSync` без фільтрів);
  Gate CLI (`scripts/pilot-pack/create-pkg-smoke.mjs:56-63`) асертить
  `SKILL.md` + `inspect.mjs`/`discover.mjs` на реальному tarball-і.
- 🔴 **Каналу оновлень немає**: канон `simplycms update` — рівно 11
  host-файлів (`packages/cli/host/`, `host-drift.mjs:16-57`), `.claude/**`
  жоден CLI-механізм не чіпає. Раз скаффолджений скіл заморожується
  назавжди — а механізм ми оновлюємо кожним інкрементом.
- 🔴 **Онбординг мовчить**: `template/README.md` (129 рядків) і вивід
  скаффолдера (`steps.mjs`) не згадують скіл узагалі; єдиний канал
  виявлення — автодискавері Claude Code.
- **Скрипти скіла самодостатні**: нуль імпортів `@simplycms/*`, лише
  node-builtins + ДИНАМІЧНИЙ `playwright`/`@playwright/test`
  (`lib/browser.mjs:83-100`, гучний exit 1 з підказкою установки) — тобто
  винесення в окремий репо технічно дешеве, без залежностей від монорепо.
- Джерело правди скіла — `.agents/skills/redesign-from-reference/`
  (розробка, фікстурні тести `tests/design-import-*`, гейти — все тут).

## 2. Контекст — стандарти доставки (веб-розвідка, з джерелами)

| Стандарт | Механіка | Оновлення | Сумісність |
|---|---|---|---|
| **skills.sh / `npx skills add <owner/repo>`** (Vercel Labs) | Реєстр — GitHub/git (НЕ npm). CLI копіює SKILL.md+бандл у теку агента проєкту (`.claude/skills/` для Claude Code, `.agents/skills/` для Cursor/Cline, …«ще 73 агенти» — детектує сам); файли комітяться в git споживача | `npx skills update` (ручний, тягне latest з git; семвер-піну немає) | Крос-агентна (формат — відкритий стандарт agentskills.io, ~40 інструментів) |
| **TanStack Intent** | `SKILL.md` живе ВСЕРЕДИНІ npm-пакета (`<pkg>/skills/<name>/SKILL.md`); `npx @tanstack/intent install` сканує dependency tree і ДОПИСУЄ в `CLAUDE.md`/`.cursorrules` посилання на шляхи в `node_modules` — без копій | `npm update` пакета (авто; CLI перезапускати лише при нових пакетах) | Пише в конфіги кількох агентів; але канал розрахований на **npm-залежності**, не на окремий git-репо |
| Claude plugin marketplace (`source: npm`) | Плагін у кеші `~/.claude/plugins/cache`, поза git проєкту | Семвер-стежить сам Claude Code | 🔴 Лише Claude Code |

Прецедент моделі «окремий репо в org»: `supabase/agent-skills` —
`npx skills add supabase/agent-skills` (+ `--skill <name>` для одного).

**Рекомендація (не догма — Фаза 0 перевіряє й фіксує): skills.sh як
основний канал.** Аргументи: (а) власник ставить усі скіли саме ним;
(б) модель «окремий репо в організації» — це рівно його модель, а Intent
розрахований на скіли всередині npm-залежностей (окремий git-репо в його
канал не вписується без пакета-носія); (в) copy-in = git-статус у репо
магазину, офлайн після установки, крос-агентність. TanStack Intent —
кандидат ДОДАТКОВОГО каналу пізніше, якщо скіли захочеться везти всередині
`@simplycms/*`-пакетів (наприклад, скіл роботи з view-ами всередині
`@simplycms/themes`) — не в цій задачі.

## 3. Скоуп

### Блок A — Фаза 0: дослідити конвенції skills.sh і зафіксувати рішення

- Зняти ТОЧНІ конвенції skills.sh з першоджерел (vercel-labs/skills README
  + живий приклад supabase/agent-skills): очікувана структура репо
  (корінь? `skills/<name>/SKILL.md`? маніфест?), як працює `--skill`,
  `npx skills update`, чи підтримуються приватні репо, як CLI детектує
  агентів, обмеження на вкладені scripts/ (наші скрипти МАЮТЬ доїхати).
- Перевірити на живо: `npx skills add supabase/agent-skills` у тимчасовій
  теці — подивитись, ЩО саме і КУДИ матеріалізується.
- Зафіксувати рішення стандарту амендментом у плані (рекомендація — §2).
  Якщо skills.sh не довозить scripts/ чи має інший блокер — чесно
  задокументувати і запропонувати власнику альтернативу ДО імплементації.

### Блок B — дистрибуційний репозиторій `simplyCMS/agent-skills`

- Створити репо в організації (через `gh repo create simplyCMS/agent-skills
  --public`; якщо прав немає — зупинитись і попросити власника) зі
  структурою під конвенції Фази 0; перший скіл —
  `redesign-from-reference` (SKILL.md + `scripts/` цілком).
- 🔴 **Джерело правди ЛИШАЄТЬСЯ монорепо** (`.agents/skills/…` — там
  розробка, фікстурні тести, гейти). Дистриб-репо — снапшот-дзеркало:
  скрипт `scripts/sync-agent-skills.mjs` у монорепо готує/оновлює вміст
  дзеркала (модель `template:sync`: байт-копія + адаптація шляхів у текстах
  SKILL.md, якщо потрібна — у магазині скіл живе в `.claude/skills/`, і
  канонічний шлях запуску там уже правильний). Пуш у дистриб-репо —
  ЯВНА дія (скрипт друкує команди або робить із прапорцем), не мовчазна
  автоматика.
- README дистриб-репо: що це, як ставити (`npx skills add
  simplyCMS/agent-skills`), як оновлювати, ліцензія (MIT, як у монорепо),
  посилання на гайд.

### Блок C — онбординг і зняття подвійного джерела в шаблоні

- 🔴 Рішення (рекомендоване; підтвердити на Фазі 0): **копію скіла з
  шаблону скаффолдера ПРИБРАТИ** — інакше два джерела правди в магазині
  (заморожена копія зі скаффолду vs жива з `npx skills add`). Наслідки
  прибрати ЧЕСНО: пара в `SYNCED_DIRS`, асерти Gate CLI
  (`create-pkg-smoke.mjs`), parity-тест — усі оновлюються під нову модель;
  секція «Агентні скіли» в `template/README.md` + рядок у
  `printNextSteps` скаффолдера: `npx skills add simplyCMS/agent-skills`.
  (Альтернатива «лишити копію для офлайну» — задокументувати відхилення,
  якщо Фаза 0 знайде вагому причину.)
- `simplycms doctor` — нова мʼяка перевірка (warn, не fail): скіл
  установлений? (наявність `.claude/skills/redesign-from-reference/
  SKILL.md`) — з підказкою команди установки. Дрейф версій не рахуємо
  (це робота `npx skills update`), лише присутність.
- Гайд `docs/guides/redesign-from-reference.md` і скіл (розділ про
  магазини) — оновити модель доставки.

## 4. Чого НЕ робимо

- TanStack Intent-канал (скіли всередині npm-пакетів) — окреме майбутнє
  рішення, не тут.
- Claude plugin marketplace — вузько-Claude, не основний канал.
- Автоматичний CI-пуш у дистриб-репо на кожен мерж — ні: публікація
  снапшота = явне рішення (як реліз).
- Інші скіли монорепо (`codebase-research`, `code-review`) — НЕ
  розповсюджуємо: вони процесні для розробки ПЛАТФОРМИ, не для магазинів.
- Механізм скіла (скрипти/фази) — не чіпаємо (паралельна задача в іншій
  сесії розширює механізм — уникати конфліктів по файлах скриптів; ця
  задача чіпає лише ДОСТАВКУ).
