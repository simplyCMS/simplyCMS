# ADR-0019: Оновлення флоту: спершу код, сумісний з обома схемами, потім обмежувальна міграція з rollback-SQL

Status: accepted 2026-08-19
Decided by: owner
Spec: `docs/superpowers/specs/2026-08-19-cloud-platform-design.md` §2

## Context
Хмара оновлює ядро в багатьох магазинах. Обмежувальна зміна БД (drop, rename, NOT NULL, звуження RLS), накачена раніше за код, дає гарантований outage. У флоті це множиться на кількість магазинів. Досвід MetaHub підтвердив це (амендмент 2026-08-20).

## Decision
Порядок оновлення магазину структурний, а не питання дисципліни виконавця. Спершу деплой застосунку, сумісного з обома станами схеми. Лише потім обмежувальна зміна БД. Вона йде з готовим rollback-SQL у тому ж кроці. Крок міграцій завжди після успішного старту нового контейнера на канарці. Розширювальні зміни (нова колонка чи таблиця) цього обмеження не мають.

## Why
- Правило й причина записані в C8: `docs/superpowers/specs/2026-08-19-cloud-platform-design.md` § «2. Зафіксовані рішення (C1–C13».
- Standalone-міграція перед кодом множить outage на N магазинів і кладе всі магазини флоту (там же).
- Пайплайн деплою мусить робити цей порядок структурним (там же).

## Rejected
- Обмежувальна міграція перед кодом — гарантований outage (C8).

## Consequences
Кожна обмежувальна міграція потребує двох кроків і rollback-SQL. Не складай drop чи rename в одну міграцію з кодом, що ще читає стару форму. Стан на 2026-11-21: у коді ще немає (хмарного пайплайна оновлення нема; `git grep rollback` у `packages/*/src` не знаходить rollback-SQL міграцій).
